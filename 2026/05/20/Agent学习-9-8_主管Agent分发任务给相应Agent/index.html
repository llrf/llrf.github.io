9-08 主管Agent分发任务给相应Agent

发表于2026-05-20|更新于2026-05-20|Agent学习第09章 Docker 部署分布式 Agent 搞定旅游规划
|浏览量:

1. 一句话定位

你要让主管 Agent 在「拆完任务」之后多干一件事：给每一步写上到底该谁来做——但本集只到「写上」为止，真正跨节点的调用还在下一集。

2. 主体

2.1 起点：9-7 已经把任务能拆开

到上一集为止，主管 Agent 已经能接 帮我规划深圳到惠州 3 日自驾游 这种 prompt，调 create_plan 工具拆成「查天气 / 制路线 / 选景点 / …」一串子任务。

但拆完之后呢？每一步该派给哪个员工——这一步还没做。

2.2 实验台：还是那个 ManagerAgentApplication

打开 ManagerAgent.java，第 35 行附近构造器还是熟悉的：

注意一个取舍：这里没有调用 .tools(routeMakingAgent, tripPlannerAgent) 把下属当工具注册进来。本集到这一步为止，两个下属节点（routeMaking_agent / tripPlanner_agent 两个 Maven 子模块）根本没启动，主管也没有任何代码层面的句柄能调用它们。

2.3 关键招数：把「下属是谁、擅长什么」喂进 prompt

runO() 里的 prompt 在 9-7 的基础上多塞了两段（图见 frames/f008_t0103.2s_anchor.jpg、frames/f010_t0116.1s_anchor.jpg）：

三段拼起来：① 原始需求；② 下属花名册（名字+擅长）；③ 硬约束「每一步必须注明 Agent」。整个「派单能力」就是这三行平铺的字符串，没有注册中心、没有反射、没有反向查询。

2.4 跑一遍看输出

控制台日志（frames/f018_t0208.9s_anchor.jpg）：

加工增量：盯紧第 3、4、5 步——它们后面没有「调用 xxxAgent」。LLM 没瞎编一个不存在的 Agent，也没报错，就空着。这说明本集的派单是「软匹配」：下属清单匹配得上的才挂名，匹配不上的就先留着，等后续课加新下属或主管自己兜底。视频里讲师没明说这点，但日志摆在那里。

末尾的 Should I proceed with this plan? 来自 ReAct 框架的人在环节确认——告诉你计划阶段到此为止。

2.5 架构图里画了，但本集还没用的东西

frames/f001_t0000.0s_scene.jpg 那张「分布式 Agent 自主旅游规划」架构图上，主管节点和两个下属节点之间画了 A2A 协议箭头，中间还挂着 Nacos 注册中心（发现其它节点的 Agent），下属节点底下还写了「按思考-执行-反馈、自主执行单一任务」。

这些都是下一集的事。本集这张图的作用是「未来全景」，不是「当下现状」。当下的现状是：主管在自己的 LLM 调用里演了一遍「如果让我派单，我会派给谁」，仅此而已。

2.6 为什么要紧接着引出 A2A

讲师抛了一个收尾问题：下属是谁、擅长什么——不能永远靠用户在 prompt 里手喂。

手喂版的痛点很具体：① 主管不知道生产环境里实际还活着哪些 Agent；② 用户要预先知道所有 Agent 的能力描述；③ 新增 / 下线 Agent 都得改 prompt。

解法是 A2A 协议 + Nacos 注册中心 + Agent 卡片（Agent Card）：远程 Agent 自己向注册中心登记一张「卡片」自述能力，主管启动时去拉名单，prompt 里的「下属清单」就自动生成了。这是 9-9 要做的事。

3. 没 get 的点

  • 「每个子任务要注明调用的 Agent」的输出格式现在是纯 Markdown，后面要不要被解析成结构化字段（JSON / 工具调用参数）再分发？光看本集还看不到。
  • Agentutils.getReActAgentBuilder(...) 链式里没有 .tools(...) 把下属注入，那 9-9 之后 A2A 拿到的远程 Agent 是以什么形态注入？是当作一种特殊的 tool 还是另起一条 RemoteAgent 路径？
  • 架构图右下「子 Agent 异步执行单一任务」的「异步」到底是 Reactor Flux 那种进程内异步，还是跨节点的真异步——本集看不出，等下属节点跑起来才知道。
  • 主管目前对「没匹配上的子任务」是闷着不分配。后续是新增 Agent，还是主管自己兜底执行？

4. 跟其他集的连接

  • 上承 9-7：9-7 把「主管能拆任务」做出来；本集补「拆完知道派给谁」。两集合起来才凑够「主管 = 拆 + 派」这两件套。
  • 上承 3-9（搞定复杂活儿得靠多个 Agent 协作）：3-9 给了「主管 + 专科」的人力组织雏形，本集是把派单这一步在代码里落地——但用的还是「prompt 喂能力」的临时方案。
  • 上承 3-12（多 Agent 核心执行流程）：3-12 的「多 Agent 五步骨架」里第二步「任务派单」就是本集做的事；本集把骨架的这一步单独抠出来反复打磨。
  • 下启 9-9：用 AgentScope 实现 A2A 协议，让主管通过 Nacos 注册中心拿 Agent 卡片，把本集 prompt 里手喂的下属清单自动化。
  • 横向 3-10（多 Agent 跨部门协作 A2A 协议）：3-10 在协议层讲「卡片 / 能力发现」，本集是没用 A2A 时的对照组——故意演一遍「手喂下属」的痛点版，让你下一集看 A2A 时知道它在解什么。
  • 横向 4-14（SpringAi 1.1 A2A 的服务发现）：4-14 是 Spring 框架封装层的服务发现，本集是引出「为什么需要服务发现」的动机篇。
  • 横向 5-5（Agent 团队和大模型无缝协作）：5-5 已经做过同进程内的「派单 + 汇总」完整骨架，本集是把派单这一步拎出来、并准备跨节点化的过渡集。

6. 自测题（5 卡）

  1. 本集主管 Agent 在 prompt 里被新增了哪三段内容？它们各自起什么作用？
  2. 跑出来 5 个子任务，为什么只有 2 个挂了下属 Agent 名字，其它 3 个空着？这暴露了「手喂下属清单」方案的什么问题？
  3. 「注明」和「调用」在本集里是两码事——具体差在哪？看代码哪里能确认「调用」这一步还没发生？
  4. 架构图里的 A2A 协议 + Nacos 注册中心在本集起作用了吗？如果没有，它们为什么还出现在图里？
  5. 如果让你不重启主管进程就上线一个新的下属 Agent（比如「美食推荐 Agent」），用本集的方案能做到吗？为什么 9-9 要换 A2A？
