11-7_主管Agent自主分发任务给远程相应的成员

发表于2026-05-20|更新于2026-05-20|Agent学习第11章 MCP+A2A，助力旅游规划团队协作
|浏览量:

1. 一句话定位

把”主管 Agent 该把活派给谁”这件事，从你写在 Prompt 里的硬编码清单，挪到运行时让主管自己去 Nacos 拉卡片读 description 挑人——这一挪，才配叫”自主”。

2. 主体

起点：前几集为什么不算自主

到 11-6 为止，主管 Agent 是会分发任务的，但它”知道有谁可用”是你在 Prompt 里告诉它的——“现在有两个智能体，一个擅长自驾游路线，一个擅长景点行程规划”。这就是作弊条。本集刻意把这条作弊条撕掉，让主管走一遍：从 Nacos 拉所有可用 Agent → 自己读每张卡片的 description → 自己挑谁干哪一步。新增一个远程 Agent 不用动主管代码。

改三处描述（这是本集的全部动作）

容易混的是反复出现的 “description” 三个字。其实是三个完全不同位置的描述，缺一不可：

① 远程 Agent 的卡片 description——SAAgent.description("擅长处理自驾游路线制定") / SAAgent.description("擅长处理景点行程规划")。这是 Agent 注册到 Nacos 时写进卡片的”自我介绍”。改完必须先去 Nacos 控制台把旧卡片删掉再重启注册，不然主管拉回来的还是”路线制定智能体”这种字面名，等于没自我介绍。

② 主管侧 @Tool 的 description——

关键点：这里不写 Agent 擅长什么，只写”怎么把它拉回来”。能力是卡片自带的，分工要清。

③ 主管的 Prompt——把”你可以调用以下 Agent: A 擅长 X，B 擅长 Y”这种硬清单，整段删掉，换成一句话：

“从 Nacos 注册中心获取远程的 Agent，把切割好的子任务分发给擅长处理相关任务的 Agent，每个子任务要注明调用的是哪一个 Agent。”

三层描述怎么串起来——这里是本集最容易绕进去的点

主管在运行时拿到用户需求后，串的是这个链条（这是我整理出来的，视频里口头讲得比较跳）：

记忆口诀：Prompt 管”要不要拉”，@Tool 管”怎么拉”，AgentCard 管”拉到的是谁”。 三层描述各管一段，谁缺一段链就断。

pull 而不是 push

理解上一个反直觉的点：主管发现下属，不是被 push 一个清单（前几集是 push），而是主动 pull——而 pull 的执行者还是它自己拥有的 @Tool 方法，不是某个隐形系统服务。所以”主管能看见远程 Agent”这件事，仍然走标准的工具调用机制，只不过工具调出来的东西是一张张卡片。

这和 10-4 讲的 Skills 渐进式加载是一个味道：先拉元数据（卡片 description），要用时再深入（调 Agent.invoke）。

跑起来看到什么

输入一个复杂自驾游需求，主管的输出会自动列成四步子任务，每步后面跟着 （由路线制定 Agent 处理） / （由行程规划 Agent 处理） 这种归属标注。

加工增量：归属标注这事，Prompt 只要求”注明调用的 Agent”——它没规定写在哪、用什么括号、写不写”由…处理”。主管自己读了卡片之后，自己决定怎么写、写多详细。这种”超出 Prompt 字面要求”的细节，就是 LLM 利用卡片信息后的涌现行为，不是教出来的。讲师在视频里没强调，但这是观察自主性是否真的发生的最直观信号。

3. 没 get 的点

  • Nacos 上如果挂了 10 个 Agent，主管是不是一次性把 10 张卡片全拉回来读？token 怎么扛？本集只演了 2 个 Agent 的小样本，没暴露这个问题。猜测要么按 namespace/group 分桶、要么有”按关键字查询卡片”的接口，但视频里没提。
  • 每加一个远程 Agent 就要在主管这边手写一个对应的 @Tool 方法（callXxxAgent）？这一步还是硬编码——只是从”在 Prompt 里硬编码”挪到”在 Java 代码里硬编码”。本集没演”通用 callRemoteAgent(agentName)”这种写法，存疑。
  • Nacos 卡片页面有一块”暂无技能配置”，那块对应的 skills 字段和 description 字段到底什么关系？匹配时优先看哪个？本集只用了 description。

5. 知识地图

6. 自测题

Q1：本集开头明明已经把两个远程 Agent 启动并注册到 Nacos 了，为什么主管还是”看不见”它们？要让主管真正能用它们，最少需要改几处描述？分别是哪几处？

答案看不见是因为：① 主管的 Prompt 还是硬清单写死的，根本没指示它去 Nacos；② 即便指示了，主管侧的 @Tool description 是函数名级别的（如 "callRouteMakingAgent"），主管不知道这个工具是"用来拉 Nacos 远程 Agent 的"；③ 即便拉回来了，卡片 description 是 "路线制定智能体" 这种字面名，主管读不出能力。三处都改：Prompt 改成"从 Nacos 拉"、@Tool description 改成"从 Nacos 获取 XX Agent"、卡片 description 改成"擅长处理 XX"。

Q2：为什么 @Tool 的 description 写”从 Nacos 注册中心获取路线制定 Agent”，而不是写”调用擅长自驾游路线的 Agent”？后者听起来更对主管胃口才对。

答案因为"擅长什么"这种能力描述是 AgentCard 自带的，应该让主管运行时去读卡片才发现，而不是在工具描述里又写一遍——那样等于回到了"在主管侧硬编码下属能力"的老路，自主性又没了。分工：@Tool description 只回答"怎么拿到这张卡片"，AgentCard description 才回答"这张卡片是谁"。如果两层都写能力，新增 Agent 时还得改主管代码。

Q3：修改 AgentCard 的 description 后，必须先做什么再重启 Agent？为什么？

答案必须先去 Nacos 控制台把旧的两张卡片删掉。因为 Nacos 注册是按 name 复用条目的，如果旧卡片还在，新启动的 Agent 注册时主管那边读到的可能仍是旧 description，看起来"代码改了没生效"。先删后写，确保运行时拉到的是新版本。

Q4：跑起来后主管输出里出现 “（由路线制定 Agent 处理）” 这种归属标注，Prompt 里只写了”每个子任务要注明调用的 Agent”。为什么主管能写出”由 XX 处理”而不是只列 “Agent: X”？这反映了什么？

答案反映了主管真的读懂了卡片的 description 并用人话复述出来——它不是机械照抄 Prompt 字面要求，而是根据卡片信息生成自然的归属说明。这是自主性发生的直观信号；如果它只能输出工具名 callRouteMakingAgent，说明它根本没读卡片，链路其实是断的。

Q5：本集和 10-4 讲 Skills 渐进式加载，本质上共享一个什么哲学？这个哲学和 MCP 的工具调用有什么对照？

答案共享 **pull-based 元数据先行** 哲学：先用很小的代价（一张卡片 / 一段 SKILL.md frontmatter）告诉调用方"我是谁、能干啥"，调用方根据元数据按需深入加载完整能力。对照 MCP：MCP 是 push（把工具列表全推给模型），Skills/A2A AgentCard 是 pull（要用时再拉）。pull 更省 token、更适合 Agent 数量动态增长的场景。
