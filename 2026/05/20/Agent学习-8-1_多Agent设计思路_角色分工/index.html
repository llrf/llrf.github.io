8-1 多Agent设计思路 角色分工

发表于2026-05-20|更新于2026-05-20|Agent学习第08章 Jmanus 懂思考、会规划、一步步动手完成任务。
|浏览量:

1. 一句话定位

把 3-12 那张”多Agent五步骨架”反过来读——如果让你来写这个框架，你得抽出哪几个类。答案是两个全局类（Env / Action）+ 一个一分为二的角色类（RoleSetting / RoleContext）。MetaGPT 的三件套设计你大概能闻到味儿了。

2. 主体

2.1 先把骨架复述一遍（别跳）

这集开头花了快两分钟回顾 3-12，原因是设计题没有骨架就无从下手。骨架是这样的：

五步：意图识别 → 任务初始化 → 任务规划 → 任务执行 → 结果整合。其中”任务执行”那一格里塞着每个 Agent 各自的小循环：

规划 → 执行 → 监测反馈，监测不达预期就动态调整。两套流程是套娃不是并列——这是这集反复强调的一句话，第一遍看很容易当成两张图看了就完事。

2.2 设计题：抽出三大核心部分

你要是动手设计，盯着上面这张图能拆出三块：

  1. 主管 Agent——开头切复杂任务、结尾整合中间结果，出场两次（图 f001 底部那个”5.结果整合”框就是它的活儿）。
  2. 多 Agent 协同——多个 Agent 必须”处于同一环境”才能共享上下文。
  3. 中间结果的存储 + 整合——每个 Agent 跑完吐个中间结果，主管最后拼装。

2.3 题外话：A2A 在这里被排除

这一段是这集最容易踩坑的地方。前面 3-10 / 4-11~4-16 整整一条线讲 A2A，到这里讲师突然说”本框架不适用 A2A”。分界线只有一句：

  • A2A 协议针对不同大模型之间的 Agent 通信（跨模型 → 跨进程 → 需要协议握手）；
  • 本集的多 Agent 框架里，所有 Agent 共用同一个 LLM，跑在同一个进程里，进程内 Env 共享就够了。

加工增量：3-10 提过 A2A 是”跨部门协作”，本集这句话相当于给那条线钉了一颗边界钉——同公司同部门内部协作（同模型）走 Env，跨公司协作（跨模型）才上 A2A。你跨模型的判断标准是底层 LLM 不是同一个，不是”Agent 长得不一样”。

2.4 两个全局类：Env + Action

Env 类（全局记忆信息）——存”谁在场 + 全局参数”。你可以把它理解成 SAA 1.1 里 OverAllState 那种 KV 状态包的对应物（参考 7-2），只是这里强调它装的是角色清单和全局配置，不是工作流中间结果（中间结果归 RoleContext 管，见下面 2.5）。

Action 类（动作）——所有”动手”的统一入口。两个方法：

  • _think()——调 LLM 做逻辑推理；
  • _act()——调工具做事。

加工增量：你能闻到 ReAct 范式的味儿吧？这就是把 Reason + Act 拆成了类的两个方法。关键反直觉点是：调 LLM 也算动作——按直觉调 LLM “只是想一下”不算动，但在这个框架里凡是”出去要资源”（不管是 LLM 还是外部工具）都得走 Action。

2.5 角色类一分为二：Setting + Context

为什么要把”角色”拆成两个类？讲师没明说，但你看一下里面装的东西就懂了：

类 装什么 性质
RoleSetting 角色名 + 可用工具清单 静态（启动后不变）
RoleContext 当前步骤 + 各步中间结果 + Agent 状态 动态（运行中一直变）

加工增量：这是静态配置 / 动态状态分离的经典套路——跟 Spring 的 @Configuration Bean vs Request Scope Bean 是同一种思想。你想，三个 Agent 同时跑，RoleSetting 部分共享（都知道彼此叫啥、有啥工具），RoleContext 各自独立（你跑到第三步、我才跑到第二步互不干扰）。

三个 Agent 样例正好给你填一遍 RoleSetting：

  • 研究分析师 → Excel 工具
  • 技术研究员 → API / 编程
  • 产品经理 → 原型图工具（转录里 ASR 错成”圓形圖” / “圆形图”，记一下别迷路）

3. 没 get 的点

  • “处于同一环境”在代码层到底是啥？是同一个 OverAllState 实例？同进程内的 Spring Bean？还是更严格的隔离机制？讲师只说”同环境”概念，没落到代码。
  • _think 调 LLM、_act 调工具——那如果工具内部又调起另一个 LLM（比如套了 Agent 的工具），算 _act 还是嵌套 _think？这里有歧义。
  • Env 的”全局记忆”和 RoleContext 的”中间结果”边界——某个 Agent 的中间结果别的 Agent 要看时，是从 RoleContext 拿还是 Env 聚合后拿？Env 是不是 RoleContext 的聚合视图？
  • 主管 Agent 也走 RoleSetting + RoleContext 吗？还是它单独一个类？讲师没说。猜测是同一套，主管就是”角色=主管”的特殊配置。

4. 跟其他集连接

上承

  • 3-12 多Agent的核心执行流程——这集就是把 3-12 那张五步骨架反向读：”给我设计这个框架”。
  • 3-9 搞定复杂活儿得靠多个Agent协作——主管+专科 Agent 的概念在本集变成”主管 Agent”实例。
  • 3-10 多Agent跨部门协作 A2A协议 / 4-11~4-16 SAA 1.1 A2A 主线——本集明确给 A2A 划了边界：”同模型不用 A2A”。
  • 7-13 总结Agent和Graph分别构建的工作流——上一集刚总结完两种 SAA 路线，本集开始钻第三种视角：类设计层。

下启

  • 本章接下来大概率沿 Env / Action / RoleSetting / RoleContext 四个类逐个落代码——MetaGPT 风格的 Python 实现，或者 Java 版的对应。
  • _think / _act 这套 ReAct 拆分往后必然对接 6-6 ReactAgent 的 ReactAgent.builder()——SAA 1.1 把这两步封装到了 builder 里。
  • Env 类的细节大概率对应 7-2 OverAllState 的 KV 状态包思路。

横向

  • 跟 5-2~5-5 旅行规划团队 互为虚实——5 章给的是业务侧“三个专科 + 一个汇总”的角色清单，本集给的是技术侧“角色用什么类来存”。
  • 跟 7-2 OverAllState 同质：Env 类 ≈ OverAllState（全局 KV 状态包）。
  • MetaGPT 的 Role / Action / Env 三件套是这套架构的源头，本集相当于 MetaGPT 设计思想的中文白话版。

6. 自测题

  1. 同模型多 Agent 为什么不用 A2A？换一句你自己的话回答。
  2. Action 类的 _think 和 _act 分别对应 ReAct 范式的哪一半？为什么调 LLM 也算”动作”？
  3. RoleSetting 和 RoleContext 为什么要拆开？如果合成一个类有什么坏处？
  4. 主管 Agent 在五步骨架里出场了几次？分别在哪两步？
  5. “两个执行流程嵌套”具体指哪两个流程？嵌套的接口在哪一步？
