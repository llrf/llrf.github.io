13-7 测试路线制定专员规划最优驾车路线

1. 一句话定位

你不再手写转发给远程 Agent 的那串 prompt——给方法加一个被 @ToolParam(name, description) 修饰的 String prompt 形参，LLM 就会从用户原句里把「深圳到惠州」这段抽出来填进来，你只负责把它包成 Msg 喂给 agent.call。

2. 主体

2.1 起点：上一集留下的硬编码尾巴

11-4 那会儿，主管 Agent 调用远程路线智能体用的 prompt 是写死在工具方法里的一个字符串常量；本集要解决的就是这件事——用户在 POST /trip 接口里塞了 "制定深圳到惠州最优的驾车路线"，怎么让这句话自动流到远程那一端。

帧 0:35 那张接口测试界面上，请求体就是这么一句话；帧 1:50 起对应的 callRouteMakingAgent 方法此刻还是个无参方法，编译器在帧 2:35 还提示 “Method ‘callRouteMakingAgent(java.lang.String)’ is never used” ——也就是参数加进去了但没人调，这是个 LLM 还没”学会”抽参的过渡态。

2.2 核心动作：给方法加参，再给参数打钩子

两层注解各管一件事，写在同一个方法上但讲给两件事听：

注解 给谁看 决定什么
@Tool(description=...) LLM 选工具阶段 主管 Agent 要不要走这个方法
@ToolParam(description=...) LLM 抽参阶段 抽什么塞到 prompt 形参里

取舍标注：消化稿里我把 @ToolParam 的 description 写成「抽取指令」而不是「字段说明」。这是因为日志里印出的 这个工具方法传入的参数：深圳到惠州 是模型自己生成的——它读到 description 是「驾车的起点和终点」，于是从用户原句 制定深圳到惠州最优的驾车路线 里挑出符合「起点终点」语义的那一段。把这串 description 改成「请用中文回答」之类的话，抽取行为会跟着变。这一点视频里没明说，是从「日志能打印出来」这个现象倒推的。

2.3 三层 prompt 流转（本集真正的核心数据流）

这是我自己加的视角——视频里没拎出来讲，但理解了它，整集就通了：

第 61 行那句 prompt = "调用百度地图MCP，制定最优驾车路线：" + prompt; 是主管 Agent 替远程 Agent 把意图焊死——远程 Agent 拿到的根本不是用户那句话，而是主管帮它改写过的「角色化指令」。

2.4 类型转换：字符串 ≠ Msg

agent.call(...) 不收裸 String，只收 Msg。所以 commons 模块里有一个 PromptUtils：

帧 5:23 起就在写这个工具类（位于 commons 模块的 utils 包），把 String 转 Msg。内部实现没展开，但功能就是套一层 AgentScope 的消息壳。

2.5 同步收齐 + 流式对外的两段切换

agent.call(userMsg).block() 这一步是个半投降：

  • 远程那一侧（routeMakingAgent）是 SSE 流式返回的（日志里 Handling streaming request, returning SSE Flux）。
  • 主管这一侧用 .block() 强行阻塞、把流收成一个完整的 Msg。
  • 方法 return remoteAgentResponse.getTextContent(); 给出去一个 String。
  • 上一层 controller 再把这个 String 包成对外的 SSE Flux<String> 推给前端。

也就是说：两个 SSE 端点（远程→主管、主管→前端）之间夹了一个阻塞中转站。代价是失去了从远程到前端的逐字透传，好处是简化了主管侧的代码——为什么这样取舍视频没解释，估计是为了减少这一集的复杂度。

2.6 验证：双控制台对账

视频末尾帧 7:00 + 给出两边日志：

  • 远程侧（RouteMakingAgentApplication 控制台）
    • Handling streaming request, returning SSE Flux
    • Created new task.
    • Subscribed to executeFunction result stream
    • 接着可以看到它在调百度地图 MCP 的各个工具。
  • 主管侧（ManagerAgentApplication 控制台）
    • 这个工具方法传入的参数：深圳到惠州 ← 证明 LLM 抽参成功
    • ====== 构建的Prompt ======ll 调用百度地图MCP，制定深圳到惠州的最优驾车路线 ← 证明二次 prompt 拼接成功
    • [xxx-uuid] A2aAgent start call ← 证明远程调用启动
    • ====== 远程Agent返回 ====== + 路线文本 ← 证明 block 收齐了

两边都对上才算通——这是从 11-3、11-4 沿用下来的「双控制台验证法」，本集是它的第三次复用。

3. 没 get 到的点

  • PromptUtils.getPrompt(String) 内部到底怎么把字符串包成 Msg，是不是 Msg.builder().role(USER).content(...)？没展开。
  • .block() 阻塞期间远程 SSE 已经在吐字，是 SDK 内部把流缓冲拼成完整 Msg 再返回？吐到一半超时怎么办？
  • 二次 prompt 里的「调用百度地图MCP」前缀是不是其实可以省掉？远程 Agent 自己就挂着 MCP，强行限定工具会不会反而限制它的选择？这一点很想验一下。
  • controller 那一层 String → SSE Flux 的转换本集没演示，应该在 13-2 那集，需要回看。

上承

  • 11-4：把 prompt 硬编码在工具方法里——本集就是来拆这条尾巴的。
  • 11-6：让远程 Agent 真正挂上百度地图 MCP，本集第 61 行的「调用百度地图MCP」前缀才有语义意义。
  • 11-7：立下「@Tool description = 拉取入口 / 决策权下沉运行时」的原则，本集把这条线推进到「连参数也让运行时抽」。
  • 13-5：管的是「用户 prompt 进主管」，本集管的是「主管 prompt 进远程」，是同一根流水线的上下两段。
  • 13-6：观测层；本集那两段 ====== 构建的Prompt ====== / ====== 远程Agent返回 ====== 日志区间就是手工版的「思考可视化」。

下启

  • 13-8：课程总结，本集刚好把「用户 → 主管 → 远程 → MCP」端到端打通。
  • 留尾巴：.block() 整段收 + 没把远程流逐字透传给前端——未来要做「打字机式」前端，得改成 agent.call(...).map(...).flatMap(...) 链路。

横向

  • 12-5（景点推荐 SubAgent）：同进程 Lambda 工厂路线；本集是跨进程 Nacos 卡片路线。两边 @ToolParam 抽参逻辑同构——都是 LLM 在 @Tool 边界拆参。
  • 11-5（百度地图 MCP）：本集二次 prompt 里那句「调用百度地图MCP」对应的就是 11-5 拿到的那个工具列表。

5. 知识地图

6. 自测题（5 卡）

  1. @ToolParam(name="prompt", description="驾车的起点和终点") 里这个 description 是给谁看的？改了会发生什么？
  2. 视频里日志打印的 这个工具方法传入的参数：深圳到惠州——「深圳到惠州」这串是从哪里来的？是代码正则解析的吗？
  3. 主管 Agent 把哪句话喂给远程 Agent？是用户那句「制定深圳到惠州最优的驾车路线」原样转发吗？
  4. agent.call(userMsg).block() 这一行为什么是 .block() 而不是 reactive 链式调用？代价是什么？
  5. 验证这一集功能跑通了，你要去看哪两个控制台、各看哪几条关键日志？

参考答案

  1. 给 LLM 看的「抽参指令」，不是代码注释。改成别的描述（比如「请用中文回答」），LLM 会按新描述决定抽什么塞进 prompt 形参。
  2. LLM 抽出来的，不是正则。LLM 读到 @ToolParam 的 description 是「驾车的起点和终点」，于是从用户原句里挑出语义匹配的片段。
  3. 不是。主管在第 61 行硬拼了前缀，远程拿到的是「调用百度地图MCP，制定最优驾车路线：深圳到惠州」，是经过主管改写的二次 prompt。
  4. 因为代码后面还要拿 getTextContent() 同步返回给 controller。代价是远程的流式输出在主管这里被拍平成一次性结果，丢失了逐字透传给前端的可能。
  5. 远程侧看 Handling streaming request, returning SSE Flux + Created new task. + MCP 工具调用；主管侧看 这个工具方法传入的参数： + ====== 构建的Prompt ====== + A2aAgent start call + ====== 远程Agent返回 ======。

7. 关键词表

术语 一句话理解
@ToolParam description = 抽参指令 写在参数上的 description 不是文档注释，是给 LLM 的抽取规则，本集用「驾车的起点和终点」让模型抽出「深圳到惠州」
三层 prompt 流转 用户原句 → LLM 抽取片段 → 主管拼接的二次 prompt，本集真正的数据流核心
PromptUtils.getPrompt → Msg commons 模块工具类，把 String 包成 AgentScope 的 Msg，是 agent.call 的唯一合法入参形式
二次 prompt 焊接 第 61 行硬拼「调用百度地图MCP，制定最优驾车路线：」前缀，主管替远程把意图焊死
agent.call().block() 半投降 reactive 链路里主动阻塞收齐远程流式结果，换简化主管侧代码，代价是丢失对前端的逐字透传
双控制台验证法 远程看 Created new task + MCP 调用，主管看 A2aAgent start call + 远程Agent返回，两边对账才算通
决策权下沉到运行时 从 11-7 的「分发哪个 Agent 让 LLM 决」推进到本集的「传哪些参数也让 LLM 决」
