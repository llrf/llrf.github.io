SpringAi 1.1的工作流状态更新

1. 一句话定位

把 1.0 工作流的代码原样搬到 1.1 工程，只有 StateGraph(...) 那一行红——这一集就是修这一行红。

2. 主体

2.1 实验装置：让红线自己出来

最干净的复习方式：拿 7-10 那个空壳 1.1 工程（pom 已经把 BOM 升到 1.1.0.0-RC2、依赖换成 spring-ai-alibaba-graph-core 且不写版本号），把 1.0 的工作流代码整包复制进去，然后只看 IDE 的红线在哪。

  • 启动类：不红。
  • Node1、Node2（实现 NodeAction）：不红。
  • new StateGraph("parallel", overAllStateFactory)：红，提示 Cannot resolve constructor StateGraph(String, OverAllStateFactory)。

加工增量：这条红线的价值在于”它证明了 1.0 → 1.1 的 breaking change 只集中在 StateGraph 这一处”。NodeAction.apply(OverAllState state) 在两个版本里的签名完全一致——所以你已经写过的节点代码是稳的，不用动。

2.3 把 1.0 的写法逐句翻译到 1.1

1.0（旧）：

1.1（新）：

两个 diff 一目了然：

  • 接口换名：OverAllStateFactory → KeyStrategyFactory。
  • lambda 返回值变了：从”返回 OverAllState 实例”变成”返回 Map<String, KeyStrategy>“——registerKeyAndStrategy 这一行必须删，1.1 会在 StateGraph 构造时自动把 map 注册到全局状态里。

加工增量：变量名 overAllStateFactory 一字没改——这是历史包袱，不是真值。真正决定类型的是冒号左边的类型声明，看到这种”老变量名 + 新接口”的组合不要被名字带偏。转录里把 KeyStrategyFactory 听成 “T-StateFetch / AllStateFetch” 也是同理：以帧画面里的类名为准，别信耳朵。

2.4 Map 内部规则没动

Map<String, KeyStrategy> 的语义在两个版本里完全一致：

  • key：状态里的某个字段名（String）。
  • value：这个字段被多次写入时怎么合并——ReplaceStrategy（覆盖）或 AppendStrategy（追加）。

例子里的约定：key1 → Replace、key2 → Append。这套语义你在 7-2（OverAllState）已经见过，只是当时是”实例上手动 register”，现在变成”工厂里 return map，框架自己 register”。

2.6 三个入参的取舍口诀

入参数 必传项 用法
1 参 KeyStrategyFactory 最简，状态合并策略一项搞定
2 参 String + KeyStrategyFactory 加个工作流名（debug/日志友好）
3 参 + StateSerializer 跨进程/持久化时再选

序列化器有 PlainTextStateSerializer / SpringAIStateSerializer / StateSerializer，本集只一笔带过，记住”什么时候选”——能本地内存搞定就不选，跨进程持久化才选——细节留到具体业务集再补。

3. 没 get 的点

  • KeyStrategy 的全限定名是不是 com.alibaba.cloud.ai.graph.KeyStrategy？OCR 没截到，得自己点进去看。
  • 除 Replace / Append 是否还有第三种内置策略（比如 Merge）？需要在 IDE 里 Choose Declaration 看接口实现列表。
  • OverAllState 在 1.1 用户层还能不能 new？本集那行 new OverAllState() 被注释了，框架是不是已经接管了它的生命周期？
  • 自动注册的时机：是 StateGraph 构造时立刻调 factory.get()，还是首次执行时才调？这关系到”同一个 factory 能不能复用”。
  • 序列化器三选一的判据：PlainText vs SpringAI 各自的用例边界。

4. 跟其他集的连接

  • 上承 7-10：7-10 把”换引擎”这件事的概念铺开了，本集是 7-10 之后第一段具体代码 diff——证明换引擎不是全推倒，只动了一个 API。
  • 上承 7-3：7-3 讲的 StateGraph 三参形态是 1.0 视角；本集是同一对象的”1.0 → 1.1 入参换血”对照面。
  • 上承 7-2：OverAllState 仍是状态载体；变的只是”怎么告诉框架合并策略”这一层。
  • 上承 4-9：pom 里 spring-ai-alibaba-graph-core 不写版本号靠的就是 4-9 那套 BOM 三件套——本集顺带证明 graph 引擎也已纳入 1.1 BOM 矩阵。
  • 下启 7-12：本集只验证”老 demo 能编过”；7-12 会把策略 + 节点拼到具体的旅游规划业务里。
  • 下启 7-13：最终会对照 6-7 / 6-8 的 Agent-as-Tool 方案 vs Graph 方案。
  • 横向 6-6：同样是 1.0 → 1.1 的 API 换血（那边是 ChatClient → ReactAgent）——都是 SAA 1.1 升级的具体表现，一个是 Agent 侧，一个是 Graph 侧。
  • 横向 3-12：多 Agent 的”中间结果存储”概念在 Graph 里就具体落成 KeyStrategy——多节点写同一 key 时怎么合并的问题答案就在这。

5. 知识地图

6. 自测题（5 卡）

  1. 在 1.1 里把 1.0 的工作流代码原样复制过来，最少要改几处？哪一处？

    答案只改 1 处：`new StateGraph("parallel", overAllStateFactory)` 那一行的 lambda 类型和返回值；Node 不动、OverAllState 不动。

  2. 1.0 的 OverAllStateFactory lambda 返回 OverAllState，1.1 的 KeyStrategyFactory lambda 返回什么？

    答案返回 `Map`——直接 return map，不要再调 `registerKeyAndStrategy`。

  3. StateGraph 在 1.1 的所有构造方法里，唯一必传的参数是哪个？

    答案`KeyStrategyFactory`。工作流名和 StateSerializer 都是可选项。

  4. 代码里写 KeyStrategyFactory overAllStateFactory = () -> ...，这个变量名为什么没改？说明什么？

    答案历史包袱/沿用旧命名而已。判断类型必须看冒号左边的接口名，变量名不是真值——这也是转录里把类名听岔的根因。

  5. spring-ai-alibaba-graph-core 在 pom 里为什么可以不写 <version>？这证明了什么？

    答案外层已经 import 了 `spring-ai-alibaba` 的 BOM（`1.1.0.0-RC2`），版本由 BOM 接管。证明 graph 引擎也已经纳入 SAA 1.1 的 BOM 矩阵。

registerKeyAndStrategy 消失 1.0 必写、1.1 不能写——框架在 StateGraph 构造时自动注册
StateGraph 构造方法重载 1.1 提供 8 个重载，必传 KeyStrategyFactory，可选 + 名称 / 序列化器
ReplaceStrategy / AppendStrategy 单 key 的更新策略：覆盖 vs 追加，1.0 / 1.1 完全一致
变量名 ≠ 类型 overAllStateFactory 这个名字沿用，但类型已换成 KeyStrategyFactory
