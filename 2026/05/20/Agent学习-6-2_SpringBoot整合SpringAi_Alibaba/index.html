6-2_SpringBoot整合SpringAi_Alibaba

发表于2026-05-20|更新于2026-05-20|Agent学习第6章 多 Agent + ReAct架构，SpringAi迈入Agent新时代
|浏览量:

1. 一句话定位

这一集要回答的就一个问题：SAA 1.0.0.2 那个 BOM（6-1 钉的）下面，到底要引哪个 starter，才能让 Spring Boot 真的跑起来？——答案不是网上博客复制粘贴的那个 spring-ai-alibaba-starter，而是带 -dashscope 后缀的版本，而且 pom 里依赖的顺序、spring-boot-starter-web 的补刀都不能漏。取舍出现在 §2.B（为什么不能信博客只能信文档），加工增量在 §2.C（”错误从 SLF4J 变 api-key 缺失” 这条经验主义判定线）。

2. 主体

B. 真值源被反咬：仓库说”停更”，文档说”换名字”

打开 mvnrepository.com 搜 spring-ai-alibaba-starter，你会看到这样一张表：

最上面那行 1.0.0-M6.1，2025-03-10——这是它的最后一次发布。再往下全是 M6、M5、M3，更老。Usages 列那个 2 也很说明问题：几乎没人用。

这里有个 4-2 立下的规矩被反过来咬了一口：4-2 教过”以 Maven 中央仓库为真值源”。但仓库能告诉你的事情其实只有一件——“这个 artifactId 停更了”。它不会告诉你”那现在正确的包叫什么名字”。这一步只有 SAA 官方文档 知道，而且必须把文档左上角的版本下拉框切到 1.0.0.2，跟 6-1 的 BOM 对齐——M6.1 的文档里给的依赖名是错的，会把你坑回这个停更包。

切到 1.0.0.2 文档之后，正确的 artifactId 是：

多了 -dashscope 后缀，因为这版 SAA 的大模型走百炼 DashScope。没写 <version> 是因为 6-1 已经引入了 spring-ai-alibaba-bom:1.0.0.2，BOM 帮我们钉死了——这是 6-1 那一节”BOM 三件套”在本集的第一次兑现。

C. 两次 SLF4J 报错 → 一次 api-key 报错，三步到位

写完上面那个 starter，敲一个最小启动类：

demo.springai.SpringAiApplication，@SpringBootApplication + SpringApplication.run，仅此而已。第一次跑——爆炸：

打开 IDEA 右侧 Maven 工具窗的 Dependencies 树，证据出来了：spring-ai-alibaba-starter-dashscope:1.0.0.2 底下只挂了 spring-ai-alibaba-autoconfigure-dashscope + spring-boot-starter:3.4.5——是裸 starter，不带 web。Spring Boot 起不来 8080 服务，错的不是 AI 这一层，是 Web 这一层。

补刀：手动加 spring-boot-starter-web，版本钉死跟传递过来的那个 spring-boot-starter 同步：

用 <springboot.version>3.4.5</springboot.version> 变量管理。

第二次跑——还炸，报的同一个 SLF4J 错。这一步是本集最反直觉的：web 加了为什么还是不行？答案是 Maven 这玩意儿依赖顺序敏感：classpath 冲突的时候，Maven 按 pom 里 <dependencies> 的声明顺序选第一个 winner。dashscope starter 拽进来的某个日志桥接包会”赢”Logback，导致 Logback 拒绝初始化。

补丁：把 spring-boot-starter-web 挪到 spring-ai-alibaba-starter-dashscope 前面——web 先声明，AI 后声明。这是这门课第一次把”Maven 依赖顺序”作为一个显式知识点抛出来，前面 4-1/4-2 都没碰过。

第三次跑——错误换了一种：

这就是”通了”的信号。Spring Boot 已经初始化到 ChatModel Bean 装配那一层、8080 端口已经开起来了，只是没给百炼的 API key。这一类”错误从 X 变 Y”的经验主义判定，跟 4-5/4-8 启动 MCP 服务那种”看到 SSE endpoint 就算通”是同一类——加工增量就在这里：消化稿里散在三个反直觉点里的信息，被我串成了一条三步报错诊断线（SLF4J/缺 web → SLF4J/顺序错 → api-key/通了）。

3. 没 get 的点

  • 依赖顺序为什么敏感？ 讲师只给”放前面”这个补丁，没解释根因。我猜是 dashscope starter 里挂了 jcl-over-slf4j 或 log4j-over-slf4j 这类桥接包，跟 logback-classic 抢 SLF4J binder，但没看 Dependencies 树确认过。
  • 为什么 SAA 不直接把 web 传递进来？ 是不是为了兼容 WebFlux 路线、不强绑 MVC？如果是这样，引 spring-boot-starter-webflux 替代 web 应该也能跑。这一点会跟 4-7（WebFlux 非阻塞）连上，等下一集如果是配 API key 看能不能顺手试一下。
  • 1.0.0.2 这个四段版本号是什么命名约定？ 1.0.0 之后正常是 1.0.1，为什么用第四段做 patch？跟 4-9 的 1.1.0.0-RC2 一致，但没人解释这个约定从哪来。
  • spring-boot-starter:3.4.5 这个版本号是谁钉的？ 是 dashscope starter 自己钉死的，还是 SAA BOM 钉的？得回 6-1 翻 BOM 内容确认——不然下次升 SAA 版本时容易漏改 <springboot.version>。

4. 跟其他集的连接

  • 上承 6-1：本集复用了 6-1 钉的 spring-ai-alibaba.version=1.0.0.2 和 BOM。dashscope starter 不写 <version> 的底气全在那里。
  • 上承 4-2：4-2 立的”Maven 中央仓库作为真值源” + “M6 红线”在本集第二次兑现：M6.1 那个 spring-ai-alibaba-starter 死在 2025-03-10，活的是 -dashscope 后缀版。同时本集也补丁了 4-2 那条规矩——仓库只能告诉你”死了”，告诉你”叫什么名”还得靠文档下拉框对齐 BOM 版本。
  • 下启：下一集大概率是配置 spring.ai.dashscope.api-key（本集最后那条报错就是钓鱼线），再往后会注入 ChatClient Bean 写第一个 @RestController。
  • 横向对照 4-7：4-7 解释了 MCP Server 为什么用 webflux 不用 webmvc（非阻塞）；本集这里走 spring-boot-starter-web（MVC 阻塞）。AI 调用是 IO 密集，理论上 WebFlux 更合适，但 SAA 快速开始示例用的是 MVC，这个张力以后会爆。
  • 横向呼应 4-16：4-16 在 SAA 1.1 RC2 那条线上也踩过同一个”web 必填”坑。说明这是所有 SAA 版本通病，不是 1.0.0.2 独有。
  • 横向呼应 4-8：同一套”启动成功 = 错误从 X 变 Y”的经验主义判定。

5. 知识地图

横向锚点：

  • 4-2 中央仓库真值源 ⟷ 6-2 加补丁（”还得问文档下拉框”）
  • 4-7 WebFlux 非阻塞 ⟷ 6-2 这边用的是 MVC（待爆）
  • 4-8/4-5 SSE endpoint 经验主义判定 ⟷ 6-2 的”报错换种 = 通了”判定

6. 自测题

  1. 在 SAA 1.0.0.2 这一版里，整合 Spring Boot 应该引哪个 artifactId？为什么不能用 spring-ai-alibaba-starter？
  2. spring-ai-alibaba-starter-dashscope 这个依赖没写 <version>，为什么仍然能解析到 1.0.0.2？
  3. 启动报 Failed to load class "org.slf4j.impl.StaticLoggerBinder" 时，有哪两种可能的根因？怎么用 IDEA Maven 工具窗的 Dependencies 树区分？
  4. 为什么 spring-boot-starter-web 必须写在 spring-ai-alibaba-starter-dashscope 前面？背后的 Maven 机制叫什么？
  5. 看到 DashScope API key must be set. Use the connection property: spring.ai.dashscope.api-key 这条错误，应该判断 Spring Boot 处于什么状态？为什么这条错误反而是”通了”的信号？

7. 关键词表

术语 一句话回忆
spring-ai-alibaba-starter-dashscope SAA 1.0.0.2 整合 SpringBoot 的正确入口包，带 -dashscope 后缀。
spring-ai-alibaba-starter（停更陷阱） 网上教程主流写法，但 Maven Central 上停在 1.0.0-M6.1（2025-03-10），不能用。
文档版本下拉框 看 SAA 文档前必须切到 1.0.0.2，跟 BOM 对齐，M6.1 文档给的依赖名是错的。
spring-boot-starter-web 手动加 dashscope starter 只传 spring-boot-starter，不带 web，必须手补，版本钉 3.4.5。
Maven 依赖顺序敏感 classpath 冲突时按 pom 声明顺序选第一个，web 必须在 dashscope starter 前面。
SLF4J/Logback 报错信号 Failed to load StaticLoggerBinder + LoggerFactory is not a Logback LoggerContext 几乎专门对应”缺 web 或顺序错”。
启动成功判定信号 错误变成 DashScope API key must be set 即说明 Spring Boot 已到 ChatModel 装配阶段，8080 已开。
传递依赖证据链 用 IDEA Maven 工具窗 Dependencies 树看 starter-dashscope 实际拽了什么，是判断”还缺什么”的硬证据。
