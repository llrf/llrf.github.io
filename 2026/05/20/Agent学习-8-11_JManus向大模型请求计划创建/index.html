8-11_JManus向大模型请求计划创建

发表于2026-05-20|更新于2026-05-20|Agent学习第8章 Jmanus 懂思考、会规划、一步步动手完成任务。
|浏览量:

1. 一句话定位

这一集把”计划阶段”的第一步——PlanCreator.createPlan()——拆给你看：它就是拼一个带 agents 清单的 prompt，丢给 LLM，最多重试三次，把返回的计划塞回 ExecutionContext。

2. 主体

2.1 你站在哪：先把上集的骨架捡回来

8-10 已经把 PlanningCoordinator 的三阶段生命周期搭好了：

  • 计划开始 = PlanCreator（意图分析 + 创建初步计划）
  • 计划执行 = PlanExecutorFactory（一步一步跑步骤）
  • 计划结束 = PlanFinalizer（汇总结果）

这一集只钻”计划开始”这一格。你要记住一个反直觉的事：Controller 不创建协调器，PlanningFactory 也不创建，最终是 PlanningCoordinator 的构造方法把三件套接进来。所以三件套是被注入的、不是被 new 的——协调器只管编排，不管造零件。这条线 8-10 已经讲过，本集开头花了 4 分钟回锅，你可以快进。

2.2 入口：PlanningCoordinator.createPlan

代码里就 4 行有意义的事：

context.setUseMemory(false) 这一行讲师没展开，但它是个业务断言——计划生成阶段不需要历史对话记忆，每次都从零开始想计划。等到后面真正”执行”的时候才用 memory。这条加工增量你自己标一下，源码注释里没写。

然后就把 context 转手给了 planCreator.createPlan(context)，真正的活在那里。

2.3 PlanCreator 的 7 个字段：按角色分三类

视频里讲师按代码顺序一个一个念，你看完一遍很容易记不住。自己重排成三类会清爽很多：

角色 字段 干什么
LLM 通道 llmService / streamingResponseHandler 一个发请求，一个收流式响应
业务数据 agents（List<DynamicAgentEntity>） / promptService / planningTool 喂给 LLM 的”我有谁、prompt 怎么拼、要 LLM 输出什么结构”
横切 recorder / manusProperties 记录 + 配置

agents 那个 List<DynamicAgentEntity> 是本集的灵魂——JManus 里”我家有哪些工人”就靠它撑着。

2.4 createPlan 内部：三段式 + for 重试

抓主干：

关于 for 循环必须澄清的一点：讲师在视频里说”for 里面向 LLM 请求”，没立刻说重试，第一遍听很容易理解成”多轮渐进生成”。它不是。它就是 maxRetries=3 的容错——拿不到合法 plan 才会进第二轮。源码注释自己写了 Retry mechanism: up to 3 attempts until a valid execution plan is obtained，对照看一眼立刻清楚。

2.5 prompt 里塞了什么：本集业务核心

讲师在视频最后五分钟反复强调一句话：prompt 里光有”用户的请求”是不够的，必须把 agents 的能力清单也塞进去。

为什么？因为 LLM 不是凭空生成计划，它要回答的是”在 JManus 这家公司里、用现有的这几个 agent，怎么分工完成用户的请求”。所以 generatePlanPrompt(userRequest, agentsInfo) 这一行的两个入参就是计划生成的两块原料：

  • userRequest：用户要什么
  • agentsInfo：你能调动谁、各擅长什么

这条对应了 5-5/3-9 的”主管 Agent 派单”模型——只不过 SAA 1.1 的 ReactAgent.builder() 是把这件事内嵌的，JManus 是手撸的：自己拼 prompt、自己用 toolCallbacks(planningTool) 让 LLM 输出结构化计划、自己 for 重试。

2.6 拿到结果之后

LLM 返回的 ChatResponse 经过提取，封装成 PlanInterface 对象，写回 context.setPlan(plan)，然后跳出 for 循环。下游”计划执行”阶段就能从 context 里取出来跑。

ExecutionContext 在这里又一次扮演”跨生命周期的状态包”角色——这是 JManus 版本的 OverAllState（见 7-2）。

3. 没 get 的点

  • buildAgentsInfo(agents) 到底把 DynamicAgentEntity 序列化成什么格式喂给 LLM？JSON / Markdown 表格 / 自然语言？视频没展开，下一集大概率会讲。
  • PlanInterface 的字段结构是 List<Step> 还是 DAG？没看。
  • planningTool 是哪个具体实现？为什么必须用 toolCallbacks 让 LLM 走 function calling 输出，而不是裸 JSON 让它自由生成？这条只能猜：FC 的 schema 约束更硬，能避免格式漂移。
  • if (useMemory && attempt == 1) 这个分支——既然 setUseMemory(false) 已经关了，那 CustomMessageChatMemoryAdvisor 那一段实际上根本不会触发？是历史遗留还是其他入口能开？
  • streamingResponseHandler 在创建计划阶段似乎是同步等结果，它真的有用还是只是统一注入备用？

4. 跟其他集连接

  • 上承 8-10：那集讲 PlanningCoordinator 的三件套构造和生命周期，本集是把”计划开始”这一段拆开看代码。
  • 上承 6-4 ChatClient / 6-5 ChatClient 流式：本集 createPlan 里冒出的 ChatClient.prompt() / advisors / Flux / ChatResponse 全是这两集打的基础。
  • 上承 3-12 多Agent的核心执行流程：那集的”主管 Agent + 计划阶段”骨架，本集是 JManus 源码层面的具象。
  • 横向 6-6 ReactAgent：手撸 vs 框架封装的对照——JManus 自己写 PlanCreator + for 重试 + tool callback，SAA 1.1 把这些塞进 ReactAgent.builder()。
  • 横向 5-5 Agent 团队协作 / 3-9 主管 + 专科 Agent：5-5 是配置式（角色卡片写死），JManus 是动态式（DynamicAgentEntity 喂给 LLM 让它自己选）。
  • 横向 7-2 OverAllState：ExecutionContext 就是 JManus 版本的”状态包”，跨生命周期传递，思想同源。
  • 下启：下一集大概率讲 prompt 的具体内容（promptService 怎么拼模板、agentsInfo 长什么样）、PlanInterface 的字段、以及 planningTool 的 FC schema。

5. 知识地图

6. 自测题（5 卡）

  1. PlanningCoordinator 自己 new 出三件套（PlanCreator / PlanExecutorFactory / PlanFinalizer）吗？为什么？
  2. PlanCreator 的 7 个字段你能按”LLM 通道 / 业务数据 / 横切”分类列出来吗？
  3. createPlan 里的 for (attempt = 1; attempt <= maxRetries; attempt++) 是用来做什么的？三种常见误解里哪种是对的：(a) 多轮渐进生成 (b) 多个 agent 各跑一次 (c) 拿不到合法 plan 时的重试容错？
  4. 为什么 prompt 里必须塞 agentsInfo 而不是只塞用户请求？如果只塞用户请求会出现什么后果？
  5. context.setUseMemory(false) 这一行的业务含义是什么？计划阶段不要历史记忆，跟”执行阶段要不要 memory”有矛盾吗？

7. 关键词表

术语 一句话
PlanningCoordinator 生命周期三件套 PlanCreator（计划开始）/ PlanExecutorFactory（计划执行）/ PlanFinalizer（计划结束），由协调器构造方法注入
PlanCreator 7 字段构造 agents / llmService / planningTool / promptService / recorder / streamingResponseHandler / manusProperties
createPlan 主干 buildAgentsInfo → generatePlanPrompt → for(maxRetries=3) → ChatClient 请求 LLM → 提取 PlanInterface → context.setPlan
maxRetries = 3 for 循环不是多步生成，是拿不到合法 plan 时最多重试 3 次
prompt 双成分 用户请求 + agents 能力清单，缺一不可，否则 LLM 不知道有谁可用
DynamicAgentEntity JManus 里”动态 Agent”的实体类，以 List 形式注入 PlanCreator
planningTool.getFunctionToolCallback 通过 function calling 让 LLM 输出结构化计划，而不是裸 JSON
ExecutionContext 贯穿三生命周期的状态包；计划创建阶段 useMemory=false
