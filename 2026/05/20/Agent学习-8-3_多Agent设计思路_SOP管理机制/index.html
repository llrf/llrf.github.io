8-3 多Agent设计思路 SOP管理机制

1. 一句话定位

多 Agent 协同的最后一块拼图：SOP（标准流程），由主管 Agent 在”切分+派单”之外画的第三张图——一张写明”谁先谁后、谁等谁产物”的塑状流程图。

2. 主体

2.1 钓鱼：单兵能打 ≠ 团队能赢

你已经有了环境、有了角色、有了通信，每个 Agent 单拿出来都很能打。问题来了：

  • 谁先做第一步？
  • A 做完，下一步是 B 接产物加工，还是 C 并行启动？
  • 这个 Agent 完成后还有空闲，要不要去帮另一个 Agent？

没人统筹，”很能打的一群人”会变成”船局一团乱”。讲师的原话是”哪怕每一个智能体很能打，但船局并没有效率高”——这就是 SOP 要解决的”船局问题”。

学习者增量：3-9 给主管 Agent 的印象只有两件事：切分任务 + 派单给专科。这集补上第三件——画甘特图。前两件回答”谁做什么”，SOP 回答”何时做、谁等谁”。三件事都归主管，但是三个独立模块。

2.2 SOP 长啥样：SOP 类 + State 节点

锚图（frames/f014_t0636.7s_anchor.jpg 等右下角”SOP 类 / 状态节点：State 类”那块）：

每个 State 节点绑死四件事：

State 节点字段 装的内容
当前 Agent 这一步轮到谁
当前任务/步骤 它要做什么
状态信息 跑到哪了
下一跳 完成后流向哪个节点

SOP 类就是把这些 State 节点串成一张塑状图（讲师反复说的”塑状结构”，画面看是树状/DAG，疑似口误，详见 §3）。

2.3 两种生成方式（取舍点）

方式 谁画 何时画 适用
预设 主管 Agent 任务一开始 流程稳定、可枚举
动态 LLM 每完成一个节点都可能改下游 流程不可预测、需要根据上一步产出临时改

学习者增量：动态生成由 LLM 来做，不是写死的流程引擎。这就把 SOP 从”DAG”模糊成了”reactive graph”——节点和边都能被改。代价是每次改图都得过一遍 LLM，成本/灵活度的取舍点讲师没展开，记下来留待落地时算账。

2.4 收尾：五大模块全景 + 两个核心流程

这集既是新内容也是全章总结，把多 Agent 协同框架拆成：

两个核心流程（骨架嵌套，源自 3-12）：

  • 宏观：意图识别 → 任务规划 → 任务执行 → 结果整合
  • 微观：单 Agent 步骤规划 → 步骤执行 → 监察 → 动态调整

五大模块：

  1. 环境（Env 类 + Action 类的 think/act）
  2. 任务切分（主管 Agent 职责一）
  3. 角色（RoleSetting + RoleContext + 主管 Agent 的角色分配算法）
  4. 通信 + 冲突协调 + 共识形成（含 WSLL 算法）
  5. SOP（本集新增，主管 Agent 职责三）

锚图（frames/f001_t0000.6s_anchor.jpg 起整个系列共用的那张大图）就是这五块的拼图，本集只往右下角加了”SOP 类 / State 类”那一小块。

3. 没 get 的点

  • State 节点的完整字段表：讲师只说了”状态信息 + 下一步”，没讲是否含”前置依赖列表 / 完成判定函数 / 失败回滚指针”。如果落地到代码大概率要补全。
  • 动态生成 SOP 的触发时机：每个节点完成都调 LLM？还是只有遇到异常/分歧才调？成本敏感的话这是必算账的点。
  • “塑状结构”的术语真伪：讲师反复说”塑状图”，画面看的是含合并节点的 DAG（不是纯树）。是口误还是别名，等后续集确认。
  • State vs RoleContext 的边界：两者都叫”状态”，颗粒度完全不同——RoleContext 存的是”这个 Agent 自己的执行进度”，SOP 的 State 存的是”全局塑状图中的位置 + 下一跳”。讲师没明说，需要自己脑里画一道线。
  • 共识形成算法 WSLL 的全称和数学形式：前集应该讲过，本集没复述。

4. 跟其他集连接

  • 上承：3-12 多 Agent 的核心执行流程 的”主管 Agent + 单 Agent 五步循环”骨架——SOP 就是补齐主管那一侧的”时序”维度。也上承本章 8-1/8-2 已经讲完的环境/角色/通信/冲突协调/共识。
  • 下启：下一集应该会摊开 State 类的字段表（节点字段 / next 指针 / 完成条件），并演示”LLM 动态改图”的 prompt 长啥样。再往后落地到 SAA 1.1，SOP 类 ≈ StateGraph、State 类 ≈ NodeAction/Edge 的组合（7-10 Graph 引擎）。
  • 横向：
    • 与 3-9 多 Agent 协作 形成”主管职责增量”——3-9 给主管两件事（切分+派单），本集加第三件（编排时序）。
    • 与 7-1 工作流编排 / 7-10 Graph 引擎 / 7-12 Graph 搭旅游工作流 是”概念层 vs 工程层”对照——SOP/State 是抽象，StateGraph/NodeAction/OverAllState 是 SAA 1.1 的具体实现。
    • 与 6-8 SAA 1.1 Agent 团队协同 的 FlowAgent（Parallel / Sequential / LlmRouting）对照——FlowAgent 三子类是”预设 SOP”的三种典型拓扑，LlmRoutingAgent 又恰好对应”LLM 动态生成”那条分支。

5. 知识地图

6. 自测题（5 卡）

Q1：主管 Agent 在前面几集里负责”任务切分 + 角色分配”两件事，这集补上的第三件是什么？为什么不能少？

答

第三件是编排 SOP——画出”谁先做、谁等谁、完成后流向哪”的塑状流程图。少了它，每个 Agent 单兵很能打但船局乱套，没有统筹，效率上不来，也没人知道整体计划是啥。

Q2：SOP 类和 State 类是什么关系？State 节点至少要装哪几样东西？

答

SOP 类是整张塑状图，State 类是图上的节点。一个 SOP 由若干 State 节点串成。每个 State 节点至少装：当前 Agent、当前任务/步骤、状态信息、下一跳指针。

Q3：SOP 的两种生成方式分别是什么？各自适用什么场景？

答
  • 预设：主管 Agent 在任务开始时一次性画好。适用于流程稳定、可枚举的场景。
  • 动态：LLM 根据上一节点的实际产出实时改下游节点。适用于流程不可预测、需要根据中间结果临时调整的场景。代价是每次改图都过一次 LLM。

Q4：RoleContext 也叫”状态”，SOP 的 State 类也叫”状态”，两者颗粒度有啥区别？

答
  • RoleContext：单 Agent 内部的执行进度——这个 Agent 自己跑到哪一步、中间产物是啥。
  • SOP 的 State：全局塑状图上的节点——在团队甘特图里处于哪个位置、完成后流向谁。

前者是”我自己的状态”，后者是”我在团队里的位置”，颗粒度差一层。

Q5：多 Agent 协同框架的”五大模块”是哪五块？两个核心流程是什么？

答

五大模块：环境（Env+Action）/ 任务切分 / 角色（含主管 Agent）/ 通信+冲突协调+共识 / SOP。

两个核心流程（骨架嵌套）：

  • 宏观：意图识别 → 任务规划 → 任务执行 → 结果整合
  • 微观（单 Agent）：步骤规划 → 步骤执行 → 监察 → 动态调整

1. 一句话定位SubAgent 是主 Agent 在干活时，把某个”单个专业场景”（写 SQL、CRUD、登录接口）外包给一个跑在独立上下文里的小弟，唯一目的就是不让这点专业脏活污染主上下文。 2. 主体2.1 先把上一集的三层架构在脑子里挂好这集前 4 分钟全在复述上一集，把那张图想清楚再往下读会舒服很多： 总协调 Agent（总监级）：只做规划和需求切分，自己不下场。 Agent 主管（领域主管，前端 / 后端 / 测试 / 运维 / 安全 / 产品 等）：拿到本领域的任务后，继续切，再派给下面的执行者。 Agent 执行者（初级 / 实习生程序员）：真正动手，具有领域知识，能自己组合工具、调 MCP 和 Function Calling，不用反复问大模型”我该用啥工具”。 每一层内部都跑同一个循环：ReAct——思考、执行、再思考”结果对不对、和目标有没有出入”、有偏差就动态调整。讲师反复强调这一条，不是凑数，是后面 SubAgent 出场时的语境：SubAgent 内部也是这个循环，只是壳子不一样。 2....
