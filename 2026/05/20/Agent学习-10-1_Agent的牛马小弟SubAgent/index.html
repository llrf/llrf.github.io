10-1 Agent的牛马小弟：SubAgent

发表于2026-05-20|更新于2026-05-20|Agent学习第10章 Skills 让 Agent 按照专业流程工作
|浏览量:

1. 一句话定位

SubAgent 是主 Agent 在干活时，把某个”单个专业场景”（写 SQL、CRUD、登录接口）外包给一个跑在独立上下文里的小弟，唯一目的就是不让这点专业脏活污染主上下文。

2. 主体

2.1 先把上一集的三层架构在脑子里挂好

这集前 4 分钟全在复述上一集，把那张图想清楚再往下读会舒服很多：

  • 总协调 Agent（总监级）：只做规划和需求切分，自己不下场。
  • Agent 主管（领域主管，前端 / 后端 / 测试 / 运维 / 安全 / 产品 等）：拿到本领域的任务后，继续切，再派给下面的执行者。
  • Agent 执行者（初级 / 实习生程序员）：真正动手，具有领域知识，能自己组合工具、调 MCP 和 Function Calling，不用反复问大模型”我该用啥工具”。

每一层内部都跑同一个循环：ReAct——思考、执行、再思考”结果对不对、和目标有没有出入”、有偏差就动态调整。讲师反复强调这一条，不是凑数，是后面 SubAgent 出场时的语境：SubAgent 内部也是这个循环，只是壳子不一样。

2.2 SubAgent 是从哪一层”再切一刀”

⚠️ 这里很容易踩坑：SubAgent 不是三层架构里的”执行者 Agent”。执行者还在主线的上下文链里——它和主管、总协调共用同一条 context。SubAgent 是从执行者再外挂出去的一类角色。

讲师举的例子很具体：执行者正在写一个登录接口，过程中要查数据库——这就需要写 SQL。”写 SQL”对登录接口这个主线来说，是一个单个专业场景。如果不剥离：

  • 执行者的上下文会塞满 SQL 表结构、字段类型、报错调试痕迹；
  • 一旦 SQL 卡住，整个主线节奏被打断；
  • 想并行做”另一个 CRUD 接口”？没法做，因为只有一条 context。

把”写 SQL”剥成一个 SubAgent，问题就反过来：

  1. SubAgent 在**独立的上下文（独立的 LLM context window）**里跑——讲师嘴里那个”独立的容器”其实是这个意思，不是 Docker 容器、不是进程隔离。
  2. 主上下文只看到结果，不沾过程，不被污染。
  3. 多个 SubAgent 可以并行——一个写 SQL、一个写 CRUD、一个数据分析、一个登录接口，同时跑。
  4. 哪怕某个 SubAgent 挂了，主线任务不受牵连。

讲师把第 4 点放最后，但核心收益其实是 2 + 3：上下文不污染和可并行。容错只是副产品。这条是我对讲师叙述的取舍——他原话顺序会让人误以为”隔离主要为容错”，反过来想效率更好用。

2.3 Claude 三连发：MCP / Skills / SubAgent

讲师在中段画了一张并列图，把 Anthropic（讲师口中的”它”）连续推出的三个前瞻概念排成一排：

概念 解决的问题 装的是什么
MCP 工具接入要个统一标准 工具协议
Skills Agent 怎么获得领域知识 领域知识
SubAgent 主上下文怎么不被脏活污染 独立的上下文

三个东西不重复也不替代。我之前会把 Skills 和 SubAgent 混着想——其实它们是正交的：Skills 让一个 Agent 懂一门手艺，SubAgent 让一个 Agent 暂时变成两个。一个 SubAgent 自己内部也可以挂 Skills。

2.4 切分粒度的判据（我加工的增量）

讲师只说”单个专业场景”，没给可操作的判据。我把它整理成一条经验线，给一年后的我直接用：

该不该剥成 SubAgent，看这个子任务的中间过程会不会把主上下文塞脏。

  • 写 SQL：中间会冒出表结构、字段类型、试错——剥。
  • CRUD：中间会冒出大量样板代码、字段映射——剥。
  • 登录接口：中间会冒出加密算法选型、token 格式调试——剥。
  • 在 IT 部里”塞给实习生”的活，几乎都是这类——这是讲师的直觉，可惜他没显式说出来。

不剥的反例（讲师没讲，我补的）：主线的核心判断、跨子任务的串联决策、最终的结果汇总——这些必须留在主上下文里，剥出去反而割裂。

3. 没 get 的点

  • SubAgent 怎么被调起？ 是主 Agent 像调函数一样 spawn，还是像 Skills 那样声明式注册？本集只讲是什么，没讲怎么写。
  • SubAgent 之间能通信吗？ 还是只能经主 Agent 中转？讲师只强调”不污染主上下文”，没说彼此。
  • 结果怎么回收到主上下文？ 只回 final result 还是带摘要？这是”不污染”承诺的真正技术点，没讲。
  • SubAgent 出错后，主 Agent 是重试、降级、还是放弃？ 讲师只说”不连累主线”，没说补偿机制。
  • **和 A2A / Nacos 那一套的取舍——**SubAgent 本地、A2A 远程，9 章里两个词同时出现说明工程化时混用，但分工边界还没明说。

5. 知识地图

6. 自测题（5 张卡）

  1. SubAgent 和三层架构里的”执行者 Agent”是同一个东西吗？

    • 不是。执行者还在主上下文链里；SubAgent 是从执行者再外挂出去的独立 context，是平铺架构里的第四类角色，不是第四层。

  2. SubAgent 存在的核心动机是什么？容错算不算？

    • 核心动机是”主上下文不被专业脏活污染” + “可并行”。容错（出错不连累主线）是副产品，不是首要动机。

  3. 讲师所说的”独立的容器”具体指什么？

    • 指独立的 LLM context window，不是 Docker 容器、不是进程隔离。

  4. MCP / Skills / SubAgent 三者的分工？

    • MCP 是工具接入的统一协议；Skills 让 Agent 装载领域知识；SubAgent 让 Agent 把单个专业场景剥到独立上下文里跑。三者正交、互补。

  5. 一个子任务该不该剥成 SubAgent，你怎么判断？

    • 看这个子任务的中间过程会不会把主上下文塞脏（大量样板代码 / 字段映射 / 试错痕迹 / 领域专属对话）。会就剥，不会就留。

Skills 的文件结构标准1. 一句话定位Skills 是一个文件夹，文件夹里以 SKILL.md 为入口索引，Agent 先把这个 md 加载进上下文，再按需拉脚本/资源/指令——上一集讲的”渐进式加载”，落到磁盘上就长这样。 2. 主体2.1 为什么一定是”文件夹”，而不是一个大 prompt你装一个完整的专业 SOP（领域知识 + 工作流 + 工具调用逻辑），那玩意往往几千上万字，外加示例数据、API 文档、脚本代码——一次性塞进上下文窗口会爆，复制粘贴又难以版本化。 文件夹解决两个问题： 分级懒加载：Agent 先吃索引（SKILL.md），到正文写”要用 examples.md / execute_api.py”时才按需拉细节。 可移植性：把整个文件夹拷给 B Agent，B 立刻具备和 A 一样的技能——不是 fine-tune，不是 prompt 复制，文件夹本身 = 技能包。 加工增量：讲师按”先讲是什么 → 再讲怎么用”的顺序展开，我把它倒过来重写为”先讲为什么必须是文件夹”，因为如果不先想清楚”上下文为什么会爆”...
