7-1 以工作流方式编排旅行规划的团队协同

1. 一句话定位

你已经在第 6 章用 AgentScope 把”主管 + 三专员 + 汇总”这套五人编制串成了 Agent 自主代理的版本；这一集换轨——同样五个角色，改用工作流编排（Graph 引擎为核心）来摆位置，决定谁在前谁在后、谁和谁并行、谁汇聚到谁。本集只画图、不写代码，目标是把”业务依赖”翻译成”DAG 拓扑”。

2. 主体

2.1 先把上一阶段产物列清楚

旅行规划这个需求过去几集已经孵出来 5 个 Agent——三个干活的、一个调度的、一个善后的：

  • 路线制定 Agent：地点搜索、经纬度转换、路线规划、距离计算、路线可视化
  • 行程规划 Agent：景点信息搜索、抓网页/抓图、天气查询、本地文件、表格制作
  • 费用统筹 Agent：数学计算、表格制作、网络抓取、脚本制作
  • 主管 Agent：意图识别 + 任务拆解（用户 raw prompt 的第一站）
  • 汇总 Agent：整合三个干活 Agent 的执行结果，做最终交付

这 5 个角色在 5-2 / 5-3 / 5-4 / 5-5 已经各自立过卡片了（同模板：角色定义 + 能力清单）。本集不动这套编制，只决定他们怎么连线。

2.2 两条范式的分岔

讲师把多 Agent 协同拆成两条对立的设计思想——

  • Agent 自主代理（Agentic 为核心）：代表是 AgentScope（SAA 生态），靠 ReAct 思维框架让 Agent 自己想”下一步用什么工具走什么路”。第 6 章主线。
  • 工作流编排（Graph 引擎/图形引擎为核心）：代表是 JManus（Java 版 Manus），节点和边显式声明，开发者画拓扑。SAA 也内置了 Graph 引擎（这就是 4-9 那个 DAG Graph 标签的伏笔）。

讲师口误：屏幕上只列了两种，但他口播说”第三种是工作流编排”——中间那”第二种”消失了。按上下文判断，对立面只有两种，按你自己的理解归类即可。

本集开始走第二条。

2.3 三种工作流拓扑（这是本集骨架）

把 5 个 Agent 摆成 DAG，可能的拓扑形态有三种——

形态 ①：线性串行

主管 → 路线 → 行程 → 费用 → 汇总 → 用户。一条直线，前一个完成才轮到后一个。

形态 ②：完全并行 + 汇总

主管把任务同时派给路线、行程、费用三人，三人各干各的，结果都汇到汇总 Agent，再返回用户。

形态 ③：混合（并行 + 顺序汇聚）

路线和行程并行干活，干完都汇给费用统筹做加总，三家最后再汇给汇总 Agent。

三种拓扑哪种合身？这就到了取舍出现在 §2.4。

2.4 业务依赖驱动拓扑选择（取舍）

取舍出现在 §2.4：选哪种拓扑不是凭直觉，是看业务依赖。

把”费用统筹”这件事拆开看——它要算的是 路线费 + 景点费 + 住宿费 + 餐饮费。前一项是路线 Agent 的产出（深圳→惠州的车费/距离），后三项是行程 Agent 的产出（景点/住宿/餐饮安排）。

由此推出两条铁律：

  • 路线 Agent 和行程 Agent 互不依赖 → 可以并行
  • 费用 Agent 依赖前两者的输出 → 必须排在它俩之后

这就否决了形态 ②——形态 ② 把费用和路线/行程平级并行，但费用根本没东西可算；也否决了形态 ①——把它们串成一条直线浪费了路线/行程的并行机会。

唯一合身的是 形态 ③：路线 ∥ 行程 → 费用 → 汇总。

这里有个反直觉的认知翻转：5-2 ~ 5-5 一直把”费用统筹”当作和路线、行程平级的第三个专员；到这集突然降格成二级汇聚节点——它的真实身份是”消费别人输出的求和器”，不是平起平坐的干活者。这就是把”业务依赖”翻译成”工作流拓扑”的真正学问——卡片立得对不对，要靠拓扑来检验。

2.5 定型最终工作流（加工增量在 §2.5）

加工增量在 §2.5：消化稿”重新组织顺序”那一节把讲师的论述抽象成了”形态 ① ② ③ + 业务依赖判据”的双层结构；这里继续把每个节点的输入输出语义补出来，方便后续翻译成 Graph 代码。

最终拓扑（f015 那张图）按时间顺序读：

  1. 用户 Prompt → 主 Agent（主管）
  2. 主 Agent：接收任务 → 意图识别 → 任务分解。把”路线相关”派给路线制定专员，把”行程相关”派给行程规划经理。
  3. 路线制定专员 ∥ 行程规划经理：并行干活（两者输入互不依赖）
  4. 路线 + 行程的输出 → 费用统筹管家：做费用加总（这是第一个汇聚点）
  5. 路线 + 行程 + 费用的输出 → 汇总 Agent：整合成表格/图表（这是第二个汇聚点）
  6. 汇总 Agent → 用户：流式输出最终交付

注意此处出现了两个汇聚点——费用统筹是”二级汇聚”，汇总 Agent 是”三级汇聚”。两者职能完全不同：

  • 费用统筹 只 sum 费用数字
  • 汇总 Agent sum 全量结果（路线 + 行程 + 费用），产出面向用户的表格

第一遍听非常容易把这两个”汇总”混成一个角色，要分清。

2.6 主管 Agent 的两职 + 流式输出

主管 Agent 干两件事：意图识别（理解用户到底想要什么）+ 任务拆解（把 raw prompt 路由到正确的子节点）。它是整张 DAG 的入口路由器。

汇总 Agent 的产物以流式形式返给用户——这点呼应 6-5 ChatClient 的 SSE 流。在 Graph 引擎里，”流式输出”很可能是 DAG 的终端节点特殊属性，而不是普通 ChatClient.stream，留待下集代码看。

2.7 工作流编排的卖点

为什么选工作流编排而不是 Agent 自主代理？讲师明说一句话：可视化。

DAG 摆出来后，谁在哪个节点、谁和谁并行、谁汇聚到谁——一眼看清。相比 ReAct 自主代理那种”LLM 自己决策黑盒”，工作流编排在调试、复审、向团队解释方面有压倒性优势。这是它存在的根本理由。

3. 没 get 的点

  • 讲师说”有三种设计思想”但只列出了两种（自主代理、工作流编排）——中间那”第二种”是真的有，还是口误？大概率是口误，但留个尾巴。
  • f015 里费用统筹既是”接收者”又是”发送者”（既接路线/行程的输出，又发给汇总 Agent）——代码层面这种二段汇聚是用 SequentialAgent 嵌套 ParallelAgent 实现，还是直接在 Graph 里画两条 edge？6-8 提过这些组合 Agent，但这里属于哪种待下集验证。
  • 主管 Agent 的”任务拆解”是 LLM 推理动态产出（动态拓扑），还是开发者在 Graph 里写死（静态拓扑）？工作流编排范式倾向后者——那”拆解”还需要 LLM 吗？如果不需要，主管 Agent 就退化成纯路由器，不需要大模型。
  • “流式输出”的实现层：是汇总 Agent 内部 stream（普通 ChatClient.stream），还是 Graph 引擎把整个 DAG 的中间状态流式吐出？前者是常规手法，后者是 SAA Graph 的特性。

5. 知识地图

6. 自测题

Q1：旅行规划的 5 个 Agent 中，哪个的真实身份是”汇聚节点”而不是”和路线/行程平级的干活者”？说明理由。

参考答案

费用统筹 Agent。它要算的是”路线费 + 景点费 + 住宿费 + 餐饮费”，其中路线费来自路线 Agent，景点/住宿/餐饮费来自行程 Agent。它必须在路线和行程之后才有数据可消费，本质是消费别人输出做求和的二级汇聚节点。5-4 立卡片时把它和路线/行程平级，是从”职能描述”角度看；这一集从”工作流拓扑”角度看，必须降格成汇聚点。

Q2：三种工作流拓扑里，旅行规划场景为什么不能选”完全并行”形态？

参考答案

完全并行（主管 → {路线, 行程, 费用} → 汇总）要求三个干活 Agent 输入互不依赖。但费用 Agent 的输入恰恰是路线和行程的输出——并行调起时费用根本没数据可算。强行并行只会让费用 Agent 拿空输入跑空结果。所以必须改成混合形态（路线 ∥ 行程 → 费用 → 汇总）。

Q3：f015 那张最终工作流图里有几个”汇聚点”？分别汇什么、谁是消费者？

参考答案

两个汇聚点：

  • 二级汇聚（费用统筹管家）：汇路线 Agent 的”路线费”+ 行程 Agent 的”景点/住宿/餐饮费”，消费者是费用统筹自己，产出”总费用”。
  • 三级汇聚（汇总 Agent）：汇路线 Agent 的全量结果 + 行程 Agent 的全量结果 + 费用 Agent 的总费用，消费者是用户，产出表格/图表面向交付。

第一遍听这两个”汇总”很容易混成一个，记住”费用只汇钱、汇总汇全量”。

Q4：Agent 自主代理 vs 工作流编排，对应的核心引擎分别叫什么？SAA 同时支持两种吗？

参考答案
  • Agent 自主代理 → Agentic 为核心（代表：AgentScope，靠 ReAct 思维框架）
  • 工作流编排 → Graph 引擎（图形引擎）为核心（代表：JManus）

SAA 1.1 两种都支持——Agentic 那条线就是 6-6 ~ 6-8 的 ReactAgent；Graph 那条线就是 4-9 提到过的 DAG Graph 标签，本集开始展开。

Q5：相比 Agent 自主代理（ReAct），工作流编排的核心卖点是什么？为什么这个卖点对生产环境很重要？

参考答案

核心卖点是可视化：节点位置、并行/串行/汇聚关系一眼看清。

生产环境重要性：

  1. 调试——出 bug 时能立刻定位是哪个节点的问题，不用 trace LLM 的内部决策链
  2. 复审——团队 review 时不用读代码，看图就懂业务流
  3. 解释——和非技术方对齐时图比代码直观
  4. 稳定性——静态拓扑可预测，不会出现 ReAct 那种”LLM 今天选 A 工具明天选 B 工具”的飘移

ReAct 的”自主决策”在 demo 阶段很惊艳，但生产环境要的是确定性。这就是为什么”工作流”这条路一直没死。
