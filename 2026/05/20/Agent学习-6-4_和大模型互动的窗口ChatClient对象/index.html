1. 一句话定位

你把上一集 UserMessage → Prompt → call → 三层剥皮 的糖葫芦串压成 chatClient.prompt(msg).call().content() 一行——代价是 ChatClient 不是简单 POJO，注入进来还得 .build() 一次才能用。

2. 主体

2.1 痛点：上一集的代码有多丑

把 6-3 写的 simpleChat 拉出来看一眼：四个 new、一次 call、三层 getResult().getOutput().getText()、外加判空——光”问大模型一句话”就铺了 20 行。这一集要做的事就一句话：把这 20 行压成一行。

2.2 starter 白送两个 bean，不是一个

SAA 官方文档原话：”spring-ai-alibaba-starter 依赖将通过 Spring Boot 自动装配机制初始化与阿里云通义大模型通信的 ChatClient、ChatModel 相关实例。”——上一集只用了 ChatModel，但 starter 同时也把另一个 bean 塞进了容器。这一集就是去取那另一个。

2.3 反直觉：注入进来的不是 ChatClient 本身

直接 this.chatClient = chatClient 就完事——这是 6-3 写 ChatModel 时的肌肉记忆。但到 ChatClient 这里行不通，要多调一次 .build()：

为什么？ 容器实际给你的是 ChatClient.Builder（一个 inner interface），不是 ChatClient 本体。视频里讲师签名写的是 ChatClient chatClient——这一处大概率是讲师笔误或 OCR 误识，按 SAA 1.0.0.2 源码应当是 ChatClient.Builder chatClientBuilder，否则不可能 .build()。详见 §3 第 1 条。

记住这个”必须 build 一次”——它不是 Spring AI 的怪癖，而是 Builder 模式的入场费。

2.4 为什么是 Builder 模式：new + setter 的三个原罪

讲师在 .build() 之后插了一段长长的设计模式科普，看似离题，其实就是 ChatClient 接口设计的全部理由。把 new + 一堆 setter 的三个缺点摆出来，再把 Builder 的三个对称优点贴上去：

原罪 场景 Builder 的解法
1. 属性多了 setter 海洋丑陋 user.setAge(); user.setName(); user.setBirthday(); ... 链式调用 .age().name().birthday().build()
2. 高并发下 setter 状态不一致 线程 A 跑 setAge、线程 B 跑 setBirthday，可能某属性没更新就被读走 所有字段 final，build 后整个对象不可变，无中间态可读
3. 漏 set 的属性是 null，业务里炸 NPE setName 忘了写就 NPE build 时统一兜底默认值 + 校验

ChatClient 之所以必须走 Builder，是因为它要打包”一次对话所需的所有上下文”——system prompt、advisors、tools、memory……属性多、要不可变、要默认值，三个特征全中。

取舍出现在 §2.4：ChatClient 不走 new ChatClient(...) + setter，是用 API 表面复杂度换运行时不可变性和并发安全。

2.5 Builder 上挂”全局默认”：defaultSystem / defaultAdvisors

.build() 之前的链上可以挂任意”全局默认”，本集只演示空调用占位：

  • defaultSystem(...) — 后续传角色提示词字符串，例如”你是一位资深咖啡师”。
  • defaultAdvisors(...) — SAA 的”高级能力”接入口，聊天记忆、RAG 检索、日志拦截器全往这里挂。

这两个空调用是后续整个 SAA 高级特性的入口——记住”全局默认通过 Builder 链挂”这个套路，后面所有功能都是同一节奏。加工增量在 §2.5：讲师只口述了两个空调用、没演示参数；本集把它定位成”后续 RAG / 记忆 / 日志的总挂载点”，是顺着 §4 横向对照（4-6 的 toolObjects、4-13 的 tools）补出来的。

2.6 链式调用三段式：prompt / call / content

写新接口 /simple/chatclient，目标体感就一行：

三段拆解：

  • prompt(message) — 这个方法名容易和上集 new Prompt(userMessage) 撞车：前者是 ChatClient 上的方法，链式入口；后者是 Prompt 类的构造器。两条路径名字撞车，留个心眼。
  • call() — 同步打到大模型（流式版叫 stream()，在 6-5）。
  • content() — 提取纯文本字符串。讲师在视频里口误说”返回是 stream 类型”，实际同步路径 call().content() 返回 String，流式才是 Flux<String>。

注意：这里没有任何判空——6-3 那套 getResult() / getOutput() 三层判空被 content() 一刀切了。这正是 Builder + 不可变 + 链式糖衣的甜头。

2.7 跑通验证

ApiFox 打 GET http://127.0.0.1:8080/simple/chatclient，能看到模型对”在咖啡馆里，想要杯星巴克”的回答即闭环成功——和 6-3 完全等效，只是源码体感清爽了。

3. 没 get 的点（待查）

  • 注入进来的到底是 ChatClient 还是 ChatClient.Builder？视频构造方法签名 OCR 出来是 ChatClient chatClient，但代码里调了 .build()。这只可能在”实参类型是 ChatClient.Builder“时成立。打开 SAA 1.0.0.2 的 ChatClientAutoConfiguration 验一下 bean 暴露类型。
  • defaultAdvisors() 空调用真合法吗？参数应该是变长 Advisor... 或集合，传 0 个等于不挂——但下一集若给具体参数才能确证。
  • Builder 模式如何”提供默认值”？是 Builder 字段初始化时给，还是 build() 内部检查后填？这是设计模式细节，SAA 不影响，但自己写 Builder 时要回查。
  • content() 同步路径返回 String 我看是确定的，但流式版 stream().content() 是 Flux<String> 还是 Stream<String>？响应式栈应该是 Reactor Flux，6-5 流式那集会揭晓。

4. 跟其他集连接

  • 上承 6-3：6-3 那条”`UserMessage → Prompt → call → 三层取”对象链是本集要压扁的对象。没看 6-3 直接看 6-4 会丢失”为什么需要糖衣”这个动机。
  • 上承 4-1：BOM + spring-ai-alibaba-starter-dashscope 导入。本集真正用到 starter 白送的第二个 bean（第一个在 6-3）。
  • 下启 6-5（流式响应）：call() → stream()、content() 返回类型从 String → Flux<String>，SSE 推送。本集 content() 同步返回 String 是 6-5 的对照基线。
  • 下启 后续 advisors 集：defaultAdvisors() 这里挂空，下一波要展开成聊天记忆、RAG、日志拦截器——SAA 高级能力全走这个口。
  • 横向 4-6（MCP 工具用 MethodToolCallbackProvider.builder().toolObjects(...).build()）：同一个 Builder 套路。
  • 横向 4-13（ReactAgent.builder().tools(...).build()）：1.1 版 Agent 抽象继续沿用 Builder。Builder 模式是 SAA 在 1.0 → 1.1 演进里始终保留的 API 风格——.xxx().yyy().build() 这个节奏会出现在所有”配置一次终身用”的对象上。

6. 自测题

  1. 为什么 ChatModel 注入后能直接 this.chatModel = chatModel，但 ChatClient 注入后必须 this.chatClient = chatClient.build() 才能用？容器实际给你的是哪个类型？
  2. new + setter 创建对象的三个缺点是什么？Builder 模式分别用哪三个特性把它们解掉？
  3. chatClient.prompt(msg).call().content() 三段方法分别在做什么？prompt(msg) 这个方法名容易和上集哪段代码撞车，怎么区分？
  4. defaultSystem() 和 defaultAdvisors() 在本集是空调用，它们各自的”非空”用法将分别承载哪一类后续能力？
  5. 如果想把同步调用改成流式 SSE，链式调用要改哪一段？content() 的返回类型会从什么变成什么？

7. 关键词表

术语 一句话定义
ChatClient SAA starter 自动装配的两个核心 bean 之一，封装”默认上下文 + 链式糖衣”的对话客户端。
ChatClient.Builder 注入到构造方法里的实际类型（ChatClient 的内部接口），必须 .build() 一次才能拿到 ChatClient 实例。
Builder 模式 先建 Builder → 链式赋值 → .build() 产出不可变 final 对象，对应 new+setter 的三个原罪。
不可变对象 所有字段 final、build 后不可改，规避 setter 多线程竞态；任何”修改”都得新 build 一个。
链式调用 .xxx().yyy().build() 节奏，本集体现在 prompt(msg).call().content() 同步三段。
构造方法注入 private final 字段 + 构造方法参数，本集场景被迫使用——成员要先 build 再赋值，字段注入做不到。
defaultSystem 与 defaultAdvisors Builder 链上挂”全局默认”的两个口子；System 挂角色提示词，Advisors 挂记忆/RAG/拦截器。
自动装配两 bean 导入 dashscope starter 后，Spring Boot 启动时同时初始化 ChatModel 和 ChatClient.Builder 两个 bean。
