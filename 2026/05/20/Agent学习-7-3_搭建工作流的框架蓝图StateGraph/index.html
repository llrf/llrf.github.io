7-3 搭建工作流的框架蓝图：StateGraph

发表于2026-05-20|更新于2026-05-20|Agent学习第07章 Graph 搭建旅游规划工作流，像拼积木一样轻松
|浏览量:

一句话定位

StateGraph 是工作流的”空蓝图”——一个能装节点（addNode）和箭头（addEdge）的容器。7-2 你造好了贯穿全流程的状态包 OverAllState，这一集你把”装东西的图”本身 new 出来，但还不往里装。

主体

1. 工作流四对象，第二个登场

SAA 1.1 的工作流（DAG Graph）由四类对象拼起来：

  1. OverAllState——KV 状态包，每个 key 带 Append/Replace 更新策略（7-2 全程在讲的东西）
  2. 节点（NodeAction）——干活的执行单元
  3. 边（Edge）——节点之间的箭头连线，决定执行顺序
  4. StateGraph——把上面三者装进去的”蓝图”对象

这一集只造第 4 个，第 2、3 个下集再说。

2. 构造方法：表面两参，本质三参

**【加工增量】**讲师在视频里把 GsonSerializer 念成”追审框架”，全程绕口令。听写时反向校对：每次听到”追审”就在脑子里替换成”Json 序列化器（Gson）”，否则后面看源码会对不上号。同理 addNode 念成”at node”、addEdge 念成”h 方法”。

**为什么？**视频没明说，但隐含逻辑是：工作流可能被多次 invoke，并行节点也可能要分支各自的副本——所以要”图纸”而不是”已经造好的成品”。这个动机要等到下一集（甚至 7-6 运行工作流）才能彻底验证。

4. 读源码硬技巧：跳过划线的，挑参数最少的

点进 StateGraph 类一看，构造方法满屏 @Deprecated：

  • StateGraph(OverAllState) —— 划线
  • StateGraph(String, OverAllState) —— 划线
  • StateGraph(String, OverAllStateFactory) —— 没划线 ✓
  • StateGraph(String, OverAllStateFactory, PlainTextStateSerializer) —— 没划线，但要多传序列化器
  • 还有几个更复杂的重载

挑没划线的、参数最少的——这是阅读 SAA 源码的通用招式（4-9 里挑 BOM 版本也是同一种思路）。

6. 这一集结束时你手上的东西

工作流的名字叫 parallel——这个细节剧透了后面要演并行节点结构，呼应 6-8 的 ParallelAgent。

没 get 的点

  • **为什么必须用 Factory 不能传 State？**讲师没解释。猜测两条：① 多次 invoke 时每次要新鲜状态；② 并行分支需要独立副本。要等 7-6 运行工作流时验证。
  • **StateGraph(OverAllStateFactory, PlainTextStateSerializer) 这个重载什么时候用？**讲师快进了，目前只知道默认 GsonSerializer 够用。
  • **addNode 的具体签名——节点到底是 NodeAction 还是别的什么类型？**这一集只点名不展开，留给 7-4。
  • **OverAllStateFactory.create() 是 SAA 在每次 invoke 时调一次、还是每个节点调一次？**关系到状态副本数量，目前不清楚。

跟其他集连接

  • 上承 7-2：本集开头 80% 时长在回顾 OverAllState 的 KV + Append/Replace 双策略；lambda 里那一坨原样复用 7-2 写过的代码。更上游是 6-8 OverAllState 第一次露面，4-14 取 A2A 返回值时已经把它当 KV 状态包用过。
  • 下启 7-4：本集最后 30 秒预告 addNode / addEdge，下一集开始往 StateGraph 里塞节点——NodeAction 登场。再往后 7-5 边，7-6 编译运行。
  • 横向 6-8：6-8 的 SequentialAgent / ParallelAgent / LlmRoutingAgent 是高层封装，本集回到底层 StateGraph——相当于把 6-8 那些封装拆开看到内部就是 StateGraph + nodes + edges。视频里起名 parallel 直接暗示这是 ParallelAgent 的底层重演。
  • 横向 4-5 / 3-7：lambda 替继承、@Tool 注解替继承、Skills 文件配置替继承——SAA 全栈都在用”声明式 / 函数式”替代”OOP 继承式”，是同一种轻量化哲学的三个侧面。
  • 横向 4-9：”跳过 @Deprecated、挑参数最少的”这个读源码技巧在 4-9 挑 BOM 版本时已经用过，本集再次复用。

知识地图

自测题（5 卡）

  1. Q：StateGraph 的构造方法看起来要两个参数，实际上有几个参数？被省掉的那个是什么？
    A：本质三个。第 3 个 stateSerializer 由构造方法内部 new GsonSerializer() 兜底，所以表面只写两个。讲师口误念成”追审框架”，实际是 Json 序列化器。

  2. Q：为什么 StateGraph 构造方法接受的是 OverAllStateFactory 而不是 OverAllState 本身？
    A：因为工作流要支持多次 invoke 和并行分支，每次/每分支可能要一份新鲜的状态实例，所以传”造状态的图纸”而不是”已经造好的状态成品”。StateGraph(OverAllState) 这种签名在源码里已经被 @Deprecated 划掉了。

  3. Q：@FunctionalInterface 的判据是什么？为什么遇到它要立刻切 lambda？
    A：判据 = 接口里有且只有一个抽象方法。看到这个注解就说明可以用 lambda 表达式直接给出那一个方法的方法体，省掉 new XXX() { @Override ... } 的匿名内部类样板。OverAllStateFactory 只有 create() 一个方法，标准函数式接口。

  4. Q：阅读 SAA 源码挑构造方法时的硬技巧是什么？
    A：跳过所有 @Deprecated 划线的旧签名，在没划线的活着签名里挑参数最少的那一支。本集 StateGraph(String, OverAllStateFactory) 就是这么挑出来的。

  5. Q：本集结束时手上有什么、还差什么才能让工作流跑起来？
    A：手上有：StateGraph stateGraph = new StateGraph("parallel", lambdaFactory) 这个空蓝图。还差三件：① addNode(...) 塞节点（7-4），② addEdge(...) 塞箭头（7-5），③ 编译 + invoke 真正运行（7-6）。
