6-10_AgentScope构建搭载工具的ReAct_Agent2

1. 一句话定位

把 6-9 留下的 ReActAgent.builder() 半成品补齐——给它装上 Toolkit（手脚）+ Memory（记忆）+ 系统提示词，最后用一个 Msg 把它跑起来。

2. 主体

2.1 Toolkit 三步走

AgentScope 把”一组工具”抽象成一个一等公民对象，叫 Toolkit。流程很直白：

  1. new Toolkit()——空容器；
  2. 写工具类 WeatherTool，里面写个 getWeather(String city) 方法；
  3. toolkit.registerTool(new WeatherTool()) 塞进去。

留意 registerTool 的方法签名——入参类型居然是 Object。第一眼会以为”啥都能塞”，但讲师故意演了个反例：先丢一个没加任何注解的纯 POJO 进去，编译过、运行不报错，但大模型根本不知道这工具是干啥的、不会去调。

所以 Object 不是”啥都行”的烂签名，它是为了同时接住两种合法形态的最小公倍数：

  • 一种是 AgentTool 子类（运行时动态生成的工具，可能用于”把另一个 Agent 包装成工具”，本集没展开）；
  • 一种是带 @Tool 注解的普通类，Toolkit 内部反射扫方法。

2.2 @Tool 注解：同名不同神

这是迁移 SAA 1.1 → AgentScope 最容易踩的坑：

两个框架都用 @Tool 这个名字，但完全是两套体系。属性也类似（name + description），但 description 的角色更重要——它是 LLM 真正”理解”工具用途的依据，缺了等于工具不存在。

挂到 Agent 上就一行：.toolkit(toolkit)。对比 SAA 1.1 的 .tools(callback1, callback2, ...)——AgentScope 这种”先组装包再挂载”省掉了为每个工具单独造 ToolCallback 的样板代码（取舍出现在 §2.6）。

2.4 Msg + ContentBlock：为什么这么”重”

发一句话给 Agent 跑起来，完整形态长这样：

只发一句文本要写 6 行——讲师自己也吐槽”封装得还是比较厉害”。然后揭晓 AgentScope 提供了捷径：

为什么要 ContentBlock 这一层抽象？答案是多模态。同一个 Msg 容器要装得下 7 种子类：

  • TextBlock / ImageBlock / AudioBlock / VideoBlock
  • ThinkingBlock（思维链片段）
  • ToolUseBlock / ToolResultBlock（ReAct 里”调工具”和”工具回结果”两步）

这是**”未来兼容性 vs 当前便利性”的经典权衡**——纯文本场景用捷径，多模态场景回到完整形态。

2.5 MsgRole 四个枚举

USER / ASSISTANT / SYSTEM / TOOL。最后一个 TOOL 角色用在哪？大概率是 ReAct 循环里”工具返回结果”那一步用它封装回喂给 LLM——本集没明说，留到后面集证实。

2.6 SAA 1.1 → AgentScope 的三处便捷化

讲师压轴的横向对比，取舍出现在这里——AgentScope 用更高的抽象层级换取了”少写代码”，代价是开发者需要先理解一层新概念（Toolkit / ContentBlock / Memory interface）：

维度 SAA 1.1 AgentScope
工具挂载 每个工具造一个 ToolCallback 再 .tools(...) 一个 Toolkit 容器 + registerTool(Object)
流式开关 调用时选 agent.stream(p) vs agent.call(p) model.builder().stream(true) 构造时定死
思维链 自己拼 prompt 引导 enableThinking(true) 内置开关（DeepSeek 风气影响）

.stream() 不在 agent 上而在 model 上——这点反直觉。决策点从”调用时选”下沉到”模型构造时配”，于是 agent 这边统一调用即可。

3. 没 get 的点

  • agent.stream(msg) 返回什么？是 Flux<NodeOutput> 那种结构吗？本集只起头没跑通，apiKey 和 sysPrompt 都还空着。
  • enableThinking(true) 真开了，思维过程是拼在 content 前面，还是单独走 ThinkingBlock 流式分块下发？
  • AgentTool 那个分支的真实用例——是不是 Agent-as-tool 模式？需要看子类清单。
  • @Tool 的 description 写得多详细才有效？token 成本和召回率之间的甜点在哪？
  • Msg.builder().textContent(...) 是不是 .content(List.of(TextBlock.build())) 的语法糖？看源码验。
  • MsgRole.TOOL 是开发者手动封装，还是 AgentScope 内部 ReAct 循环自动处理？

4. 跟其他集连接

上承：

  • 4-5 创建 MCP 工具——SAA 的 @Tool 用法，本集等于换 import 重写一遍。
  • 4-6 注册 MCP 工具到 MCP 服务——MethodToolCallbackProvider + toolObjects(Object...) 和本集 Toolkit + registerTool(Object) 是两个”工具集合容器”的同构设计。
  • 4-13 SAA 1.1 A2A 服务注册——.tools(weatherTool) 是 SAA 1.1 的工具挂载范式，本集是 AgentScope 对照版。

下启：

  • 6-11 MCP 客户端连接 MCP 服务端——本集只演本地 POJO 工具，下集大概率把工具来源扩展到远程 MCP Server。
  • 6-12 大模型调用本地自定义的 MCP 服务——6-11 客户端 + 6-10 工具组装合体。
  • 6-15 测试 AgentScope 的 Agent 运行——本集 agent.stream(msg) 只起头，6-15 大概率端到端跑通。

横向：

  • 跟 3-7 3-8 的”工具按需加载”思想呼应——Toolkit 作为对象级容器天然适合做动态注册/卸载，比 SAA 1.1 启动时变长参数定死灵活。
  • 跟 3-12 多 Agent 核心执行流程 的”大脑/手脚/记忆”三能力完整对齐——本集的 builder 链就是这三能力的代码具现（见 §2.7）。
  • 跟 4-12 SAA 1.1 MCP 注解 互为对照——那边 @McpTool，这边 @Tool，并存时看清 import。

6. 自测题（5 卡）

  1. toolkit.registerTool(Object) 的入参为什么是 Object 而不是某个固定接口？
  2. 一个 POJO 工具类没加任何注解，能 registerTool 进去吗？会发生什么？
  3. SAA 1.1 的 @Tool 和 AgentScope 的 @Tool 是同一个吗？怎么区分？
  4. 用 Msg 发一句纯文本”你好”的完整形态和捷径形态分别长什么样？为什么 AgentScope 不直接简化成 Msg.of("你好")？
  5. 想从”流式”切到”非流式”，应该改 agent 上的什么方法，还是改哪里？

7. 关键词表

术语 一句话定义
Toolkit AgentScope 的工具集容器，new Toolkit() + registerTool(...) + .toolkit(toolkit) 三步挂到 Agent
@Tool 注解（AgentScope 版） io.agentscope.core.tool.Tool，和 SAA 的 @Tool 同名不同神；description 是 LLM 理解工具用途的依据
registerTool(Object) 入参为 Object 是为了兼容 AgentTool 子类和带 @Tool 注解的普通类两种形态
Memory 接口与 InMemoryMemory .memory(Memory) 是 interface 注入式设计；本集用最简实现 InMemoryMemory，换存储只换实现类
Msg + ContentBlock 多模态封装 Msg 装 List<ContentBlock>；ContentBlock 7 子类（Text/Image/Audio/Video/Thinking/ToolUse/ToolResult）；纯文本走 .textContent(...) 捷径
MsgRole 枚举 USER / ASSISTANT / SYSTEM / TOOL 四种角色
agent.stream(msg) 跑 Agent 的入口；返回 Flux；流式与否在 model 构造时 .stream(true) 就定死了
SAA 1.1→AgentScope 三处便捷化 (1) 工具不用造 ToolCallback；(2) stream/format 下沉到 model 构造时；(3) 内置 enableThinking(true)
