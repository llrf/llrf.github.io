8-13_不同的执行者调用不同的执行流程

发表于2026-05-20|更新于2026-05-20|Agent学习第8章 Jmanus 懂思考、会规划、一步步动手完成任务。

1. 一句话定位

上一集你已经知道”工厂按 plan 类型造出一个 executor”，这一集就是把那个 executor 拆开看：simple 计划 = 步骤 for 循环，complex 计划 = 节点 for 循环 + 步骤 for 循环，两条路最后都收口到同一段”选 agent → run() → setState()”——这就是 JManus 把”执行流程”做成接口的全部理由。

2. 主体

2.1 入口：一个接口，三个实现

executeAllSteps 是 PlanExecutorInterface 的唯一接口方法。IDE 跳进去会看到三个实现类（这里讲师在视频里只点了两个，第三个是隐藏彩蛋）：

加工增量：消化稿点出一个反直觉——agent 选择发生在 step 粒度而非 plan 粒度。所以一个 plan 里可以混用多种 agent，每个 step 单独派单。这跟 6-7 的 Agent-as-Tool 路线（在 builder 里固定 subAgents）形成对比：JManus 是运行时按 stepType 动态选，SAA 1.1 是编译期按 builder 锁定。

2.5 BaseAgent：所有 agent 的根

run() 内部那个 executor 是一个继承 BaseAgent 抽象类的对象。BaseAgent 强制实现两个方法：

  • run() — 真正干活（这里面才是 ReAct 循环 / 工具调用 / LLM 请求）
  • setState() — 状态记录

自定义 agent 的全部入口就这两个方法。后面拆 run() 内部那一集（大概率紧跟 8-13），就是要回答”LLM 到底在哪一行被请求”。

3. 没 get 的点

  • getExecutorForStep(stepType, ...) 内部怎么按 stepType 匹配 agent？讲师没拆。是注册表查找（类似 Spring Bean 按 qualifier），还是 LLM 路由（类似 6-8 的 LlmRoutingAgent）？这是”派单逻辑”的真正心脏——很可能下一集补。
  • MapReduceNode 名字暗示并行，executeMapReduceNode 是不是真的开线程池 / Flux.parallel？讲师一笔带过。
  • executor.setState(IN_PROGRESS) 之后谁负责改回 SUCCESS/FAILED？按命名规律应该在 run() 内部，但本集没演示。
  • DirectResponseExecutor 跟 plan.isDirectResponse 分支的关系，本集没讲——按 8-12 那张图推测，是”plan 直接是答案”的快路径。

4. 跟其他集连接

  • 上承 8-12：上一集讲 PlanningCoordinator 三段生命周期 + PlanExecutorFactory.createExecutor() 怎么按 type 造对象；本集是”造出来之后那个对象怎么干活”。
  • 再上承 3-12：多 Agent 五步骨架里”主管派单 + 中间结果存储”——getExecutorForStep 就是主管派单的具象，step.setResult() 就是中间结果存储的具象。
  • 下启：下一集大概率拆 BaseAgent.run() 内部（ReAct 循环），并跟 6-6 ReactAgent 形成”JManus 自研版 vs SAA 1.1 高阶 API”的对照。
  • 横向对照：
    • 跟 7-10 / 7-13 SAA Graph DAG 引擎同源异构——Graph 用 StateGraph + 显式 addNode/addEdge 声明拓扑，JManus 这套用 for 循环 + instanceof Node 隐式分发；两条路都解决”多步执行”，Graph 更可视化，JManus 更紧凑。
    • 跟 6-8 FlowAgent 三子类对照——MapReduceNode ≈ ParallelAgent、SequentialNode ≈ SequentialAgent，但 JManus 这层不暴露给用户配，是内部 instanceof 分发。
    • BaseAgent.run() ↔ 6-6 ReactAgent ↔ 6-9 AgentScope ReactAgent.builder()——同一个 agent 抽象的三种实现栈。

5. 知识地图

记忆抓手三句：

  1. 工厂按计划类型分发：simple → PlanExecutor，complex → MapReducePlanExecutor。
  2. 简单一层 for，复杂两层 for，最里层永远是同一个 executeStep。
  3. 最底层永远是 BaseAgent.run() + setState() 两件套，这也是自定义 agent 的唯一入口。

6. 自测题

  1. executeAllSteps 有几个实现类？分别在什么 plan 类型下被调用？
  2. 简单计划和复杂计划的执行流程，差异点和共同点各是什么？为什么共同点能复用同一段代码？
  3. executeStep 定义在哪个类？它内部完成了哪四件事？
  4. agent 选择发生在 plan 粒度还是 step 粒度？这个设计意味着一个 plan 里能不能混用多种 agent？
  5. 自定义一个 agent 需要继承哪个抽象类、实现哪两个方法？这两个方法各管什么？

7. 关键词表

术语 一句话
PlanExecutorInterface 所有执行者的统一接口，唯一方法 executeAllSteps；3 个实现（PlanExecutor / MapReducePlanExecutor / DirectResponseExecutor）
PlanExecutorFactory.createExecutor 按 plan.type 分发执行者的工厂方法，策略 + 工厂模式组合点
executeAllSteps 接口方法，simple 一层 for，complex 两层 for，差异只在”切片粒度”
MapReducePlanExecutor 复杂计划执行者，先按节点（SequentialNode / MapReduceNode）for，再按步骤 for
AbstractPlanExecutor.executeStep 两个执行者共用的步骤执行模板，干”选 agent → setAgent → setState → run → setResult”四件事
BaseAgent 抽象类 所有智能体的根，强制实现 run()（干活）和 setState()（状态记录）
getExecutorForStep 按 stepType 匹配 agent 的派单方法，本集没拆内部，是下一集线索
节点 → 步骤两层嵌套 复杂计划比简单计划多的那一层，节点是分支单元，节点里面才是步骤
