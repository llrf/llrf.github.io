9-4 创建不同节点的ReAct Agent

1. 一句话定位

这集不是真去”分布式部署”，而是把 9-2 那张架构图拆成 四个 Maven 模块（一个公共池 + 三个 Agent 模块），并把”创建 ReActAgent 的公共部分”抽到 AgentUtils / ToolUtils 两个工具类——给 9-5 之后真正装配主管/路线/行程三角准备代码骨架。

2. 主体

2.1 模块切分（f019 / f047 那张图）

看 f047 那张橙色框图，它就是你这一集要记住的全部地图：

四个 module 在父 pom 里都登记好了（f012 里能看到 <module>manager_agent</module> 等四行）。每个 Agent 模块都额外引入 spring-boot-starter-web + lombok（f016）——这俩依赖现在用不上，但提前说明：这三个模块将来要各自起一个 HTTP 服务，跑在不同节点。

2.2 AgentUtils：只封”半成品”

AgentUtils 里两个静态方法，你需要把它当作”模板方法在 Builder 层的变形”来理解。

方法 1：getReActAgentBuilder(name, description)（f028 / f030）

返回的是 ReActAgent.Builder，不是 ReActAgent。

[加工增量]
第一遍看到这里我的第一反应是”为啥不一步到位封死成 ReActAgent？”——直到看到 ManagerAgent 里那行 ).build(); 才反应过来：子模块还要往 Builder 上追加自己的 tools / sysPrompt / memory。如果在 Utils 里就 .build() 掉，调用方就没机会插话了。
取舍点：公共部分（模型、API Key、模型名）封死；可变部分（name、description、未来的 tools/prompt）开放。这是”模板方法”模式在构造器层面的写法。

方法 2：streamResponse(agent, prompt)（f037 / f039）

返回类型是 Flux<Event>（Reactor 的响应式流，承载 Agent 流式输出的事件序列）。Msg → MsgRole → TextBlock 三层套娃就是 AgentScope 1.0.8 里发一条用户 prompt 的标准姿势——封到一个静态方法以后调用方只写一行就完事。

旁注：f039 右下角 IDE 提示 Method 'streamResponse' is never used。这集没人调它，备着给 9-10”远程 Agent 封装为工具”用。

2.3 ToolUtils：包一层 registerTool

两点要盯着看：

  • 入参类型是 Object，不是某个 Tool 接口。原因在第 28 行的注释里说得清楚：AgentScope 靠 @Tool 注解扫描方法、不靠类型——所以类型签名再严也约束不到任何东西，干脆 Object 收下。
  • 为什么要包一层？ 现在它就一行 toolkit.registerTool(Tool)，看着脱裤子放屁。但讲师明说：以后这个注册过程要是变了（比如要加权限校验、要加日志），只改这个工具类一处，三个 Agent 模块都不用动。这是”封装变化点”。

2.4 ManagerAgent：构造方法里把自己 new 出来

f064 / f065：

注意：没有 @Component / @Service / @Configuration + @Bean——纯 Java 构造方法装配。讲师在选择”避开 Spring 容器”，暗示这些模块未来既能跟 Spring 跑也能脱离 Spring 跑。

路线、行程两个 Agent 同样套路，讲师说”我就不演示了”。

3. 没 get 的点

  • “牛市响应“ 听了三遍才明白是 流式响应（streamResponse）的口音转写。
  • 一直以为”分布式”=Nacos 注册中心 / 多 JVM 进程，到 12 分钟才意识到这集只切 Maven 多模块骨架——真正”跨节点”在 9-9 才发生。
  • streamResponse 这一集没人调用（IDE 灰提示），属于”先放进工具池备用”。

4. 跟其他集的连接

  • 上承：9-2 画的架构图（主管 + 路线 + 行程）在这一集落成代码骨架；9-3 整合好的 SpringBoot 4 + AgentScope 1.0.8 BOM 是这一集所有 import 能跑通的前提；6-9 / 6-10 第一次出现 ReActAgent.builder() / Toolkit.registerTool()，本集把它们抽到 commons 复用。
  • 下启：9-5 给 ManagerAgent() 构造方法里追加 SysPrompt 和 PlanNotebook；9-6 给 ToolUtils.getToolkit(...) 接第一个真实工具；9-9 把三个 Agent 模块的卡片注册到 Nacos 才真正”分布式”；9-10 大概率把现在没人用的 streamResponse 改造成”主管调远程”。
  • 横向：5-2 / 5-3 / 5-5 的”角色定义 + 能力清单”模板，本集就是从 PPT 进到 IDE 的那一步——同一套主管/路线/行程三角。SpringAI Alibaba 版本（4-11 ~ 4-16）走的是 A2A + Nacos；AgentScope 这边大概率走”远程 Agent 封装为工具”（9-10），方案不一样但要解决的问题同构。

5. 知识地图

6. 自测题（5 张卡）

  1. Q：AgentUtils.getReActAgentBuilder 为什么返回 ReActAgent.Builder 而不是 ReActAgent？
    A：因为子模块（ManagerAgent 等）还要在 Builder 上追加自己的 tools / sysPrompt / memory，再 .build()。公共 Utils 封死共性、开放差异点——模板方法在 Builder 层的变形。

  2. Q：ToolUtils.getToolkit(Object Tool) 入参为什么是 Object 而不是某个 Tool 接口？
    A：AgentScope 靠 @Tool 注解扫描方法、不靠类型，所以参数类型再严也约束不到任何东西；统一收成 Object，反而避免误导。

  3. Q：streamResponse 返回的 Flux<Event> 来自哪个框架？为什么用它？
    A：Reactor（响应式流）。承载 ReActAgent 流式输出的事件序列，让调用方能 subscribe 拿到一段段 token。

  4. Q：为什么 ManagerAgent 用纯构造方法装配，而不是 @Component / @Bean？
    A：让这个 Agent 类既能在 Spring 容器里跑，也能脱离 Spring 独立跑——后续 9-9 / 9-10 三个模块要拆成独立进程，过度依赖 Spring 容器反而成包袱。

  5. Q：每个 Agent 模块为什么都要引 spring-boot-starter-web + lombok？这集明明没用到。
    A：预告。后面几集这三个 Agent 模块要各起一个 HTTP 服务、跑在不同节点接收主管调用，所以 Web 依赖必须现在就备好。

7. 关键词表

术语 释义
分布式Agent多模块骨架 commons + manager_agent + routeMaking_agent + tripPlanner_agent 四个 Maven module；每个 Agent 模块准备独立成 SpringBoot 进程
AgentUtils 公共工具类，封装 ReActAgent 创建的共性（模型、apiKey、modelName 写死），开放 name/description 给调用方
返回Builder而非Agent 模板方法在构造器层面的变形——公共部分封死、差异部分留给调用方在 .build() 前继续追加
streamResponse三层套娃 agent.stream(Msg.builder().role(USER).content(List.of(TextBlock.builder().text(prompt).build())).build())，返回 Reactor Flux<Event>
ToolUtils.getToolkit(Object) 把 toolkit.registerTool(obj) 包一层；入参用 Object 是因为 AgentScope 靠注解扫描而非类型识别工具
@Tool 注解 标注在方法上，让 LLM 知道这是给智能体使用的工具；Toolkit 在注册时自动扫描带此注解的方法
构造方法装配Agent 在 ManagerAgent 的无参构造里 new 出 ReActAgent 字段——避开 Spring 容器，保留模块独立运行的能力
SpringBoot Web + Lombok 双依赖 三个 Agent 模块都必须引入；预告它们未来将以独立 HTTP 服务的形式被远程调用
