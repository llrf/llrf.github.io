6-05 ChatClient流式响应获取数据 (SSE)

发表于2026-05-20|更新于2026-05-20|Agent学习第06章 多 Agent + ReAct架构，SpringAi迈入Agent新时代
|浏览量:

1. 一句话定位

把 6-4 那条 prompt().call().content() 链里的 .call() 改成 .stream()，返回类型从 String 变成 Flux<String>，再给 @GetMapping 加上 produces = TEXT_EVENT_STREAM_VALUE——你就拿到了”浏览器一字字蹦”的那种打字机效果，背后协议是 SSE。

2. 主体

2.1 现象先纠错：打字机效果是后端能力，不是前端动画

你大概也曾以为 ChatGPT 网页那种”一字一字蹦出来”是 JS 用 setTimeout 拼出来的渲染特效。这集第一刀就砍掉这个直觉：那是后端在用 SSE 实时推每个 chunk，前端拿到一段就贴一段，根本没有动画层。

这件事一旦扳过来，后面所有改造的目的就变得清楚——你要让 SpringBoot API 也具备”按 token 顺序持续推”的能力。

2.2 两个前提条件（需求侧）

要让后端能”一字字蹦”，API 必须同时满足两件事：

  1. 与大模型保持长连接——HTTP 一来一回就断的模式不够用，大模型还在算下一个 token 时连接不能挂掉。
  2. 大模型能主动推——不能每出一个 token 都要客户端再发一次请求，那延迟和握手开销直接爆掉。

把这两条独立列出来，比把它们和”SSE 怎么工作”混在一起讲清楚得多。加工增量在 §2.2：消化稿里这两条前提是我从思路推导那段单独抽出来的，原讲解是边讲思路边引出 SSE，我把”需求侧 = 前提条件”和”供给侧 = SSE 机制”切成两节。

2.3 SSE 是 HTTP 的子用法（供给侧）

这是第二个反直觉点。SSE 不是另起炉灶的新协议，建连那一刻发的就是普通 HTTP 请求，只是请求头里多塞一行：

服务端看到这个头，才决定”这个响应不一次性写完，改成持续推”。所以前面 3-6 和 4-4 提过的”SSE 协议”，在 Java API ↔ 大模型这条线上的落地就这么一行请求头加一行 produces。

通道建立三步：

  1. 客户端发普通 HTTP，但带 Accept: text/event-stream
  2. 服务端识别该头，把响应模式从”一次写完”切成”持续推”
  3. 长连接保持，服务端 emit 一段你收一段

另外一条不要忘：SSE 是单向的。长连接一旦建立，客户端只收不发。要再问一句就得开新请求。这点拿来跟 4-4 讲过的 WebSocket 双向对照刚好。

2.4 Spring AI 三处改造（代码侧）

回到 6-4 的那条三段式链，你要动的就三个地方：

① .call() 改成 .stream()

② 方法返回类型从 String 改成 Flux<String>

如果忘了改，IDE 立刻给你红线：Incompatible types: Found 'reactor.core.publisher.Flux<java.lang.String>', required 'java.lang.String'。这条报错本身就是把”返回类型变了”这件事按到你脸上。

③ @GetMapping 加 produces

produces 这一行是”告诉服务端要按 SSE 来写响应头/响应体”在代码侧的落地。不写的话，Spring 不会把这个 endpoint 当 SSE 处理，前面的改造就白做了。

2.5 ChatClient = ChatModel 的 Builder 封装（顺手补一刀）

ChatClient.create(ChatModel) 这帧明确告诉你：ChatClient 拿一个 ChatModel 进去就能造出来。以后业务侧只跟 ChatClient 打交道，ChatModel 退到底层。这条 6-4 已经讲过，这集只是借机再强调——它是你后面所有调用（call、stream、加 prompt、加 tools）的统一入口。

取舍出现在 §2.5：讲师在选用什么协议时其实没有显式对比，但你在脑子里要记住——WebSocket 能双向、能更通用，但本场景客户端就是只收不发，SSE 单向 + 基于普通 HTTP 头切换 = 更轻量。够用就别上 WebSocket。

3. 没 get 的点

  • Flux<String> 在 WebMVC（Tomcat）下到底能不能直接吃？ 视频里没切依赖、没改启动类，看起来 WebMVC 直接吞下了 Flux 返回类型。Spring 应该有适配层（大概率走 Servlet 3.0 异步 + reactive adapter），但具体路径要查。
  • 每一个 String 是一个 token 还是一段 chunk？ 视频里 APIFox 能看见流式蹦字，但没特地打印颗粒度。猜测是大模型 SSE 推什么就 emit 什么（按 chunk 不按 token），但要写个 .doOnNext(System.out::println) 验证一次。
  • 前端怎么消费 Flux<String>？ APIFox 看见的是”分块到达”，但真到浏览器侧渲染打字机，就要 EventSource 或 fetch 的 ReadableStream。这集没讲，后续应该会补。
  • Accept vs Content-Type：严格说客户端发 Accept，服务端响应 Content-Type，produces 控制的是后者。这两者讲解时被笼统说成”请求头”，自己写代码时要分清。

4. 跟其他集的连接

上承

  • 6-4：给了 ChatClient.prompt().call().content() 三段式链。本集就在这条链上把中间那一段从 .call() 改成 .stream()。
  • 4-4 MCP 的通信 SSE 实时传输：第一次讲 SSE 协议本身（单向 vs WebSocket 双向、text/event-stream、长连接）。本集是同一套 SSE 在”Java API ↔ 大模型”线上的复用。
  • 3-6 体验 MCP JManus 配置 MCP 服务：那里提过 SSE 是 MCP 三种传输方式之一。

下启

  • 6-6 之后大概率会讲：ChatModel 直接做流式（对照本集的 ChatClient 版本）、或者前端怎么用 EventSource 消费 Flux<String>。
  • 流式 + 工具调用 / 流式 + RAG 的组合（边检索边推 token）。

横向

  • 4-7 WebFlux 框架：Flux<String> 就是 reactor 反应式的核心类型，本集第一次把它放进业务代码。produces=text/event-stream 这条线其实暗含”要能撑住长连接”，Tomcat NIO 也行但 WebFlux 更对路。
  • 4-10 SAA 1.1 整合 MCP：提到 Streamable HTTP 是 SSE 的升级版——SSE 是基础，Streamable HTTP 是 2025 之后的演进。

术语 一句话说明
流式响应 大模型按 chunk 顺序持续推，浏览器一字字蹦的真实成因；是后端能力，不是前端动画
ChatClient 对 ChatModel 的 Builder 封装 ChatClient.create(ChatModel) 即可，业务侧只用 ChatClient，不再裸用 ChatModel
call → stream 单字改造 .call() 一次性返回 String；.stream() 流式返回，配 .content() 得到 Flux
Flux 返回类型 Controller 方法签名必须从 public String 改成 public Flux<String>，否则 IDE 报 Incompatible types
SSE 两大前提条件 ① 与大模型保持长连接；② 大模型能主动推。普通 HTTP 一来一回都不满足
SSE 通道建立三步 ① 客户端发普通 HTTP 但带 Accept: text/event-stream；② 服务端识别该头；③ 服务端持续推
SSE 单向通信 长连接建立后客户端只收不发；想再问就得开新请求。与 WebSocket 双向区分
produces = MediaType.TEXT_EVENT_STREAM_VALUE @GetMapping 上必须显式声明，否则服务端不会按 SSE 写响应头/响应体
