5-1 旅行规划的复合任务拆解

发表于2026-05-20|更新于2026-05-20|Agent学习第05章 Agent 团队打造专属你的旅行规划
|浏览量:

§1 一句话定位

把一个旅行需求拆成”领域 × 动作”，给后面每个 Agent 划好边界。

§2 主体

2.1 别把”费用”当成第四个并列分支

你看到旅行规划被分成交通、住宿、景点、费用四块的时候，第一反应大概率跟我一样：四个平级模块，分头处理。

但只要继续往下画，你就会发现费用这条线再往下展开，会重新出现”交通 / 景点 / 住宿”——也就是说，下半张图其实是上半张图在”钱”这个维度上的投影。


alt: 复合任务的可视化

这就是为什么图会变成上下两半。费用不是第四个领域，它是横切关注点（cross-cutting concern）：穿过其他三个领域，每个领域都要做一次”费用计算”。

取舍出现在 §2.1：要不要把费用画成跟交通/住宿/景点平级？讲师选了”平级 + 重新展开”的画法（图里费用下面又挂了一份交通/景点/住宿）；如果改成 AOP 式的注解层叠在原节点上，图会更紧凑但失去任务流的层级感。我倾向于讲师的画法在白板教学里是更易读的折中。

2.2 交通有两层意思，别混

“交通”这个词在旅行规划里其实指两件不同的事：

  • 跨城交通：怎么从你家到目的地（火车 / 高铁 / 动车）。
  • 城内交通：景点之间怎么走、景点 ↔ 住宿怎么走。

第二条隐含一个硬约束：住宿必须挨着景点，否则城内交通就是天天打车。所以后面会出现一个独立的动作叫住宿路线规划，专门处理”景点 ↔ 住宿”这条线。


alt: 交通分层的可视化

2.3 餐饮被并进住宿

讲师有个小操作：把”餐饮”塞到”住宿”节点里，合并成 住宿+餐饮 一个节点。

理由是它俩的属性几乎完全重合：

  • 都有折扣（要监控）。
  • 都是”在哪里吃 / 睡”这种位置类问题。


alt: 住宿合并餐饮的可视化

2.4 景点推荐是”双轨”，不是单一规则

你以为景点推荐就是”按用户喜好排个序”？不够——讲师明确分成两条：

  • 根据天气推荐（硬约束）：下雨天剔除室外景点。
  • 根据偏好推荐（软约束）：用户喜欢什么类型。

两条都不是顺序执行，而是规则分支。所以图里用虚线把这两个动作连到”景点推荐”父节点上，而不是实线。


alt: 景点推荐双轨的可视化

讲师顺手定义了一个图例约定：

  • 实线：父子结构 / 任务流（A 完成后做 B）。
  • 虚线：推导关系 / 规则分支（A 是 B 的依据，不是顺序步骤）。

这个约定后面整张图都要遵守，记住对看图有用。

2.5 固定 vs 变动——这条线决定哪些要做 Agent

费用展开后会得到四个动作。把它们排成一张小表：

动作 性质 触发方式 要不要 Agent
交通费用计算 固定（高铁/动车不打折） 请求触发 工具就够
景点费用计算 固定（门票不打折） 请求触发 工具就够
住宿费用计算 变动（要折扣） 请求触发 工具就够
监控折扣 变动 定时 / 事件触发 得做成 Agent

加工增量在 §2.5：讲师原视频里只是把这四个动作画在图上，并没有展开”哪些要做成 Agent”。我把它整理成一张二维表，把”性质 × 触发方式”作为决策依据——你可以直接拿这张表去判断后续 5-x 每一节该不该新起一个 ReactAgent。规则很简单：固定 + 请求触发 = 工具；变动 + 定时触发 = Agent。


alt: 费用动作拆分的可视化

2.6 别忘了作用域裁剪

讲师扔了一句很容易被忽略的话：这个项目只做火车交通，不做飞机。

理由是飞机有动态定价，要把”机票折扣监控”做进去，复杂度直接翻倍。这是个有意识的作用域裁剪——告诉你不是没想到，是主动砍掉。

记住这种动作：做项目时，先画出全集，再标出”本期只做哪些”，比临时遗漏要专业得多。

§3 没 get 的点

  • 监控折扣具体怎么实现？是 Cron 定时拉取，还是 MCP 工具被动查询？这一集没说，等 5-x 后续。
  • 最终架构是单 Agent 多工具，还是多 Agent + A2A？从 4-x 的铺垫看像是后者，但本集没明说。
  • 用户偏好从哪里来？要不要做用户画像子模块？还是直接 prompt 里要？
  • “监控折扣”和”住宿费用计算”是否会复用同一个数据源？如果都查美团/携程，是不是应该共享一个 cache 层？

下启

后续 5-x 大概率是逐个动作落代码，最可能的顺序：

  1. 景点推荐 Agent（带天气工具调用 → 对应 3-7 Agent Skills / 4-5 @Tool）。
  2. 路线规划 Agent。
  3. 住宿折扣监控 Agent（定时任务，可能引入 Cron / Schedule）。
  4. 费用聚合 Agent。
  5. 最后用 A2A 把四个 Agent 串起来。

横向

  • 跟 3-12 是骨架与切法的关系——3-12 讲多 Agent 五步骨架，本集演示骨架第一步”任务切分”长什么样。

§5 知识地图

§6 自测题

  1. Q：旅行规划被拆成”交通 / 住宿 / 景点 / 费用”四块，这四块是平级的领域吗？为什么图里”交通 / 景点 / 住宿”会出现两次？
    A：不平级。费用是横切关注点，它穿过其他三个领域；下半部分的”交通 / 景点 / 住宿”是同一组节点在费用维度上的投影。

  2. Q：图里实线和虚线分别表示什么？景点推荐用哪种线？为什么？
    A：实线表示父子结构 / 任务流；虚线表示推导关系 / 规则分支。景点推荐用虚线，因为”根据天气”和”根据偏好”不是顺序步骤，是两条并行的规则依据。

  3. Q：费用拆出四个动作，哪个最值得做成 Agent？依据是什么？
    A：监控折扣。因为它是唯一一个定时 / 事件触发的动作（其他三个都是请求触发），且数据源是变动的（美团 / 携程实时折扣），需要长期运行的智能体来处理。

  4. Q：”交通”在旅行规划里其实包含哪两层含义？后一层暗含什么硬约束？
    A：跨城交通（火车 / 高铁）+ 城内交通（景点 ↔ 住宿）。后者暗含”住宿必须挨着景点”的硬约束，所以才会有独立的”住宿路线规划”动作。

  5. Q：为什么本项目只做火车不做飞机？这种处理叫什么？
    A：飞机有动态定价，做折扣监控复杂度翻倍。这种主动砍掉部分需求集的做法叫作用域裁剪，是项目设计阶段的有意识取舍。

§7 术语

术语 含义
复合任务 一个用户需求拆成多个有依赖的子需求，存在”先 X 才能 Y”的约束
横切关注点 不属于某个具体领域、但穿越多个领域的关注点；本集里费用就是横切关注点
四象限需求 旅行规划 = 交通 + 住宿（含餐饮） + 景点 + 费用
固定费用 vs 变动费用 固定 = 火车票 / 景点门票（不打折）；变动 = 住宿 / 餐饮（有折扣，要监控）
景点推荐双轨 根据天气推荐（硬约束） + 根据偏好推荐（软约束），两条并行的规则分支
实线 vs 虚线 实线 = 父子结构 / 任务流；虚线 = 推导关系 / 规则分支，讲师自定的图例约定
监控折扣 唯一的定时 / 事件驱动动作，数据源是美团 / 携程之类的外部平台
作用域裁剪 主动砍掉一部分需求集（本项目只做火车不做飞机），降低复杂度的设计动作
