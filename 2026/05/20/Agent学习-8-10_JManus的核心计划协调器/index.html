8-10_JManus的核心计划协调器

发表于2026-05-20|更新于2026-05-20|Agent学习第8章 Jmanus 懂思考、会规划、一步步动手完成任务。
|浏览量:

1. 一句话定位

PlanningCoordinator 是 JManus 真正的”大脑”——它本身不干活，只是把”计划开始 / 计划执行 / 计划结束”三个协作者攥在手里，串起整条业务时间轴。

2. 主体

2.1 入口只做两件事，剩下全甩给异步

上一集你已经走到 ManusController.executeQuery 的门口，这一集要钻进去看里面到底发生了什么。把 200 多行的方法体折叠掉冗余，骨架其实就两行：

之后那一坨 CompletableFuture.supplyAsync(() -> planningFlow.executePlan(context)) 第一遍看会把注意力吸走，但本集主线和异步无关——它的意义只是”把真正干活的部分丢到后台线程，立刻给前端返回 200 + planId + processing”。

这里有个反直觉点要标住：用户提交 query，Controller 不返回结果，只返回一张”号牌”（planId）。这跟”请求-响应”的本能预期是反的，但 Manus 这种任务可能跑几分钟，长任务场景就必须这么写。后续答案靠前端轮询 / SSE 推流取回。

2.2 协调器不是”自己 new 出来”的——工厂帮你装配

planningFactory.createPlanningCoordinator(context) 这一行讲师有个自我纠正值得记一下：他先说”这是个静态方法”，下一秒又改口”不是，planningFactory 是 @Autowired 注入进来的 Bean，所以是实例方法”。这种”工厂在 Spring 里可能是静态门面、也可能是 Bean”的歧义，看注入痕迹就能判别——@Autowired @Lazy private PlanningFactory planningFactory 这一行（f075）就是铁证。

取舍/加工增量：讲师反复在三个文件之间来回跳，看起来很乱。其实只要把它当成”双层套娃”就清晰了——

工厂的作用不是”代理你 new”，而是”帮你把三个依赖装配好再 new”。这是工厂模式很容易被误读的点：很多人以为工厂方法就是 return new XXX() 一行包装，其实价值在中间那几行 new PlanCreator(...)、new PlanFinalizer(...)——把分散的依赖（agentEntities、llmService、recorder、streamingResponseHandler…）聚拢成三个高内聚的协作者。

2.3 构造方法的参数列表，就是整张业务图

钻到最里层 PlanningCoordinator 的构造方法，简单到让人怀疑人生：

三个 this.x = x，看着像废话，但参数列表本身就是一张业务图——回到那张架构图（f088），右侧把三个字段名和业务节点一一对上：

参数 业务节点 干什么
PlanCreator 计划开始 任务分析 + 高层规划（把 query 变成结构化 plan）
PlanExecutorFactory 计划执行 注意是 Factory — 按 plan type 动态选执行器
PlanFinalizer 计划结束 汇总收尾（看依赖里有 llmService，应该是 LLM 生成总结）

第二个参数是 Factory 不是 Executor，是值得注意的双层间接——一个执行器不够用，因为简单任务直接派给 Agent、复杂任务要进主管 Agent 拆解，这两条分支需要不同的执行器。类注释里那句 “Enhanced Planning Coordinator that uses PlanExecutorFactory to dynamically select the appropriate executor based on plan type”（f070）就是这个”工厂的工厂”存在的理由。

2.4 为什么要花这么多力气拆这个构造方法

讲师在最后反复强调一句话：”没有协调器，后面任务执行、工具调用、派单给智能体，这些都不存在。”

这不是煽情。它是 JManus 整个架构的拱顶石——读懂 PlanningCoordinator(PlanCreator, PlanExecutorFactory, PlanFinalizer) 这一行签名，等于读懂 OpenManus 那张”开始 → 执行 → 结束”的设计骨架。后面所有集都会从这三个字段往下钻：钻 PlanCreator 就是看任务怎么拆、钻 PlanExecutorFactory 就是看派单逻辑、钻 PlanFinalizer 就是看怎么汇总回复。

3. 没 get 的点

  • PlanExecutorFactory 到底根据什么 plan type 选执行器？架构图上有个”任务复杂度”的菱形决策，但本集没展开。是按某个枚举字段、还是按 step 数？得看 Factory 的 select(...) 方法源码。
  • PlanCreator 的入参里有 agentEntities + llmService + planningTool + manusProperties + streamingResponseHandler 一大堆，它内部把 query 转成结构化 plan 的过程是一次 LLM 调用还是多步迭代？目前不知道。
  • PlanFinalizer 居然也拿了 llmService——说明结束阶段还要再调一次 LLM，应该是用来生成”最终给用户的总结回复”。但具体回复格式、要不要带引用源，本集没说。
  • streamingResponseHandler 在三件套全都出现——意味着从开始到结束都要往前端推流。推什么、用什么协议（SSE / WebSocket）值得回去对照 7-9 Flux 包装 SSE。
  • 字段修饰符不齐：planExecutorFactory 是 private final，planFinalizer 却只有 private（无 final）。要么是讲师/IDE 风格不一致，要么是 finalizer 真的会在运行时被替换。值得留个心眼。
  • 类注释里写的是 “Enhanced” Planning Coordinator——暗示存在一个非 Enhanced 的早期版本。早期 JManus 可能直接持有单个 PlanExecutor，后来升级成 Factory 来支持多执行器。这是版本演进的痕迹，能看 git log 印证一下。

4. 跟其他集的连接

  • 上承（8-9）：上集讲 JManus 文件架构 + executeQuery 入口 + ExecutionContext + PlanningFactory 是谁。本集是”接着上集那个 planningFactory.createPlanningCoordinator 调用，往里再钻一层”。讲师好几次说”上节课已经说过了”，是显式接力。
  • 下启：下一集大概率拆 planningFlow.executePlan(context) 这个真正干活的方法。路径会进入 PlanCreator / PlanExecutorFactory / PlanFinalizer 三选一，最可能先讲 PlanCreator（把 query 变结构化 plan，对应”任务分析 + 高层规划”那块）。
  • 横向：
    • 3-12 多Agent的核心执行流程 的”多Agent五步骨架”和本集映射很干净——协调器三件套 ≈ 创建（任务拆解）/ 执行（派单）/ 结束（汇总）。JManus 是把那个抽象骨架落到 Java 类的具体实现。
    • 5-5 Agent团队和大模型的无缝协作 里的”主管 Agent + 汇总 Agent”对得上：PlanCreator ≈ 主管的拆解，PlanFinalizer ≈ 汇总 Agent 的收尾。
    • 3-11 主流的多Agent开发框架 提到的”JManus / OpenManus 规划-执行-验证 3 层分工”——这一集就是看 3 层分工在源码层怎么落。
    • 7-1 以工作流方式编排旅行规划的团队协同 是另一条腿：同一个”协调”问题，JManus 用 Coordinator + Factory 走面向对象套娃，SAA 1.1 用 StateGraph + DAG 走数据流编排。两种风格值得对照。

5. 知识地图

读这张图的顺序：先看构造方法签名（②的最底层），把它当成业务时间轴；再回头看工厂方法（②的中间层），理解”装配 ≠ 代理”；最后看 Controller（①+③），看到”异步号牌”模式。

6. 自测题

  1. PlanningCoordinator 的构造方法收了哪三个参数？分别对应业务图上的哪三个阶段？
  2. 为什么第二个参数是 PlanExecutorFactory 而不是 PlanExecutor？多了一层 Factory 是为了解决什么问题？
  3. executeQuery 拿到用户 query 后，返回给前端的是什么？不是答案，那答案怎么回到用户手上？
  4. planningFactory.createPlanningCoordinator(context) 到底是静态方法还是实例方法？怎么从代码里一眼分辨？
  5. 用一句话说清”工厂装配”和”工厂代理”的区别，对应到本集 PlanningFactory.createPlanningCoordinator 是哪一种？

7. 关键词表

术语 一句话定义
PlanningCoordinator JManus 核心协调器，本身不执行任务，靠组合三件套把”计划生命周期”串起来
三参数构造方法 PlanningCoordinator(PlanCreator, PlanExecutorFactory, PlanFinalizer)——参数列表 = 业务时间轴
PlanCreator 计划开始阶段的对象，负责任务分析 + 高层规划，把 query 变结构化 plan
PlanExecutorFactory 计划执行阶段的工厂，按 plan type 动态选执行器（双层间接）
PlanFinalizer 计划结束阶段的对象，依赖 llmService，应是用 LLM 生成最终总结回复
PlanningFactory.createPlanningCoordinator 装配入口：先 new 三个协作者再 new 协调器，是”工厂装配”而非”工厂代理”
异步返回200模式 长任务必备：立刻返回 planId + processing，真正执行甩给 CompletableFuture.supplyAsync
工厂装配 vs 工厂代理 装配=工厂在方法体里组装多个依赖再 new；代理=工厂只是包装一行 new，没增量价值
