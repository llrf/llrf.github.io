Manus多Agent的技术架构

1. 一句话定位

把前面 3-11/3-12 反复出现的”多 Agent 五步骨架”放到 Manus 这个真实产品里——抽象图上的”主管 Agent”在这里被拆成两个组件（任务规划器 + 任务执行调度器），并且在 Agent 和 MCP 工具之间多塞了一层”隔离容器”。

2. 主体

2.1 先把”骨架”听对（避坑）

讲师整段都在念”两条股价流程”——这是口音引起的口误，原词是两条骨架。骨架=3-11/3-12 抽出来的两条通用结构：

  • 协作骨架：拆解需求 → 派单到单个 Agent → 整合结果返回。
  • 单 Agent 骨架：思考 → 行动 → 观察（每完成一步就回头判断结果是否符合预期，决定要不要调整后续步骤）。

第二条里”观察”这步，对应到 Manus 标签上的”验证“。这就是为什么 3-11 那张图把 Manus 标成”规划-执行-验证 3 层分工”。本集你可以把对应关系记成：

  • 规划层 = 任务规划器
  • 执行层 = 任务执行调度器 + 子任务 Agent
  • 验证层 = 单 Agent 内部 ReAct 循环里的”观察”步

讲师没明说这条对应关系——这是加工增量，验证层默认藏在每个子任务 Agent 内部，不是一个外部组件。

2.2 Manus 的入口：任务规划器

用户提请求 → 进任务规划器。这一个组件干两件互相独立的事：

  1. 任务初始化 + 切分：理解需求、规划步骤、把需求切成若干”简单子任务”、判断哪个子任务交给哪个 Agent。
  2. 初始化隔离容器 + 创建任务目录：在调度执行之前，先把隔离环境拉起来，给后面工具调用准备落脚的”任务目录”。

第二件事第一遍很容易漏听——讲师只用一句”它要初始化一个隔离容器”带过。但这是 Manus 区别于 AutoGen / CrewAI 的核心动作：它把”工具调度”做成了一个带环境隔离的中间层，不再是 Agent 直接调 MCP。

2.3 隔离容器：Manus 最突出的特点

把隔离容器画在 Agent 和外部工具中间，所有第三方 API（高德地图等）、浏览器操作、本地命令（查数据库）都要先穿过它。也就是：

为什么要塞这一层？讲师没展开，但从结构能反推两个意图：

  • 安全隔离：Agent 自动产生的命令不直接落到宿主机上跑。
  • 统一调度：所有外部工具的入口收口到一个组件，方便审计、限流、超时控制。

这是把 3-12 那张”多 Agent 五步骨架”图额外塞了一层——抽象图里 Agent 直接连工具，Manus 在中间垫了块”调度+隔离板”。

加工增量：隔离容器到底是 Docker、子进程沙箱、还是 Manus 自定义层？讲师没说，记成”具体实现待查”。

2.4 任务执行调度器：派单 + 收尾，一个组件两个相位

任务规划器把切好的子任务和初始化好的容器交给任务执行调度器。这个调度器有两个相位：

相位 1 · 派单：把子任务分给底下的子任务 Agent1 / Agent2 / Agent3。每个 Agent 在执行时：

  • 用 LLM 做推理 / 思考；
  • 调外部工具时必须进隔离容器。

相位 2 · 收尾：读取每个子任务的结果，等”所有子任务完成”信号到达，触发任务汇总生成 → 把整合结果转成对用户友好的输出 → 返回用户。

注意：汇总不是新 Agent，是调度器的第二职责。3-12 抽象图里那个”结果整合”节点，在 Manus 里就是调度器自己再干一次。比 5-5 里独立”汇总 Agent”模式更紧凑。

2.5 业界横切（讲师附送的全景图）

讲完抽象骨架后，讲师把当下主流框架按一句话标签摆出来：

  • AutoGen：多 Agent 协调能力 + 人工干预；
  • CrewAI：团队自主协作 + 角色专业化 + 任务动态委派 + 争议解决；
  • LangChain：大规模流程定制、模块化、需手动配置；
  • Manus：规划-执行-验证 3 层分工协作（本集主角）；
  • 京东 JoyAgent：本地部署 + 复用历史任务经验 + 工具原子化；
  • 蚂蚁 muAgent：基于知识图谱 + LLM 增强决策。

结论：都基于上面那两条骨架。讲师顺嘴明确”Manus 不是开源的”，但整体流程跟开源框架同构——所以拿它当业界范本讲。国内对应的开源复刻是 OpenManus / JManus（3-11 里出现过）。

3. 没 get 的点（先记下来）

  • 隔离容器到底是什么？ Docker 容器？子进程沙箱？还是 Manus 自定义的隔离层？讲师只说”必须到这里面调用”，实现待查。
  • 任务目录是什么形态？ “任务规划器创建任务目录”——是文件系统目录还是抽象任务队列？工具调用的中间结果存哪？
  • 子任务 Agent 之间怎么通信？ 图里 Agent1/2/3 只跟调度器和隔离容器连线，互相之间没线。是 Manus 假设子任务完全独立，还是图省略了？
  • 隔离容器和 Agent 是几对几？ 一个 Manus 实例一个？每个请求一个？每个 Agent 一个？图上画的是单数。
  • Manus 商业版还活着吗？ “不开源”+”国内有 OpenManus / JManus”暗示原品热度可能下降，待查。

4. 跟其他集连接

上承：

  • 3-11 主流的多Agent开发框架 给了一句话标签”规划-执行-验证 3 层分工”——本集把标签摊开。
  • 3-12 多Agent的核心执行流程 给了抽象的”多 Agent 五步骨架 + 单 Agent 五步循环 + 骨架嵌套”——本集是这张抽象图在 Manus 上的特化版：主管 Agent → 任务规划器+任务执行调度器，单 Agent → 子任务 Agent，结果整合 → 调度器第二相位。
  • 3-4 ~ 3-6 MCP 系列 给了 MCP Host/Client/Server 的概念——本集首次把 MCP 调用塞进”隔离容器”里，多一层环境隔离视角。

下启：

  • 8-5 / 8-6 大概率讲 OpenManus 或 JManus 的代码实现——把”任务规划器””任务执行调度器””隔离容器”映射到具体类（参考 3-12 提到的 RoleSetting / RoleContext / Action / Env）。
  • 隔离容器的具体实现（Docker / 沙箱进程 / 任务目录的文件系统形态）应该在后面落地课。

横向：

  • 5-5 Agent团队和大模型的无缝协作 是”概念演练 vs 产品范本”的关系——5-5 用旅行规划演主管+汇总+三专科 Agent，本集换成 Manus 的产品命名。
  • 6-7 / 6-8 SAA 1.1 Agent 团队 是”自建 vs 大厂产品”的关系——SAA 1.1 用 ReactAgent + FlowAgent + OverAllState 自己拼，Manus 把这套打包成产品并加了隔离容器。
  • 3-9 搞定复杂活儿得靠多Agent协作 的”主管+专科”两件套同源，但本集多出”隔离容器”这第三件套。

5. 知识地图

6. 自测题（5 卡）

  1. Manus 的两个核心组件分别叫什么？各自的双重职责是什么？

    • 任务规划器：① 理解需求 + 切子任务 + 角色匹配；② 初始化隔离容器 + 创建任务目录。
    • 任务执行调度器：① 派单给子任务 Agent；② 读结果 + 汇总 + 生成友好输出。

  2. 隔离容器在 Manus 架构图里位于哪两者之间？为什么要塞这一层？

    • 在子任务 Agent 和外部工具（第三方 API / 浏览器 / 本地命令）之间。意图是安全隔离 + 把所有 MCP 工具调用收口到统一调度点。

  3. 3-11 把 Manus 标成”规划-执行-验证 3 层”，对应到本集的组件，验证层在哪里？

    • 验证层不是独立组件，藏在单 Agent 内部的 ReAct 循环的”观察”步——每完成一步就判断结果是否符合预期，决定要不要调整后续步骤。

  4. Manus 跟 5-5 旅行规划那种”主管+汇总+专科”模式比，少了哪个独立组件？这个职责跑哪去了？

    • 少了独立的”汇总 Agent”。汇总职责被合并到”任务执行调度器”的第二相位里。

  5. 讲师为什么花一整节讲一个不开源的产品？

    • 因为 Manus 的流程跟所有主流多 Agent 框架（AutoGen / CrewAI / LangChain / JoyAgent / muAgent）同构，都基于”协作骨架 + 单 Agent 骨架”两条骨架。讲 Manus = 给业界趋势找一个落地范本。
