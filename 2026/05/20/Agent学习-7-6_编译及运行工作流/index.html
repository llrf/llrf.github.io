7-6 编译及运行工作流

发表于2026-05-20|更新于2026-05-20|Agent学习第07章 Graph 搭建旅游规划工作流，像拼积木一样轻松
|浏览量:

1. 一句话定位

你手上的 StateGraph 只是张纸上的蓝图，要让它跑起来，得调一次 .compile() 拿到 CompiledGraph，再用 invoke(map) 把用户输入塞进去——本集就是把这个”蓝图 → 实物 → 启动”的胶水层焊上。

2. 主体

2.1 第三个对象登场：CompiledGraph

前两集你已经认识了两件套——OverAllState（贯穿所有节点的全局状态包）和 StateGraph（往里 addNode / addEdge 加节点和连线的框架对象）。这集补上第三个：CompiledGraph。

讲师一开始把它叫”工作流编译对象”，半路自己纠正成”工作流编译后的对象”——后者准确得多。CompiledGraph 不是你 new 出来的独立类，而是 StateGraph 调用自己的 .compile() 方法吐出来的产物。

加工增量：这里有个命名陷阱我踩了——@Bean(name="parallelGraph") 的 Bean 名、parallelGraph() 的方法名、/workflow/parallel 的 HTTP 路径全用了”parallel”，但本集做的明明是链式工作流。猜是项目骨架沿用了上一节的并行演示命名，没改。下次看到 parallel 别条件反射当作并行节点结构。

2.2 跨类传蓝图：把 GraphConfiguration 改造成 Spring 配置类

蓝图原本是 GraphConfiguration.parallelGraph() 方法里的局部变量，要让 WorkFlowController 用上，必须走 Spring 容器。三处改动一起上：

  1. 类上加 @Configuration——让 Spring Boot 启动时把它装进容器
  2. 方法上加 @Bean(name="parallelGraph")——把这个方法的返回值作为 Bean 暴露
  3. 返回类型从 void 改成 StateGraph，方法体最后 return stateGraph;

少一处都不行。讲师特意把 Bean 名显式写成 parallelGraph——默认 Bean 名就是方法名，这步是冗余的；但他要后面用 @Qualifier("parallelGraph") 按名注入。这是防御性写法，不是语义必需，将来同类型多 Bean 时按名取货才不会二义。

2.3 控制器拿蓝图：构造方法 + @Qualifier

WorkFlowController 头顶 @RestController。Bean 注入有两种姿势：@Autowired 字段注入和构造方法注入。这集选构造方法注入——更利于把字段标 final，也利于单元测试。

@Qualifier("parallelGraph") 告诉 Spring：去容器里找名字叫 parallelGraph 的 Bean 注入进来。

2.4 编译动作就这一行

控制器再加个成员变量 private final CompiledGraph compiledGraph;，在构造方法里 this.compiledGraph = graph.compile();。

compile() 会抛 GraphStateException——直接在构造方法签名上 throws 出去就行。讲师选择”抛出”而不是 try-catch，因为编译失败属于启动期错误，让 Spring Boot 启动直接挂掉比埋雷强。

之所以把 compiledGraph 设为成员变量而不是 invoke 接口里的局部变量，是因为同一个控制器可能有多个 HTTP 接口都要复用同一个编译后的工作流——只编译一次。

2.5 运行：invoke 一次性 vs stream 流式

CompiledGraph 提供两种运行姿势：

  • invoke(...)：阻塞式运行，等所有节点跑完后一次性把最终结果返回
  • stream(...)：非阻塞流式运行，每个节点执行完就把这个节点的中间结果马上吐出来

本集只用 invoke——invoke 有三个重载，讲师选了”参数最少”的那个，签名是 invoke(Map<String, Object>)。

2.6 入参 Map 的 key 不是随便起的

工作流的第一个节点是”用户 prompt”——所以 invoke 的入参必须把用户输入喂进去。讲师塞了一个 HashMap<String, Object>，key 是字符串 "prompt"，value 是用户输入（演示用的还是那句”在咖啡馆里想要杯星巴克”）。

加工增量：这个 "prompt" 不是魔法字符串，它必须匹配全局状态对象（OverAllState）里能被第一个节点读到的字段名。本集没明说，但回看前面 OverAllState 那集就知道——首节点会从状态对象里 value("prompt") 取值，key 对不上首节点拿不到输入，整条流水线就空跑。这是”全局状态”和”工作流入口”之间的接缝。

3. 没 get 的点

  • invoke 的另外两个重载（参数更多的版本）语义是啥？讲师只说”选参数最少的”就跳过了，可能是带 RunnableConfig、带 checkpointer 之类，下一集补不了就得自己翻源码。
  • graph.compile() 还有没有带参重载？比如能不能传 interrupt before/after 这种调试钩子？SAA 1.0.0.2 可能就裸的，等 1.1 / ReactAgent 章节才填。
  • 本集 compiledGraph.invoke(map) 写完就停了，没真正启动 Spring Boot 跑一次——所以”链式工作流到底输出什么”还是悬空的。下一集如果不联调，整章空转。

4. 跟其他集连接

  • 上承：7-5 上一集刚把 StateGraph 的节点 / 边都搭好，本集是把”画在纸上的蓝图”搬进容器跑起来；上承 6-2 的 Spring Boot 启动骨架，上承 4-13 的 @Configuration + @Bean 套路。
  • 下启：下一集大概率讲 stream() 流式响应（参考 6-5 的 Flux<String>）；再往后会把 invoke 的入参接到真正的 ChatModel 节点跑通端到端；最后用 OverAllState.value(key) 取最终答案（参考 4-14 的 flatMap + value(key)）。
  • 横向：跟 6-8 的 SAA 1.1 ReactAgent.builder() 形成”低层 vs 高层”对照——本集手撸 StateGraph + Compile + invoke 三步，1.1 把这三步全塞进 builder 里；@Qualifier 按名注入跟 4-14 / 4-15 的”按 name 取 Bean”同源。
