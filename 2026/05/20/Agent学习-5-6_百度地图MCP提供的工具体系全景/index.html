5-6_百度地图MCP提供的工具体系全景

发表于2026-05-20|更新于2026-05-20|Agent学习第5章 Agent 团队打造专属你的旅行规划
|浏览量:

1. 一句话定位

这一集你不写一行代码，只干一件事：把百度地图 MCP Server 官方文档里的工具清单当 API 文档来读，挑出”旅行规划”项目要用的那几把刀。

2. 主体

2.1 一个心智模型先放在最前面

你会反复听到一句被弱化的话：“MCP 跟 API 其实差不多，只是由智能体来调”。这话听起来像把前面 3-4/3-5/4-3 的协议分层全压平了，但你别误会——它不是在否定分层，而是给你一把读文档的钥匙：功能等价（都是给智能体用的工具）+ 接口风格等价（都看 input/output/必填字段）+ 调用机制不同（你不写 HTTP，由 MCP Client→Server 走 SSE/Streamable HTTP）。所以你这一集完全可以当作”读 RESTful 文档”来对待，只看能力，不看协议。

2.2 不要按文档目录读，要按数据流读 (加工增量在 §2.2)

文档目录的顺序是：天气查询 → 地理编码/逆地理编码 → 地点检索 → 路线规划 → 马克地图。讲师就是顺着这个目录从上往下翻的。但这个顺序对应不上项目里实际的调用先后——你脑子里如果还按目录记，一年后回来根本想不起来”哪个先调、谁的输出喂给谁”。

所以你应该按数据流重组成五层：

记住这一条：所有路径的第一脚都是地理编码。用户嘴里只有”天安门”，但 MCP 工具几乎全吃经纬度。

2.3 入口转换层：地理编码 / 逆地理编码

  • 地理编码：地址字符串 → 经纬度（bd09ll 坐标系）。必填 address，可选 city。
  • 逆地理编码：经纬度 → formatted_address / uid / addressComponent。必填 latitude + longitude。

注意 bd09ll 这个坐标系——百度自家的，跟 WGS84、GCJ-02 不是同一套，将来你要跨平台联调（比如把数据送进 OpenStreetMap）就得做转换。

2.4 信息发现层：地点检索（周边）

这里你要分清两个东西：

  • 地点检索：传统检索，分”城市内检索”和”圆形周边检索”。关键参数 query（关键词，至多 10 个用英文逗号隔开）+ tag（中文分类如”美食,购物”）+ region + location（圆心 lat,lng）+ radius（米）。输出 POI 列表 name/location/address。
  • 多维检索：是”语义升级版”，支持自然语言模糊匹配。这一集没用，你只要知道它存在就行。

项目里你会用周边检索：传天安门的经纬度做圆心，加 query=美食/购物/酒店，拿候选列表。

2.5 一个显式的取舍：地点详情检索被丢掉 (取舍出现在 §2.5)

文档里”地点检索”下面紧跟着一个地点详情检索——传 POI 的 uid 就能拿到评分、营业时间、brand、price 这些精细信息。听起来正是项目想要的。

但讲师一句话把它划掉了：”个人申请的级别用不到“。

这是个隐藏信号你必须接住：百度 MCP 的工具是按 AK 等级分层授权的。免费档拿不到 POI 详情。项目设计要主动绕开这把锁——如果你的旅行规划逻辑里强依赖营业时间或评分，那要么换数据源、要么去申请高级 AK，不能假装这工具能用。

2.6 决策辅助层：天气查询

输入二选一：location（经纬度，经度在前纬度在后，逗号分隔）或 district_id（6 位行政区划代码）。输出：实时天气 + 未来 5 天预报。

这把刀的存在感是项目级的——它决定某天该不该去某景点。下雨就跳过户外景点，往室内候选切。所以你看到它接在”地点检索”后面：先有 POI 候选，再用天气过滤。

2.7 路径连接层：路线规划

必填三件套：origin + destination + model。model 是这里唯一需要记牢的枚举——driving / riding / walking / transit，驾车/骑行/步行/公交四选一。输出 steps + distance + duration。

另外有个批量算路版本，一次最多 100 条，步行有 200 KM 上限。项目里如果要算”住宿→景点 A→美食→景点 B”这种串联路径，就该用批量算路一把搂下来，别循环单次调用。

2.8 结果可视化层：马克地图

名字一开始唬人。别把”马克”当人名/品牌——它就是 mark（标记）地图。

  • 输入：text_content（你之前所有工具产出的旅行规划文本拼起来的一段描述）。
  • 输出：个性化地图 URL + 二维码。

它是整个清单里唯一一个”出图”的工具——别的工具都产生结构化数据（坐标、POI、路线 JSON），只有它产出可分享的展示物。所以它必然是流水线的最后一棒，吃所有人的输出，吐给用户。

文档里有句小字：”避免传入特殊字符如 \ 等”——这暗示着它可能没做严格 escape，你真用时要自己清洗一下文本。

3. 没 get 的点

  • 百度 MCP Server 的具体 endpoint URL 是什么？SSE 还是 Streamable HTTP？AK 该塞 query 还是 header？这一集没说，估计下一集开始接入时会给。
  • 马克地图说”避免特殊字符”——到底是什么转义规则？是 URL encode 就够、还是有自己的黑名单？真用之前要试一下。
  • 多维检索 vs 地点检索的实际效果差多少？如果多维检索的语义匹配靠谱，是不是就能省掉 tag 那套硬分类？
  • AK 等级分层的官方文档在哪？哪些工具属于免费档、哪些是高级档，没有一张表。

4. 跟其他集连接

  • 上承：3-6 体验 MCP：JManus 配置 MCP 服务——那集告诉你 MCP Server 是啥、怎么挂到 JManus 上；这一集换”具体一家 MCP（百度地图）暴露了哪些工具”。也上承第一章里申请 AK 的环节。
  • 下启：下一集大概率开始在代码里调用——要么 JManus 配置百度 MCP（参考 3-6 那套 SSE URL + 三要素），要么在 SAA 工程里通过 spring-ai-starter-mcp-client 接入。”地图调起”（马克地图）应该会作为项目最终交付入口。
  • 横向：和 4-5 创建 MCP 工具 互为正反——4-5 是你自己写一个 @Tool 注解的天气工具，5-6 是看别人（百度）写好的工具清单。两个角度都加深一个事实：MCP Server 的本质就是一堆带 input/output schema 的函数。和 4-8 JManus 导入自定义 MCP 也呼应——同样是”消费端看 server 暴露了什么”。

5. 知识地图

6. 自测题（5 卡）

  1. 百度 MCP 这套工具里，”所有路径的第一脚”几乎都是哪一个工具？为什么？

    答案地理编码。因为用户输入永远是地名（"天安门"），但下游绝大多数工具——周边检索、天气、路线规划——都吃经纬度。

  2. 地点检索和地点详情检索的区别是什么？为什么这一集只用前者？

    答案地点检索按圆心+关键词检索 POI 列表（name/location/address）；地点详情检索传 POI 的 uid 拿评分/营业时间/brand/price。后者需要高级 AK，个人申请的 AK 拿不到，所以项目要绕开。

  3. 路线规划的 model 参数有哪四个枚举值？分别对应什么？

    答案driving = 驾车，riding = 骑行，walking = 步行，transit = 公交。

  4. 马克地图在工具链里的角色为什么特殊？

    答案它是唯一一个"出图"工具——别的工具都产生结构化数据（坐标/POI/路线 JSON），它产生可分享的展示物（地图 URL + 二维码）。所以它必然是流水线最后一棒。

  5. “MCP 跟 API 差不多”这句话对不对？怎么理解？

    答案从功能视角和接口风格看是对的：都给智能体当工具、都看 input/output/必填。但从调用机制看不一样：API 是你自己写 HTTP 调用，MCP 是由 Client→Server 走 SSE/Streamable HTTP 给智能体用。这一集刻意忽略协议层，只看能力。
