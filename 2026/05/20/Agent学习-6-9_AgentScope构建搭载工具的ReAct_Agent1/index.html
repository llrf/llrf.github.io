6-09 AgentScope构建搭载工具的ReAct Agent（1）

发表于2026-05-20|更新于2026-05-20|Agent学习第06章 多 Agent + ReAct架构，SpringAi迈入Agent新时代
|浏览量:

1. 一句话定位

这一集你做的事是：把 SAA 1.1 里用熟的 ReactAgent.builder() 范式平移到 AgentScope Java 1.0.7，并在「.model() 入参类型」和「.tools() 改名 .toolkit()」这两个分歧点上停下来逐个比对——本集只搭完 Model 这一半，Toolkit 留到下一集。

2. 主体

2.1 心智模型：「基于 SAA 1.1」不等于「等于 SAA 1.1」

文档站 java.agentscope.io/zh/intro.html 的开篇说 AgentScope Java 是「面向智能体的编程框架」，强调 ReAct 推理 + 工具调用 + 内存管理 + 多智能体协作。

关键反直觉点：底层「基于 SAA 1.1」，但 API 不是 SAA 1.1 的子集——AgentScope 在 Spring AI 之上又包了自己一层抽象，所以 .model() 入参类型变了，.tools() 改名了。一开始你以为可以照搬，结果连最基础的方法签名都对不上。

点进 SAA 1.1 的 Builder.class，model(Model model) 这里的 Model 是 org.springframework.ai.chat.model.ChatModel——Spring AI 的接口。点进 AgentScope 的 ReActAgent.Builder，model(Model model) 的 Model 是 io.agentscope.core.model.Model——AgentScope 自己定义的接口。

加工增量在 §2.4：消化稿只是说「接口类型不一样」，但真正的含义是——AgentScope 没有复用 Spring AI 的 ChatModel 体系，而是自己接管了「对接各家大模型」的封装责任。这意味着如果阿里以后想给 DashScope/DeepSeek/Gemini 加什么 AgentScope 专属能力（比如统一的 Formatter 钩子），它不需要去改 Spring AI 上游，自己一层就够了。代价是：你在 SAA 里写的 @Autowired ChatModel 这种 Spring 依赖注入习惯，到这里要换成手动 DashScopeChatModel.builder()...build()。

取舍出现在 §2.5：SAA 1.1 的「变长参数」写起来轻便，一行 .tools(weatherTool, calcTool) 就完事；AgentScope 的「先组装对象再塞进去」写起来啰嗦（多了一次 new Toolkit(...)），但换来了「工具集本身是一等公民」——可以被命名、复用、动态加载/卸载，甚至可以传给多个 Agent 共享。两种 API 哲学的分叉点：要轻便，还是要可管理。这一集只占了一行 .toolkit(new Toolkit()) 的位置作为悬念，Toolkit 内部怎么装工具留到 6-10。

2.7 Formatter：从 prompt 工程下沉到框架层

.formatter(new DashScopeChatFormatter()) 这一行容易被忽略，但它的位置很关键——它是 Model 对象级的属性，不是 Agent 级，更不是 prompt 级。

含义：「返回什么格式（JSON / 文本 / 自定义结构）」这件事，在 SAA 1.1 里你通常会在 prompt 里写 “请返回 JSON: {…}”，或者用 BeanOutputConverter；AgentScope 把它做成了 Model 的一个属性，框架级保证「类型安全的响应」。文档站原话叫「自纠错输出解析器，当 LLM 输出偏离预期格式时，系统会自动检测」。

源码里的泛型签名很长：Formatter<DashScopeMessage, DashScopeResponse, ...>，由 DashScopeChatFormatter 具体实现。

3. 没 get 的点

  • Toolkit 内部到底长什么样？ 是 Toolkit.builder().tool(weatherTool).tool(...).build() 这种链式？还是 new Toolkit(List<Tool>) 直传？本集没揭晓。
  • AgentScope 自己有没有 @Tool 注解？ 跟 SAA 用的 org.springframework.ai.tool.annotation.Tool 是否兼容？如果不兼容，4-5 写的 WeatherTool 在这里就得重写。
  • Memory 怎么接？ Builder 上能看到 .memory(Memory memory)，但本集没碰。
  • .formatter(...) 在不要求结构化输出时是否必填？ Builder 里 formatter 是有默认值还是必传，目前不确定。
  • 「基于 SAA 1.1」在代码层是真的 import 了 spring-ai-alibaba 的 jar，还是只是设计上参考？ 需要去 AgentScope 的 pom 看传递依赖才能确认。
  • DeepSeekChatModel 的 apiKey 配置方式跟 DashScope 一样吗？ 老师暗示了能用，但没演示。

6. 自测题（5 卡）

  1. AgentScope Java 1.0.7 的 .model() 方法入参类型是什么？跟 SAA 1.1 的 .model() 入参有什么区别？
  2. SAA 1.1 用 .tools(ToolCallback...)（变长参数），AgentScope 改成 .toolkit(Toolkit)（单一对象）。这个改动背后的设计哲学是什么？
  3. 为什么 AgentScope 的 pom.xml 里除了 agentscope 还要加 logback-classic？只加 agentscope 行不行？
  4. DashScopeChatModel.builder() 上常用的属性是哪几个？其中 .formatter(...) 这个属性「下沉」到了哪一层——prompt 层、Agent 层，还是 Model 层？
  5. 本集留了 .toolkit(new Toolkit()) 这个空壳没填，预测下一集会怎么把工具装进 Toolkit？给出至少两种可能的 API 形态。

7. 关键词表

术语 一句话解释
AgentScope Java 1.0.7 阿里在 SAA 1.1 之上又包一层的 Java Agent 框架，API 独立、不是 SAA 子集
ReActAgent.builder() AgentScope 唯一一类智能体的构造入口，Builder 模式，和 SAA 1.1 同名
io.agentscope.core.model.Model AgentScope 自己的模型抽象接口，不是 Spring AI 的 ChatModel
DashScopeChatModel Model 接口的 DashScope 实现，extends ChatModelBase，用 builder 构造
Toolkit AgentScope 的工具集对象，作为一等公民传给 .toolkit(...)，替代 SAA 的变长参数 .tools(...)
Formatter Model 对象级的输出格式化器，把结构化输出从 prompt 下沉到框架层
SLF4J + Logback SLF4J 是日志接口，Logback 是实现，AgentScope 用了 SLF4J 所以必须显式引入实现
SpringAI Alibaba 1.1 对照 本集主轴：两段代码并排，圈出 .model() 入参类型差异 + .tools() 改名 .toolkit() 这两个分歧点
