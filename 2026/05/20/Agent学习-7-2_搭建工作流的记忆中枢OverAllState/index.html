搭建工作流的记忆中枢：OverAllState

1 · 一句话定位

工作流要让多个节点接力处理同一份数据，那这份数据存哪儿？这一集回答这个问题——OverAllState 就是工作流的那块共享白板，所有节点都能往上写、往上读，是 SAA Graph 四大对象里第一个被搭出来的。

2.3 怎么往里塞？方法签名说的算

点进 OverAllState，看到一个关键方法 registerKeyAndStrategy，两个重载（截自第 297 秒的源码帧）：

读这段源码有三个发现值得标下来：

  1. 存储的载体是 Map<String, KeyStrategy>——key 是字符串，value 不是数据本身，是一个叫 KeyStrategy 的对象。
  2. 两个重载分别对应”单 key 注册”和”批量 Map 注册”——讲师选了批量这条路。
  3. 返回值是 this——支持链式调用，本集没用，但顺手记一笔（参见 §3）。

2.4 反直觉的点：value 位置上坐的不是 value

第一遍看会自然以为：注册嘛，肯定是 put("messages", "你好") 把数据塞进去。错。

Map<String, KeyStrategy> 这个签名告诉你：注册阶段，你只声明 key 叫什么、以及这条 key 将来要怎么被更新，并不写实际数据。

点进 KeyStrategy 接口（第 471 秒的帧）：

一个继承 BiFunction<Object, Object, Object> 的接口——“输入两个 Object，输出一个 Object”——明显是在描述 「旧值 + 新值 → 合并后的新值」 这种合并函数。

我自己的加工：可以把 KeyStrategy 类比成数据库的 列定义 + 写入触发器。registerKeyAndStrategy 干的是 DDL（建表+定义触发器），不是 DML（insert）。真正写数据的事，要等到后面节点跑起来。

2.5 两个开箱即用的策略

IDEA 给出 KeyStrategy 接口有两个实现类（第 479 秒的弹窗帧）：

实现类 语义 典型用途
AppendStrategy 在旧值基础上追加新值 消息历史 / 多节点累积输出
ReplaceStrategy 用新值覆盖旧值 最新单值 / 临时结果字段

讲师对 AppendStrategy/ReplaceStrategy 的”判断依据”是看类名——这其实是合理的工程提示：SAA 的命名足够直白，不必每次都点进源码。

我自己的加工：选错策略不是报错，而是业务逻辑悄悄出 bug——你以为节点 B 能看到节点 A 写过的全部消息，结果 key 配的是 Replace，B 只能看到最后一条。这种坑没有编译器拦你，调起来很疼。

3 · 没 get 的点

  • KeyStrategy 既然是 BiFunction，能不能自己写第三种策略（比如 DistinctAppend 去重追加、JSON Merge 深合并）？看接口签名是开放的，但讲师没演示。
  • 注册时不给初值，那”没被任何节点写过的 key”取出来是 null 还是抛错？这关系到节点逻辑要不要 Optional/判空。
  • AppendStrategy 的”追加”对 String/List/自定义对象分别怎么实现？字符串拼接？List.addAll？需要扒一眼 AppendStrategy.apply() 源码才能确认。
  • registerKeyAndStrategy 返回 this 支持链式，但本集用的是先建 Map 再批量注册。两种写法在多 key 场景下哪种更顺，是看场景的——批量注册更适合配置集中在一处。
  • OverAllState 是否线程安全没看到。6-8 出现过的 ParallelAgent（并行多分支）如果并发写同一个 key，AppendStrategy 会不会丢数据？这个得等后面集或自己写测试验证。

5 · 知识地图

6 · 自测题（5 卡）

Q1：OverAllState.registerKeyAndStrategy(map) 这一步是不是把数据写进白板了？
A：不是。这一步只声明”会出现哪些 key、每条 key 的合并规则是什么”，相当于建表+定义触发器，不是 insert。真正的数据要等节点运行时往里写。

Q2：KeyStrategy 到底是个什么类型？为什么这样设计？
A：它是个继承 BiFunction<Object, Object, Object> 的接口，签名意思是”(旧值, 新值) → 合并值”。这样设计是因为多节点协作时同一个 key 会被反复写，框架需要知道”再次写入时怎么合并”，而不是简单覆盖或简单追加——把这个决定权交给配置方。

Q3：现在有 key=”chatHistory” 要存对话历史，应该用哪个策略？为什么？
A：用 AppendStrategy。每个节点写入新一轮对话时希望累加到历史里，而不是把之前的全擦掉。如果误用 ReplaceStrategy，下游节点只能看到最后一轮，整个上下文丢失。

Q4：registerKeyAndStrategy 有两个重载，怎么选？
A：单 key 用 (String, KeyStrategy)，批量注册用 (Map<String, KeyStrategy>)。本集用了 Map 批量，原因是配置集中在一处更易维护；如果只是临时加一个 key，单参数版本更顺。两种最后都返回 this，支持链式串起来。

Q5：工作流总共四个对象，本集覆盖了哪个？剩下三个是什么？
A：本集只讲了全局状态（OverAllState）。剩下三个是节点（Node）、边（Edge，节点之间的连线）、整个工作流（Graph）。后续集会一个个展开，OverAllState 是这四个里的”地基”——节点/边都会引用到它。

7 · 关键词表

术语 一句话解释
OverAllState 工作流的全局状态白板，贯穿整个 Graph，所有节点可读可写
registerKeyAndStrategy 注册 key + 合并策略的方法，两个重载（单 key / Map 批量），返回 this 支持链式
KeyStrategy 接口 继承 BiFunction<Object,Object,Object>，描述”旧值 + 新值 → 合并值”
AppendStrategy 追加策略，新值拼在旧值后面（消息历史 / 累积输出场景）
ReplaceStrategy 覆盖策略，新值替换旧值（单值字段 / 最新结果场景）
Key-Value 注册 vs 写入分离 注册阶段只声明 schema + 合并规则，运行时节点才填值
Map<String, KeyStrategy> 批量注册的载体，本质是 HashMap，集中管理多个 key 的策略
工作流四对象 全局状态 / 节点 / 边 / Graph，本集只覆盖第一个
