8-7 PlanAct是全局流程规划的主管

发表于2026-05-20|更新于2026-05-20|Agent学习第08章 Jmanus 懂思考、会规划、一步步动手完成任务。
|浏览量:

1. 一句话定位

OpenManus 在”处理复杂任务”这个核心模块下挂了两个思考框架，本集只展开第一个 PlanAct——你可以把它当作一个”先拆任务、再派单、还要边走边监督边改计划”的项目主管。

2. 主体

2.1 先把上集那张架构图找回来

上集（8-6）讲过 OpenManus 有三个核心模块：

  • 模块化：让你能很方便地新建一个 Agent 并塞进集群，因为它是多 Agent 协同框架。
  • 工具驱动：借鉴 Manus 的思路，工具箱可拔可插，里面也包含 MCP。
  • 处理复杂任务：这一集的主战场。

[frame f001 @0.7s] 这张架构总览图里，处理复杂任务这一块下面挂着两条平行分支——思考框架 Plan-and-Execute (PlanAct) 和 思考框架 Reason-and-Action (ReAct)。中间还有一个孤独的绿块”动态 Agent 分配与调度”，下面是”规划模块 / 执行模块”两个具体模块。

第一遍我卡在这里：这两个思考框架到底是挂在哪个模块下？答案是只挂在第三模块”处理复杂任务”下，不是 OpenManus 顶层概念。讲师没明说，看图才确认。

2.2 为什么复杂任务要分两阶段

PlanAct 的核心特点就是分阶段——规划阶段 + 执行阶段。

[frame f002 @172s] 这张图在 PlanAct 红框旁边新长出了两个黄色块：”规划阶段”和”执行阶段”，挂在”复杂任务”这个椭圆的两侧。

为什么必须分？讲师给了一句很朴素的话：复杂任务不可能一上来就埋头苦干。一个复杂任务要做的是：

  1. 先拆成一堆简单任务；
  2. 再排序——先做什么、后做什么；
  3. 而且第三步可能要拿前两步的结果加上另一条分支的结果合并才能跑——也就是说，依赖关系不是一条直线，是 DAG。

这就跟你 7-1 工作流编排 里画的那张 DAG 拓扑图对上了——区别在于，那集是人在 Graph 里画死 DAG，PlanAct 是 LLM 在运行时自己拆 DAG。

2.3 用”团队主管”这个类比来锚定

[frame f003 @227s] 这是讲师正在打主管比喻的那一帧。把 PlanAct 翻译成你公司里的项目主管，全流程就清楚了：

  1. 领会需求：先弄明白用户的真实意图（不是字面意思）。
  2. 拆解需求：把整个需求切成简单需求。
  3. 派单：分派给底下的专科队员（对应 3-9 的专科 Agent / [5-2~5-5] 那四个旅行规划 Agent）。
  4. 沿计划监督：按顺序盯着每个子任务的完成情况，看是否符合预期、是否偏离目标。
  5. 动态调整：一旦偏离，改计划顺序或改某个队员的需求，把整体拉回目标轨道。

【加工增量】：消化稿原文一直把 PlanAct 讲成”阶段”——但讲师在第 3 帧明显把它讲成了”角色”。这两种解读其实是同一个节点的两个视角：阶段是过程视角（时间切片），主管是组织视角（人格）。理解 PlanAct 时你得同时握住这两根线，不然图上”规划阶段 / 执行阶段”和讲师口中”主管这个人”会对不上号。

2.4 PlanAct 的真正硬核不是”会拆”，是”会改”

很多人对 Plan-and-Execute 的传统印象是：”一次性拆好计划，然后按部就班执行完”——这是静态规划。

PlanAct 的灵魂恰恰把这个印象推翻：每走一步都要监测，偏离就动态改。这才是它和”工作流编排”最大的差异：

  • Graph 工作流（7-x）：DAG 在编译时定死。
  • PlanAct：DAG 在运行时由 LLM 拆出来，而且还能边跑边改。

所以那个图中央孤悬的绿块”动态 Agent 分配与调度”，其实就是 PlanAct”按计划派单 + 监督偏离 + 动态调整”这条动态调度逻辑的可视化对应物。

2.5 PlanAct 是”管两端”的协调者

注意一个反直觉点：直觉上 PlanAct 应该只对应”规划”，但图上 PlanAct 红框下挂着规划模块 + 执行模块两块。也就是说 PlanAct 不是单纯的 planner，它是一个跨规划阶段和执行阶段的协调者——既拆又派又监督。

ReAct 是这一帧另一个并列的绿块，本集只点名不展开——它管单个子任务内部的 Thought/Act/Observation 循环，留给下一集。

3. 没 get 到的点

  • 规划模块 vs 规划阶段是不是同一个东西？ 图上规划阶段是过程切片（时间），规划模块是实体（组件）。讲师没明说两者的关系。猜测：规划模块就是 PlanAct 在规划阶段调用的那个组件——但要等源码或下一集才能确认。
  • “动态 Agent 分配与调度”绿块同时连到 PlanAct 红框和”规划模块/执行模块”，到底是 PlanAct 的子能力，还是和 PlanAct 平级的独立调度器？图上看像后者，讲师叙事像前者，待查。
  • PlanAct 在 OpenManus 源码里到底叫什么类名？ 是不是有 PlanAgent / ExecuteAgent 这种拆分？得看 OpenManus 仓库。
  • PlanAct 和 ReAct 是嵌套还是并列？ 本集只展开 PlanAct，并列出现在图上让人以为是 either/or——但讲师在最后一句又说”无论是对于整体的规划、还是对于子任务的执行，都是自主去思考”，暗示两者是嵌套（PlanAct 拆出来的每个子任务里再跑 ReAct）。需等下集 8-8 确认。

5. 知识地图

6. 自测题（5 卡）

  1. Q：PlanAct 和 ReAct 在 OpenManus 架构里挂在哪个模块下面？是顶层并列还是嵌在某个模块里？
    A：嵌在第三个核心模块”处理复杂任务”下，是这个模块下两条平行的思考框架分支，不是 OpenManus 顶层概念。

  2. Q：用一句话说出 PlanAct 的真正硬核是什么——不是”会拆”，是什么？
    A：会动态调——每走一步都监测是否偏离预期，偏离就改计划顺序或改某个队员的需求。静态拆完按部就班执行不算 PlanAct 的灵魂。

  3. Q：图上 PlanAct 红框下面挂着规划模块和执行模块两块，能不能说”PlanAct 就是 planner”？
    A：不能。PlanAct 是管两端的协调者——既负责规划阶段（拆+排序），也负责执行阶段（按计划派+监督+调整）。它不是单纯的 planner。

  4. Q：复杂任务为什么不能”一上来就埋头苦干”？至少说出两个层面的原因。
    A：（a）子任务之间有依赖顺序，先后做什么不能乱；（b）第三步可能要合并前面几个分支的结果，不是线性链，是 DAG；（c）执行过程中可能偏离目标，没有规划+监督就无法纠偏。

  5. Q：PlanAct 跟 [7-1 工作流编排] 那个 Graph DAG 的核心差异是什么？
    A：Graph 是人工把 DAG 画死在编译时；PlanAct 是 LLM 在运行时自己拆 DAG，而且能边跑边改——前者是静态编排，后者是主动规划+动态调度。
