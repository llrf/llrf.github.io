5-2_团队成员路线制定专员Agent

发表于2026-05-20|更新于2026-05-20|Agent学习第5章 Agent 团队打造专属你的旅行规划
|浏览量:

1. 一句话定位

把 5-1 那张”旅行规划复合任务大拆解图”里的第一个专科节点实例化成一张 Agent 卡片——上半张写”角色定义”（一句话职责契约），下半张列”能力清单”（3 条工具级能力），再用一根虚线把它同时挂到「景点路线规划」和「住宿路线规划」两个云朵上。

2. 主体

2.1 起点：用户给你的永远是半成品

把用户原话拆开看，你拿到的只有四样东西：

用户给你的 用户没说但你必须补的
时间：十一国庆 玩什么景点
地点：深圳 → 清远 住哪、住多远
期限：自驾三天 景点之间怎么连
偏好：不想旅程太满 餐饮 / 折扣怎么省

记住这个不对称——它是整个多 Agent 设计的前提，不是抱怨。正因为用户「不知道自己想要什么」，你才需要拆出”根据天气推荐””根据偏好推荐””折扣监控”这种主动型子任务。Agent 不是来执行命令的，是来补全意图的。

2.2 终态先看：Agent 卡片长什么样

跳过过程，直接看产出物——这一集真正要你记住的就是这张卡的模板：

两块东西，分工很清楚：

  • 角色定义是写给主管 Agent看的”招牌”——一句话锁定职责边界，主管 Agent 拿它来路由派单（”哎，这单是关于路线的，丢给你”）。
  • 能力清单是写给系统看的——它是支撑这个职责的工具列表，未来落到代码（4-13 ReactAgent + .tools(...)）就变成一组 @Tool 注入。

这两块不是一回事，它们在卡片上是分两段写的，别揉在一起。

加工增量在 §2.2：原讲解按时间线先讲用户需求再画 Agent 卡，我把顺序倒过来——先把终态卡片摆出来当模板，后面所有 Agent（景点推荐 / 住宿规划 / 费用计算 / 折扣监控）都会按这个模板填，先抓模板比顺着时间线走更容易迁移。

2.3 为什么是 3 条能力？

第一遍看你会觉得”路线规划不就是调高德地图吗，一条搞定”。但拆开看必须是 3 条，少一环用户就看不见结果：

注意三个设计决策：

  1. 地点搜索 + 经纬度转换被绑成一条，不是两条。因为它们必须串联用——拿到自然语言地名才能转坐标，转出坐标才能进下一步，中间断了没意义。
  2. 可视化是独立一条而不是”顺便干”。Agent 输出不能只是结构化数据，必须最终变成用户能看的地图，所以单列出来强调它是必须的输出形态。
  3. 3 条都是工具级能力（地图 API / 几何算法 / 渲染），不是 LLM 自带的——这呼应了 3-7 Agent Skills 里那句”领域专业知识靠工具补”。

取舍出现在 §2.3：把”地点搜索”和”坐标转换”绑成 1 条而不是拆 2 条，是一次刻意的颗粒度选择。拆 2 条更细，但中间产物（自然语言地名）对外面没意义；绑成 1 条意味着这条能力对外的契约是”喂地名 → 吐坐标”，内部怎么实现是黑盒。颗粒度的标准是契约能不能独立成立，不是”步骤够不够小”。

2.4 横跨挂载：一个 Agent 服务两个云朵

把这张卡画完之后，讲师用虚线把它指向大拆解图上的两个节点：

  • 「景点路线规划」（景点 → 景点之间怎么连）
  • 「住宿路线规划」（住宿 → 景点之间怎么连）

虚线的语义是”同一个 Agent 实例服务多个挂载点“，不是画两份。这是这一集为什么单独把”路线规划 Agent”拎出来定义的根本原因——它可复用，所以值得有自己的卡。如果一个 Agent 只服务一个挂载点，那它的卡和挂载点的描述其实可以合并，不必单独列。

2.5 这张卡未来怎么落代码

提前对一下后面的章节，今天写的这张卡其实就是 AgentCard 的草稿：

卡片这一行 对应代码里的
“路线规划 Agent” AgentCard 的 name（要符合 4-15 那条”name 一致性铁律”）
“角色定义：能够根据地点，规划最优路线” AgentCard 的 description
能力清单 3 条 ReactAgent 的 .tools(routeSearchTool, geoTool, visualizationTool)
横跨挂载（虚线复用） 一个 ReactAgent Bean 被多个上游调用

3. 没 get 的点

  • 可视化展示到底是这个 Agent 自己输出 HTML / 图片，还是只输出结构化路径数据交给前端渲染？落到 4-13 的 ReactAgent 时，这一步会变成一个 @Tool 还是一个 ResponseFormat？这一集没回答。
  • 地点搜索 + 经纬度转换背后是接 MCP（比如高德 / 百度地图 MCP，5-6 会讲）还是用 @Tool 自己写？讲师没说，等 5-x 实现集。
  • “最优路线”的最优 metric 是什么？时间最短 / 距离最短 / 还是带住宿和景点的多约束优化？这一集没给出，估计要等 Tool 的具体实现才能锁。

5. 知识地图

6. 自测题

  1. 用户在 5-1 给的需求里只说了四件事，是哪四件？剩下”什么景点 / 住哪 / 怎么连”为什么由 Agent 来补，而不是再问用户一遍？
  2. 路线规划 Agent 的”角色定义”和”能力清单”分别是写给谁看的？为什么必须分开写？
  3. 为什么能力清单第 1 条是”地点搜索 + 经纬度坐标转换”绑在一起，而不是拆成两条独立能力？如果拆成两条，会出什么问题？
  4. 大拆解图上为什么用虚线把路线规划 Agent 同时连到「景点路线规划」和「住宿路线规划」？这跟用实线分别画两个独立 Agent 有什么本质区别？
  5. 如果让你按本集的卡片模板写「折扣监控 Agent」的卡，角色定义那一句会怎么写？至少列出 2 条能力。

7. 关键词表

术语 含义
路线规划 Agent 旅行规划复合任务里第一个被实例化的专科 Agent，职责是”根据地点规划最优路线”
角色定义 一句话的职责契约，给主管 Agent 路由派单时看的”招牌”
能力清单 支撑角色职责的工具能力列表，本集是 3 条（地点搜索+坐标 / 路线规划 / 可视化）
地点搜索+经纬度转换 第 1 条能力，把自然语言地名变成坐标，是路线计算的输入前置
路线可视化 第 3 条能力，把 JSON 路径数据渲染成用户能看的地图，是 Agent 输出的必须形态
横跨挂载（虚线复用） 同一个 Agent 实例同时服务多个子任务节点，在大拆解图上用虚线表达
用户需求 raw 用户只给时间/交通/期限/一句模糊偏好，剩下都靠 Agent 团队补全，是多 Agent 拆解的根本动因
Agent 卡片模板 角色定义（一行）+ 能力清单（编号列表）的固定结构，后续每个 Agent 都按这个格式填
