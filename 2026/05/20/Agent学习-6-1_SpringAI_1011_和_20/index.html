6-1_SpringAI_1011_和_20

发表于2026-05-20|更新于2026-05-20|Agent学习第6章 多 Agent + ReAct架构，SpringAi迈入Agent新时代
|浏览量:

1. 一句话定位

你把 SAA 三个版本（1.0 / 1.1 / 2.0-M1）摆在同一张图上看，不是为了”挑最新版学”，而是用版本差识别出真正值得花时间的三件套：ChatClient / MCP / 对话记忆——其余的（包括 RAG）要么稳定不变，要么有行业争议。

2. 主体

2.1 一个反直觉先放在最前面

你的直觉大概是：1.0 → 1.1 → 2.0 是常规迭代，挑最新的学就行。但你看完这一集会推翻这个直觉——AI 半年就过时，跟版本号没意义，跟”哪个组件被持续加码”才有意义。

所以这一集真正给你的不是”三个版本的 release notes”，而是一把方法论的尺子：把版本差当信号，识别出框架的”重点发展方向”。这个判断角度直接承袭 5-6（看长期价值，不看当下热闹）。

2.2 三版本是怎么排的

时间线很短：

  • 1.0 正式版 — 2025.5 发布，四件套：ChatClient / RAG / 对话记忆 / 支持 MCP。
  • 1.1 正式版 — 2025.11 发布，叠加：MCP 开箱即用（基于注解 + OAuth2 + 0.10 版本）/ 提示词缓存（多策略）/ 原生支持 Gemini 2.0 Flash / RAG 更高效 / 对话记忆存储方案增加。
  • 2.0.0-M1 — 2025.12 发布，只是 M1 预发布，正式版预计 2026。叠加：基于 Redis 的对话记忆组件 + 性能调优 / Redis 向量检索升级 / OpenAI 原生 SDK 接入 / Gemini 思考深度调节。工程红线：只支持 Java 21 + SpringBoot 4.0+。

2.3 加工增量：把时间线纵向 → 翻转成”加码强度”横向 (加工增量在 §2.3)

原始素材是时间线纵向走（1.0 → 1.1 → 2.0），到最后才归纳”哪些是重点”。你要做的不是按这个顺序记，而是把同一组件在三个版本里的演进抽出来横着看——这样你立刻能看出”谁在被加码”。横着排你会得到这张表：

组件 1.0 1.1 2.0-M1 判断
ChatClient 引入，API 稳定 API 未变 API 未变 跨版本冻结 → 学一次受益三版本
MCP 支持 注解化 + OAuth2 + 0.10 没再递增 1.1 已成熟，2.0 是固有组件
对话记忆 内存/文本/数据库 存储方案增多 Redis + 性能调优 持续加码，2.0 押注 Redis
RAG 引入 更高效 Redis 向量检索升级 SAA 持续加码，但行业有争议
提示词缓存 — 多策略新增 — 1.1 特性，未必延续
Gemini 适配 — 2.0 Flash 原生 思考深度调节 模型适配，跟业务无关
OpenAI 原生 SDK — — 新增 模型适配

横着看你就有结论了：ChatClient（冻结）、MCP（已稳定）、对话记忆（仍在加码） 三件套是重点。

2.4 为什么 ChatClient 是头号重点

ChatClient 是 SAA 跟大模型对话的统一入口——阿里、DeepSeek、OpenAI、Gemini 你都不需要改代码，配置文件切一行就换了模型。

更关键的是它的 API 自 1.0 起就冻结：1.0 学的方法签名到 1.1、2.0 还在用。这意味着你在 1.0 上投资的学习时间，半年后不会贬值。这就是课程选 1.0 作主力版本的根因——不是因为 1.0 最新，而是因为 1.0 的 ChatClient API 跨版本兼容性最稳。

2.5 为什么 MCP 是第二重点

MCP 的成熟曲线很陡：

  • 1.0：支持 MCP（你能调，但要手写适配）。
  • 1.1：开箱即用 —— @McpTool 注解化、OAuth2、0.10 版本。第 4-10 / 4-12 学过的就是这个。
  • 2.0：没再递增 —— 不是被冷处理，而是已经变成”固有组件”（infrastructure-level），框架重心转移到对话记忆和 RAG 了。

你要接住的信号是：MCP 已经稳定到不需要再升级。后面的课程不会再花大力气教 MCP 的协议层，4-2 ~ 4-12 学的东西足够你长期吃。

2.6 对话记忆：被持续加码的那条线

也叫”上下文记忆”——让 AI 记住你之前说过什么。三版本里它一直被加码：

  • 1.0：三种存储 —— 内存 / 文本 / 数据库。
  • 1.1：存储方案再增多（具体几种本集没说全）。
  • 2.0：基于 Redis 的对话记忆组件 + 性能调优，押注 Redis。

你要记的不是”哪些存储方案”，而是**”对话记忆是一个还在主动演进的组件”**——它后续会有专题课讲存储方案对比，本集只是埋个伏笔。

2.7 RAG：取舍出现在 §2.7 (取舍出现在 §2.7)

按”持续加码”的方法论判断，RAG 应该也是重点——它在 1.0/1.1/2.0 都在加强，2.0 还用 Redis 做向量检索升级。但这一集明确把 RAG 从”重点”里拿掉。

理由是：2025 年末 RAG 有争议，被视为过渡方案（长上下文 + Agent Skills + MCP 的组合在很多场景里能替代 RAG）。你要在这里学到的是一个更上层的判断模式：

框架的发展方向 ≠ 学习重点。
SAA 在押注 RAG，但行业共识不一定认可。两个信号都要看，只有”框架加码 + 行业共识”两路对齐，你才该把它当核心。RAG 是反例——SAA 在加码，但行业在质疑，所以课程降级处理。

把这条规则记下来，下次评估任何”新框架特性”都用得上。

2.8 2.0-M1 不学也不亏：M1 ≠ GA

2.0 在 2025.12 只发了 M1（Milestone 预发布）。回想 4-9 学过的 Spring 预发布层级：M < RC < GA。M1 是最早期的里程碑预发布，不能投产。

更要命的是 2.0-M1 只支持 Java 21 + SpringBoot 4.0+——你现有 SAA 工程大概率还在 Java 17 / SB 3.x，升上去成本不小。所以课程主力依然是 1.0：

  • 1.0 的核心组件（尤其是 ChatClient）跨版本兼容到 2.0。
  • 1.0 是 GA 正式版，可以投产。
  • 1.0 不挑 Java 版本和 SpringBoot 版本。

这是”稳定 API + 工程兼容”的双重选择，跟单纯追新版本完全是两个逻辑。

2.9 1.1 还有一个值得记的特性：提示词缓存

OCR 帧里能看到 1.1 多了”提示词缓存（多种缓存策略）“。这一集没展开，但你要先在脑子里贴个标签：

  • prompt template 的缓存（输入端缓存）还是响应缓存（输出端缓存）？本集没说，等后续课印证。
  • 多策略 = 至少有 LRU / TTL / 按 token 等几种切换。
  • 跟对话记忆是两套东西——对话记忆是”记上下文”，提示词缓存是”省 token / 省费用 / 省延迟”。

放到 §3 的”没 get 的点”里继续追。

5. 知识地图

6. 自测题（5 卡）

  1. 这一集为什么对比三个版本？目的是”学最新版”吗？

    答案不是。目的是用版本差识别"被持续加码的组件"——AI 半年就过时，跟版本号没意义，跟"哪个组件被持续加码"才有意义。这是一把方法论的尺子。

  2. 横向归纳后，这一集圈出的三大学习重点是哪三个？为什么不是 RAG？

    答案ChatClient（API 冻结）/ MCP（已成熟稳定）/ 对话记忆（持续加码）。RAG 虽然 SAA 在持续加码，但 2025 末行业有争议（被视为过渡方案），所以课程降级处理。判断规则：框架加码 ∩ 行业共识，两路对齐才学。

  3. 为什么选 1.0 作主力学习版本，而不是最新的 2.0-M1？

    答案两个理由：(1) ChatClient API 自 1.0 起冻结，跨版本兼容到 2.0；(2) 2.0-M1 是 M 级预发布不能投产，且只支持 Java 21 + SpringBoot 4.0+，工程门槛高。1.0 是 GA、稳定、可投产。

  4. MCP 在三个版本里的演化怎么走？2.0 为什么”没再递增”？

    答案1.0 支持 MCP → 1.1 开箱即用（注解 + OAuth2 + 0.10）→ 2.0 没再递增。不是被冷处理，而是已经成为框架的"固有组件"（infrastructure-level），框架重心转移到对话记忆和 RAG。

  5. 1.1 新增了”提示词缓存”。它跟”对话记忆”是同一个东西吗？

    答案不是。对话记忆是"记上下文，让 AI 知道你说过什么"；提示词缓存是"省 token / 省费用 / 省延迟"——可能缓存 prompt 模板渲染结果，也可能缓存模型响应。多策略指至少有 LRU/TTL 等几种切换。具体本集没展开。
