Skills 的文件结构标准

1. 一句话定位

Skills 是一个文件夹，文件夹里以 SKILL.md 为入口索引，Agent 先把这个 md 加载进上下文，再按需拉脚本/资源/指令——上一集讲的”渐进式加载”，落到磁盘上就长这样。

2. 主体

2.1 为什么一定是”文件夹”，而不是一个大 prompt

你装一个完整的专业 SOP（领域知识 + 工作流 + 工具调用逻辑），那玩意往往几千上万字，外加示例数据、API 文档、脚本代码——一次性塞进上下文窗口会爆，复制粘贴又难以版本化。

文件夹解决两个问题：

  • 分级懒加载：Agent 先吃索引（SKILL.md），到正文写”要用 examples.md / execute_api.py”时才按需拉细节。
  • 可移植性：把整个文件夹拷给 B Agent，B 立刻具备和 A 一样的技能——不是 fine-tune，不是 prompt 复制，文件夹本身 = 技能包。

加工增量：讲师按”先讲是什么 → 再讲怎么用”的顺序展开，我把它倒过来重写为”先讲为什么必须是文件夹”，因为如果不先想清楚”上下文为什么会爆”这一点，后面”先加载元数据”这套机制就纯属凭空规定。

2.2 SKILL.md 三段式（核心）

这是整集最重要的一个对象。它同时是元数据、是索引、是入口——讲师在前几集里换了三个词，其实指的是同一个 markdown 文件。

① YAML frontmatter 两个必填字段

  • name：唯一 ID。只能用小写字母 + 数字 + 连字符，≤64 字符。是这个技能在 Agent 里的身份证。
  • description：≤1024 字符。这是分诊台——Agent 决定何时调用这个 Skill，靠的就是它。description 写废了，Agent 就永远找不到入口。

讲师贴了一组对照：

低效：”该 Skill 可处理 PDF 和文档相关事务。”

高效：”全面的 PDF 处理工具，支持文本/表格提取、创建新 PDF、合并/拆分文档及表单填写。当 Claude Code 需要批量处理或分析 PDF 文档时触发，适用于文档工作流及批量操作场景。不支持简单查看或基础格式转换。”

差别在哪？高效版本写齐了三件套：做什么 + 何时触发 + 不支持什么。

加工增量：讲师的口播只反复强调”细节要丰富”。我把它压成”功能 + 触发场景 + 边界”三要素——尤其”边界”那条往往被忽略：写明”不支持什么”，就是在帮 Agent 拒绝错误的派单，避免本来该让别的 Skill 处理的请求被你这个 Skill 抢走然后翻车。

② 执行步骤 vs ③ 指令结构——这两个一开始我混了

执行步骤 指令结构
维度 横向（时序） 纵向（每条指令的字段规约）
长什么样 “先 A，再 B，再 C” “做这件事时，入参怎么传/参考哪份文档/出错怎么办/返回什么 JSON”
例子 理解中文 → 调 execute_api.py → 返回 JSON API 文档要先读、入参类型约束、优先级（最短行驶距离）、协议、JSON 模板、错误处理

讲师推荐的”指令结构”六段式模板：概述 / 前置条件 / 执行步骤 / 示例 / 错误处理 / 局限说明。

注：这个六段式截图来自他自己整理的 Untitled-1，不是 Claude Code 文档原文，待 10-7 看代码确认（见 §3）。

2.3 SKILL.md 之外，文件夹里还有什么

子目录/角色 放什么 谁来吃
脚本 可执行文件，目前只支持 Python；未来可能扩展 shell / C++ / JAR Agent 直接 invoke
指令 已写好的代码文件 Agent 直接调用
资源 md / txt 的样例数据、说明文档、模板（examples.md / reference.md / template.txt） 正文里出现引用时按需拉
外部文件 一个 md 里贴外部链接 当成资源处理

讲师反复用 imooc-trip-manager（路线规划）做例子：脚本是 execute_api.py，资源是百度地图 API 文档和 JSON 模板。

2.4 可移植性是”结果”，不是”目的”

很多人把”可移植”当 Skills 设计的目标。讲师的意思其实更狠：因为采用了”文件夹”这种粒度，可移植自动成立。

A 智能体装载了路线规划技能 = A 的工作目录下有 imooc-trip-manager/ 这个文件夹。把整个文件夹拷给 B 智能体 → B 立刻拥有同款技能。不是 prompt 复制，不是 fine-tune，是文件系统级别的能力转移。

3. 没 get 的点

  • “指令”在 Claude Code 文档里叫什么？ 讲师中文一直说”指令”，但 Claude Code 文档示例的小节标题是 ## Instructions / ## Examples。中文”指令”到底对应 instructions 这个一级 section，还是”指令结构”里那种 <file>reference.md</file> 引用语法？10-7 看代码确认。
  • 调用 execute_api.py 怎么变成进程？ 在 markdown 里写一句文本字符串，Claude Code runtime 是用 Bash 工具看 .py 后缀就启 Python 解释器吗？是否必须配合 allowed-tools 声明 Bash(python:*)？
  • description 的”相匹配”是基于什么？ 讲师说”提示池跟描述匹配就调用”。这个匹配大概率不是向量检索，而是 LLM 直接读所有已装载 Skill 的 description 自行决断（因为只有 SKILL.md 在上下文里），但需源码确认。
  • name 是全局唯一还是目录内唯一？ 跨 Agent 拷文件夹时会撞名吗？
  • 六段式（概述/前置/步骤/示例/错误处理/局限）是 Claude 官方还是讲师自创？ 截图是他自己的 Untitled-1，不是 Claude Code 文档截图，待验证。
  • 脚本未来扩展非 Python 时，runtime 用什么判断解释器？后缀名还是 shebang？

5. 知识地图

6. 自测题（5 卡）

Q1：description 字段最重要的作用是什么？字符上限是多少？

A1：充当分诊台——Agent 通过它判断何时该调用这个 Skill。上限 1024 字符。一个合格的 description 至少要写清”做什么 + 何时触发 + 不支持什么”。

Q2：”执行步骤”和”指令结构”有什么区别？

A2：执行步骤是横向时序（先 A 再 B 再 C，固定 SOP）；指令结构是纵向规约（每条指令要约束哪些字段——参考文档、入参规范、优先级、调用协议、返回模板、错误处理、示例）。一个回答”按什么顺序做”，一个回答”每一步要遵守什么”。

Q3：为什么 Agent 不会一次性加载整个 Skills 文件夹？只加载哪个文件？

A3：因为整个文件夹可能很大（脚本、文档、样例都在里头），全量加载会爆上下文。Agent 只加载 SKILL.md——它既是元数据也是索引，正文里写到要用 examples.md / execute_api.py 时，再按需把对应文件拉进上下文。

Q4：把 A 智能体的 imooc-trip-manager/ 整个拷给 B 智能体，B 能立刻具备同款路线规划能力吗？这背后的设计前提是什么？

A4：能。前提是 Skills 采用了”文件夹”作为粒度——技能 = 文件系统的目录树，不是 prompt，也不是模型权重。所以拷文件夹 = 转移能力，是文件级别的可移植。

Q5：name 字段的命名规则是什么？为什么这么严？

A5：只能用小写字母 + 数字 + 连字符，≤64 字符。严格规则是因为 name 是这个 Skill 的唯一 ID——会被用作目录名、Agent 内部标识、跨 Agent 复用时的引用键，所以不能有空格、大写、特殊符号这类容易出歧义的字符。

7. 关键词表

术语 一句话解释
SKILL.md Skills 文件夹的唯一入口，同时充当元数据/索引/正文宿主，是 Agent 优先加载的那一个文件。
YAML frontmatter SKILL.md 顶部 --- 包裹的元数据段，承载 name / description 两个必填字段。

description Skill 的分诊台描述。≤1024 字符，必须写清”做什么 + 何时触发 + 边界”。
执行步骤 SKILL.md 正文的横向时序段——固定 SOP，”先 A 再 B 再 C”。
指令结构 SKILL.md 正文的纵向规约段——每条指令的字段约束（文档/入参/优先级/协议/模板/错误处理）。
