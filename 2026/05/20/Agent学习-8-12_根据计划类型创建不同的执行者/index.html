8-12_根据计划类型创建不同的执行者

发表于2026-05-20|更新于2026-05-20|Agent学习第8章 Jmanus 懂思考、会规划、一步步动手完成任务。
|浏览量:

1. 一句话定位

PlanningCoordinator.executePlan() 把上一集创好的 plan 从 ExecutionContext 里掏出来，丢给 PlanExecutorFactory，工厂读 plan.getPlanType()、走一个 switch，按 simple / advanced 分别 new 出 PlanExecutor 或 MapReducePlanExecutor——这就是计划执行子系统的入口分派。

2. 主体

2.1 从协调器三阶段说起

你在 8-11 已经知道，PlanningCoordinator 这个类里挂着三个域成员：planCreator / planExecutorFactory / planFinalizer，分别对应计划的创建 / 执行 / 结束三段生命周期。上一集拆的是 createPlan(ExecutionContext) 这个方法，里面只干了一件事——把 LLM 返回的 plan 写进 context.setPlan(...)。

这一集换 executePlan(ExecutionContext)。打开它，你会看到这种骨架：

加工增量：讲师在视频里先讲了 createPlan 是上一集，再讲 executePlan 也调 createPlan——容易绕。实际上 executePlan 是”完整链路”，它内部又调了一次 planCreator.createPlan(context)；而 createPlan(context) 是”只造不执行”的纯净版。两个公共方法共享同一个 PlanCreator，对外暴露不同粒度。所以你在协调器里看到两个 createPlan 调用，不是 bug 是双入口设计。

2.2 工厂里到底发生了什么

点进 PlanExecutorFactory.createExecutor(plan)，剥掉判空和 DirectResponse 分支（讲师明说”先不管”），核心就 10 行：

三件值得盯住的事：

  • planType 字段不是协调器加的，是 LLM 在 8-11 创建计划时塞进 JSON 的——所以工厂这边只读不写。
  • simple 既是默认也是异常兜底：null、空串、未知值，三种情况统统落到 PlanExecutor。
  • switch 的两个 case 名字（simple / advanced）和返回类名（PlanExecutor / MapReducePlanExecutor）不对称——advanced 这条分支的真名是 MapReduce。命名暴露了实现范式：复杂计划走的是”拆→并→合”，不是顺序执行，所以才必须独立一个 Executor 类。

2.3 锚图：工厂派单一张图

t=480.5s 那张架构图（frames/f055_t0480.5s_scene.jpg）把这件事画得最清楚：

  • 上半部分还是 8-11 的”PlanCreator → 请求 LLM → 创建计划”
  • 下半部分新长出一块 planning/executor/factory/PlanExecutorFactory，箭头标着”根据 计划类型”，指向”计划执行对象”

到了 t=601s（frames/f065_t0601.1s_scene.jpg），这个”计划执行对象”被进一步炸开成两条分支：

  • 计划类型=简单 → planning/executor/PlanExecutor
  • 计划类型=复杂 → planning/executor/MapReducePlanExecutor

把这两张图按时间叠在一起，本集 7 分钟讲的事就是这一个”由 1 变 2”的展开动作。

3. 没 get 的点

  • plan.isDirectResponse() 这个判断条件是 LLM 在 plan JSON 里写好的字段，还是代码事后做的某种检查？讲师明说”先不管”。
  • executeAllSteps(context) 这一行往下展开，simple 和 advanced 的循环结构到底差多少——是步骤数量级的差异还是执行模型级的差异？等后续集。
  • planType 除了 simple / advanced 还有没有别的合法值？现在代码里只有这两个 case，但 default 分支的存在暗示讲师可能预留了扩展（hierarchical / DAG / …）。
  • context.setUseMemory(true) 跟 createPlan 里 setUseMemory(false) 形成对称——这个 Memory 开关到底关掉了什么，能不能跨集看清？

4. 跟其他集的连接

  • 上承：[8-11] 计划”创建”——PlanCreator 把 LLM 返回的 plan（含 planType 字段）写入 ExecutionContext。本集是 8-11 把字段写好后的”读出 + 分派”。再上承 3-12 多 Agent 五步骨架，”执行计划”对应骨架里的执行阶段。
  • 下启：下一集大概率拆 PlanExecutor.executeAllSteps() 的内部循环（单步执行、工具调用、Memory 写入）；再下一集拆 MapReducePlanExecutor 的拆分 / 并发 / 归并；最后才轮到 planFinalizer 和本集跳过的 direct response 分支。
  • 横向：
    • 跟 7-13 的 FlowAgent 三子类（Parallel / Sequential / LlmRouting）同源——都是”按类型选执行策略”，区别是 FlowAgent 在 builder 时就编排好，PlanExecutorFactory 是运行时按 plan 字段动态选。
    • 跟 6-7 的 ReactAgent.builder() 是反例：那边声明式编排（开发者写死 subAgents），本集运行时分派（LLM 决定 planType，工厂查表）。
    • “工厂方法 + switch” 这套写法跟 4-15 的 “name 一致性 + AgentCardProvider 接口注入” 同一家族——都用一个间接层把”具体实现”从调用方剥离。

6. 自测题

  1. PlanningCoordinator 里同时存在 createPlan(context) 和 executePlan(context) 两个方法，它们的关系是什么？为什么 executePlan 内部还要再调一次 planCreator.createPlan(context)？
  2. plan 的 planType 字段是谁、在哪一步写进去的？工厂是只读还是会修改它？
  3. 工厂的 switch 一共有几条分支会落到 PlanExecutor（simple 执行者）上？分别是哪三种输入情况？
  4. 为什么 advanced 分支返回的类叫 MapReducePlanExecutor 而不是 AdvancedPlanExecutor？这个命名暴露了什么实现细节？
  5. 本集明确跳过的 isDirectResponse 分支属于计划生命周期的哪一段？由谁负责生成最终回答？
