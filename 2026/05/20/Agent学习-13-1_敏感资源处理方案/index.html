13-1_敏感资源处理方案

发表于2026-05-20|更新于2026-05-20|Agent学习第13章 旅游规划优化，监控，部署
|浏览量:

1. 一句话定位

把”散落在代码里的 API key / MCP 地址”按 .env → application.yml → Properties.java → @Resource 注入 这条链路抽出来，顺手把 commons 里所有 static 工具方法改成实例方法——这是整章项目优化的开场。

2. 主体

你为什么不能继续把 key 写死

AgentUtils 里之前写的 static String API_KEY = "sk-..."——提交到 git 就泄露，换密钥要改代码，多人协作时每个人本地的密钥还不一样。前面 11~12 章先把功能跑通，本集开始还技术债，第一个动的就是机密外置。

三层链路怎么搭

整条链路是这样三步走，每一步换一种文件、换一种语法：

第一层：.env（项目根目录，明文 KEY=VALUE）

帧 f005 里 .env 只有 3 个变量：

加工增量：消化稿里指出来——视频帧 f011 的 yml 里实际还引用了 BAIDU_MAP_ADDR，但帧 f005 的 .env 里没截到，讲师一笔带过了。你自己照抄时记得把 BAIDU_MAP_ADDR 也补进 .env，否则 mcp.baidu_map_addr 占位符解析不出来。

IDE 会把 .env 显式标成 plain text（帧 f005 顶上那行 “This file was explicitly re-assigned to plain text”），不是 properties，不进 classpath。

第二层：application.yml（每个 agent 模块各一份）

manager_agent / routeMaking_agent / tripPlanner_agent 三个模块的 application.yml 都要做两件事：

optional:file:.env[.properties] 这一行是关键——它告诉 Spring：”把项目根目录下的 .env 当 properties 文件挂进 Environment，缺了也别报错”。[.properties] 是把 .env 当 properties 格式解析的提示。

帧 f011 里讲师强调”不要忘了这个，不要的话它不知道 .env 文件的存在”——意思是每个模块都得自己写一遍，不是项目级一次性配置。三个 agent 模块漏写一个，那个模块启动时 ${VAR} 就解析不出来。

第三层：commons/conf/Properties.java（聚合 + 暴露 getter）

帧 f016 把这个类的全貌摆出来：

@Configuration 让 Spring 把它当 Bean 装配，@Getter 是 Lombok 自动生成 getAlibabaDashscopeKey() 这种 getter，@Value("${...}") 从 Environment 里拉值——拉到的就是上一层 yml 里转手过来的 .env 值。

commons 为什么没有自己的配置文件

这是第一遍最容易卡的点。commons 模块里没有 resources/ 目录，也就没有自己的 application.yml。但 Properties.java 用 @Value("${agent.model_name}") 又明明在读配置——读的哪份？

答：commons 是被 manager_agent 这种宿主模块作为 Maven 依赖装配的。运行时只有一个 Spring 进程，Environment 是宿主模块的 Environment，commons 的 Bean 拿到的就是宿主的那一份。这是 Spring “一份 BeanFactory 走天下”的副作用——库代码不需要自己带配置文件，跟着宿主走。

消费端：@Resource + 实例方法

帧 f020 / f021 看 AgentUtils 怎么用：

最大的隐藏成本：祛 static

帧 f024 的注释——“从配置中读取敏感资源，不能使用 static“——这一行是本集最贵的一句话。

之前所有 AgentUtils.xxx(...) 这种 static 工厂方法都得改写：

  • 类加 @Service
  • 方法去 static
  • 字段 @Resource private Properties properties;
  • 所有调用方从 AgentUtils.xxx() 改成 @Resource AgentUtils agentUtils; agentUtils.xxx()

为什么？@Value 注入发生在 Spring 实例化 Bean 时机，static 字段没有实例上下文，注入根本不会发生，properties 会是 null。这是一个全局回滚动作——影响面比 .env 本身大得多。

3. 没 get 的点

  • .env 在 jar 包/docker 里还能被 file:.env 找到吗？file: 用的是工作目录相对路径，IDE 里跑 ok，但打成 jar 后 java -jar 的工作目录就是 jar 所在目录，挂到容器里又得看挂载点。生产环境多半要换成 classpath 或 K8s ConfigMap/Secret。
  • 三个 agent 模块各自启动时都会去加载根目录 .env——它们是同一个 Spring 进程还是三个？如果是三个独立进程，工作目录都得能定位到同一个 .env，开发机上跑同一个项目 OK，分别部署时就要各自带一份。
  • Properties 类名和 java.util.Properties 撞了——同一个文件里如果还要用 JDK 的 java.util.Properties，必须写全限定名。讲师为什么不叫 AppProperties 或者干脆用 @ConfigurationProperties(prefix = "agent") 一次性绑定整个前缀？后者更省字段。
  • optional: 前缀去掉会怎样？团队成员第一次拉代码、本地还没建 .env，启动会不会直接挂？带 optional: 是缺文件不报错（但 ${VAR} 占位符会解析失败，启动还是会挂在另一处）。

6. 自测题

  1. application.yml 里 spring.config.import: optional:file:.env[.properties] 这一行，optional:、file:、[.properties] 三段各自的作用是什么？少写哪一段会出什么状况？
  2. 为什么 commons 模块没有 resources/application.yml，它里面的 Properties.java 却能用 @Value("${agent.model_name}") 正常注入？
  3. 之前 AgentUtils.getReActAgentBuilder(...) 是 static 方法，本集为什么必须改成实例方法？把它继续保留为 static 会在运行时观察到什么现象？
  4. .env 里有 BAIDU_MAP_KEY=xxx，application.yml 里写 baidu_map_key: ${BAIDU_MAP_KEY}，Properties.java 里 @Value("${mcp.baidu_map_key}")——这三处的 key 命名规则不一样，三段是怎么对应上的？
  5. manager_agent、routeMaking_agent、tripPlanner_agent 都要在各自 yml 里写一遍 spring.config.import 才能读到 .env。如果想让它”项目级生效一次就够”，从 Spring Boot 的视角看为什么做不到？

7. 关键词表

术语 一句话解释
.env 文件 项目根目录的明文 KEY=VALUE 文件，IDE 标为 plain text，不进 classpath
spring.config.import yml 里把外部文件挂进 Environment 的入口，optional:file:.env[.properties] 形式，每个模块单独写一遍
占位符链路 .env 的 KEY → yml 用 ${KEY} 引用 → Java 字段 @Value("${前缀.key}") 注入，三层串联
Properties 配置类 commons.conf.Properties，@Configuration + @Getter 的聚合 POJO，集中暴露 getter
@Value 与 static 互斥 Spring 注入只在 Bean 实例化时生效，静态字段拿不到值，必须改实例方法
commons 无 resources commons 作为依赖被宿主装配，跟宿主进程的 Environment 走，自己不需要 yml
三层敏感资源 DashScope API Key（LLM）+ 百度地图 MCP 地址和 Key（外部 MCP Server）+ 模型名（非敏感同处理）
模块级 import 开关 spring.config.import 是模块级而非项目级，三个 agent 模块各自漏写都会让该模块读不到 .env
