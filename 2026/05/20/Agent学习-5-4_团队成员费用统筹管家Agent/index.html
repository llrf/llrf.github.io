5-4 团队成员：费用统筹管家Agent

1. 一句话定位

这是你团队的第三位也是最后一位被显式定义的员工——把 5-1 拆解图里**整个下半部分（4 个费用相关节点）**全部归并给一个 Agent 承包，并且在结尾偷偷剧透了一个”框架默认提供”的汇总 Agent。

2. 主体

2.1 先看归并：为什么 4 个需求点合并成 1 个 Agent？（取舍出现在 §2.1）

5-1 拆解图的下半部分一共有 4 个虚线挂载点等着接 Agent：

  • 交通费用计算
  • 景点费用计算
  • 住宿费用计算
  • 监控折扣

你完全可以给这 4 个节点各起一个 Agent，但这里做的是反方向的取舍——4 个节点全部连到同一个费用统筹 Agent。判据还是 5-3 那条铁律：”已有能力清单能覆盖，就不开新 Agent”。前 3 个节点共享”数学计算 + 表格输出”，最后一个监控节点共享”网络抓取 + 脚本制作”——能力上互不打架，归并成本最低。

这条取舍值得记一笔：颗粒度没有铁律，纯粹按”职责能否被同一套能力清单完成”来定。路线规划 Agent 有 3 条能力，行程规划 Agent 有 5 条能力，费用统筹 Agent 有 4 条能力——数量差异完全是被职责拉出来的，不是设计美学。

2.2 再看异构性：4 条能力横跨三类工具

费用统筹 Agent 的 4 条能力其实是三类完全不同的东西：

类别 能力 落地猜想
计算类 数学计算 @Tool 注解的方法（呼应 4-13）
输出类 表格制作 跟行程规划 Agent 重叠
IO 类（被动） 网络抓取 大概率走 MCP
IO 类（主动） 脚本制作（定时） @Scheduled 或 cron

“数学计算”被单列你可能会觉得多余——LLM 自己不就会算 1+1 吗？这里的潜台词是 “别让 LLM 自己估算总价，必须走工具”，呼应 3-7 Agent Skills 那套”该外挂的别让大脑硬算”。让 LLM 心算总价 = 把幻觉风险塞进结算单。

最反直觉的是脚本制作这一条。”脚本”不是写代码意义上的脚本，而是定时脚本——cron 类的周期触发器。监控优惠券发放不是来一个请求算一次，而是后台得有人盯着。这条能力把费用 Agent 从”被动算账员”提升到”主动监控员”，是它独有的能力，前两个员工都没有。

2.3 角色定义：注意那段被临时追加的话

角色定义的最终形态：

计算住宿、交通、饮食、景点的费用，统计出详细的费用明细以及总费用，监控优惠券的发放

后半段加粗的部分是临时追加的——前半段写完觉得不够，又把”监控优惠券的发放”补上。这条编辑痕迹有信息量：角色定义不是一次性写完的，它会随着你想清楚”还有什么职责”而生长。如果你也在为自己的 Agent 写角色定义，别强求一次写完。

2.4 优惠券监控的边界扩展（加工增量在 §2.4）

5-1 那集里”监控折扣”听起来只针对住宿 + 餐饮（变动费用）。这一集明确监控对象是优惠券发放——这是一个更广义的概念：

  • 5-1 的口径：住宿打折、餐饮折扣
  • 5-4 的口径：优惠券（含景点门票券、交通优惠码、住宿折扣等）

这是这一集对 5-1 的隐式修正——折扣不只是”商家自降价格”，还包括”发放可使用的券”。这条概念升级在原视频里没有显式说明，但你从角色定义文字（监控优惠券的发放）和虚线连接节点的语义对比可以推出来。

2.5 三人组到齐

到此 5-1 拆解图所有需求节点都有 Agent 接管：

  • 路线规划 Agent（5-2）
  • 行程规划 Agent（5-3）
  • 费用统筹 Agent（5-4）

5-2 / 5-3 / 5-4 是同一套两段式岗位说明书（角色定义 + 能力清单）的三次套用。三次写完，你应该能闭眼默写这个模板。

2.6 隐藏的第四个 Agent：汇总 Agent

视频末尾抛了个伏笔：还有第四个 Agent——汇总 Agent，负责把三个员工的产出合并成”包含文字、图片、表格的本地文档”。注意这里有一处临时纠错：

“这个表格不是表格是文档”

口径修正：产出物是文档（文字 + 图片 + 表格的复合体），不是单纯的 Excel。未来代码大概率走 docx / markdown 生成，不是 xlsx。

更关键的剧透是”这个应该是在我们后面的一个框架，它会默认提供这个汇总的智能体，所以这里就不单独列出来了”——这是白盒提示：5-5 之后的代码里大概率不用自己写主管 / 汇总，SAA 1.1 的 graph framework（DAG Graph）自带这个能力。对应 4-9 提到的”1.1 三大核心标签”里 DAG Graph 那条。

3. 没 get 的点

  • “数学计算”具体落地是哪种工具？SAA 1.1 有没有内置 calculator？还是自己写 @Tool？大概率自写，但不排除有现成 MCP。
  • “脚本制作（定时）”是 Agent 在运行时生成并执行脚本，还是开发者预先用 @Scheduled 注册好定时任务？前者更”agent”，后者更”工程化”，倾向后者。
  • “网络抓取”用来监控优惠券——具体抓哪个站？携程？美团？5-6 是百度地图 MCP，跟优惠券不直接相关，可能是另一个未提到的 MCP。
  • “汇总 Agent 由框架默认提供”——是指 SAA 1.1 graph framework 的某个内置节点，还是 JManus 的某个特性？等 5-5 确认。
  • 4 个费用节点全合并到 1 个 Agent——同一个 ReactAgent 既要算账又要爬虫，prompt 会不会拉扯？这是颗粒度的反思题。

4. 跟其他集的连接

  • 上承：5-1 拆出的费用横切关注点 + 监控折扣定时任务（本集是 5-1 下半部分的归并实现）；5-2 / 5-3 同一套”角色定义 + 能力清单”模板的第三次套用。
  • 下启：5-5 Agent 团队和大模型的无缝协作——三个员工 + 一个汇总 Agent 接到主管下面，主管派单 / 汇总两步骨架，对应 3-12 的多 Agent 五步骨架；脚本制作能力（定时监控）的实现大概率绕开 LLM，直接用 Spring 的 @Scheduled 或独立 cron。
  • 横向：3-9 主管 + 专科 Agent——本集”4 节点合并到 1 Agent”是颗粒度归并的极端例；3-12 多 Agent 核心执行流程里那个隐式的”主管 / 汇总”——本集讲师明说”框架默认提供”，对应 SAA 1.1 的 DAG Graph（4-9 提到过）；4-13 ReactAgent + @Tool——本集的”数学计算”和”脚本制作”未来落地就是 @Tool 注解的具体方法；3-7“该外挂的别让大脑硬算”——对应本集”数学计算”必须单列工具。

5. 知识地图

6. 自测题（5 卡）

  1. 5-1 拆解图下半部分有 4 个费用相关节点。这一集为什么选择全部归并到一个 Agent，而不是开 4 个 Agent？归并判据是什么？
  2. 费用统筹 Agent 的 4 条能力清单分别属于哪三类？为什么”数学计算”要被显式单列（LLM 不是自己会算吗）？
  3. “脚本制作”在这里指什么？为什么这条能力把费用 Agent 从”被动算账”升级成”主动监控”？前两个员工为什么不需要这条能力？
  4. 角色定义里”监控优惠券的发放”这半句是临时追加的——这条编辑痕迹告诉你写角色定义时的什么经验？
  5. 视频结尾提到的”汇总 Agent”为什么不单独画？讲师说”框架默认提供”，指的是 SAA 1.1 的什么能力？这条剧透对 5-5 意味着什么？
