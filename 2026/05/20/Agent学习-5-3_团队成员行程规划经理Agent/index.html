团队成员：行程规划经理Agent

1 · 一句话定位

延续 5-2 的”角色定义 + 能力清单”两段式模板，给团队的第二位员工——行程规划 Agent 写岗位说明书；同时用一根虚线把这一位 Agent 同时挂到”景点推荐”和”餐饮推荐”两个需求节点上，落地了 3-9 提的”专科 Agent 颗粒度”问题。

2 · 主体

2.1 先看复用关系：一份说明书覆盖两个需求（加工增量在 §2.1）

你打开 5-1 那张需求树会看到：旅行规划下面挂着”景点推荐”和”餐饮推荐”两个并列子节点。直觉是给每个子节点配一个 Agent——餐饮 Agent、景点 Agent 各一个。

这集给的答案是反直觉的：两个节点共用一个行程规划 Agent，画布上用两根虚线指过去。

判据不是”需求节点数 = Agent 数”，而是”已有 Agent 的能力清单能不能覆盖这两个节点”。景点推荐要的是”按偏好+天气挑地方+给理由+配图+排日程”；餐饮推荐要的也是”按偏好挑餐厅+给理由+排到日程里”——能力同构，就合并。这也解释了为什么后面 5-4、5-5 始终没出现”餐饮 Agent”。

记住这条判据，你以后画自己的多 Agent 系统就不会盲目按需求树 1:1 开 Agent。

2.2 路线 Agent vs 行程 Agent：别被中文同义词坑了（取舍出现在 §2.2）

中文里”行程规划”和”路线规划”几乎是同义词，但这门课把它们拆成两个独立 Agent。一年后你看代码里两个 ReactAgent 名字相像，先确认这道分工边界：

路线规划 Agent（5-2） 行程规划 Agent（5-3）
关心什么 几何 内容
输入 一串地点 一个目的地 + 用户偏好 + 时间
输出 最优路径、距离、地图可视化 推荐去哪儿、为啥推、配图、按天排表
能力 地点搜索、经纬度转换、距离计算、地图可视化 网络搜索、抓文本+图、天气、本地文件、表格

这里有个明显的取舍：完全可以做成一个大 Agent 把所有能力堆在一起，但讲师把”几何能力”和”内容能力”拆开了——单 Agent 工具一多 LLM 的工具选择质量会下降，工具少的专科 Agent 调用准确率高。代价是后续要做 Agent 间通信（5-5 才讲），把两位的产出拼起来。

2.3 角色定义：一句话身份

行程规划 Agent 的角色定义比路线 Agent 那句长，因为内容编排比几何计算复杂：

根据目的地给出行程安排，包括根据用户偏好以及天气状况，推荐景点，提供理由以及提供景点图片，并且制定详细的行程安排。

要拆出来五个关键词，你后面对照能力清单就一一对应：

  • 目的地 → 输入参数
  • 用户偏好 → 需要读本地文件
  • 天气状况 → 需要天气查询
  • 推荐景点 + 理由 + 图片 → 需要网络搜索 + 抓文本 + 抓图
  • 详细的行程安排 → 需要表格输出

角色定义不是文学修辞——它是把能力清单倒推出来的”需求陈述”。

2.4 能力清单 5 项：每一项对应一个工具坑

接下来这张图是这一节的终态，你以后回看脑子里就靠它：

逐项过一遍，备注你以后落地代码时大概要做什么：

  1. 景点信息的网络搜索 —— 调搜索引擎/地图 API，找候选景点。落地大概率走 4-5 的 @Tool 自写 + 4-13 的 .tools(...) 注入，或者接 5-6 要出现的百度地图 MCP。
  2. 抓取网络文本信息，以及抓取图片 —— 推荐”提供理由”需要爬评论/简介；”提供图片”需要把图抓下来。这是两类爬虫工具，对应”理由+配图”两个产出形态。
  3. 天气查询 —— 角色定义里”天气状况”的入口。能力清单上看不出来接的是自写 @Tool 还是外部 MCP，待 5-6 揭晓。
  4. 本地文件的操作 —— 反直觉的一项。讲师的逻辑是”用户偏好要持久化”（比如”我不爱爬山”写在本地文件里），Agent 得能读这个文件。这其实把 3-7 Agent Skills 的”文件配置赋能”思路用到了产品功能层。
  5. 表格制作 —— 输出格式能力。大概率不是真”表格工具”，只是 prompt 里要求 Markdown 表格输出。但从 Agent 视角看，输出 schema 本身也算一种”工具”。

比路线 Agent 多出来的两条是 2 和 4——网络抓取（文本+图）和本地文件操作，因为内容型推荐比纯几何计算要多一层”质性数据”。

2.5 操作收尾：把虚线连回需求图

把这个 Agent 的框画好后，画布上还差一步：

  • 从”景点推荐”需求节点拉一根虚线到行程规划 Agent
  • 从”餐饮”需求节点也拉一根虚线过去

虚线的语义：这是”复用关系”，不是”实线主调用链”。一年后你看到画布里某个 Agent 框有多条虚线进来，第一反应就是”这是个被复用的专科 Agent”。

3 · 没 get 的点

  • “天气查询”具体接哪个工具？ 是 4-5 自己写的 @Tool，还是后面 5-6 百度地图 MCP 提供的？这集只写在能力清单里，代码侧没落地。
  • “抓取网络文本信息和图片”会用 MCP 现成的爬虫服务，还是自己写 ReactAgent 工具？ 怀疑后面会接到某个开放 MCP（爬虫类的开放 MCP 很多），但本集没明示。
  • “本地文件操作”对应的是不是 Claude Code 风格的 Read/Write 工具？ 还是 Spring 这边另有封装？等 5-x 落地代码时再回填。
  • 表格制作是不是只是 prompt 里要求 Markdown 表格输出？ 大概率是前者——并不是真有”表格工具”，只是输出格式约束。但讲师把它单列成一条能力，说明在他的世界观里”输出 schema 也算工具”。

4 · 跟其他集连接

  • 上承：5-1 拆出的需求树（旅行规划 → 景点/餐饮等子节点）是这集挂虚线的对象；5-2 立的”角色定义+能力清单”两段式模板被本集原样复用。
  • 下启：[5-4] 会写第三个团队成员（费用统筹管家 Agent），继续同模板；[5-5] 把 5-2/5-3/5-4 三个专科 Agent 挂到主管 Agent 下面，才进入”多 Agent 协作”阶段；代码落地要回看 4-5/4-6 的 @Tool 注册和 4-13 的 ReactAgent.builder().tools(...)。
  • 横向：3-9 的”专科 Agent 颗粒度”问题在这集得到具体回答——一个 Agent 管多个需求节点是允许的，判据是能力清单覆盖度；3-7 的”文件配置赋能”思想在”本地文件操作”这条能力上重现；和 3-12 的”多 Agent 五步骨架”一比，这集还停在”定义专科 Agent”阶段，还没到通信/中间结果。

5 · 知识地图

6 · 自测题（5 卡）

  1. Q：旅行规划下的”景点推荐”和”餐饮推荐”是两个并列需求节点，按 1:1 应该开两个 Agent，但这集只开了一个，判据是什么？
    A：判据是”已有 Agent 的能力清单能不能覆盖这两个节点”。能力同构（按偏好挑+给理由+配图+排日程）就合并，画布上用虚线把同一个 Agent 连到多个需求节点。需求节点数 ≠ Agent 数。

  2. Q：路线规划 Agent 和行程规划 Agent 名字相像，分工边界在哪？
    A：路线 = 点到点的几何（地点搜索、经纬度、距离、地图可视化）；行程 = 内容编排（推荐去哪、为啥推、配图、按天排表）。前者输出路径，后者输出推荐+日程表。

  3. Q：行程规划 Agent 的能力清单 5 项是哪 5 项？比路线 Agent 多出来的两类是什么？
    A：① 景点信息网络搜索 ② 抓取网络文本+图片 ③ 天气查询 ④ 本地文件操作 ⑤ 表格制作。比路线 Agent 多出来的两类是”网络抓取（文本+图）”和”本地文件操作”——因为内容型推荐要”提供理由+配图”，光靠地理坐标不够。

  4. Q：”本地文件操作”作为 Agent 能力很反直觉，它是用来干嘛的？呼应哪一集的思想？
    A：用来读用户偏好的持久化数据（比如”我不爱爬山”写在本地文件）。呼应 3-7 Agent Skills 的”文件配置赋能”——把领域知识/用户偏好写成文件让 Agent 读，而不是塞进 prompt。

  5. Q：画布上一个 Agent 的框有两条虚线分别连到”景点推荐””餐饮”两个需求节点，虚线的语义是什么？
    A：复用关系——同一个 Agent 同时承担多个需求节点。虚线区别于实线主调用链，看到虚线就知道”这是个被复用的专科 Agent”。
