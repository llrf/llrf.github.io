6-11_MCP客户端连接MCP服务端

发表于2026-05-20|更新于2026-05-20|Agent学习第6章 多 Agent + ReAct架构，SpringAi迈入Agent新时代
|浏览量:

1. 一句话定位

把上一集那个还只是”启动成功”的 MCP 服务端，第一次真正接上一个由你自己写的 Spring AI 应用——pom 加两个依赖、yml 写一段 sse.connections、再补一行文档没写的 enable: true，就完成了 MCP 协议层的握手。

2. 主体

2.1 客户端到底”长”在哪里

你打开 IDEA 看到两个工程并排：左边 Demo-MCP/mcp-server（上集那个，跑 8081），右边 Demo-SpringAi（4 章那个调 DeepSeek 的壳，跑 8080）。MCP Client 不是新开项目，它就写在 Demo-SpringAi 里。

理由很自然：客户端的责任是对外承接用户请求、对内连 MCP Server。承接用户请求的入口本来就是 ChatController 那一侧，所以 MCP Client 必须长在 ChatClient 应用里——它不是独立角色，是”大模型应用 + 一段连接配置”。

这也解释了为什么客户端进程跑 8080（Tomcat，web 给用户用），服务端进程跑 8081（Netty，给 client 用）：两个 Spring Boot 进程、两套 web 框架栈、两个端口，同 IDE 同时运行。

2.2 pom 的”上下两段”：BOM 在上，依赖在下

先看服务端 pom 是怎么写的（参考对照）：dependencyManagement 里有两个 BOM——spring-ai-alibaba-bom（管 SAA 自己）+ spring-ai-bom（管 spring.framework.ai 体系）。dependencies 里则放真正引入的 spring-ai-mcp（底层依赖）+ spring-ai-starter-mcp-server-webflux（SSE 服务端实现）。

为什么 BOM 要引两遍？因为 spring-ai-mcp 这个底层依赖归属 org.springframework.ai，不属于 spring-ai-alibaba 包。只引 SAA 的 BOM 兜不住它的版本，必须把 spring-ai-bom 也独立 import 进来。这是客户端 pom 第一段要做的事，和服务端完全一样。

2.3 客户端依赖：换后缀就行

下半段的 dependencies 节，照着服务端 SSE 那套抄，把 server 改成 client：

  • spring-ai-mcp（底层依赖，server/client 都要）
  • spring-ai-starter-mcp-client-webflux（客户端 SSE 实现，对应服务端的 -server-webflux）

整个命名是完全对称的套路——这就是 4-7 课”为什么 MCP 选 webflux”的延续：非阻塞、SSE 友好，client 端直接换 artifactId 后缀就照搬过来。

2.4 文档冗余依赖陷阱

官方文档在”基于 SSE 的 MCP 客户端实现”那段，写的依赖是 spring-ai-starter-mcp-client（没有 -webflux 后缀）。如果你照搬，再加上 webflux 版本，会发生什么？

打开右侧 Maven 面板看 Dependencies 树——spring-ai-starter-mcp-client-webflux 已经传递依赖把 spring-ai-starter-mcp-client 拉进来了，pom 里那一份会变灰提示”重复”。所以文档说的那个依赖根本不用单独引。

取舍出现在 §2.4：文档不是金科玉律，Maven Dependencies 树才是真值源。讲师亲手按文档导一遍再删掉，就是要把这个判断动作演示给你看。

2.5 yml 配置：四行四个坑

挨个拆：

  1. connections.<别名> 不是关键字——这一层 key 是用户自定义名字。文档里写的 server1 只是示例，改成服务端自报的 imooc-weather-mcp-server 更可读（运行时实际靠 url 找服务端，别名是给人看的）。

  2. url 不带 /sse/... 后缀。这跟 4-8 课用 JManus 那套连法不同——JManus 走的是 sse-message-endpoint: /mcp/sse/weather 这种自定义路径，而 SAA Client Starter 这套直接 http://host:port 就行，由 starter 内部去拼协议路径。

  3. mcp.client.enable: true 是文档遗漏字段——少了它不连接。这是讲师踩坑后补上的，需要自己记住。

  4. 端口必须是服务端 server.port 配的那个（本例 8081），别照抄文档的 8080。

加工增量在 §2.5：把 yml 的四层缩进配置拆成”键、别名、url、enable”四个独立判断点，每个都标注了”为什么这么写 / 文档怎么说 / 实际怎么填”——消化稿原文是按缩进顺序读的，这里改成按”易踩坑顺序”重排。

2.6 验证标准：握手日志（不是启动日志）

两个进程都跑起来后，启动成功 ≠ 连上。真正的验证信号是双向握手：

  • 服务端日志多出一行：
    Client initialize request - Protocol: 2024-11-05, Capabilities: ...
  • 客户端日志反向收到服务端自报家门：
    received server info: name=imooc-weather-mcp-server, version=0.0.1

这两条日志对应的是 3-4 课讲过的 MCP 协议”会话建立阶段”——上半集都是配置，这条日志才是协议层第一次真的通了。

3. 没 get 的点

  • connections.<别名> 这层 key 真的只是给人看的吗？还是 SAA 内部会按 key 去匹配服务端自报的 name？4-15 课讲过 A2A 协议里有”name 一致性铁律”，MCP 是否同理需要查 McpClientProperties 源码验证。
  • mcp.client.enable: true 还是 enabled: true？SAA 1.0.0.2 的属性名拼写需要查源码确认（视频里口述是 enable，但很多 Spring Boot 风格是 enabled）。
  • 这一集协议层连上了，但 LLM 还没用上工具。DeepSeek 是怎么知道服务端有 getTemperature / getUltraviolet 这两个工具的？要靠下一集补一段类似 chatClient.builder().toolCallbacks(...) 的桥接代码吗？
  • 客户端整体用 Tomcat（同步线程模型），但内部嵌的 MCP Client 用 WebFlux（响应式）——两套线程模型混搭会不会有问题？
  • 如果配多个 MCP Server（connections 下并列多个别名），工具清单是自动合并的吗？

4. 跟其他集连接

  • 上承：4-7 讲 MCP 为什么选 webflux，本集把同一套理由复制到 client 端，artifactId 后缀 -server-webflux 改成 -client-webflux 就行。4-6 在服务端注册的两个工具，本集让 client 第一次能去拉它们的清单。4-8 用 JManus 当 client 验证过服务端，本集把”Host=JManus”换成”Host=自家 ChatClient 应用”——这是第一次让 client 节点在代码里具象化。
  • 下启：下一集大概率讲把 MCP 工具桥接到 ChatClient——本集只跑通协议层握手，LLM 还看不见这些工具。再往后就是端到端跑通：”北京温度多少” → DeepSeek 决策 → MCP 调 getTemperature → 返回。
  • 横向：和 3-4 / 3-5 讲的”三节点架构图”形成实物对照：Host=DeepSeek 模型、Client=Demo-SpringAi 进程、Server=Demo-MCP 进程。和 4-10 形成新旧版对比——本集是 SAA 1.0.0.2 时代的写法，1.1 时代依赖名 / 配置 key 都变了。

5. 知识地图

6. 自测题

  1. 为什么 MCP 客户端不另开一个新项目，而是写在 Demo-SpringAi 里？
  2. dependencyManagement 里为什么 spring-ai-bom 必须独立 import 一遍，不能只靠 spring-ai-alibaba-bom 兜底？
  3. 文档说要导 spring-ai-starter-mcp-client，但实际开发中你会不会加这一行？怎么验证你的判断是对的？
  4. yml 里 connections.server1: 的 server1 是 SAA 关键字、是服务端 name、还是用户自定义别名？
  5. 客户端进程启动成功就算”连上 MCP Server”了吗？你看哪条日志确认握手成功？
参考答案
  1. 客户端的职责是对外承接用户、对内连 MCP Server。承接用户请求的入口是 ChatController，所以 MCP Client 必须长在调用 LLM 的那侧——它不是独立角色，是”大模型应用 + 连接配置”。
  2. spring-ai-mcp 归属 org.springframework.ai 包，不属于 spring-ai-alibaba 包，SAA 的 BOM 管不到它，必须用 spring-ai-bom 独立管版本。
  3. 不加。打开 Maven 面板看 Dependencies 树，spring-ai-starter-mcp-client-webflux 已经传递依赖把它拉进来了，再写一遍会变灰提示重复——文档不是金科玉律，Maven Dependencies 树才是真值源。
  4. 用户自定义别名。文档里的 server1 只是示例占位，运行时靠 url 定位服务端，别名只是给人读的。推荐改成与服务端 spring.ai.mcp.server.name 一致（本例 imooc-weather-mcp-server）。
  5. 不算。验证信号是协议握手日志——服务端打 Client initialize request - Protocol: 2024-11-05，客户端打 received server info: name=..., version=...，对应 MCP 协议的会话建立阶段。

术语 含义

spring-ai-starter-mcp-client-webflux 客户端 SSE 实现的 starter，与服务端 -server-webflux 命名对称。

mcp.client.sse.connections yml 客户端连接配置树，下一层是自定义别名，再下是 url；别名推荐与服务端 name 一致。
mcp.client.enable 文档遗漏字段，必须显式设为 true 才会真正连接（讲师踩坑后补的）。
