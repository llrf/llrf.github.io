学习笔记 · 3-2 困境解决方案：函数调用（Function Calling）

来源：慕课网 imooc.com，视频 3-2 困境解决方案：函数调用( Function Calling ).mp4（约 9 分钟）
本笔记基于自动化 pipeline：whisper 转录 + scenedetect 关键帧 + PaddleOCR + Claude 多模态读图。原始产物：transcript.txt / frame_index.json / frames/。

一、本集主旨

承接 3-1 留下的悬念——大模型有「无法获取实时数据」「无法拥有用户私有数据」两个致命缺陷。本集给出统一解法：让 LLM 自己根据外部 API 文档生成调用程序，去取实时数据；同样的机制也能去读用户本地文件 / 数据库。这个”自主调用外部能力”的程序就叫 Function Calling（函数调用）。

二、回顾：3-1 的”标准闭环”再次出场

视频开头 0~17 秒，讲师把 3-1 集的核心 PPT 重新放出来作为起点：

这是熟悉的”用户 → Prompt → LLM → 语义分析 → 返回”垂直闭环——之后整集所有 PPT 都从这张图演化。

加上一个气泡：”Prompt：今天气温多少度？“——立刻进入 3-1 集结尾的反例。

三、旧方案的尴尬：人工写代码调外部 API

讲师在 17~63 秒指出，3-1 之前面对实时数据问题，唯二的处理方式只有：

  1. 让 LLM 直接回答”我没有当前数据”——用户体验崩了
  2. 人工另写代码去调用外部 API，把结果反馈给 LLM——绕过 LLM 而非用 LLM

PPT 上是这么呈现的：

注意流程图底部多出来的 绿色横幅：「人工额外编写代码 调用外部 API」——红色错误横幅之下，临时叠加一块绿色补丁，视觉上就像在”擦屁股”。

讲师在此集中提出三个反问（66~149 秒）：

反问 含义
实时湿度也要专门写一个 API 吗？ 横向扩展无止境
实时股票也要专门写一个 API 吗？ 同上
API 文档变了员工还要去维护吗？ 维护成本爆炸
通过员工写代码，LLM 还叫”人工智能”吗？ 本集的灵魂拷问

隐藏论证：人工是为了弥补 LLM 的不足而存在；只要有人工介入这个闭环，LLM 就还不算”智能”。

四、新方案：让 LLM 自己写调用代码

讲师从 150 秒开始抛出本集核心思路——把”写 API 调用代码”这件事还给 LLM 自己：

PPT 在原闭环底部接出红色菱形决策块「是否需要 调用 外部信息」，再向左拉出三步法——这是讲师口述里没有完整念出来的关键 OCR 信息：

这三步是 Function Calling 的算法骨架：先判别是否需要外部信息 → 再选择 + 编写 + 调用 → 最后整合回复。

整个新方案的核心论断（讲师 165~180 秒原话）：

LLM 能够根据外部的 API 文档，自己编写这个 API 的函数，然后获取实时数据进行返回——这种才叫人工智能。

五、完整调用流程：以”深圳气温”为例

讲师用 183~273 秒走了一遍完整的时序流程，PPT 从垂直闭环切到了横向时序图——这是本集第二种视觉语言：

第 1 步：用户向 LLM 发问（183~190 秒）

时序图左到右排了三条纵向时间线——用户、LLM、第三方应用。LLM 收到 Prompt「深圳今天气温多少度？」之后自我评估：

  • 「我没有实时数据哦」——LLM 内部回应（黑底白字气泡）
  • 「去墨迹天气问问，它有天气 API」——LLM 想到了第三方

关键认知：LLM 在自己的向量空间里有一个向量指向”能查实时天气的第三方应用” ——这是 3-1 论断”没向量就答不出来”的反向利用。LLM 答不出气温本身，但答得出”该去哪里查气温”。

第 2 步：LLM 调用墨迹天气，深圳作为参数（203~261 秒）

完整时序图（自上而下）：

# 动作 方向 视觉
① 用户问”深圳今天气温多少度？” 用户 → LLM 实线红色箭头
② LLM 自述：「我没有实时数据」 LLM 内部 黑底气泡
③ LLM 自述：「去墨迹天气问问」 LLM 内部 黑底气泡
④ LLM 调用墨迹天气，将”深圳”作为参数传递过去 LLM → 第三方 实线红色箭头
⑤ 墨迹天气返回数据 第三方 → LLM 蓝色虚线 + 蓝底气泡
⑥ LLM 整合回复给用户 LLM → 用户 蓝色虚线 + 蓝底气泡

视觉密码：红色实线 = 请求方向，蓝色虚线 = 返回方向。整张图把”自主写代码 + 调用 + 整合”压缩在一页里——这是本集最高密度的图。

六、概念命名时刻：Function Calling

讲师在 281 秒处给这个流程正式起名——PPT 直接用一个变暗的时序图当背景，亮色横幅打在中央：

  • 黄色高亮横幅：「Function Calling」
  • 背景：变暗的”墨迹天气”时序图（强化”这一切就是 Function Calling”）
  • 画面左侧出现橙色竖线——讲师的”概念定义”视觉锚点

讲师给出了临时的、最简定义（294~305 秒原话）：

同学们先暂时把 Function Calling 理解为一段程序，而这个程序它是能够调用外部的 API 的。

⚠ 这是一个教学化简定义——后续课程会展开”由 LLM 生成 + 由宿主程序执行”的真实分工。本集只需要建立”它是 LLM 的一个能力”的直觉。

七、第二个困境：私有数据

讲师在 311~328 秒显式回到 3-1 的两大困境：「Function Calling 解决的不只是实时数据问题，第二个困境同样可以用它解决。」

7.1 反例重现：客户订单生成季度销售报告

PPT 复用了反例 1 的红色错误模板——只换了 Prompt 内容：

反例 Prompt 内容 错误横幅
1（3-1） 今天气温多少度？ 模型训练的数据并没有当天的数据
2（本集） 根据客户订单生成季度销售报告 模型训练的数据并没有客户订单数据

7.2 旧方案：人工导出数据喂给 LLM

底部又出现熟悉的绿色横幅：「人工从内部数据库 导出订单数据」——和反例 1 的”人工写 API 代码”是同一种”擦屁股”模式。讲师反问（401~409 秒）：

通过人工来进行的，怎么称得上是人工智能呢？

7.3 新方案：Function Calling 调本地

视觉语言完全复用第六节的命名幻灯——但这次在画面右上角追加了新的黄色下划线大字：

调用本地文件

这是一种很克制的设计：用同一张”Function Calling”幻灯，仅靠右上角的副标题切换适用场景，强化”同一种机制、两种用法“的印象。

讲师在 442~470 秒列举的”本地”对象覆盖范围非常广：

类别 例子
本地文件 Excel、PDF、Word、Markdown
本地数据库 MySQL、Access
大数据栈 Hadoop
云端数据库 阿里云、腾讯云

八、本集总结幻灯（475~547 秒）

讲师最后做了一个口头收束（没有新的总结 PPT），把全集压缩成一段定义：

语言大模型有两个致命弱点：① 不能获取实时数据，② 无法拥有用户私人数据。要解决这两个问题，语言大模型的内部有这么一个程序，叫 Function Calling（函数调用）。这个程序能够帮助 LLM 自主调用外部 API，也能够帮助 LLM 自主调用本地文件、查询数据库——包括 MySQL、Hadoop、阿里云、腾讯云这些。同学们暂时先把它理解为是 LLM 内部的一个程序。

⚠ “LLM 内部的一个程序“ 是一种教学化简。在工程实现上，Function Calling 是 LLM 输出 + 宿主程序执行 的协作机制——LLM 决定”调什么 + 传什么参数”，宿主进程负责真正的网络请求和文件 IO。这一层在后续课程会展开。

十二、思考题（自测）

  1. 本集把 Function Calling 简化定义为”LLM 内部的一个程序”——你能想到这个简化在哪里会”漏气”吗？（提示：LLM 真的能在自己的进程里发起 HTTP 请求或读本地磁盘吗？）
  2. PPT 三步法里第 2 步是”匹配 API 函数”——为什么不是”编写”？”匹配”和”编写”在语义上有什么差别？
  3. 假设墨迹天气的 API 文档下个月改了字段名，LLM 要怎么知道？这暴露了 Function Calling 的什么前提？
  4. 第二个困境（私有数据）用 Function Calling 解决——这和后续要讲的 RAG（检索增强生成）有重叠吗？两者的边界在哪里？
  5. 把 3-1 的”标准闭环图”和本集的”时序图”放在一起——讲师为什么要换一种视觉语言？这种切换暗示了什么？

十三、与上一节（3-1）笔记的对照

维度 3-1（困境） 3-2（解法）
主线 提出两个困境 用同一个机制解决两个困境
核心 PPT 标准闭环（垂直） 时序图（横向三列）
总结页设计语言 变暗背景 + 亮色横幅 完全复用 + 副标题切换场景
留下的悬念 “怎么解决？” “Function Calling 内部到底是什么？”
关键论断 没向量 ⇒ 答不出 LLM 答不出值，但答得出”去哪查”
