3-12 多Agent的核心执行流程

发表于2026-05-19|更新于2026-05-19|Agent学习第3章 MCP + Skills，Agent"工具+技能"的双轮驱动
|浏览量:

摘要：本集梳理多Agent团队的核心执行流程，主轴是”外层5步团队流水线 + 内层5步个体循环”的嵌套骨架。取舍出现在 §2.1（先讲多Agent大图、再下钻到单Agent，与原素材”从小到大”的顺序相反）。加工增量在 §2.4（把”通信 + 中间结果存储”重新定位为”协作落地的两个工程接口”，并补了一张三层视角图）。

1. 一句话定位

多Agent骨架 = 外层团队5步 + 内层个体5步的嵌套。

2. 主体讲解

2.1 先抓总图：多Agent的五步骨架

如果你只能记一张图，就记这张：一个用户请求进来，要走五步才能拿到结果。

步骤 做什么 谁来做
1. 意图识别 听懂用户到底要什么 LLM 的推理能力
2. 任务初始化 把”想要”翻译成”任务实体” 系统
3. 任务规划 / 复杂任务划分 把大任务切成可执行子任务 主管 Agent
4. 任务执行 多个专业 Agent 协同跑各自的子任务 多个子 Agent
5. 结果整合 把碎片产出拼回一个完整答案 主管 Agent

注意你看到 1→5 是顺序的，但第 4 步本身是个”团队子过程”，不是一个动作——这是下一节要拆的。

这里我做了取舍：原素材的顺序是先单Agent、再多Agent。我倒过来——先看大图、再下钻到第4步内部。理由是一年后回看，你最先想找的是”团队怎么跑”，而不是”一个 Agent 怎么跑”。

2.2 第 4 步内部：每个子 Agent 的五步循环

第 4 步打开来看，每个被分配到任务的子 Agent，自己内部也跑一个五步流程：

关键不是”5 步”，关键是第 3、4、5 步是个循环：每执行完一步就评估、反馈、再决定要不要调整下一步。不是流水线一路冲到底——单步可能不符合预期，要动态修正。

2.3 骨架嵌套：大循环里套小循环

把 §2.1 和 §2.2 合起来看，结构就出来了：

记住这层嵌套之后，就不会再把”单 Agent 流程”和”多 Agent 流程”当成两套东西看。它们是同一个系统的两层。

2.4 真正的难点：通信 + 中间结果存储

如果你以为多 Agent 的难点是”怎么让 Agent 更聪明”，方向就偏了。难点是这两件工程性的事：

(a) Agent 间通信
Agent 不能各做各的——团队协作必然要交换信息。冲突出现时（比如 A 和 B 对同一子任务给出矛盾产出），由主管发起投票来裁决。所以通信不只是”传消息”，还包含”冲突仲裁协议”。

(b) 中间结果存储
每个子 Agent 干完活，产出要落到某个共享位置，主管最后才能拿来整合。这个位置叫”中间结果”。

加工增量：原素材把这两点说成”两个关键点”。我更愿意把它们看成协作落地的两个工程接口——通信是”运行时接口”，中间结果存储是”状态接口”。主流多Agent框架（包括下一阶段要学的 JManus）会为这两个接口各设独立模块。当你拿到一个新框架，直接去找它的”通信模块”和”存储模块”，就能 90% 摸清它的协作设计。

注意图里”处于同一环境”这个标注——它是前提，不是装饰。共享环境/上下文是通信和中间结果存储能成立的物理基础；如果 Agent 跨进程、跨网络、跨租户，这两个接口都要重新设计。

2.5 主管 Agent：贯穿全程的角色

主管 Agent 不是只在开头切任务时露一下脸。它至少在三个时刻出现：

  1. 任务规划阶段：切复杂任务 → 分配给子 Agent
  2. 执行阶段：当子 Agent 间有冲突时，组织投票裁决
  3. 整合阶段：从中间结果存储里捞出所有产出，拼成最终答案

记成一句话：主管 = 调度员 + 裁判 + 编辑。

3. 我一开始没 get 的点

  • 如果你把”任务规划”理解成 Agent 拿到任务马上干，会得到错的执行模型。实际是”规划 → 执行 → 评估 → 反馈 → 调整”，后三步是循环，不是单程。
  • 如果你以为多Agent核心是某种”协作算法”，会去找根本不存在的”魔法”。实际两个具体的工程关键点是：通信 + 中间结果存储。所谓”协作”是这两件事的合成。
  • 如果你以为主管 Agent 只在切任务时出场，会漏掉它在冲突投票和结果整合中的角色，导致设计时主管模块功能不全。
  • 如果你以为单 Agent 流程和多 Agent 流程是两个独立模型，会找不到它们的对应关系。实际是嵌套——多 Agent 第 4 步内部就是单 Agent 五步循环。

4. 跟其他集的连接

上承

本集是 3 章多Agent主题的入口集，前序集（3-1 ~ 3-6 等）集中讨论 MCP / 大模型困境，没有直接前置依赖。如果你跳着看，直接从本集进入多Agent线是 OK 的。

下启

原素材明确预告：后续课程会讲 JManus 的执行流程，骨架同样是”意图识别 → 任务初始化 → 任务划分 → 结果整合”。本集就是为 JManus 落地铺的地基——读 JManus 源码时，直接去找它的通信模块和中间结果存储模块，对应的就是本集 §2.4。

横向

和 3-4 / 3-5 / 3-6 的 MCP 主题是正交关系：

  • MCP 解决 “Agent 怎么调用外部工具”（对外接口）
  • 本集解决 “多个 Agent 怎么组队”（对内协作）

一个工具一个团队，互不冲突。MCP 是 Agent 的”右手”，多Agent 骨架是 Agent 的”组织架构”。

6. 自测题

Q1（概念回忆）：多Agent的五步骨架是哪五步？
A：① 意图识别 ② 任务初始化 ③ 任务规划/复杂任务划分 ④ 任务执行 ⑤ 结果整合。

Q2（概念辨析）：单Agent五步流程里，哪几步是循环？为什么？
A：第 3、4、5 步——执行步骤、步骤评估、反馈调整——是循环。因为单步执行结果可能不符合预期，需要评估后动态调整，而不是流水线一冲到底。

Q3（反直觉）：如果有人告诉你”多Agent的核心是设计一个聪明的协作算法”，你怎么反驳？
A：核心不是抽象的”协作算法”，而是两个具体的工程接口：Agent 间通信和中间结果存储。主流框架都为这两件事单独设模块——所谓”协作”在落地层就是这两件事的合成。

Q4（跨集连接）：本集和 3-4~3-6 的 MCP 主题是什么关系？
A：正交关系。MCP 解决”Agent 对外调用工具”，本集解决”多个 Agent 对内组队”。一个对外、一个对内，互不依赖。

Q5（应用推广）：拿到一个新的多Agent框架（比如 JManus、AutoGen），怎么用 30 分钟摸清它的协作设计？
A：直奔两个接口——找它的”通信模块/消息模块”和”中间结果存储/共享状态模块”。这两个模块的实现方式（消息总线 vs RPC、共享内存 vs 数据库）决定了它的协作能力上限。其它都是包装。

7. 关键词表

术语 一句话定义
多Agent五步骨架 团队层流水线：意图识别 → 任务初始化 → 任务规划 → 任务执行 → 结果整合
单Agent五步循环 个体层执行：接收 → 规划 → 执行 → 评估 → 反馈，后三步成环
主管Agent（Supervisor） 团队调度+裁判+编辑：切任务、组织冲突投票、整合结果
Agent间通信 协作的”运行时接口”，含冲突时的投票仲裁
中间结果存储 协作的”状态接口”，子 Agent 产出落到共享位置供主管整合
