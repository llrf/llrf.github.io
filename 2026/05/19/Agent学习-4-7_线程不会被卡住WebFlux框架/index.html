4-07 线程不会被卡住：WebFlux框架

线程不会被卡住：WebFlux 框架

§1 一句话定位

SSE 服务端选 WebFlux 不选 WebMVC，是因为一个线程能扛多个请求且不被 IO 卡住。

§2 主体讲解

2.1 真正在选的，是线程模型，不是 jar 包

⏱ 04:10–05:00 · 引出两个 starter 二选一即选通信内核，纯讲

当你在 pom 里写下 spring-ai-starter-mcp-server-webflux 的那一刻，你其实做了一个比”加依赖”大得多的决定——你在给整个 SpringBoot 应用挑通信内核。SpringBoot 的核心通信框架只有 WebMVC 和 WebFlux 两个，自动装配机制要求两者只能存在一个，所以你不是”加组件”，你是”二选一”。

这就是为什么这节课表面叫”WebFlux”，骨子里要讲的是阻塞 vs 非阻塞线程模型。

⏱ 10:56

2.2 WebMVC：一个请求霸占一个线程

⏱ 10:20–11:55 · 解释阻塞模型一请求一线程，纯讲

WebMVC 走阻塞模型（视频音轨里你会反复听到”主摄模型”，这是口音版的 blocking，你听到”主摄”就在脑子里自动翻译成”阻塞”）。它的两个特征是连体的：

  • 一请求一线程：1 万个并发就要 1 万个线程
  • 线程等 IO 时啥也干不了：被这个请求”霸占”住

你可能会想”线程数不够才是问题吧”——其实顺序反了。原因是”线程在等待期间不能做别的”，结果才是”必须为每个请求各分一个线程”。第二个特征是因，第一个是果。

2.3 WebFlux：一个线程伺候多个请求

⏱ 12:00–13:50 · 解释非阻塞一线程多请求，纯讲

WebFlux 走非阻塞模型，两条镜像对照：

  • 一线程多请求：10 万个请求理论上可以由一个线程轮流处理
  • 线程在等 IO 时能去干别的：这才是”不阻塞”的真正含义

这两条也是因果连体的：因为线程不会被一个请求卡住，所以它有余力去伺候下一个请求。

这里我主动取舍：WebFlux 之所以能做到”等 IO 时做别的”，底层是 Reactor / Netty 的事件循环 + NIO selector——但本节不展开，因为本节的目标是”能在 pom 上做出正确选择并解释为什么”，不是”调优 Reactor”。等你将来要排查 SSE 长连接性能问题再回头补 Mono/Flux 和 event loop 的细节。

2.4 协议相同，性能不同

⏱ 09:30–10:30 · SSE 两套框架都支持差异在线程模型，纯讲

容易踩的反直觉点：SSE 协议本身并不挑框架。WebMVC 和 WebFlux 都能跑 SSE，SAA 官方文档里两套依赖都摆出来了。区别只在背后的线程模型——同样一条 SSE 长连接，WebMVC 跑就是”占着一根线程不撒手”，WebFlux 跑就是”一根线程上挂一堆连接”。SSE 是长连接、并发数动辄上千，这恰好就是阻塞模型最难受、非阻塞模型最舒服的场景。所以”SSE 选 WebFlux”不是协议要求，是性能要求。

⏱ 10:44

2.5 一个 starter 等于一捆依赖

📺 07:20–09:00 · IDEA Maven 窗口展开 starter 看传递依赖三件套

把 spring-ai-starter-mcp-server-webflux 复制进 pom 后，去 IDEA 的 Maven 依赖窗口展开看，你会发现它传递性地拖进来三块：

  1. spring-boot（SpringBoot 基础）
  2. spring-boot-starter-webflux（WebFlux 通信框架）
  3. spring-ai-mcp（MCP 基础模块——客户端和服务端都得引）

这解释了你在第一遍看视频时的两个疑问：

  • 疑问 1：MCP 服务端的依赖怎么和 SpringBoot 扯上关系了？ 因为 starter 的语义就是”一揽子勾选”，它替你把 SpringBoot 带进来了，你不用也不该再单独引 web 启动器。
  • 疑问 2：为啥后缀是 -webflux？ 因为这个后缀就是在标”我用 WebFlux 实现 SSE 协议”——把”基于 SpringBoot 的 WebFlux 框架实现 MCP 服务端的 SSE 协议”这一长串行话压缩成一个连字符。

⏱ 04:40

2.6 groupId 是 spring-ai 原生，不是 SAA

📺 05:00–06:00 · IDEA 中复制 starter 检查 groupId 来源

复制依赖时要注意：groupId 是 org.springframework.ai（原生 Spring AI），不是 com.alibaba.cloud.ai。这就是为什么 4-2 课要先把 spring-ai-bom 加进根 pom 的 dependencyManagement——本集的 webflux starter 是靠那个 BOM 解析版本的。如果你跳过了 4-2 直接来这一节，IDEA 会标红找不到版本。

⏱ 08:19

2.7 pom 怎么写：留 webflux，删 webmvc

📺 08:00–09:40 · pom 中保留 webflux 删 webmvc

为了对比你可能会把两个 starter 都写一遍，但最终的状态应该是只留 webflux，把 webmvc 注释掉或删掉——因为两个通信框架不能并存，留着 webmvc 会让自动装配冲突。

不要写 <version>——版本由 4-2 引入的 spring-ai-bom 管。

§3 我一开始没 get 的点 / 容易踩的坑

  1. “主摄模型”是什么鬼？ 是口音版的 “阻塞模型 / blocking”。听到”主摄”立刻心里翻译成”阻塞”，这一集就不会卡住。
  2. 以为 WebMVC 和 WebFlux 能共存。不能——自动装配只挑一个。你不是在”加 web 模式”，你是在”选 web 内核”。
  3. 以为 SSE 协议决定了必须用 WebFlux。错。SSE 两套框架都支持，性能差异来自线程模型，不是来自协议。
  4. 以为 starter 是单个 jar。错。starter 是一组依赖的入口，本集的 webflux starter 一勾就带进来 SpringBoot + WebFlux + spring-ai-mcp。

§4 跟其他集的连接

  • 4-4（SSE 实时传输）：那一集讲了 SSE 协议本身（单向、实时、长连接），这一集回答”用什么框架把 SSE 跑起来”。
  • 4-6（注册工具）：上一集完成了”声明工具 + 注册到清单”，本集回到”用什么传输把这些工具透出给客户端”。

下启

  • 启动 + SSE 联通性验证：依赖 + 配置都备齐后必然要起服务、用客户端连一下。
  • （远期）Reactor / Netty 事件循环：本集刻意没展开的部分。

横向

§5 知识地图

§6 自测题

Q1： WebMVC 和 WebFlux 能不能同时存在于一个 SpringBoot 应用里？为什么？
A1： 不能。自动装配机制只允许配置其中一个；它们是核心通信框架的二选一，不是可并存的组件。

Q2： SSE 协议是否只能用 WebFlux 实现？
A2： 不是。两个框架都支持 SSE 协议。区别只在线程模型——WebFlux 在高并发长连接场景下性能优于 WebMVC，所以推荐用它跑 SSE。

Q3： 视频里反复说的”主摄模型”应该理解成什么？
A3： 阻塞模型（blocking）。是口音版本的发音，意思是线程在处理请求期间不能做其他事。

Q4： 引入 spring-ai-starter-mcp-server-webflux 后，依赖树里会自动多出哪些关键依赖？
A4： 至少三块——SpringBoot 基础、spring-boot-starter-webflux、spring-ai-mcp（MCP 基础模块）。因此你不需要再手动加 SpringBoot Web 启动器。

Q5： 这个 starter 的 groupId 是 com.alibaba.cloud.ai 还是 org.springframework.ai？这件事为什么重要？
A5： 是 org.springframework.ai（原生 Spring AI，不是 SAA）。重要是因为它的版本要靠 spring-ai-bom 来管，所以 4-2 课的 BOM 前置是这一集能跑通的隐藏前提。

§7 关键词表

术语 一句话解释
WebFlux 框架 SpringBoot 的非阻塞通信框架，一个线程能处理多个请求，且等 IO 时线程能做别的事
WebMVC 框架 SpringBoot 的阻塞通信框架（口音版”主摄模型”），一请求一线程且线程等待期间不能做别的
阻塞 vs 非阻塞线程模型 本集真正的核心选择题，”线程会不会被一个请求卡住”二选一
spring-ai-starter-mcp-server-webflux 原生 Spring AI 提供的 MCP 服务端 starter，本集最终保留的依赖
spring-ai-starter-mcp-server-webmvc 孪生 starter，同样能跑 SSE 但走阻塞模型，本集结论是不用
starter 传递依赖 一个 starter 等于一组依赖的入口，本集的 webflux starter 一勾就带进 SpringBoot + WebFlux + spring-ai-mcp
spring-ai-mcp 基础模块 MCP 客户端 / 服务端都必须引入的基础包，本集靠 starter 传递依赖自动带入
SSE 协议同点 / 性能不同点 WebMVC 和 WebFlux 都支持 SSE，差异不在协议而在线程模型
