3-8 工具调用最强组合：Agent Skills+MCP

发表于2026-05-19|更新于2026-05-20|Agent学习第03章 MCP + Skills，Agent"工具+技能"的双轮驱动
|浏览量:

摘要：本集解决”MCP 把工具一股脑全返”导致的两个连锁问题——上下文爆炸 + 智能体不会选工具——并给出 Agent Skills 这一调用方智能层。取舍出现在 §2.5（把”农民比喻”降级为助记，前移核心主干）；加工增量在 §3、§5（把渐进式加载与 RAG 索引-检索做同构对照，并补一张三段式触发时序的 ASCII 地图）。

1. 一句话定位

Agent Skills 解决”该用哪个工具”，MCP 解决”工具从哪来”，二者合体。

2. 主体讲解

2.1 你要先记住一组提问，再看答案

回到工具调用的演化路径，你要问的是三个问题，越往后越尖锐：

阶段 解决的问题 留下的新问题
Function Calling 让大模型能调外部 API 每家模型协议不同，重复造轮子
MCP 协议统一，跨模型复用 工具一次全返，上下文爆炸 + 选工具靠问 LLM
Agent Skills 让智能体自己知道该用哪个 （本集没回答，但要留意它得有配置文件）

读到这里你应该有个直觉：Agent Skills 不是替换 MCP，是补 MCP 的下游短板。

2.2 MCP 的真痛点不在”调用慢”，在”目录页太厚”

如果你第一次听到”MCP 有缺点”，大概率会以为是工具执行慢或者协议复杂。这是错的方向。

真正的痛点是：MCP 服务端返回工具列表时，一次性把它名下的全部工具元信息塞进上下文。一个服务端动辄十几二十个工具，几个服务端叠加，你的上下文窗口就开始告急。这是问题一。

紧接着是问题二：智能体看到这么大一坨工具清单，它自己不知道哪个能干活。它得回头问语言大模型——“嘿，这个任务用哪个工具？”——一问一答耗 token、耗时间。如果一个任务需要工具组合，它还得反复问。

把这两个问题串起来：MCP 解决了”工具从哪来”的标准问题，但把”该用哪个、怎么组合”全甩给了运行时的 LLM 对话回合。

2.3 Agent Skills 是什么：装进智能体脑子里的”专业知识”

解法很直接——让智能体自己就懂这个领域，不必每次回头请教大模型。

打个粗糙的比方（仅当助记，不是核心）：你给智能体挂上”农民”这个角色后，关于耕地施肥，它自己就知道该拿哪几样农具、按什么顺序用。这个”自己知道”，就是 Agent Skills。

技术上的实现方式：通过文件配置把领域知识喂给智能体。你不需要 fine-tune 模型，只要写配置文件。注意这里——喂的是”知识与索引”，不是工具本体。这一点是下一节的关键。

2.4 渐进式三段加载（这一节是 how，是它能成立的命门）

如果 Agent Skills 启动时就把”全部领域知识 + 全部工具文档 + 全部辅助脚本”塞进上下文，那它和 MCP 的”全返”就没区别了。所以它必须分段加载：

三段的本质：把”我有什么”和”我现在要用什么”剥开。第一段只回答”我大致会做什么”，第二段才告诉智能体”具体怎么调”,第三段才把”运行时需要的料”端上来。

这跟 RAG 的索引-检索是同构的：元数据 ≈ 向量库的 metadata；详细指令加载 ≈ retrieve chunk；附加资料 ≈ 二次扩展检索。如果你做过 RAG，这套机制对你不陌生，只是从”为知识检索”换成了”为工具选择”。

2.5 农民比喻只是助记，主干是”问题→定位→分工→实现”

这里我做一次取舍：原讲解把”农民”比喻插在 MCP 痛点之后、Agent Skills 概念之前，容易让人以为”角色化”是核心机制。不是。核心是”通过外挂文件给智能体装专业知识，且渐进加载”。农民只是个让你记得住的钩子，挂在最后就行。

2.6 MCP × Agent Skills 的分工：提供者 vs 选择者

最后回到开头那张分工图。把它读成一句话：

  • MCP：工具的提供者。跨模型可复用，不再重复造轮子。
  • Agent Skills：工具的选择者与使用者。代表智能体自身的”能力与智慧”。

智能体凭借 Agent Skills 知道”这个任务我要用 A 和 B”，于是它主动告诉 MCP 服务端：”只返回 A 和 B 给我，其他别塞过来。”——这就把上下文爆炸的源头堵住了。

3. 我一开始没 get 的点

  • 如果你以为 Agent Skills 是新的工具调用协议要替代 MCP，会得到错的结论：你会去找它的协议规范。实际上它是调用方的智能层，没有取代 MCP 的工具提供职能。
  • 如果你以为 MCP 的痛点是”工具调用慢”，会得到错的优化方向：去优化执行链路。实际瓶颈在”返回工具列表”这一步的目录膨胀。
  • 如果你以为”让智能体有专业知识”等于 fine-tune，会得到错的实现路径：你会去准备训练集。实际上是写配置文件，启动时加载元数据。
  • 如果你以为”渐进式加载”只是性能优化的可选项，会得到错的优先级判断：你可能省掉它。实际上它是 Agent Skills 能成立的架构必需——没有它，”专业知识 + 工具集”会再次撑爆上下文。

横向

  • 与 RAG 同构：先索引后按需取详细内容，避免一次性灌满上下文。
  • 与 3-1 的”外挂动机”呼应：3-1 讲为何要外挂数据，本集讲外挂工具知识时如何不撑爆上下文——同一组工程约束的两个面。

5. 知识地图

6. 自测题

Q1（概念回忆）：Agent Skills 的三段式加载分别是什么？
A1：① 启动时加载元数据（领域知识 + 工具索引）；② 任务匹配后加载该工具的具体文档/命令；③ 执行过程中按需加载辅助脚本、数据库等附加资料。

Q2（概念辨析）：Agent Skills 会取代 MCP 吗？为什么？
A2：不会。MCP 是工具提供者（解决”工具从哪来、能否跨模型复用”），Agent Skills 是工具选择者/使用者（解决”该用哪个、怎么组合”）。二者分工不同，结合才是完整方案。

Q3（反直觉）：MCP 的核心痛点是”调用慢”还是”目录页太厚”？
A3：是”目录页太厚”。MCP 一次性把全部工具元信息返给智能体，造成上下文爆炸；同时智能体面对一大堆工具不会选，被迫反复问大模型，浪费 token。瓶颈不在执行链路。

Q4（跨集连接）：渐进式加载和 RAG 有什么共通之处？
A4：都遵循”先索引后按需取详细内容”的思路，避免一次性把全部内容灌进上下文。元数据 ≈ 向量库 metadata；详细指令 ≈ retrieve chunk；附加资料 ≈ 二次扩展检索。本质都是控制上下文的工程约束。

Q5（应用推广）：如果你要给一个客服智能体设计 Agent Skills，元数据阶段应该放什么、不应该放什么？
A5：应放：客服领域知识概览、可用工具索引（如”查订单”、”开退款”、”转人工”的名字和一句话描述）、工具组合模式（如退款流程涉及”查订单 + 开退款”）。不应放：每个工具的完整 API 文档、SQL 查询语句、知识库全文。后者要等任务匹配后再加载，否则三段式就退化成”一次性全返”。

7. 关键词表

术语 一句话定义
Agent Skills 通过外挂文件给智能体装上领域专业知识，让它自己知道该用哪几个工具、怎么组合，不必每步问 LLM。
渐进式加载（三段式） 启动加元数据 → 匹配加详细指令 → 运行加附加资料，三段触发时机不同，避免一次塞爆上下文。
元数据加载 启动阶段只加载领域知识概览 + 工具索引（目录），不加载工具本体——这是控制上下文的关键钩子。
上下文爆炸 MCP 一次性返回全部工具列表导致的窗口告急问题，Agent Skills 的解药。
工具组合 智能体不仅知道单个工具，还知道哪几个工具组合效率最高，是”专业知识”的体现。
MCP × Agent Skills 分工 MCP 提供工具（跨模型复用），Agent Skills 选择并使用工具（代表智能体能力）。分工不替代。
