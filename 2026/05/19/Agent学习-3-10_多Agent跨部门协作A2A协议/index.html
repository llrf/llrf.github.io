多Agent跨部门协作：A2A协议

1. 一句话定位

A2A 是远程 agent 之间通过中心协调者通信协作的协议。

2. 主体讲解

2.1 先扔结论：A2A 到底是什么

如果你只能记一句话，记这个：A2A = Agent-to-Agent，Google 提的、用来让两个远程 agent 互相通信 + 协作的协议。它和你之前学过的 MCP 是兄弟关系，但解决的问题完全不同：MCP 让 agent 调用外部工具，A2A 让 agent 调用另一个 agent。

但这里有一个让你少走弯路的前置认知：A2A 并不是所有”多 agent 场景”都要用的协议。你下面要先搞清楚”远程 agent vs 同模型多 agent”这条分界线，否则会把它套到不该套的地方。

2.2 划线：什么时候才轮到 A2A 出场

先记住一个定义性的约定：一个 agent 只挂一个大模型。就像人只有一个大脑——这不是技术限制，是给 agent 下的定义。所以：

  • 一个 agent 用了 QWen，就不可能同时挂 OpenAI。
  • 你想让 QWen 和 DeepSeek 一起干活？那就是两个 agent，而且天然分布在不同节点上。

由此就分出了两种”多 agent”：

场景 典型例子 通信方式
同一大模型下的多 agent，共同解决一个需求 同一个购物任务里拆出”选品 agent”、”比价 agent”、”下单 agent”，都跑在同一节点 gRPC + 本地内存/文件即可
不同大模型节点的远程 agent 深圳节点的 QWen agent 协作上海节点的 DeepSeek agent A2A 协议

A2A 真正服务的是后者。前者用 A2A 是杀鸡用牛刀。这里有我做的第一处取舍：消化稿里把这条单独列为”反直觉点”，我把它前置到第 2 章正文，因为这是决定”要不要学这章”的判断依据，必须先讲清楚。

2.3 核心机制：为什么必须有一个”协调者”

这一段是 A2A 最关键的设计取向。你可能直觉地以为 agent1 和 agent2 应该像 HTTP 一样直连，谁找谁就发消息过去。错。

A2A 是中心化的，必须有一个叫 A2A Server 的协调者卡在中间。所有消息——任务、进度、格式协商、结果——全部经它中转。为什么？因为 agent 之间的协作有两个硬需求：

  1. 数据交互：消息要送到，这是基本的。
  2. 状态同步：要有条不紊地协作，就得知道对方现在干到哪了。

远程节点之间没法靠共享内存来同步状态，所以必须有一个”知道全局发生了什么”的中间人。A2A Server 同时承担”数据中转 + 状态同步”两个职责。

类比一下：agent1 像甲方，agent2 像乙方，A2A Server 是甲乙双方都信的中介。甲方不会直接打电话给乙方，所有需求、催进度、改要求都通过中介喊话。

2.4 7 步协作流程：把抽象落到动作

下面这一串是 A2A 一次完整协作要走的路径。你看着图把每一步对应过来：

  1. 查询 Agent 卡片：agent1 想找帮手，先去问 A2A Server：”你这有什么 agent 可用？”
  2. 能力发现：A2A Server 翻 Agent 卡片，挑出能干活的那个（这里是 agent2）。
  3. 提供 Agent 卡片：把 agent2 的卡片回给 agent1，”找到了，就它能办”。
  4. 发起任务：agent1 提交任务给 A2A Server（不是直接给 agent2）。
  5. 任务管理：Server 接收、记录、转交给 agent2。
  6. 接收执行任务：agent2 拿到任务开干。
  7. 询问进度 / 进度更新：agent1 通过 Server 问进度，agent2 通过 Server 回进度——这是”协作”的部分。
  8. 指定输出格式 / 调整输出格式：agent1 说”我要 JSON 还是 Markdown”，Server 转告，agent2 调整——这是”协商”的部分。
  9. 生成最终结果 → 输出 → 呈现：agent2 出结果给 Server，Server 给 agent1，agent1 呈现给用户。

这里我做了一个加工增量（取舍/加工的第二处）：流程图上写的是「协作」「协商」两个标签横跨多步，原稿没解释这两个标签到底圈住了什么。我把它们对应到 步骤 7 = 协作（进度同步）、步骤 8 = 协商（格式对齐），这样你看图就能秒懂为什么这两个标签横跨多步。

记忆抓手：能力发现 → 建立联系 → 任务管理 → 协作 → 协商 → 输出。前两步是”找到对的人”，中间三步是”把事做对”，最后一步是”把结果送回”。

2.5 关于 Agent 卡片（Agent Card）

这一节里 Agent 卡片是最容易被一带而过的概念，但它是 A2A “服务发现”的钥匙——Agent 卡片就是 agent 的能力简历。A2A Server 凭这张卡片才知道”哪个 agent 会干哪种活”。视频没展开它的具体 schema（JSON？YAML？谁来注册？），这是我留给后续课程的待查。

2.6 学习预算建议（一个明确取舍）

视频明确说：”A2A 了解一下就可以了”。理由：生态远不如 MCP。MCP 这边支付宝、百度地图都接入了，调一下就能付款、查路况；A2A 这边目前没看到这种级别的现成接入。

所以你的学习投入应该是：MCP 重学 + 上手，A2A 了解概念 + 知道何时不该用就够了。这条判断对你的时间分配很重要。

3. 我一开始没 get 的点

  • 如果你以为「多 agent」= 一堆并行的小弟，你会得到错的设计。同模型多 agent 用 gRPC + 内存就够了，套 A2A 会把架构搞重。A2A 是为”跨节点、跨大模型”准备的。
  • 如果你以为 A2A 像 HTTP 是 P2P 直连，你会画错架构图。它是中心化的，必须有 A2A Server，所有消息都过它。原因是状态同步在远程节点之间无法靠内存。
  • 如果你以为 A2A 和 MCP 是同优先级的”必学”协议，你会浪费学习预算。视频明确降级 A2A：”了解就行”，因为生态没起来。
  • 如果你以为「一个 agent 一个大模型」是技术限制，你会想错”为什么不能让一个 agent 跨模型”。这是定义层面的约定（人只有一个大脑），不是技术约束。它是”远程 vs 本地多 agent”分类的前提。

上承

  • 3-1 ~ 3-3 LLM 缺陷 + Function Calling：本集开头 5 分钟复习了 LLM 没手没脚需要 agent 这条主线。如果你看过那几集可以跳过。

下启

本集没有明确点名下一集。但 7 步流程里几乎每一个名词都可能展开：Agent 卡片的具体 schema、能力发现的实现方式、A2A Server 的高可用——这些都是潜在的下集主题。

横向

  • 与**分布式系统的”服务发现 + 消息中间件”**同构：Agent 卡片 ≈ 服务注册表，A2A Server ≈ MQ broker / Service Mesh，状态同步 ≈ 分布式一致性问题。
  • Google 出 A2A 的本质：把微服务那一套搬到 agent 世界。所以你之前的微服务经验对理解 A2A 是直接复用的。

6. 自测题

Q1（概念回忆）：A2A 中的两个 A 各指什么？这个协议是谁提出来的，解决什么场景？

A1：两个 A 都是 Agent。Google 提出，用于远程 agent（分布在不同节点 / 基于不同大模型）之间的通信与协作。

Q2（概念辨析）：A2A 和 MCP 都是通信协议，它们的核心区别是什么？哪个更值得现在投入精力？

A2：MCP 解决 agent ↔ 外部工具（如支付宝、百度地图），A2A 解决 agent ↔ agent。当前 MCP 生态远比 A2A 成熟，所以 MCP 重学上手，A2A 了解概念即可。

Q3（反直觉）：agent1 想给 agent2 发消息，能不能直连？为什么？

A3：不能。A2A 是中心化设计，必须有 A2A Server 中转。原因是远程节点之间不仅要送数据，还要同步状态，而状态同步在分布式节点之间无法靠共享内存解决，必须有一个”知道全局”的中介。

Q4（跨集连接）：3-1 ~ 3-9 讲了大模型、agent、Function Calling、MCP。本集的”多 agent 协作”放在这个序列末尾的逻辑是什么？

A4：是逐层放大：单 LLM（3-1）→ LLM 缺陷 → 用 FC/MCP 给 agent 装手脚（3-2~3-6）→ 单 agent 装齐了感官与动作 → 自然要扩展到多 agent 协作（本集）。MCP 把 agent 和工具连起来后，下一步必然是把 agent 和 agent 连起来。

Q5（应用推广）：你团队想做一个跨公司的 agent 协作产品（A 公司的客服 agent 调 B 公司的物流 agent），下面哪些组件不可省？

A5：（1）A2A Server 必不可少——跨公司必然跨节点，且需状态同步；（2）双方都要发布 Agent 卡片，否则 Server 无法做能力发现；（3）需要约定输出格式协商机制（步骤 8），否则 A 公司拿到 B 公司返回的数据格式可能没法消费。如果是同公司同模型的 agent 群，则 gRPC + 内存就够了，不需要 A2A Server。

术语 一句话解释

远程 Agent 分布在不同节点 / 基于不同大模型的 agent，A2A 的真正服务对象
A2A Server（协调者） 中心化中转节点，所有 agent 间消息必经它，承担数据交互 + 状态同步
