4-9 · SpringAi Alibaba 1.1 以 BOM 方式导入依赖

1. 一句话定位

1.1 文档没写 BOM，但 BOM 依然能用——验证靠仓库不靠文档。

2. 主体讲解

2.1 从”文档差异”切入：1.1 只给你两个依赖

📺 01:00–04:30 · 浏览器中对比 1.1 与 1.0 官方快速开始文档

打开 1.1 的快速开始，会发现它跟你在 4-1 里背熟的 1.0 文档完全不是一个味儿——整页只塞了两个 dependency，连 dependencyManagement 那一段都没了。

⏱ 04:09

两个依赖是：

  • spring-ai-alibaba-agent-framework：1.1 新增的智能体入口包
  • spring-ai-alibaba-starter-dashscope：跟 1.0 同名，调阿里百炼大模型的入口

每个 dependency 都硬编码了 1.1.0.0-RC2 版本号。注意是四段制 + RC2 后缀，写成 1.1 会直接 Maven resolve 失败。RC（Release Candidate）比 1.0 时代的 M（Milestone）稳一档，RC 再往后就是 GA 正式版，可以拿来练手。

2.2 反应：1.0 的 BOM 习惯还能用吗？

⏱ 05:00–06:30 · 提出文档没列 BOM 的疑问要去仓库验证，纯讲

按 4-1 的肌肉记忆，所有版本号都该靠 BOM 兜底——你不应该手写 1.1.0.0-RC2 三遍。问题是：1.1 文档故意没列 BOM，是不能用，还是只是没写？

取舍出现在 §2.2：你可以选信文档（认为 1.1 拿掉 BOM 是官方在引导新手”显式写死版本号”），也可以选信仓库（认为文档只是简化）。我选后者——因为”文档真值”不可信，Maven 中央仓库 + GitHub 源码目录才是依赖能不能用的最终判据。

2.3 去 GitHub 反证：bom 子目录还活着

📺 06:30–07:30 · 浏览器中翻 GitHub 仓库找 bom 子目录验证可用

打开 spring-ai-alibaba 仓库根目录，往下翻 module 列表：

⏱ 06:39

spring-ai-alibaba-bom 这个 module 静静躺在那里，提交时间标着 2 weeks ago，commit 是 chore[release]: 1.1.0.0-RC2 release——它跟 1.1.0.0-RC2 是同一波发出去的。结论：BOM 工程存在 = BOM 能用。

加工增量在 §2.3：这是讲师没明说但你应该提炼的判定规则——版本是否支持某种依赖方式，不看文档列了没，看 Maven 中央仓库（或 GitHub release 同步的 module）有没有对应 artifact 发布。以后再升级任何 Spring 生态版本，第一步都是去仓库根目录找对应 bom 子目录的 commit 时间。

2.4 套用 1.0 的 BOM 三件套，只换版本号

📺 07:30–08:50 · IDEA 中编辑 pom 写 properties 和 BOM 三件套

确认 BOM 可用后，剩下的就是把 4-1 的三件套搬过来。先在 properties 里固定版本变量：

⏱ 07:34

然后在 dependencyManagement 里塞 BOM，三件套 type=pom + scope=import + version=${spring-ai-alibaba.version} 一字不改；最后在 dependencies 里写 spring-ai-alibaba-agent-framework——不写 version，让 BOM 接管。

2.5 验证：External Libraries 树就是证据链

📺 08:50–09:29 · IDEA Maven reimport 后展开 External Libraries 看依赖

光看 pom 没解析成功不算数。让 Maven reimport 后展开侧边栏的 External Libraries：

⏱ 09:07

你会看到一串自动带出来的东西：

  • spring-ai-alibaba-agent-framework:1.1.0.0-RC2 ← 版本号被 BOM 喂对了
  • io.modelcontextprotocol.sdk:mcp:0.14.0 ← MCP SDK 默认进来了
  • spring-ai-alibaba-graph-core:1.1.0.0-RC2 ← DAG Graph 底层
  • io.github.a2asdkc:a2a-java-sdk-client:0.2.5.Beta2 ← A2A 协议被当一等公民拉进来
  • com.alibaba:fastjson:1.2.83 ← JSON 序列化

这串传递依赖才是”BOM 生效 + agent-framework 是 1.1 设计核心”两件事的唯一可信证据——你不只是配通了，还顺手看到了 1.1 的设计哲学（Agent 是中枢，MCP / A2A / Graph 都挂在它下面）。

2.6 为什么是 agent-framework，不是 ChatClient

⏱ 01:00–02:00 · 解释 1.1 把工具调用收口到 Agent，纯讲

1.0 时代你拿 ChatClient 直接调工具、直接跟大模型对话。1.1 把这条线收口了：

⏱ 01:16

文档首页三个大标签——Context Engineering / Multi-agent / Workflow——共同点是都基于 DAG Graph，操作主体是 Agent。讲师明确预告：”从 1.1 起，工具调用 / MCP 调用 / LLM 交互全部由智能体来调用“，意味着你之前用 ChatClient 直调工具的写法在 1.1 下要重写成”Agent 持有工具”。

3. 我一开始没 get 的点

  • 以为 1.1 拿掉了 BOM 支持：其实只是文档没写。这一集本质教的是”依赖能不能用看仓库不看文档”的元方法。
  • 以为 RC 是不稳定的预发布：RC 已经是正式版前的最后一档（M → RC → GA），1.1 已经在 RC2，2.0 还停在 ME。讲师直接拿 1.1.0.0-RC2 当练手版。
  • 以为 agent-framework 只是个新包：它是 1.1 整个智能体能力的”主操作者”——所有工具调用、MCP 调用、LLM 交互都收口在它下面，跟 1.0 的 ChatClient 是替代关系而不是并存。
  • 以为版本号 1.1 能用：完整版本号是 1.1.0.0-RC2（四段 + 后缀），少一段都报 not found。

4. 跟其他集的连接

上承

  • 4-1：BOM 三件套（dependencyManagement + type=pom + scope=import）和 spring-ai-alibaba.version 版本变量在本集 100% 平移，没新增任何 Maven 语法。
  • 4-2：两层 BOM 并存（SAA BOM 跟 spring-ai BOM）在 1.1 下依然成立。
  • 4-2：”Maven 中央仓库 / artifact 是否真实存在”作为真值源，本集用 GitHub module 目录把这条规则又重复实证了一次。

下启

  • 后续多 Agent 章节：agent-framework 引入的 ReactAgent、系统提示、工具、记忆、outputSchema 这一串目录都挂在它下面。后面所有”Agent 怎么写”的课都在这个包上。
  • 工具注册方式可能要重写：4-5 / 4-6 学的 @Tool 注册到 ChatClient，到 1.1 可能要改成 Agent 持有工具。这个迁移点是后面集的硬骨头。

横向

  • 3-10 A2A 协议：External Libraries 里冒出来的 a2a-java-sdk-client 就是 3-10 学过的协议，SAA 1.1 已经把它当默认依赖了。
  • 3-4 MCP：mcp:0.14.0 自动进 classpath，意味着 1.1 下接 MCP 不用再单独拉 spring-ai-mcp 了。
  • 3-12 多 Agent 五步骨架：graph-core 就是把多 Agent 编排做成 DAG 的底座，文档首页的 Multi-agent 标签底层就是它。
