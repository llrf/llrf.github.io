4-3_MCP能连接万物的原因通信的分层设计

发表于2026-05-19|更新于2026-05-19|Agent学习第4章 SpringAi 1.1 实现 MCP+A2A
|浏览量:

1. 一句话定位

搞清楚 MCP 为什么能当”通用插头”——答案是协议层 + 传输层这两条横切线。

2. 它到底解决了什么

先把结论钉在墙上：通用插头 = MCP 协议层 + MCP 传输层。其他细节都是围绕这个等式展开的。

但只看公式没法消化，你需要先理解它在解决什么。MCP Server 一边连着墨迹天气这种第三方 API、一边连着本地 Excel 文件、还可能连着云端数据库。把这堆杂七杂八的工具放一起，你会发现两个尴尬的事实：

①格式不统一。墨迹天气返回的 JSON 字段和高德地图返回的字段长得完全不一样；本地 Excel 读出来的内容和数据库查询的结果更没法比。如果让大模型自己去逐家适配字段含义，那这事就不可能”换个模型就能用”——千问要学一套、DeepSeek 要学一套、豆包又得学一套。

②传输方式不统一。调第三方 API 走的是 HTTP；可读本地 Word 文档走 HTTP 就是笑话，它只能通过本地进程通信。如果协议把传输方式写死成 HTTP，本地工具直接出局。

这两个”不统一”是这一集所有讨论的母题，把它们记牢就行了。下面这张图把问题的位置标出来——不同的工具 → 返回的格式不统一 → 返回方式的不统一 三件事是从右往左追溯的。

协议层负责”统一格式”

针对问题①，MCP 在中间塞了一个协议层：它约定一个统一的响应数据格式，所有工具——不管是天气 API、地图 API 还是本地 Excel——返回的东西都得按这个格式包一层再给出去。

这件事的杀伤力在于：大模型从此只需要会解析”一种”格式。换模型不用重新训、加新工具不用让大模型重新学。这就是 4-2 里那个”为什么 MCP 跨厂商复用”的口号在机制层面的落地。

传输层负责”自主选传输机制”

针对问题②，MCP 又塞了一个传输层：它的职责不是规定走什么，而是”看情况选”。

  • 调远程 API → 选 HTTP
  • 读本地文件 → 选本地进程
  • MCP Server 和 MCP Client 跨机部署 → 选 HTTP
  • MCP Client 和 MCP Host 在同一台机器 → 选本地进程

这里有个特别值得停一下的点：“同节点 / 跨节点”不是协议规定死的部署形态，而是传输层运行时根据实际情况切换的开关。你可以把 Host 和 Client 塞同一台机器（开发时常见），也可以分两台机器（生产时常见），传输层会自动适配。

关键转折：两层是”贯穿”的，不是”某一段”

我一开始想当然以为协议层只覆盖 Server↔外部 API 这一小段（因为问题是从那里冒出来的）。错了。

协议层和传输层是垂直切片，从 MCP Host 一直贯穿到 MCP Server。你可以这么想：Host↔Client 是一段链路、Client↔Server 是另一段，两层就像两条横线，把这两段链路同时穿起来。Host 端拿到的数据已经被协议层包成统一格式了；Host 和 Client 之间的传输方式也是传输层在管。

这一点不展开”为什么这样设计更优雅”，因为本质就是 OSI / TCP-IP 那套关注点分离的老套路，单独展开会偏离主线——取舍标记：见 §6 摘要。

验证一遍流程

回到三节点时序：会话建立（初始化 Client → 请求工具列表 → 返回工具列表）→ 循环阶段（模型触发 → 调用工具 → 返回响应 → 返回给模型）。把”协议层 + 传输层”这两条横线叠到这张时序图上，你会发现：

  • 工具执行那一步，返回数据先被协议层格式化
  • 节点之间的每一段通信，传输层都在替你选机制

公式就闭环了。

3. 我一开始没 get 的点 / 容易踩的坑

  1. 如果你以为 MCP 协议核心只是”统一返回格式”，你会得到一个错的结论：MCP 应该全程走 HTTP。本地 Excel 根本不可能走 HTTP，传输层必须存在，”格式 + 传输”两件事缺一不可。
  2. 如果你以为协议层只管 Server↔外部 API 那一段，你会推不出”为什么换大模型也能用”。真正的关键是协议层一路延伸到 Host 端，让大模型只看到统一格式——所以换千问、DeepSeek 都不用改。
  3. 如果你以为”同节点本地进程”是 MCP 协议硬性规定的部署方式，你会困惑为什么有的教程把 Client 和 Host 画在一起、有的分开。其实是传输层运行时自选——同机就走本地进程，跨机就走 HTTP，这是机制，不是部署规范。
  4. 如果你以为传输层只在 Server↔外部 API 这一段起作用（因为只有那里有”远程/本地”之分），你会漏掉 Host↔Client 之间也可能跨机这件事。传输层是贯穿三节点的，每一段链路它都管。

4. 跟其他集的连接

上承

3-4 给出了 MCP 三节点（Host / Client / Server）和”会话建立 + 循环”的骨架；3-5 解释了 MCP 相对 Function Calling 的”位置→分发→生态”三层差异。本集是在那个骨架上加了两条横贯线（协议层 + 传输层），把上一节”为什么能跨厂商复用”的口号落到机制：因为大模型只看协议层约定的统一格式，所以谁来都能用。

下启

3-6 已经在配置 JManus 时见过 STDIO / SSE / Streamable HTTP 三种传输方式，当时只是当作工具来用。本集是那三选一的理论解释——STDIO 对应本地进程（同机），SSE 和 Streamable HTTP 对应 HTTP 家族（跨机）。后续讨论 MCP Server 部署形态（Hosted vs Local）时，这套传输层判定逻辑还会继续用。

横向

和 OSI 七层、TCP-IP 分层是同一种关注点分离哲学。”传什么格式”和”怎么传”被解耦成两层，任意一层换实现不影响另一层——所以新工具接入只需要适配协议层，新部署形态只影响传输层。

5. 知识地图

6. 自测题

Q1（概念回忆）：用一个等式总结 MCP 能当”通用插头”的原因，并说出等式两端各自解决什么问题。
A1：通用插头 = MCP 协议层 + MCP 传输层。协议层解决”不同工具返回数据格式不统一”，传输层解决”不同工具传输方式不统一”。在 §2 / 图 f020。

Q2（概念辨析）：MCP 协议层和 MCP 传输层各自的”管辖范围”是工具到 Server 这一段，还是覆盖整条链路？
A2：两者都是贯穿三节点的横切关注点，不是某一段的属性。协议层从 Server 包好格式一路送到 Host；传输层在 Host↔Client、Client↔Server 每一段链路都参与传输机制选择。在 §2”关键转折”段。

Q3（反直觉陷阱）：如果设计 MCP 时把所有传输方式都规定成 HTTP，会出什么问题？
A3：本地 Excel、Word 等本地文件工具直接出局，它们只能通过本地进程通信。所以传输层必须存在并能”自选”，这就是为什么”统一格式”一件事不够，必须”格式 + 传输”两件事一起统一。在 §3 第 1 条。

Q4（跨集连接）：3-6 提过 STDIO / SSE / Streamable HTTP 三种传输方式，本集的传输层理论如何映射到它们？
A4：STDIO 对应本地进程通信，用于同节点场景（如 Host 和 Client 同机）；SSE 和 Streamable HTTP 属于 HTTP 家族，用于跨节点场景（如 Client 和 Server 在不同机器）。传输层运行时根据”是否同节点 / 是否本地资源”自动选择其中之一。在 §4 下启。

Q5（应用 / 推广）：假设你要给一个新协议 X 设计”跨厂商复用”能力，能否套用本集结论？要套用需要满足什么前提？
A5：能。前提是 X 也面临”格式不统一”和”传输方式不统一”两个独立问题。套用做法是引入两层横切：一层约定统一数据格式（让消费方只解析一种格式），一层自选传输机制（让生产方按场景换通道）。底层是关注点分离思想，前提是这两个维度的变化频率/原因不一样，分层才有收益。在 §4 横向 + 知识地图底部。

7. 关键词表

术语 一句话定义
MCP 协议层 约定响应数据的统一格式，让大模型用一套解析逻辑应对所有工具返回
MCP 传输层 自主选择合适的数据传输机制（HTTP / 本地进程），按场景切换
两个不统一 ①工具返回数据格式不统一 ②工具传输方式不统一，本集所有讨论的母题
通用插头公式 通用插头 = MCP 协议层 + MCP 传输层
分层贯穿三节点 协议层和传输层都是贯穿 Host↔Client↔Server 全链路的横切关注点，不是某一段
同节点 / 跨节点 Host 与 Client 可同机（走本地进程）也可跨机（走 HTTP），由传输层运行时自选
本地进程通信 同机节点间的传输机制，针对本地文件这类不能走 HTTP 的资源
关注点分离 “传什么格式”和”怎么传”被解耦成两层的设计哲学，与 OSI / TCP-IP 同源

摘要：取舍出现在 §2”关键转折”段（不展开”为什么分层更优雅”，只点到关注点分离）。加工增量在 §6 Q5——把本集结论抽象成”双层横切”通用方法论并加上”两个维度变化频率不同才有收益”的前提条件，这一前提在 understanding.md 中并未出现，属于强制加工。
