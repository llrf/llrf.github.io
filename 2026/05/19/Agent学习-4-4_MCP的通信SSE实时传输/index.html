4-4_MCP的通信SSE实时传输

发表于2026-05-19|更新于2026-05-19|Agent学习第4章 SpringAi 1.1 实现 MCP+A2A
|浏览量:

§1 一句话定位

看完这一集，你能解释清楚 MCP 三节点之间到底走的是什么协议，并能用 DeepSeek 网页 F12 里的两个细节，反推出”这不是 WebSocket，这是 SSE”。

§2 主体讲解

先把结论钉在墙上

MCP 三节点（Host / Client / Server）之间的通信，跨机器走 SSE，同机器走 STDIO。不是普通 HTTP，也不是 WebSocket。

之所以要先把结论钉死，是因为如果你跟着”侦探式推理”走，会被中间一堆”是不是 WebSocket？也不是 WebSocket”绕晕。结论一出，下面所有内容就只是在解释这条结论里的两个字——为什么是 SSE 而不是 HTTP/WebSocket，为什么同机器要换成 STDIO。

为什么不是”普通 HTTP”

普通 HTTP 的灵魂只有一句：服务端不能主动找客户端，必须等客户端再问一次才能再答。一次请求一次响应，连接随即断开。

但大模型不是这么用的。你在 DeepSeek 网页里发一个问题，模型像打字机一样一个字一个字往外吐——你只发了一次请求，服务端却分了几十上百批回传。这跟”一次请求一次响应”是冲突的。

所以肯定不是普通 HTTP。但这里要小心一个坑：SSE 在协议层面其实仍然是 HTTP，只是 Content-Type 改成了 text/event-stream，连接保持不关，服务端持续往这条同一条 TCP 上推 data: 行。所以”不是普通 HTTP”指的是不是”一来一回就断”的用法，而不是不走 HTTP。这一点 transcript 没有挑明，是我加工出来的——加工增量在 §2 这一段。

F12 里的两条铁证

打开 DeepSeek 网页，F12 → Network → 过滤 fetch，发一个 prompt。你会看到两件事：

  1. 那条 completion 请求的”大小”一直在涨（1.6KB → 几十 KB），不是一次拿完，是分批往同一条响应上追加。
  2. 在它还在吐字时，输入框的发送按钮是灰的，根本点不动，必须等这一轮结束才能发下一条。

第 1 条说明：这是流式长连接，不是普通 HTTP。
第 2 条说明：这不是 WebSocket——WebSocket 的双向意味着你应该可以随时再发一条打断它。按钮灰着，就是单向的物证。

如果你还想再加一条铁证，点开那条 completion 看响应头，会看到 Content-Type: text/event-stream——这是 SSE 的正脸。

SSE vs WebSocket 一句话讲清

  • WebSocket：长连接 + 双向。建好连接后，客户端可以随时发，服务端也可以随时推。
  • SSE：长连接 + 单向（服务端→客户端）。客户端发一次请求开启连接，期间不能再发，只能听服务端”播报”，直到这条连接断开，才能发下一条。

判别它俩的最快锚点就是上面那条：”在长连接期间，客户端还能不能主动发请求？”能就是 WebSocket，不能就是 SSE。

为什么大模型不选更”强”的 WebSocket

你直觉上会想：WebSocket 双向，功能是 SSE 的超集，那为啥不直接上 WebSocket？两点：

  1. 业务上根本不需要双向。你提完问题之后，在模型”吐字”期间没必要再插一句嘴——你只会等它说完，再发下一条。双向能力浪费。
  2. SSE 是”轻量级 WebSocket”。同样实现”服务端主动推”，SSE 的连接管理、协议握手都更便宜。大模型服务同时面对海量在线用户，省一点是一点。

第二点这个”轻量级”我不打算展开到字节级，这点不展开，因为这一集的重点是协议选型的工程取舍，不是性能基准。取舍出现在 §2 此处。

把推理传染到 MCP 三节点

现在回到开场的结论。前端 ↔ 大模型是 SSE，这是被业务场景（流式吐字）逼出来的。但 MCP 三节点之间为什么也是 SSE？

逻辑链是这样：大模型要把答案分批回吐给前端 → 那它在内部调用 MCP 工具时，工具回来的数据也得能”流着回”，不能等全部就绪一次性扔回去 → 所以 Host ↔ Client ↔ Server 这条链也得用支持流式的协议 → SSE 是最合适的选择。

这种”前端用什么 → 内部就得配什么”的传染，是本集真正的钩子。

同机器特例：STDIO

跨机器的故事讲完，还剩一种情况：MCP Host 和 MCP Client 本来就跑在同一台机器上（很常见，因为 Client 是 Host 的”小弟”），那走网络协议就太奢侈了。直接走标准输入输出（STDIO）即可——本质是进程间通信，不经过 TCP/IP 栈。

同理，MCP Server 如果访问的是本地服务（不是第三方 API），那也走 STDIO（线程间通信）。

边界条件总结：

  • MCP Server 调第三方 API：HTTP
  • MCP Server 调本地服务：STDIO
  • MCP Host ↔ Client（跨机器）：SSE
  • MCP Host ↔ Client（同机器）：STDIO
  • MCP Client ↔ Server（跨机器）：SSE

§3 我一开始没 get 的点

  1. “不是 HTTP” ≠ “不走 HTTP 协议栈”。如果你听到”MCP 通信不是基于传统 HTTP”就以为它换了一套底层协议，会得到错的心智模型。SSE 仍然跑在 HTTP 之上，只是用 text/event-stream 把连接掰成了流式单向。换句话说：协议是 HTTP，用法不是传统 HTTP。

  2. WebSocket 更强 ≠ 应该用 WebSocket。如果你按”功能超集”原则选协议，你会选 WebSocket，但你会得到一个被浪费一半能力、还更耗资源的方案。判别业务到底需不需要双向，比”哪个更强”重要。

  3. F12 里的”按钮灰掉”才是 SSE 的诊断标志。如果你只看到流式吐字就判定”这是 WebSocket”，你会错。流式吐字是 SSE 和 WebSocket 共有特征；单向限制（不能在长连接期间再发）才是 SSE 独有。

  4. STDIO 不是”另一种网络协议”。如果你把 STDIO 跟 SSE/HTTP 放在同一个分类下比较，你会困惑”它的端口在哪里”。STDIO 根本不走网络，是进程之间互相通过标准输入输出读写——和 Unix 管道一个原理。

§4 跟其他集的连接

上承

3-6 把 MCP 的三种传输方式（SSE / STDIO / Streamable HTTP）当名词清单丢出来过，本集补上了 SSE 和 STDIO 的”为什么”——为什么这俩是首选，分别在什么场景下用。上一集 4-3 抛出过”MCP 传输层能根据节点位置自主选机制”的承诺，本集把这个”自主选”具体化成了：跨机器 SSE、同机器 STDIO。

下启

讲到这里，Streamable HTTP 这个名词还没兑现——3-6 提过它，本集没讲。按 MCP 官方时间线，Streamable HTTP 是 SSE 的升级版（解决了 SSE 单向、连接管理、断线重连等限制），很可能就是下一集 4-5 的内容。

横向

和 3-4 / 3-5 的”MCP 三节点架构”强耦合——本集是给那个架构图加上”通信线”。和 3-6 形成上下层呼应：3-6 是”用 MCP”，本集是”MCP 怎么传”。另外，这一集解释清楚了一个工程现象：为什么大模型网页会有打字机效果——不是为了酷，是 SSE 流式输出的天然产物。

§5 知识地图

§6 自测题

Q1（概念回忆）：SSE 的全称是什么？它在 HTTP 响应头里靠哪个字段把自己跟普通 HTTP 区分开？
A1：Server-Sent Events。响应头 Content-Type: text/event-stream。答案见 §2”F12 里的两条铁证”。

Q2（概念辨析）：SSE 和 WebSocket 都是基于长连接的实时通信，最关键的一处差别是什么？给出一个能在浏览器里直接观察到的判别现象。
A2：方向。SSE 单向（仅服务端→客户端），WebSocket 双向。判别现象：在长连接期间客户端能不能再主动发请求。在 DeepSeek 网页上，模型还在吐字时发送按钮是灰的——这是 SSE 的特征；如果是 WebSocket，按钮应该可点。答案见 §2”SSE vs WebSocket 一句话讲清” + §3 第 3 条。

Q3（反直觉陷阱）：朋友说”MCP 通信不是基于传统 HTTP”，因此推断”MCP 用了一套和 HTTP 平行的全新底层协议”。这个推断哪里错了？
A3：错在把”不是传统 HTTP 用法”等同于”不走 HTTP 协议栈”。SSE 仍然跑在 HTTP 之上，只是用 text/event-stream 把连接掰成了流式单向；底层协议栈没换，换的是用法。答案见 §3 第 1 条。

Q4（跨集连接）：3-6 把 MCP 传输方式列成”SSE / STDIO / Streamable HTTP”三选一。本集补足了哪两个的”为什么”？剩下那个为什么还没讲？
A4：本集补足了 SSE（跨机器，因为要配合大模型流式输出）和 STDIO（同机器，进程/线程间通信省网络开销）的为什么。Streamable HTTP 没讲，它是 SSE 的升级版，很可能是下一集 4-5 的内容。答案见 §4”上承”和”下启”。

Q5（应用推广）：假设你在做一个股票实时行情推送网页，行情每秒推送几十次，用户基本不需要在推送期间再发请求（只是看）。你会选 SSE 还是 WebSocket？为什么？
A5：选 SSE。理由完全同本集大模型场景：业务上不需要客户端在推送期间发请求（单向就够了），SSE 比 WebSocket 更轻量、资源占用更少，对”一台服务器扛大量在线用户”的场景更友好。如果业务里加上了”用户要发交易指令打断行情”，那才需要 WebSocket。答案见 §2”为什么大模型不选更’强’的 WebSocket”。

单向 vs 双向实时通信 区分 SSE 和 WebSocket 的关键维度，判别锚点是”长连接期间客户端能否再发请求” §2 + §3 第 3 条
