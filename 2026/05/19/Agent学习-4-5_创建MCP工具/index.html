4-5_创建MCP工具

发表于2026-05-19|更新于2026-05-19|Agent学习第4章 SpringAi 1.1 实现 MCP+A2A
|浏览量:

1. 一句话定位

学完这集，你能用两个 Spring AI 注解把一个普通 Java 方法变成”大模型可调用的工具”。

2. 主体讲解

先把两个核心疑问钉在墙上

你写一个 WeathTool 类，里面打算放两个方法：查城市气温、查城市紫外线。问题立刻就来了——

  1. 大模型怎么知道这个类里有这两个方法可以用？
  2. 假设它知道有这两个方法，当用户问”上海紫外线强不强？”时，它怎么知道该选哪一个？

把这两个问题钉牢，因为接下来要讲的所有东西，本质上都是在回答它们。你会发现 Spring AI 给的答案极其朴素：用注解告诉它。

@Tool：白名单 + 雷达描述

第一个注解 @Tool 一次性解决了上面两个问题，但它解决的方式分两层：

第一层是白名单。一个类里可能有 10 个 public 方法，但大模型默认看不见任何一个。只有打上 @Tool 的方法才会被”亮出来”。换句话说，没有 @Tool 等于对模型不可见——这就是工具暴露的安全边界。如果你下意识以为”public 方法模型就能看到”，会得到错误的心智模型。

第二层是路由依据，靠 @Tool 的 description 参数承载。这里要小心一个反直觉点：description 看起来像 Javadoc 一样的”注释文档”，但它不是给人看的，它是大模型挑工具时唯一能读到的元数据。你写 description = "获取指定城市的温度"，模型才知道用户问气温时该来敲这个方法的门。

所以 description 本质是一段面向模型的微型 prompt。写得含糊（比如就写个 “huo”）模型就会乱选，写得清晰精准模型才能命中。这是必填项，不是装饰。

@ToolParam：告诉模型”这个洞要塞什么”

接下来你想：方法肯定要传入”城市名”作参数。直接写 String cityName 行不行？不行。模型默认也看不见参数。

第二个注解 @ToolParam 就是干这个的——加在形参前，让模型知道”调用时要喂一个城市名给我”。这样模型才能把用户原话里的”上海”抽出来，塞进 cityName 这个槽位。

至此模型完成了一整条调用链：

  • 通过 @Tool 知道有哪些方法可调用
  • 通过 description 决定这次该调哪个
  • 通过 @ToolParam 知道要塞什么参数

方法体里到底怎么实现、调不调墨迹天气 API、还是返回个假字符串占位——模型完全不关心。这一集其实只解决”声明”，不解决”实现”。墨迹天气这种真 HTTP 调用是后面的事，本集不展开（取舍点 1）。

加工增量：为什么 @Tool 来自 spring-ai 主包，不是 mcp 专属包？

这里有个非常容易看走眼的细节——@Tool 不在 spring-ai-mcp 包里，而在 org.springframework.ai.tool.annotation 下。看起来只是个 import 路径问题，背后其实是一条很有意思的设计脉络（这点 understanding.md 没展开，是本节强化加工的地方）：

工具调用这个抽象在 Function Calling 阶段就已经成熟（参考 3-2/3-3）。FC 时代你把工具列表手动塞给模型，模型决定调谁。MCP 时代变了什么？变的是工具住在哪——不再嵌在你的应用进程里，而是搬到独立的 MCP Server。但”什么算一个工具、模型怎么读它”这套抽象没必要重新发明，Spring AI 直接复用了原本 FC 时代的 @Tool / @ToolParam。

所以你看到一个奇景：本集的 mcp-server 子模块 pom.xml 里一个 MCP 专属依赖都没引，光靠父 pom 的 spring-ai-mcp + spring-ai 主包的注解，工具就能写完。这暗示：工具定义本身和 MCP 协议是解耦的，MCP 那一堆传输层依赖（SSE、STDIO 这些 4-4 提过的东西）是注册和暴露阶段才需要的——也就是下一集的事。

工程脚手架：放在最后扫一眼就好

至于 Maven 子模块怎么建、mcp.server.tools 包怎么切分、@Component 为什么要打——这些是工程体力活，记住三件事就够：

  • 子模块叫 mcp-server，parent 指向主项目 Demo-MCP，未来会有对称的 mcp-client。
  • 工具类约定放在 mcp.server.tools 下，一个类聚一组同主题工具（如 WeathTool 聚天气类）。
  • 类上要打 @Component，否则 Spring 容器扫不到，MCP Server 也就不知道这个 Bean 的存在——它是”注册”的前置条件，但不是注册本身，注册过程是 4-6 的内容。

3. 我一开始没 get 的点

  1. 如果你以为 description 是给人看的注释，会得到错的工具调用结果。 它是大模型挑工具时唯一能读到的元数据，写得越含糊模型越容易选错——本质是一段 prompt。
  2. 如果你以为 public 方法默认对大模型可见，会构建错的安全模型。 没有 @Tool 注解的方法对模型完全不可见，这是”白名单暴露”，不是”黑名单屏蔽”。
  3. 如果你以为 @Tool 来自 spring-ai-mcp 包，会找错 import。 它来自 spring-ai 主包的 org.springframework.ai.tool.annotation，因为工具抽象从 Function Calling 时代就存在，MCP 只是换了宿主。
  4. 如果你以为这一集的 demo 真能跑出天气数据，会失望。 方法体只返回占位字符串，连第三方 API 都没调；本集的边界是”声明工具”，”实现工具 + 注册工具”在下一集。

4. 跟其他集的连接

上承

3-4 / 3-5 把 MCP Server 抽象成”工具列表的提供方”，说”MCP 解决了 FC 时代工具要手动投喂的痛”。但那时讲的都是黑盒——“工具列表”到底长什么样、Java 里怎么写一个工具，没落地。本集就是把这个抽象砸到代码层：你看到的 @Tool + @ToolParam 就是 3-4 那个”工具列表”的最小构造单元。同时 4-2 引入了 spring-ai-mcp 依赖、4-4 讲完了 SSE 传输怎么搭，整套传输管线已经就位，本集补的是”管线里跑什么货”。

下启

工具现在写好了，但 MCP Server 还不认识它——它只是一个标了 @Component 的普通 Spring Bean。4-6 会回答”谁在收集所有 @Tool 方法、把它们注册成对外暴露的工具列表”，那时 mcp-server 模块的 pom 才会真正开始引入 MCP 专属依赖。另外业务方法目前都是占位字符串，下一集大概率把真实 HTTP 调用（墨迹天气之类）补上。

横向

和 3-6 JManus 配 MCP 形成完美镜像——3-6 是”用别人造好的 MCP 服务”，本集是”造自己的 MCP 服务”。和 3-7/3-8 的 Agent Skills 对照也很有意思：Skills 的元数据描述、本集的 description、FC 的工具描述，三者在结构上高度同构——都是”让模型按需发现能力”的元信息层。

6. 自测题

Q1（概念回忆）：@Tool 注解在 Spring AI 里同时承担哪两个作用？
A1：一是白名单——只有被它标注的方法对大模型可见；二是承载 description 属性，作为大模型决定何时调用此方法的依据。详见 §2 / 图 f061。

Q2（概念辨析）：@Tool 和 @ToolParam 的职责差别是什么？
A2：@Tool 修饰方法，解决”暴露哪些工具 + 何时调用”；@ToolParam 修饰形参，解决”调用时该往里塞什么值”。前者回答模型”调谁、何时调”，后者回答”调用时参数怎么填”。详见 §2 / 图 f071。

Q3（反直觉陷阱）：把 description 当成普通 Javadoc 注释写得很含糊，会发生什么？为什么？
A3：模型会频繁选错工具甚至放弃调用。因为 description 是模型在路由阶段唯一能读到的元数据，本质是一段面向模型的微型 prompt，不是给人看的文档。详见 §3 / understanding.md。

Q4（跨集连接）：本集只写了 @Tool + @Component，但工具还没真正出现在 MCP 暴露的工具列表里——缺的环节由哪一集补上？补什么？
A4：4-6 补上”注册”环节，会回答谁来收集所有 @Tool 方法、把它们装配成 MCP Server 对外暴露的工具列表，此时 mcp-server 模块也才会真正引入 MCP 专属依赖。详见 §4 下启。

Q5（应用 / 推广）：你现在要给一个 Spring 项目加上”查询订单状态”的能力让大模型能调用，最少要做哪几步？
A5：写一个方法 getOrderStatus(String orderId)；方法上加 @Tool(description="根据订单号查询订单当前状态")；参数前加 @ToolParam；类上加 @Component。这四件事完全套用本集结论。注册到 MCP 暴露则等 4-6 的机制接进来。详见 §2。

7. 关键词表
