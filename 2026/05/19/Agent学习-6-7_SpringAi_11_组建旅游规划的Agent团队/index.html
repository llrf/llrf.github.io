6-07 SpringAi 1.1 组建旅游规划的Agent团队

发表于2026-05-19|更新于2026-05-21|Agent学习第06章 多 Agent + ReAct架构，SpringAi迈入Agent新时代
|浏览量:

1. 一句话定位

这一集你做的事只有一句：把一个 ReactAgent 塞进另一个 ReactAgent 的 .tools() 里，多 Agent 团队就组建完了——不是 A2A、不是主管派单，是同辈横向嵌入。

2. 主体

2.1 从单 Agent 出发：你已有的肌肉

⏱ 00:00–03:15 · 回顾 6-6 单 Agent 六件套 + 1.1 自主决策能力

前一集 6-6 你刚把 ReactAgent.builder() 五件套（model / tools / hooks / systemPrompt / saver）拼出过一个 weather_agent。本集开头用大段时间复习它，是为了告诉你：ReactAgent 不仅有大脑、手脚、记忆、感知，还多了规划和自主决策两个能力——所以它现在可以独立干活。

⏱ 00:40

但单个 Agent 不够。讲师的话：”多个 ReActAgent 协调合作，才叫 Agentic AI。”于是从单 Agent 跳到团队。

📺 04:04–06:42 · IDE 写 MultiAgentsController + 四个 ReactAgent.builder

把单 Agent 复制粘贴四份，改 name / description，就是一支团队的骨架。新建 controller/MultiAgentsController.java：

⏱ 04:25

注意这里的 builder 只用了 name + description + tools + build 四件——model / saver / systemPrompt 全省。取舍出现在 §2.2：demo 简化用了”省略 model”的偷懒写法，能编译过是因为 1.1 RC2 在没显式传 model 时会兜底（用全局配置），生产代码该补回来。

四个角色对应 5-1 拆出来的需求树：

  • routeMakingAgent——路线制定
  • tripPlannerAgent——行程规划
  • budgetAgent——费用统筹
  • managerAgent——全局主管

⏱ 06:27

2.3 关键发现：description 才是路由表

⏱ 05:02–06:04 · description 不是注释，是 LLM 多 Agent 派单依据

你写 .description("你是负责统筹旅游费用") 时容易当成注释。不是。讲师反复说：”你不可能把做财务的智能体调去写代码。”——上游 LLM 看到一堆候选 Agent，只能靠这段自然语言决定派谁。

把它当 prompt 工程对待，不是 Javadoc。name 只是 ID，description 才是 LLM 在多个 Agent 之间路由的唯一依据。

2.4 协同的最弱实现：Agent 套 Agent

📺 07:20–09:00 · IDE 调整 budgetAgent 顺序 + 把它嵌入 route/trip 的 tools

四个 Agent 声明完，问题来了——怎么让它们协同？

讲师给的不是 A2A，不是主管调度，而是最朴素的一招：做路线、做行程都涉及费用 → 把 budgetAgent 当一个工具塞进 routeMakingAgent 和 tripPlannerAgent 的 .tools()。

2.5 接口胶水：AgentTool.getFunctionToolCallback

📺 09:16–11:00 · IDE 现场调 AgentTool.getFunctionToolCallback 接口胶水

.tools() 的签名是 Builder tools(ToolCallback... tools)——只吃 ToolCallback。但 ReactAgent 不是 ToolCallback。所以中间需要一层适配。

⏱ 05:05

AgentTool 这个类有一个静态方法 getFunctionToolCallback(agent)，把 ReactAgent 包装成 ToolCallback。这就是 Agent-as-Tool 的全部秘密——一个静态工厂方法。

⏱ 10:37

加工增量在 §2.5：消化稿提到 .tools() 这一集起接受两种来源（@Tool 注解 → MethodToolCallbackProvider；Agent → AgentTool.getFunctionToolCallback）。这里挑明：本质都是 ToolCallback，工厂方法不同，接口统一——这是为什么团队组建能这么轻。

2.6 团队拓扑：本集结尾的状态

⏱ 12:03–12:27 · 总结本集团队结构：两线嵌入，主管悬空

只画了两条线，managerAgent 还悬空：

本集名字是”组建团队”而不是”协作“——招齐人 + 拉两条横向依赖线，主管怎么派单留给下一集。

3. 没 get 的点

  • managerAgent 怎么跑？ 这一集只声明它，没让它接管 route / trip / budget。下一集大概率把这三个全嵌进它的 .tools()——如果真是这样，”主管”在技术上和 budgetAgent 没区别，只是语义不同。
  • GraphRunnerException 从哪里冒出来的？ 单 Agent 的 streamChat 不抛这个。/multi/agent 方法签名里有——是不是说多 Agent 自动编排成 4-9 提的 Graph？需要看源码确认。
  • Agent-as-Tool 时 budget 收到什么输入？ 上游 LLM 调它，参数是 ToolCallback 的 input schema 还是 prompt？description 是同时给上下两层 LLM 看吗？要去翻 AgentTool.getFunctionToolCallback 的源码。
  • 本集没运行——只是把代码写完，不知道 run 起来什么效果。

4. 跟其他集连接

  • 上承 6-6（单 Agent ReactAgent.builder 五件套）——本集只用四件，少了 model/saver。
  • 上承 5-1 / 5-2 / 5-3 / 5-4——需求文档里的”角色定义 + 能力清单”，落成一行 Java 字符串。
  • 上承 4-13（.tools(@Tool 方法)）——本集替换的只是塞进 tools 的”内容物”。
  • 横向对照 3-9 / 3-12（主管 + 专科五步骨架）——3-9/3-12 讲纵向调度，本集讲横向嵌入。两层不同，应该并存，本集只演示一半。
  • 横向对照 3-10 / 4-11~4-16 A2A——A2A 是跨进程同辈协作（Nacos 注册），本集是同 JVM 同辈协作（直接拿对象引用）。同一种”Agent 调 Agent”，两种部署形态。
  • 下启：managerAgent 真正跑起来 / tools 里具体放什么（百度地图 MCP / 自定义 @Tool）→ 5-6 提供工具源。

7. 关键词表

术语 一句话
Agent-as-Tool 把一个 ReactAgent 嵌入另一个 ReactAgent 的 tools 列表，形成横向协作。
ReactAgent.builder 1.1 装配 Agent 的链式入口；本集只用 name/description/tools/build 四件。
description 即派单依据 自然语言描述能力边界，上游 LLM 据此选谁干活；name 只是 ID。
AgentTool.getFunctionToolCallback 把 ReactAgent 适配成 ToolCallback 的静态工厂方法，是接口胶水。
横向嵌入 vs 纵向调度 横向 = 同辈工具化（本集），纵向 = 主管派单（3-9/3-12，本集未做）。
MultiAgentsController @RestController + /multi/agent SSE 端点 + 抛 GraphRunnerException，多 Agent demo 载体。
四角色团队 routeMaking / tripPlanner / budget / manager——三专科 + 一主管，对应 5-1 需求树。
ToolCallback 接口胶水 .tools() 统一只吃 ToolCallback；@Tool 方法和 Agent 走不同工厂，落点相同。
