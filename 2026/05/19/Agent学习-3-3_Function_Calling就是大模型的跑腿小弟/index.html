3-3 Function Calling 就是大模型的”跑腿小弟”

一、本集主旨

承接 3-2 的”调用外部 API 解决实时性问题”思路，本集要拆穿一个最容易被忽略的隐藏角色：当我们说”大模型会调用天气 API”时，真正干这件事的并不是大模型本身，而是它体内的一个小弟——Function Calling（函数调用），并且 Function Calling 也只是”传话的”，真正执行 HTTP 请求的还在大模型外部。

讲师围绕两个核心问题铺开：

# 核心问题 一句话答案
Q1 第三方应用的 API 到底是谁调用的？ 大模型内部的 Function Calling（调用者），但执行者是外部的 API 工具函数
Q2 为什么大模型不直接调用第三方 API？ 大模型的价值在于理解语义 + 逻辑推理，写代码 / 调 HTTP 不是它该干的事

四、关键概念逐一拆解

4.1 Function Calling 的精确定义

维度 描述
中文名 函数调用
位置 大模型内部的一个模块（不是外挂、不是工具）
角色 调用者（caller）——但不是真正的执行者
拿什么 拿大模型生成的”调用参数”（如 {"city":"深圳","date":"今天"}）
干什么 把参数传给大模型外部对应的 API 工具函数
比喻 老板（LLM）的前台 / 跑腿小弟

4.2 外部 API 工具函数（External API Tool Function）

维度 描述
位置 大模型外部
谁写的 开发人员手写
为什么写 因为用户不断追问实时类问题（天气、股票、交通），开发者必须给 LLM 配一套”手脚”
角色 真正的执行者——真正发起 HTTP 调用第三方原生 API 的代码就在这里
例子 墨迹天气 API 工具函数、高德地图 API 工具函数、同花顺 API 工具函数
入参从哪来 由 LLM 通过 Function Calling 传进来

4.3 “手动投喂”（Manual Registration）

LLM 自身并不天然知道外部有哪些工具函数。开发人员要把这些工具函数的签名 / schema / 说明主动**注册（投喂）**给 LLM。LLM 只有读到这份”工具清单”，才能在推理时挑选出哪个工具可以解决用户当前需求。

视觉表达：图 f018 的左下”手动投喂”绿色标签 + 红色竖箭头，方向是从外部 → LLM。

五、讲师的”老板/前台/打印机”比喻（本集第二大记忆点）

讲师在 9~10 分钟处用了一段非常生活化的比喻：

PPT 抽象概念 老板比喻
LLM 老板
Function Calling 前台
外部 API 工具函数 打印机（具体执行打印的设备）
第三方原生 API 打印机里的打印业务

老板要打印东西 → 把材料和参数给前台 → 前台去操作打印机 → 打印机打印出结果。
老板没有也不应该亲自去操作打印机；老板的职责是找投资、定战略、带公司盈利。

底层论点：”大模型公司投入巨资训练 LLM，不是让它写代码调 HTTP 的，而是让它做擅长的事——理解语义、逻辑推理、判断意图。”

这个比喻把”为什么要分层”讲透了：职责分离 = 高价值资源用在高价值事情上。

六、为什么不让大模型直接调用 API？——三层论证

讲师没有直接给结论，而是层层推进：

第一层（直觉级）：”不就是绕了一圈吗？”

学生的疑问：既然 LLM 知道墨迹天气提供了 API，为什么不直接调用？非要走 Function Calling → 工具函数这两层中转。

第二层（职责级）：LLM 擅长的事 vs. 该让它做的事

  • LLM 擅长：理解用户语义输入 + 逻辑推理 + 判断意图
  • LLM 不擅长 / 不该做：写工具函数、发 HTTP 请求、解析 API 响应

第三层（投资级）：训练成本视角

“大模型公司投入这么大资源、这么多金钱训练大模型，不是为了让它去写工具函数。” 这是一句很硬的商业逻辑——把模型用到刀刃上。

结论

LLM 只做两件事：

  1. 判断用户需求是否需要外部数据；
  2. 在已注册的工具清单里挑出最合适的工具，并生成调用参数。

剩下的”传参 + 执行调用 + 拿回结果”全部下放给 Function Calling + 外部工具函数。

八、思考题（自测）

  1. 角色辨析：下列三者各自属于”大模型内部”还是”大模型外部”？
    • ① Function Calling
    • ② 墨迹天气 API 工具函数
    • ③ 墨迹天气服务器本身
  2. 数据流向：当用户问”深圳今天气温”时，参数 "深圳" 是由谁生成、传给谁、最终交给谁？请用 4 步描述。
  3. 手动投喂：如果开发者没有把”高德地图 API 工具函数”投喂给 LLM，那么用户问”现在去机场堵车吗？”会发生什么？LLM 会编造结果还是承认无能？
  4. 职责切分：假如让 LLM 自己用 Python 直接 requests.get(...) 调用墨迹天气 API，会带来哪些工程上的问题？（提示：可控性、错误处理、密钥管理、可观测性、成本）
  5. 延伸思考：如果 LLM 选错了工具函数（比如把”查股票”问题派给了天气 API 工具函数），是 LLM 的错还是 Function Calling 的错？应该在哪一层加防护？

九、关键词表

术语 含义
Function Calling 大模型内部的一个模块；负责把 LLM 生成的调用参数转交给外部工具函数。本集核心比喻”前台 / 跑腿小弟”
函数调用 Function Calling 的中文译名
外部 API 工具函数 大模型外部、由开发者手写的代码；真正执行第三方 API 调用的执行者
第三方应用 提供原生 API 的服务方，如墨迹天气、高德地图、同花顺
手动投喂 开发者把工具函数的描述 / schema 注册给 LLM 的过程；LLM 据此知道有哪些工具可用
调用者 vs 执行者 调用者 = Function Calling；执行者 = 外部 API 工具函数。两者是分离的角色
实时性数据 训练后才发生 / 持续变化的数据，如气温、股价、交通——LLM 自身无法回答，必须靠工具
老板 / 前台 / 打印机 比喻 讲师用的生活化类比：LLM = 老板、Function Calling = 前台、工具函数 = 打印机
