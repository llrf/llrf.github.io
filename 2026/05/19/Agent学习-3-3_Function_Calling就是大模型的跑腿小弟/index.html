3-03 Function Calling 就是大模型的"跑腿小弟"

发表于2026-05-19|更新于2026-05-21|Agent学习第03章 MCP + Skills，Agent"工具+技能"的双轮驱动
|浏览量:

§1 一句话定位

看完这集你就能回答：当用户问”深圳今天多少度”时，是谁真正去敲了墨迹天气的 API。

§2 主体讲解

2.1 先把三段调用链立起来

⏱ 01:50–02:46 · 拆开两段→三段调用链，纯讲

你脑子里大概默认有一条链：LLM → 第三方 API。这一集要把它拆成更长的一条：

这条链里，前两段（LLM、Function Calling）住在大模型内部，后两段（工具函数、第三方 API）住在大模型外部。把这张图先在脑子里钉死，后面所有的疑问都是绕着它转。

⏱ 08:49

这张图里有四个角色和两道虚拟的墙。左边是 LLM，被一道”内部边界”圈住；右边一串”墨迹天气 API 工具函数 / 高德地图 API 工具函数”住在边界外；最远端才是真正的第三方应用。Function Calling 就贴在那道边界的内侧——它是大模型派出去喊话的小弟，不是 LLM 本人。

2.2 调用者 vs 执行者：这一集的核心二分

⏱ 04:00–04:51 · 区分调用者与执行者，纯讲

第一遍听很容易把”调用”和”执行”画等号。这一集偏要把它们劈开：

  • Function Calling 是调用者：它拿着 LLM 给的参数（深圳、今天）发起一次调用，仅此而已。
  • 工具函数才是执行者：它内部封着 HTTP 请求、签名、参数序列化——真正干脏活的是它。

你如果把这俩混为一谈，就会得到一个错觉：”那 FC 不就是包了一层 HTTP 调用吗？”——不是的。FC 这一层里没有任何 API 业务逻辑，它只负责”按 LLM 给的工具名 + 参数去戳一下对应的工具函数”。

之所以要这么劈开，本质是分工：LLM 不该知道墨迹天气的鉴权方式，工具函数也不该知道用户原始问题长什么样。中间这层小弟就是负责把”LLM 的意图”翻译成”工具函数能吃的参数表”。

2.3 用”深圳今天几度”走一遍这条链

⏱ 03:21–04:25 · 完整走一次深圳气温链路，纯讲

把抽象的图灌进具体例子，记忆才挂得住：

  1. 用户问 LLM：”深圳今天气温多少度？”
  2. LLM 想了一下：这是实时数据，我答不上来，但我知道外面有个墨迹天气 API 工具函数能解。
  3. LLM 把决策结果（用哪个工具、传哪些参数）丢给内部小弟 Function Calling，告诉它：拿着 地点=深圳, 日期=今天 去敲那个工具函数。
  4. Function Calling 出门，调到墨迹天气工具函数。
  5. 工具函数发起真正的 HTTP 请求到墨迹天气 API，拿回 JSON 数据。
  6. 数据沿链返回 LLM，LLM 用自然语言整合回复用户。

⏱ 01:27

2.4 为什么非要绕这么一圈

⏱ 09:30–10:55 · 老板-前台-打印机比喻，价值定位推理

你可能会想：LLM 既然知道墨迹天气有 API，干脆自己发 HTTP 不就行了，何必架两层中间人？

答案是价值定位。训练一个大模型烧的钱，是为了换它的语义理解 + 推理能力。让它去拼 HTTP 请求、处理重试、做鉴权——是在拿吉他当筷子用。所以架构上故意剥离执行能力：

  • LLM 只做两件事：听懂用户意图 + 挑出合适的工具。
  • 至于怎么发请求、怎么解析响应，外推给工具函数。

这里有个老板-前台-打印机的比喻挺好记：老板（LLM）要打文件，他不会自己跑去打印机前操作，而是把内容交给前台（Function Calling），前台再去操作打印机（工具函数）。老板的价值在战略和决策，不在按打印按钮——一年后忘了术语，记住这个比喻就能反推。

2.5 工具函数从哪来：本集埋的伏笔

⏱ 07:35–08:15 · 开发者手动投喂工具清单，纯讲

最后一个问题：LLM 怎么知道外面有”墨迹天气工具函数”这种东西存在？

答案是开发者手动投喂。每一个工具函数（墨迹天气、高德地图、同花顺……）都是开发者写好、然后把”工具清单”塞给 LLM 的。LLM 是被动接收这个清单的，它没法自己去外面”扫描”还有什么工具。

这一段我点到就停——因为”手动投喂”恰好是 3-4 MCP 要解决的痛点。这里展开会喧宾夺主，留到下一集再炸开。

§3 我一开始没 get 的点

  1. 如果你以为”Function Calling 调用了 API”，你会漏掉中间那层工具函数。FC 调用的是开发者写的工具函数，工具函数才去敲第三方 API。这条链是三段（LLM → FC → 工具函数 → API），不是两段。
  2. 如果你把”调用者”和”执行者”画等号，你会以为 FC 里有业务逻辑。其实 FC 这层是空壳——它只搬参数，业务代码在工具函数里。”调用 != 执行”是本集的钥匙。
  3. 如果你以为大模型能”自己发现”外部有什么工具，你就跳过了开发者那一步。LLM 不会扫描、不会嗅探，它的工具清单完全靠开发者手动塞进来。这条限制就是 3-4 MCP 存在的理由。
  4. 如果你纠结”为什么不让 LLM 直接发 HTTP”，你就把它当成万能脚本引擎了。LLM 烧的训练成本是买它的”判断力”，不是买”执行力”——执行力外包反而更便宜可控。

§4 跟其他集的连接

上承

3-2《困境解决方案函数调用 Function Calling》提到过”调用外部 API 的执行者是 Function Calling”这句话——但那只是甩了一个名词。这一集把那个名词里的”执行者”三个字纠正了：FC 是调用者，工具函数才是真正的执行者。所以本集既是 3-2 的补全，也是对它一个口误的修正。

下启

3-4《更优的困境解决方案：MCP》会接住本集留下的两个钩子：(1) 工具函数要开发者手动投喂，工程上没法规模化；(2) 每家大模型 + 每家 API 各搞各的工具函数格式，没有统一标准。MCP 就是要把”手动投喂 + 各自为政”换成”标准协议 + 自发现”。

横向

跟 3-7《具有专业知识的 Agent Skills》形成对比：本集的”全量投喂工具清单”和 Skills 的”按需加载工具 + 领域知识”是同一个问题的两种解法。本集是 Skills 出现之前的原始形态。

§5 知识地图

§6 自测题

Q1（概念回忆） 在 LLM 调用外部 API 的链路里，Function Calling 到底是”调用者”还是”执行者”？真正的执行者是谁？
A1: Function Calling 是调用者——它只搬参数，没有业务逻辑。真正的执行者是大模型外部、开发者手写的工具函数（如墨迹天气 API 工具函数），由它真正发 HTTP 请求第三方 API。见 §2.2。

Q2（概念辨析） “Function Calling”和”工具函数”听起来都像”调用 API 的东西”，怎么区分？
A2: 看两个维度。位置：FC 在大模型内部，工具函数在大模型外部。职责：FC 只负责传参数（调用者），工具函数才封装真正的 HTTP / 鉴权 / 参数序列化（执行者）。一句话——FC 是空壳搬运工，工具函数才是干活的。见 §2.2 和图 f018。

Q3（反直觉陷阱） 如果你以为”大模型能自动发现外部有哪些工具可用”，会得到什么错误推论？
A3: 你会以为只要某个 API 在公网存在，LLM 就能找到并调用它——但实际上 LLM 的工具清单完全靠开发者手动投喂。没投喂的工具，LLM 根本不知道它存在。这正是 3-4 MCP 要解决的痛点。见 §3 第 3 条 + §2.5。

Q4（跨集连接） 3-2 说”调用外部 API 的执行者是 Function Calling”，这一集为什么要”修正”这句话？
A4: 3-2 那句话把”调用”和”执行”混了。本集精确化：FC 是调用者（搬参数），工具函数才是执行者（真正发请求）。这不是名词游戏——它决定了你画架构图时是画两段链还是三段链。见 §4 上承。

Q5（应用 / 推广） 假设你要让 LLM 能”查公司内部员工的入职日期”，套用本集结论，应该怎么搭？
A5: 完全套得上。开发者写一个”HR 系统查询工具函数”（封装内部 HR API 的 HTTP 调用 + 鉴权），把它的元信息手动投喂给 LLM 的工具清单。用户提问时，LLM 判断”这是 HR 数据问题”→ 选中该工具函数 → 通过 Function Calling 把参数（员工 ID、日期范围）传过去 → 工具函数执行 → 返回。LLM 自己绝不去碰 HR API 的鉴权。见 §2.4 价值定位。

§7 关键词表

概念 一句话
Function Calling 大模型内部的”小弟”模块，只搬参数、不写业务，是调用者不是执行者
工具函数 大模型外部、开发者手写的函数，封装第三方 API 的真实调用逻辑，是真正的执行者
三段调用链 LLM → Function Calling → 工具函数 → 第三方 API，看清这条链才不会把 FC 和工具函数混为一谈
调用者 vs 执行者 本集核心二分：FC 发起调用，工具函数完成执行；分清这俩才理解 FC 的定位
手动投喂 工具清单要开发者主动塞给 LLM，LLM 没法自发现工具——这是 3-4 MCP 要解决的痛点
大模型价值定位 LLM 的钱花在语义理解 + 推理，不该用来跑 HTTP；执行力外包给工具函数
老板-前台-打印机比喻 LLM=老板（决策）、FC=前台（搬参数）、工具函数=打印机（干活），一年后忘了术语用它反推

摘要：取舍出现在 §2.5（点到”手动投喂”即止，把展开留给 3-4 MCP，避免本集喧宾夺主）。加工增量在 §4 上承（明确指出 3-2 的”执行者是 FC”是一个口误，本集做了语义修正——这层”修正关系”在 understanding.md 里没有写）。
