总结Agent和Graph分别构建的工作流

一句话定位

SAA 1.1 给”多智能体协同的工作流编排”留了两条并列路线：Graph 引擎拼方法，FlowAgent 基类拼智能体——本集是第七章的收尾盘点，把这两套体系并排摊开来对照看。

主体

路线 A · Graph 引擎：编排的是”方法”

⏱ 00:00–04:50 · Graph 引擎两核心对象总结回顾，纯讲

这条路是从 SAA 1.0 沿用过来的，1.1 几乎没怎么动。整个引擎就靠两个核心对象撑起来。

第一个对象：StateGraph——工作流的视图定义器。你想把”一个旅游规划任务”画成一张图，节点和边都从这个对象上挂。它封装了三个 add 方法，刚好对应三种流程逻辑：

StateGraph 方法 干什么 对应流程
addNode(...) 往图里塞一个执行单元 ——
addEdge(...) 在两个节点间连一根线 顺序 / 并行
addConditionalEdges(...) 按当前状态分发到不同分支 路由

加工增量：讲师把”并行 / 顺序 / 路由”这三种业务流程逻辑当成了StateGraph 三个方法的语义投影。换句话说，Graph 这条路是用”画线”来表达流程的——并行就是从一个节点甩出多根 edge，顺序就是 edge 首尾相接，路由就是 conditionalEdges 按 state 分叉。

自定义节点和边走两组成对接口：

  • 节点：NodeAction（同步）/ AsyncNodeAction（异步），都是接口，得自己重写方法把”这个节点干啥”塞进去。
  • 边：EdgeAction（同步）/ AsyncEdgeAction（异步），同样是接口，重写”这条边怎么判定走向”。

带 Async 前缀的就是异步版，本质区别只是同/异步执行语义。

第二个对象：OverAllState——工作流的传话筒。这是一个 KV 格式的状态包，贯穿整个工作流：

没有它，Graph 的 node 就是一堆孤岛，谁也认不出谁。invoke(...) 最终返回的 Optional<OverAllState> 也是它——这一点上一集（7-12）已经踩过。

一句话总结路线 A：StateGraph 画骨架 + OverAllState 串血液，但每个节点里跑的只是一段普通的业务代码——是方法，不是会思考的智能体。这正是 1.1 觉得”不够用”的地方。

路线 B · FlowAgent 基类：编排的是”会思考的智能体”

⏱ 04:50–08:00 · FlowAgent 基类与三子类对比讲解，纯讲

为什么 1.1 还要新搞一套？讲师给出的理由是：

1.1 的重点是智能体——执行任务的应该是一个能思考、会用工具的 Agent，不是一段死代码。

于是有了 FlowAgent。两个反直觉的点先记住：

  1. FlowAgent 继承自 Agent 基类，但它自己根本不执行任务——它只负责摆队形。
  2. 真正干活的是装进它 subAgents(...) 里的那些 ReActAgent——FlowAgent 是排班表，ReActAgent 才是上班的人。

FlowAgent 派生出三个子类，正好对应同一组流程逻辑（并行 / 顺序 / 路由）：

FlowAgent 子类 流程逻辑 子智能体之间的关系
ParallelAgent 并行 互无依赖，同时跑，结果不交叉
SequentialAgent 顺序 上游 agent 的结果作为下游 agent 的输入
LlmRoutingAgent 路由 让 LLM 看任务属性，自己决定派给哪个子 agent

三个子类都用同一个入口 subAgents(...) 把若干个 ReActAgent 塞进来，差异只在于”塞进来之后怎么调度”。

加工增量：LlmRoutingAgent 跟前面 6-7 提到的 Agent-as-Tool 派单是同一思想换皮——都是让 LLM 看 description 决定派给谁。Agent-as-Tool 把 sub-agent 包成工具挂到 manager 的 tools 上；LlmRoutingAgent 直接做成 FlowAgent 子类，把”由 LLM 派单”这件事框架化了。

⏱ 08:00–09:57 · 两条路线对照表总结，纯讲

把上面两段并排放一起，就看到 1.1 留两条路的”对称美”了：

加工增量：这张对照表是消化稿里没明说但本集真正想传达的东西——1.1 不是用 FlowAgent 替代 Graph，而是按”执行单位的颗粒度”分了两条赛道。颗粒度细到一段方法 → 用 Graph；颗粒度粗到一个会思考的 agent → 用 FlowAgent。

没 get 的点

  • LlmRoutingAgent 的 description 跟 6-7 那个 Agent-as-Tool 的 description 是不是同一个字段、规则一不一样？本集没明说。
  • 两条路线能不能在同一个工作流里混用？比如一个 SequentialAgent 内部嵌一段 Graph？讲师只把它们并列摆出来，没讲交叉。
  • AsyncNodeAction / AsyncEdgeAction 的实际触发场景——只是为了不阻塞，还是有别的语义（比如取消、超时）？
  • FlowAgent 调度 subAgents 时底层是不是借了 Graph 的状态机制？invoke(...) 返回 Optional<OverAllState> 这条线索很可疑，但本集没拆开看。

  3. FlowAgent 三个子类各自实现哪种流程逻辑？它们装入子 agent 的统一方法叫什么？

关键词表

术语 一句话解释
Graph 引擎（StateGraph + OverAllState） 1.0 沿用、1.1 几乎没改的工作流编排引擎，靠”视图 + 状态包”两件套构图
StateGraph 三方法（addNode / addEdge / addConditionalEdges） 加节点 / 加边 / 加条件边，分别承载顺序、并行、路由三种流程逻辑
NodeAction / EdgeAction × 同步异步 自定义节点和边的接口，Async 前缀版本走异步执行
OverAllState（KV 状态包） 贯穿整个工作流的 KV 状态对象，节点写回、下游读取，是节点间唯一传话筒
FlowAgent 基类（不执行任务，只摆队形） 1.1 新增、继承自 Agent；自身不执行，只负责编排会思考的子智能体
FlowAgent 三子类（Parallel / Sequential / LlmRouting） 三种流程逻辑的”智能体版”实现：并行 / 顺序 / 由 LLM 派单
subAgents 装入口 FlowAgent 子类统一用它把若干个 ReActAgent 塞进来
