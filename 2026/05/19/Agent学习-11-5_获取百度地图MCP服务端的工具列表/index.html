11-5 获取百度地图MCP服务端的工具列表

一句话定位

把 11-4 留在 TODO 里的”调用百度地图 MCP”补齐——拆成”创建客户端”和”初始化客户端”两个独立方法，然后用 listTools 把工具列表打印出来，证明客户端跟服务端真的握上手了。

主体

1. 为什么是两个方法，而不是一个

⏱ 01:31–02:17 · 拆分创建与初始化两个方法的动机，纯讲

你在 11-4 里写的 getBaiduMapMCP() 只打了几行日志，方法名虽然叫”get”，但其实什么也没”get”——既没建对象，也没握手。本集要做的是把它真正实现，并且额外加一个 initBaiduMapMCP() 方法。

为什么不在 getBaiduMapMCP() 里一口气连初始化也做了？因为 MCP 客户端的生命周期里这是两件事：

  • 创建客户端对象（McpClientBuilder 链式调用 → 一个本地 Java 对象）
  • 初始化客户端（让这个对象真的跟远端 server 走一次握手，建立会话）

第一步是配置阶段，第二步才涉及网络。把它们拆成两个方法，等于把”构造好但还没说话”这个中间状态显式建出来，方便后面别的代码（比如真正的工具调用）按需触发握手。

2. 创建：McpClientBuilder 的链式套路

📺 02:22–03:42 · IDE 照文档抄 McpClientBuilder 链式属性

讲师直接照着 AgentScope 文档抄了模板。关键几个属性：

①最关键：传输协议两端必须对齐。 服务端用 SSE，客户端就只能用 sseTransport；服务端用 Streamable HTTP，客户端就只能用对应的方法。你以为 MCP 协议层会帮你抹平这个差异？不会。传输层是 4-3 讲的”两层结构”里独立的一层，两端必须提前约好——这条铁律本集第一次落到代码里。

③④的组合很 AgentScope 风。 buildAsync() 返回的是 reactor 的 Mono<McpClientWrapper>，你把它当一个”还没拿到结果的承诺”。.block() 把异步立刻转同步，相当于按下”我现在就要这个对象”的按钮。后面初始化那里还会再出现一次 block——意思一样，只是等的事不同。

加工增量：原视频对 .block() 一笔带过说”主设线程让它等等”。实际语义是”阻塞当前线程直到 Mono emit 出值”。这是 reactor 反应式 API 转回传统命令式代码的标准操作，跟 Future.get() 是一个味儿。一旦后面要做真·异步链路，你就要把这些 .block() 全删掉换成 .subscribe() 或 .flatMap()。

3. 成员字段：为什么不放局部

⏱ 03:42–04:14 · 解释把客户端放成员变量的原因，纯讲

baiduMapMcp 必须是成员变量，因为 initBaiduMapMCP() 要拿到 getBaiduMapMCP() 创建出来的对象。两个方法跨调用，只能走字段。

mcpInitialized 是讲师自己加的业务级状态——它不是 SDK 提供的握手状态，而是”我这个类的 init 方法到底有没有跑过”。后面会和 baiduMapMcp.isInitialized() 区分开。

几个反直觉的点串在一起：

  • listTools() 是握手成功的实际判据。 讲师没用 try/catch 判定 init 成败，而是直接调 listTools()——能拉到清单就证明会话真的建立了。这把 3-4 里讲的”MCP 会话两阶段”（建立 → 循环）落地成了一个非常具体的探针：进入循环前的第一次工具列表读取，本身就是握手成功的副产物。
  • 两个”isInitialized”是两层语义。 自己的 mcpInitialized 是业务级（”我这个类调过 init 没”），SDK 的 baiduMapMcp.isInitialized() 是协议级（”客户端和 server 通上没”）。它们必须都为真才安全：前者防重入，后者保握手。
  • synchronized + 双重检查锁是给业务字段加保险。 这套写法是 Java 单例那种 DCL 的搬运——MCP 协议本身不管线程，但你这里如果多线程并发调 init，可能会触发两次握手，把会话搞乱。锁的作用是确保”真正的握手”只跑一次。

5. URL 从哪儿来（复习 3-6 的流程）

📺 09:12–11:05 · 演示魔搭社区拉百度地图 URL 全流程

sseTransport(...) 那个 URL 不是凭空写的：

  1. 进魔搭社区（modelscope）
  2. 搜”百度地图”——认准官方那个，别选个人版
  3. 进服务详情 → 服务配置
  4. 选传输类型（要跟你客户端的 sseTransport / streamableHttpTransport 对齐）
  5. 填你自己申请的百度地图 API Key
  6. 提交后给你一段 JSON，里面有 url 字段
  7. 复制 url 粘到代码里

加工增量：这个 Hosted URL 大概率有 24h 有效期（参考 3-6 笔记里踩过的坑）——本集没明说，但只要你过一晚再跑代码，sseTransport 那段 URL 可能就要重新拉。日后写工程级代码应该把 URL 抽到配置文件，别硬编码进 Java。

6. 跑通的信号

📺 11:05–12:21 · 运行 main 看日志成功创建+初始化+工具列表

在 main 方法里先把 Spring 启动那段注掉，临时手动 new 一下 BaiduMapMCP，依次调 getBaiduMapMCP() → initBaiduMapMCP()，跑完看日志：

  • “百度地图 MCP 客户端已经创建” → 创建步成功
  • “百度地图 MCP 客户端初始化成功！” → 握手成功
  • 然后是一长串工具名 → server 端的能力清单（地理编码、路线规划、周边检索那些）真的拉过来了

只要工具名能打印出来，会话就真的建立了。下一集会把这个客户端正式接到 ReActAgent 的 toolkit 里。

没 get 的点

  • McpClientBuilder.create("BaiduMap-mcp") 里那个字符串到底是协议里的标识符（要跟 server 端某个名字对得上）还是纯客户端本地的逻辑名？文档没明说。猜是后者，但没核实。
  • IDE 在 mcpInitialized 字段下画了波浪线提示”may be final / never used”。如果这个字段真没被读取，那 DCL 的双重检查就形同虚设——真正在生效的是 baiduMapMcp.isInitialized()。本地状态字段是不是冗余，要看 11-6 接 toolkit 时是否还在读它。
  • 工具列表里具体有哪几个方法没拎清楚，视频里没逐项念。预计跟 5-6 那集列的”地理编码 / 路线规划 / 周边检索 / 天气查询…”10 个左右的清单吻合。
  • 如果 getBaiduMapMCP() 还没调就直接调 initBaiduMapMCP()，Optional 那条分支判到为空就直接跳过，但实际跑会 NPE——else 分支讲师没补。工程代码应该在 init 里兜底调一次 get。
