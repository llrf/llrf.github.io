9-05 主管Agent自主分解复杂任务

发表于2026-05-19|更新于2026-05-21|Agent学习第09章 Docker 部署分布式 Agent 搞定旅游规划
|浏览量:

1. 一句话定位

你给 9-4 那个 ManagerAgent 的 builder 链上加一个开关（.enablePlan() 或 .planNotebook(...)），它就从”亲自答题”切换成”先给你一张分步计划”。

2. 主体

2.1 不开 plan 时主管 Agent 在干嘛

📺 00:00–04:24 · 跑基线主管 Agent 看一把梭输出

你直接拿 9-4 build 出来的主管 Agent，丢进去这条 prompt：

帮我制定 2026 年元旦，深圳到惠州 3 日自驾游计划，包含吃住行、天气、酒店…

跑完控制台一片整齐——景点、酒店、每日行程、天气预报，全给齐了。看起来很完美，但这恰恰是错的。

为什么错：主管 Agent 的活儿是编排，不是亲自答题。LLM 一把梭出最终答案，等于把后面”派单给 routeMaking / tripPlanner / 订酒店专科 Agent”的整套机制全跳过了。你要的是”第 1 步查天气、第 2 步订酒店、第 3 步挑景点…”——一张计划表，不是一份成品。

加工增量：这些工具我叫它们”元工具集“——业务工具（查天气、订酒店）是给”做事”用的，元工具是给”管任务清单”用的。LLM 不是写一段文字”我打算这么拆”，而是被强行通过工具调用产出结构化的计划对象。这是框架约束 LLM 行为的标准姿势：不靠 prompt 求它，靠工具集逼它。

2.3 懒人开关的局限

⏱ 07:00–07:36 · 说明 enablePlan 无参数无法自定义

enablePlan() 不接任何参数。你想改默认 prompt？改子任务最大数？改元工具白名单？全没口子。所以需要方案 B。

2.6 本集主管 Agent 的能力边界

只拆不分。生成完 5 个子任务就停在”是否按此执行”那里。真正把这 5 个任务分发给 routeMaking_agent / tripPlanner_agent 等专科 Agent 的活儿，要等到 9-8。本集只解决”拆解”这一步。

3. 没 get 的点

  • PlanNotebook.Builder 究竟能改哪些字段——最大子任务数？prompt 模板？工具白名单？源码没翻，9-6 应该会展开。
  • 9 个元工具里 revise_current_plan 和 update_subtask_state 听起来很像，到底分别在啥场景调？
  • view_historical_plans 是跨会话持久化的，还是只看当前会话？涉不涉及存储后端？
  • 拆完计划后那句”是否按此执行”是 PlanNotebook 默认行为还是 ReActAgent 自己的 confirm 步？能不能关掉做成自动？
  • 工程目录里已经有 hook/planHook.java 但本集没用上——9-7 拦截 hook 那集才会动它。
  • 视频里出现过一次报错 PlanNotebook cannot be applied to ()，讲师先写错再改对：暗示 planNotebook() 必须传参（不像 enablePlan() 可空），算是个 API 设计提醒。

4. 跟其他集连接

  • 上承 9-4：那集给了 ManagerAgent 的 builder 三件套骨架，本集只在那条链上新加一节。run 方法没改，还是 AgentUtils.streamResponse + blockLast 那套。
  • 上承 8-1 / 8-3：把”主管的三职责（拆 / 派 / 排时序）”讲清楚了，本集是第一职责（拆解）的代码落地。
  • 上承 3-12：五步骨架里”主管 Agent”是入口节点，本集把它从概念变成可跑代码。
  • 同源对照 8-10 / 8-11（JManus）：JManus 自己手写 PlanCreator + planningTool + maxRetries=3 + prompt 模板 一大坨；AgentScope 一个 enablePlan() 全搞定，想自定义就传 PlanNotebook 实例——典型的”自研 vs 框架内置”。
  • 同源对照 6-6（SpringAI Alibaba）：SAA 1.1 用 .saver() 在 builder 链上挂记忆能力，AgentScope 用 .enablePlan() 挂规划能力——都是”builder 链 = 能力开关“模式。
  • 下启 9-6：必然展开 TripPlan 里 PlanNotebook.Builder 能改哪些字段，本集留的口子在那兑现。
  • 下启 9-7：hook/planHook 用来拦截 create_plan / finish_subtask 这些工具调用事件。
  • 下启 9-8：本集只拆不派，那集才真把 5 个子任务派给专科 Agent。

5. 知识地图

6. 自测题

  1. 9-4 build 出来的主管 Agent 直接 run，输出是什么形态？为什么讲师说这是”错的”？
  2. enablePlan() 和 planNotebook(实例) 在源码层面是什么关系？为什么项目选了后者？
  3. 控制台冒出来那一堆 Registered tool 'create_plan' ... 是谁注册的？这些工具属于”业务工具”还是”元工具”？职责是什么？
  4. 本集生成的 5 个子任务，后续在哪一集才真正被派发出去？本集主管 Agent 的能力边界是”只 X 不 Y”。
  5. 如果你想把默认元工具集里的 view_historical_plans 拿掉（假设它能拿掉），应该走哪个 API 入口？为什么不能走 enablePlan()？

7. 关键词表

术语 含义
enablePlan ReActAgent.builder() 链上的无参开关，内部等价于 planNotebook(new PlanNotebook.Builder().build())，不可自定义
planNotebook builder 链上的带参开关，接收 PlanNotebook 实例，留出自定义口子
PlanNotebook AgentScope 框架内置的”任务清单管理器”，一旦挂上就给 LLM 注册一组元工具
元工具集 create_plan / revise_current_plan / update_subtask_state / finish_subtask / view_subtasks / update_plan_info / get_subtask_count / view_historical_plans / finish_plan 九个，非业务工具，专门给 LLM 管理子任务清单
主管Agent 本集的角色限定是”只拆不分”——把复杂任务拆成子任务清单后停在 confirm，派单等到 9-8
任务分解 复杂 prompt → LLM 通过调用 create_plan 输出结构化子任务列表，而不是 LLM 自己写文字”计划”
TripPlan 项目里 plan/TripPlan.java，用工厂方法 getPlan() 返回 PlanNotebook 实例，对应 .planNotebook(plan.getPlan()) 调用
builder链能力开关 “在 builder 链上挂一个方法就开一项能力”的统一模式，SAA 1.1 的 .saver()、AgentScope 的 .enablePlan() 都是同思路
