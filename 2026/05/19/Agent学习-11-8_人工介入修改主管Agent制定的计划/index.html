11-08 人工介入修改主管Agent制定的计划

发表于2026-05-19|更新于2026-05-21|Agent学习第11章 MCP+A2A，助力旅游规划团队协作
|浏览量:

1. 一句话定位

把”主管 Agent 自主拆任务”这条全自动流水线开一个口子——计划刚成型、还没开始执行的那一刻，让你用自然语言（不只是 yes/no）插嘴改它。

2. 主体

2.1 为什么 needUserConfirm 不够

⏱ 01:58–02:57 · 解释 yes/no 不够要自然语言对话，纯讲

9-6 学过 PlanNotebook 上有个 .needUserConfirm(true)，跑起来效果就是计划列出后框架问你”continue? y/n”。

问题很现实：你看到主管列出来的五个子任务里，第 2 步选错了酒店筛选维度、第 4 步多了一个你根本不在意的步骤——这时候你想说的是”把第 2 步改成按预算筛、把第 4 步删掉”，而不是 yes / no。

加工增量：消化稿里把 needUserConfirm 定性为”二值确认”，这个词其实点出了它的设计哲学——框架只保证”有断点”，但”断点上能传什么数据”是它没解决的事，留给你用 Hook 自己填。

2.2 武器一：UserAgent

📺 02:57–04:34 · main 里 new UserAgent + 跑 hello 验证监听

AgentScope 自带的一个 Agent，注意：

  • 不挂 LLM
  • 不挂工具
  • 不需要 prompt

它只是被包装成 Agent 接口的”键盘监听器”，本质就是 Scanner.nextLine() 的 Agent 化。

跑起来你输入 hello，它就把 Msg 打印出来——单元测试到此结束，证明这个监听器能用。

2.3 武器二：PostReasoningEvent（来自 9-7）

⏱ 05:04–05:30 · 复习 Hook 四事件 + 提示 ReAct 多轮坑，纯讲

9-7 的 Hook 接口给了你四个事件切点：

事件 时机
PreReasoningEvent 思考前
PostReasoningEvent 思考后
PreActingEvent 动作前
PostActingEvent 动作后

直觉会以为”PostReasoning = 思考完成”，这是坑。ReAct 是循环结构，每一轮都触发一次 PostReasoning。你不能见到这个事件就拦——否则主管思考三轮就被你打断三次。

2.4 真正的定稿信号：getCurrentPlan() != null

⏱ 06:58–07:16 · 推理用 getCurrentPlan 非空判定定稿，纯讲

判据要去 PlanNotebook 这个对象里找。

注意这是双向注入：main 函数里 new 出来一个 PlanNotebook，两个引用都指向同一个对象。这样 hook 里调用 notebook.getCurrentPlan()，读到的就是 agent 此刻往里写的计划状态。

getCurrentPlan() 返回非空 = 计划列表已经被框架填进去 = 主管思考定稿了；返回 null = 还在迭代，跳过本次 hook，等下一轮 PostReasoning。

2.5 拼装

📺 06:10–08:22 · IDE 实现 PlanHook + 注入 UserAgent 与 PlanNotebook

两个易错点：

  • UserAgent 必须是成员变量：放进 onEvent 里 new 看起来也跑得通，但每次打断都新建一个监听器实例，浪费且语义怪。
  • PlanNotebook 也必须是成员：而且要在外部 new 完后注入进来，不能 hook 里自己 new——hook 自己 new 出来的那个根本不是 agent 在用的那个，读出来永远是 null。

2.6 跑起来

📺 09:16–09:45 · 运行看主管列出五子任务后停下等输入

主管列出”获取天气 / 规划行程 / 筛酒店 / 餐饮 / 整合”五个子任务，然后程序就停在 请输入修改意见： 处等你敲键盘。人机断点接上了。

3. 没 get 的点

  • 修改意见 接到之后怎么塞回去让主管重做计划？本集只演示”接住 Msg”，不演示反馈回路。猜测是把 Msg 拼回 memory 或当下一轮 PreReasoning 的输入，但没现场验证。
  • user.call().block() 在 Mono.onEvent 里同步阻塞——Reactor 调度线程会不会被卡死？生产环境是不是该非阻塞？
  • getCurrentPlan() 在 LLM 流式输出 plan 的时候到底是哪一刻第一次变非空？如果是边流边写，本集这个判空可能踩在半成品上。

4. 跟其他集连接

上承

  • 9-6 PlanNotebook：本集复用了它的 .needUserConfirm(true) 和 .maxSubtasks(5)；并且把”yes/no 不够”这个痛点用 Hook 补全。
  • 9-7 Hook 拦截：9-7 只是把 PostReasoning 分支占位 log.info，本集第一次给它真实落地场景。
  • 11-7 主管自主分发：上一集刚跑通”主管 → 远程成员全自动”链路，本集就在这条链路上开人机断点。

下启

  • 反馈回路：拿到的修改意见怎么回灌给主管重新规划。
  • 把 UserAgent 换成 Web 前端 SSE 输入（参考 7-9 SSE 输出方向的镜像），关注点分离的设计正好为此留口。

横向

  • 6-6 .saver(...) 存事件状态、本集 hook 拦事件流——同一根事件总线的两端。
  • 8-3 SOP “主管 = 编排时序”——本集等于在时序里打了一个人机断点。
  • 6-8 OverAllState 的 KV 共享 vs 本集 PlanNotebook 的对象引用共享，是同一个”状态共享”问题的两种解法。

5. 知识地图

6. 自测题

  1. 为什么不能见到 PostReasoningEvent 就调用 user.call().block()，必须配合 getCurrentPlan() != null 一起判？
  2. PlanNotebook 实例在 main 里被传给了几个地方？为什么必须是同一个对象引用？
  3. UserAgent 跟你自己用 ReActAgent.builder() 写的 Agent 最大的区别是什么？（提示：依赖项）
  4. .needUserConfirm(true) 和本集的 PlanHook 在功能上能不能互相替代？为什么？
  5. 如果想把控制台输入换成 Web 前端输入，本集架构里需要改哪一块、不需要改哪一块？

7. 关键词表

术语 一句话解释
UserAgent AgentScope 自带、不挂 LLM/工具的 IO Agent，call().block() 阻塞读 stdin
PostReasoningEvent ReAct 每轮思考结束触发；多轮 reasoning 会多次触发，需要状态判据补强
PlanNotebook 双向注入 同一个 PlanNotebook 实例既给 ReActAgent.planNotebook(…) 又给 PlanHook 构造方法
getCurrentPlan 定稿信号 返回非空 = 计划已生成 = 此刻才适合打断
needUserConfirm 的局限 只能 yes/no 二值确认，不支持自然语言改计划
Hook 拦截四件套 PreReasoning / PostReasoning / PreActing / PostActing 四个切点
IO 与决策关注点分离 UserAgent 当 IO 适配器，主管 Agent 当决策中枢，将来换前端只换前者
