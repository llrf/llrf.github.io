12-5 景点推荐SubAgent执行景点推荐任务

一句话定位

把”景点推荐”从行程规划主 Agent 里剥出来变成子 Agent，再以工具的姿态挂回主 Agent——主 Agent 只派单，子 Agent 干活，Skills 跟着子 Agent 走。

主体

起手是在 Toolkit 的 register 家族里挑方法

你已经认识这几位了：

  • registerTool(...)：装普通工具，比如 Calculate。
  • registerMcpClient(...)：装 MCP 工具。
  • registerAgentTool(AgentTool)：装”把另一个 Agent 当工具”。

第三个就是这集的入口。点进 AgentTool 是个接口，搜实现，唯一一个就是 SubAgentTool——所以”子 Agent 作为工具”这个抽象，落地只有一条路。

第一种写法：new SubAgentTool(...)——然后立刻被推翻

为什么？因为 SubAgentTool 构造器吃的第一个参数是 SubAgentProvider<?>——这是个工厂，不是实例。直接 new 一个子 Agent 塞进去，工厂每次 provide() 都返回同一个对象，多轮调用之间状态会串。Lambda () -> new Agent() 才是”每次现做一个新的”。

加工增量：消化稿里这条被升到铁律级——它的反直觉点在于 Java 语义上 new SubAgentTool(someAgent) 编译跑都没问题，框架不会拦你；只有跑多轮才会显形。把”反直觉但必须吃下去”的约束放在 §3 没 get 的点里更合适。

  • 11-6 路线制定专员Agent挂载百度地图MCP 是把”专员”挂 MCP，本集是把”专员”装进主 Agent 的工具袋——外挂工具 vs 委派子 Agent 是扩展主 Agent 能力的两种对偶手段。

知识地图

自测题

  1. toolkit.registration().subAgent(new SubAgentTool(agent)) 这么写编译能过，但运行起来会出什么问题？
  2. AgentTool 接口在 AgentScope 1.0.8 里有几个实现？意味着什么？
  3. 主 Agent 把 Skills 全部剪给子 Agent 之后，它靠什么决定”什么时候要派单给子 Agent”？
  4. SubAgentTool 构造器吃 SubAgentProvider 和 SubAgentConfig 两个参数——文档为啥强调 Provider 必须是 Lambda 而不能是已经 new 好的对象？
  5. 本集 MakeATableSkill 被注释掉了，结合章首总图，你预期下一节会出现什么类、挂在哪？
参考答案
  1. Provider 每次 provide() 都返回同一个子 Agent 实例，多轮对话之间状态会串（消息历史 / 内部状态污染）。Lambda () -> new Agent() 才能保证每次现做一个干净实例。
  2. 只有一个，SubAgentTool。意味着”把 Agent 当工具”这个抽象只有一条标准落地路径，没有别的实现可选。
  3. 靠主 Agent 工具清单里的 tool name + description——而这两段文字是从子 Agent builder 里的 .name("SuggestSightAgent").description("擅长景点推荐") 反向 resolve 出来的。所以子 Agent 的 description 写得好不好直接决定主 Agent 派单准不准。
  4. 因为 SubAgentTool 内部会调 agentProvider.provide() 取得 sampleAgent 来 resolve name/description，并在每次真正被调用时再 provide() 一次拿运行实例。Lambda 是”每次现做”，已 new 好的对象是”每次同一个”——后者会让会话状态在多次调用间串。
  5. 预期下一集出现 MakeATableAgent 类（也在 agents/ 下），同样用 toolkit.registration().subAgent(() -> makeATableAgent.getMakeATableAgent()).apply() 挂到 TripPlannerAgent。表格制作 Skill 跟着搬到这个新子 Agent 上。
