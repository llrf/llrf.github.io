3-7 具有专业知识的Agent Skills

摘要：本集把”agent 该用哪个工具”这件事从”每次回 LLM 请示”挪到”本地文件直接知道”。取舍出现在 §2.4（不展开 Skills 文件格式与训练机制）。加工增量出现在 §2.1 的”三种范式对照表”和 §5 的知识地图——把零散的 FC / MCP / Skills 串成一条”自治程度递增”的演化轴，这不在 understanding.md 里。

§1 一句话定位

把”该用哪个工具”的判断从 LLM 卸载到本地文件，省 token 也省上下文。

§2 主体讲解

§2.1 先把地图摊开：工具调用的三种范式

如果你只记一件事，就记这张表。后面所有内容都是在解释”为什么会从上往下演化”。

范式 工具住在哪 谁决定用哪个工具 痛点
Function Calling agent 自己代码里手写 LLM 每个模型/每个 API 都要重写一遍
MCP 远端 MCP 服务器 LLM（要回去问） 工具列表全量塞上下文 + 来回问浪费 token
Agent Skills 本地文件（专业知识 + 工具配置） agent 自己（已经”懂行”） （本集未展开落地细节）

把它读成一条线：agent 的自治程度在递增——FC 阶段是”工具我自己写但用哪个还得问 LLM”，MCP 阶段是”工具我不写了但用哪个还是要问 LLM”，到 Skills 阶段才终于做到”工具不写、选工具也不问”。

这张三列对照表是加工增量——原视频按时间顺序讲，没有横向并列的对照。我把它前置，是为了让 §2.2 的痛点一出现就有参照系。

§2.2 MCP 到底浪费在哪：两笔账要分开算

你打开一个挂了 10 个 MCP 服务器的 agent，假设每个 server 平均 8 个工具——80 个工具的 schema 会发生两件事：

第一笔账：上下文窗口被吃掉。 这 80 个工具的名字、参数、描述，每次对话都得塞进 prompt 里，LLM 才”看得见”它们的存在。本来可以塞业务对话的窗口被工具清单挤走了。

第二笔账：选工具的 round-trip。 agent 拿到任务”挖地”，它本身不知道用铲子还是锄头还是扫把，于是要问 LLM”这 80 个工具里哪个适合挖地？”——LLM 回答”用铲子”——agent 再去调铲子。这一来一回又是一次 token 消费。

注意这两笔账是独立的：第一笔是”工具列表常驻”的存储成本，第二笔是”每次选工具”的交互成本。Skills 后面会同时砍掉两笔。

§2.3 Skills 的核心动作：给 agent 一张”小抄”

要理解 Skills 必须先承认一个前提：agent 的”大脑”是 LLM。这意味着 agent 默认是个不懂行的执行者——它没有自己的判断力，所有”该用哪个工具”的决策都要回大脑请示。

Skills 做的事情很简单：在 agent 旁边放一份本地文件，写明”这个领域的任务该用哪个工具”。agent 拿到任务后直接查这份小抄，不再回大脑问。

一个常用的比喻是”种地专家”：一个懂种地的 agent，看到任务”挖地”就知道要铲子，看到”松土”就知道要锄头——它不需要回 LLM 问”这三个工具里哪个适合挖地”，因为种地的专业知识已经在本地文件里了。

§2.4 工具调用的新姿势：MCP 还在，但变成”点单制”

容易误读的地方在这里：Skills 并没有取消 MCP。MCP 服务器仍然提供工具，只是模式从”push 全部”变成”pull 单个”。

  • 旧模式（纯 MCP）：MCP server 一开会话就把所有工具列表丢过来 → agent 揣着一兜子工具回 LLM 问”用哪个” → LLM 回复 → agent 调用。
  • 新模式（Skills + MCP）：agent 凭本地知识直接得出”我要铲子” → 向 MCP server 单点请求”给我铲子” → MCP server 返回铲子 → 调用。

这种模式被称为”工具调用才加载“——工具不再开局全量 push，而是被点名时才返回。

取舍声明：本集只讲到”以文件形式赋予专业知识 + 本地配置工具”这个抽象层。Skills 文件的具体格式（markdown / yaml / 目录结构）、是否需要微调 agent、本地 skill 名怎么映射到 MCP 实际工具——这些都不展开，因为本集没给。判断依据：宁可在概念层讲清因果，不在落地层凭空脑补。后续如果有实操课再补。

§2.5 收益对账：两笔账都砍掉

回到 §2.2 那两笔账：

  • 上下文窗口：MCP 不再开局 push 全部工具，省下来。
  • 来回问 LLM：agent 自己看小抄就知道用哪个，这一跳消失，token 省下来。

这两笔是同时发生的，不是二选一。这也是为什么 Skills 被视频拎出来单独讲——它不只是”另一种工具调用方式”，而是同时优化了 MCP 的两个痛点。

§3 我一开始没 get 的点 / 容易踩的坑

  1. 如果你把 Skills 理解成”给 agent 加新工具”，会错过它真正的优化点。Skills 不增加工具能力，它减少的是”问 LLM 用哪个工具”的次数。能力侧没变，调度侧变了。

  2. 如果你以为 Skills 取代了 MCP，会画错架构图。两者并存：MCP 还是工具的来源方，Skills 是工具的”调度小抄”。Skills 改的是 MCP 的工作模式（全量 push → 按需 pull），不是 MCP 本身。

  3. 如果你以为节省 token 只来自”少调 MCP”，会算错账。真正的双重节省是：① 工具列表不再占上下文窗口（存储省）；② 选工具的”agent ↔ LLM 来回问”被砍掉（交互省）。两笔账独立成立。

  4. 如果你忘了”agent 大脑是 LLM”这个前提，整个动机会失焦。agent 默认是个空壳执行者——所有判断都要回大脑请示。Skills 的本质是给空壳塞一份”不需要请示”的领域知识。

§6 自测题

Q1（概念回忆）：Agent Skills 的本质是什么？它让 agent 多了一种什么能力？
A：本质是通过本地文件给 agent 注入领域专业知识 + 工具配置，让 agent 不再为”用哪个工具”回 LLM 请示。它多了”自己决定用哪个工具”的能力。答案在 §2.3 / understanding.md §关键概念。

Q2（概念辨析）：Agent Skills 和 MCP 的关系是”替代”还是”协作”？说出关键差别。
A：协作。MCP 仍是工具来源方，Skills 改的是工作模式：MCP 从开局”push 全部工具”变成被点名时”返回单个工具”；同时 agent 不再回 LLM 问该用哪个。答案在 §2.4。

Q3（反直觉陷阱）：为什么说 Skills 的 token 节省是”双重”的？只算其中一笔为什么会错？
A：① 工具列表不再占上下文窗口（存储省）；② 选工具的 agent ↔ LLM round-trip 被砍掉（交互省）。两笔账独立成立，只算其一会低估 Skills 的价值。答案在 §2.2 + §2.5 / 图 f006。

Q4（跨集连接）：把 FC / MCP / Skills 排在同一条”自治程度递增”轴上，三者分别处于哪个位置？
A：FC = “工具自己写、用哪个还得问 LLM”；MCP = “工具协议化不写了、用哪个还是问 LLM”；Skills = “工具不写、选工具也不问”。答案在 §2.1 表格 + §5 地图，呼应 3-2/3-3/3-4/3-5。

Q5（应用 / 推广）：如果你给一个挂了 20 个 MCP server（合计 200 个工具）的 agent 接 Skills，预期能优化什么？什么场景下优化最显著？
A：预期同时节省”工具列表占窗口”和”每次选工具回问”两笔开销。在多 server / 大工具池 / 高频会话场景下最显著——工具越多越省窗口，对话越多越省 round-trip。答案推广自 §2.5 + §5。

总结 Agent 从助手到自主协作的进化过程1. 一句话定位这一集把前面 10 章学到的全部零件（LLM、Agent、MCP、ReAct、工作流、多 Agent、SubAgent、Skills）按”出现顺序 + 各自补的洞”穿成一条五阶段时间线，是整套课程的收口图。 2. 主体：五个阶段，其实是”补五个洞”视频按阶段讲，但你听完会发现：每跳一阶段都在补上一阶段留下的洞。把”阶段”换成”洞”来记会更顺手。 阶段 1：LLM 只会问答你给 prompt，它返回内容（哪怕是图、视频，多模态也只是返回形式更花）。 留下的洞：不会自主决策。你问 A，它就答 A，不会自己把 A 拆成 A+B 再去解 B。 阶段 2：Agent 学会用工具为了让 LLM 能查数据库、生成 PPT、调第三方 API，加上”使用工具”的能力 —— 这就是 Agent。MCP 是这个阶段的工程标准化产物：在它之前各家自己写 function call，之后所有大模型基于同一套接口调同一个工具，省掉重复造轮子。 留下的三个洞（重点，整集的转折点）： 还是不会自主决策——MCP 没解决这个，它只解决”接口统一” ...

10-1_Agent的牛马小弟SubAgent
1. 一句话定位SubAgent 是主 Agent 在干活时，把某个”单个专业场景”（写 SQL、CRUD、登录接口）外包给一个跑在独立上下文里的小弟，唯一目的就是不让这点专业脏活污染主上下文。 2. 主体2.1 先把上一集的三层架构在脑子里挂好这集前 4 分钟全在复述上一集，把那张图想清楚再往下读会舒服很多： 总协调 Agent（总监级）：只做规划和需求切分，自己不下场。 Agent 主管（领域主管，前端 / 后端 / 测试 / 运维 / 安全 / 产品 等）：拿到本领域的任务后，继续切，再派给下面的执行者。 Agent 执行者（初级 / 实习生程序员）：真正动手，具有领域知识，能自己组合工具、调 MCP 和 Function Calling，不用反复问大模型”我该用啥工具”。 每一层内部都跑同一个循环：ReAct——思考、执行、再思考”结果对不对、和目标有没有出入”、有偏差就动态调整。讲师反复强调这一条，不是凑数，是后面 SubAgent 出场时的语境：SubAgent 内部也是这个循环，只是壳子不一样。 2....
