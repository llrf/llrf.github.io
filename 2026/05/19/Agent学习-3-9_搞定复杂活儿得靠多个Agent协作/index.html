搞定复杂活儿，得靠多个Agent协作

§1 一句话定位

复杂任务的解法不是更强的 Agent，而是一群 Agent + 一个主管。

摘要标记：取舍出现在 §2.1（跳过近三分钟回顾，从”行程规划”反例切入）；加工增量在 §2.3 和 §3（主管 Agent 的 prompt 设计角度 + “异质子任务 ≥ 2 就值得拆”的判断阈值，原视频未给）。

§2 主体讲解

§2.1 先从一个反例进来（这是我自己重排的入口）

你先假设手上只有一个全才 Agent：脑子是 LLM，手脚是 MCP 工具，眼睛能看数据库。按上一集的认知，这套组合”应该够用”。

现在派给它一个看似简单的任务——帮我做一次行程规划。

把这几个字摊开，你会发现它至少要做四件性质完全不同的事：

  1. 根据用户偏好排路线、选景点；
  2. 按路线和预算订酒店、订交通（火车还是飞机，看消费习惯）；
  3. 把整套计划做成一份表格，丢给用户确认；
  4. 整个过程还得有人统筹——决定什么时候做哪一步、谁先谁后、谁的输出喂给谁。

第 1、2、3 步都是异质技能（地图查询 / 偏好分析 / 文档生成），第 4 步是元任务（管别人）。一个 Agent 同时扮演四种角色，上下文会被互相稀释，准确率和效率都会塌。

这就是为什么单 Agent 跑复杂任务总感觉”什么都能做一点、什么都做不好”。

§2.2 把 LLM / Agent / MCP 重新摆一遍（为反衬铺垫）

旧的三层模型你已经熟了：

  • LLM = 推理引擎，只会聊天，单独存在形不成生产力；
  • Agent = 三能力体（感知数据库/文件 + LLM 决策 + 执行操作），是真正干活的单位；
  • MCP = Agent 的外挂工具协议，让 Agent 能查高德、查股票、查文档。

这三者互相成就。但注意：“互相成就”只解释了能干活，没解释能干多大、多复杂的活。三能力齐全只是一个 Agent 能成立的下限，不是它能扛复杂任务的保证。

§2.3 多 Agent 协作：3 个专科 + 1 个主管

照”专业的人做专业的事”这个心智模型，行程规划被拆成四个角色：

角色 专长 用什么
智能体一 地图与路线 调高德地图 MCP
智能体二 偏好分析 查数据库 + LLM 推理
智能体三 文档制作 表格输出，递交用户确认
智能体四 主管 切任务 → 派单 → 汇总 → 出最终文档

前三个是专科 Agent（Specialist），最后一个是主管 Agent（Orchestrator）。

主管 Agent 的关键特征——它不直接干活。它只做四件事：

  1. 任务切分：把”做一次行程规划”这种一句话需求展开成可派单的原子步骤；
  2. 派单：把每个步骤交给对应专科；
  3. 汇总：收回各方结果；
  4. 交付：拼成最终文档。

加工增量：原视频只把主管描述为”统筹的角色”。实际去落地时你会发现，主管必须是一个单独设计 prompt 的 Agent，而不是某个专科顺带兼职。它的 system prompt 要写明”你是项目经理，不写代码、不查地图、只切任务和复盘结果”——否则它会忍不住自己下场干活，专科就被架空了。

§2.4 为什么不能等 LLM 自己悟出”切任务”

你可能会问：现在的 LLM 推理已经很强了，把 4 个工具全挂给一个 Agent，让它自己规划顺序不行吗？

不行，有两个隐形成本：

  • 上下文稀释：地图 schema、数据库 schema、文档模板挤在同一个 prompt，重要指令会被冲淡；
  • 决策耦合：一个 Agent 同时在”我现在该用哪个工具”和”用户偏好到底是什么”两个层面来回切，错误会互相放大。

把”决定下一步做什么”独立成一个 Agent 的唯一职责，就把元决策和执行解耦了。这跟”为什么公司需要 PM 而不是让最强的工程师兼任”是同一个道理。

§2.5 升华：这是 2025 框架的方向

把整集压成一个口诀：

复杂任务处理 = 拆给专业的人 + 团队分工明确

判定一个任务是否需要多 Agent 的阈值，比你想象中低——只要涉及 2 个以上异质子任务（例如”查信息 + 生成文档”），就值得拆。不要等到任务”看起来很大”才动手，那时候单 Agent 已经被你写成屎山了。

加工增量：这条”≥2 异质子任务就拆”的阈值不在原视频里，是我对着行程规划这个例子反推出来的判断尺。

§3 我一开始没 get 的点

  1. 如果你把多 Agent 理解成”几个 Agent 平行跑”，会得到一个永远协调不起来的失败 demo。多 Agent 的核心不是数量，是层级——必须有一个只做调度、不干活的主管，专科 Agent 才不会变成散兵游勇。

  2. 如果你以为”切任务”是 LLM 自动完成的副产品，会写不出可用的主管 Agent。任务切分是要单独写 prompt、单独定义角色边界的显式职责，不是默认能力。

  3. 如果你按”行程规划只是一句话”的感觉去估它的复杂度，会低估到单 Agent 上去。一句话需求 ≠ 一步任务，关键是数它涉及几种异质技能（≥2 就拆）。

  4. 如果你觉得 LLM + Agent + MCP 已经够了，会卡在”为什么我的 Agent 看起来什么都能做但永远做不好一件复杂事”。三能力齐全只是单 Agent 的下限，不是复杂任务的解。

§4 跟其他集的连接

上承

  • 3-6 体验 MCP：单 Agent 调 MCP 工具的实操，是本集”专科 Agent 怎么干活”的基础——比如智能体一调高德 MCP，本质就是上一集的延伸。
  • 3-4 / 3-5 MCP 协议本身：让你理解 Agent↔工具的协议如何标准化。本集等于在更高一层问：那 Agent↔Agent 呢？

下启

  • 2025 年 10 月的框架已经全面向多 Agent 协作转向。下一集大概率落到具体框架（LangGraph / AutoGen / CrewAI / 或继续 JManus 的 multi-agent 模式），看它怎么实现”主管派单”和”专科通信”。
  • 留意一个未解的协议问题：Agent 之间的通信协议是什么？MCP 解决了 Agent↔工具，但 Agent↔Agent 还需要类似 A2A 的协议——下一集如果不讲，自己查。

横向

  • 3-1 大模型困境：那时的解法是”外挂数据”。本集是更高维的同一思路——“外挂分工”。LLM 解决不了的是知识边界 + 协调成本，前者靠 MCP，后者靠多 Agent。
  • 这个心智模型可以反哺单 Agent 的 prompt 设计：即使你只有一个 Agent，也应该让它在 prompt 里扮演单一专家，而不是全才。”专业的人做专业的事”在单 Agent 内部一样成立。

§5 知识地图

§6 自测题

Q1（概念回忆）：多 Agent 协作中，主管 Agent 的四项职责是什么？

A：任务切分 → 派单给专科 Agent → 汇总结果 → 输出最终交付物。关键是它自己不干活。

Q2（概念辨析）：单 Agent + 三能力齐全（感知 / 决策 / 执行）+ MCP 工具，为什么仍然处理不好复杂任务？

A：因为三能力齐全只解释了”能干活”，没解释”能干多复杂的活”。复杂任务里多种异质技能挤在同一个上下文里会互相稀释，且元决策（下一步做什么）和执行（现在怎么做）耦合在一起，错误会互相放大。

Q3（反直觉）：”行程规划”这种听起来一句话能说清的任务，为什么要拆成 4 个 Agent？

A：因为它涉及 4 种性质完全不同的工作——查地图、分析偏好、生成文档、统筹流程。判断阈值不是任务”看起来大不大”，而是数它有几种异质子任务；≥2 就值得拆。

Q4（跨集连接）：本集和 3-4 / 3-5 / 3-6（MCP 协议）的关系是什么？

A：MCP 解决了 Agent↔工具的协议层，让单 Agent 能外挂能力。本集上升一层，问的是 Agent↔Agent 怎么协作。下一步自然要找 Agent 间通信协议（如 A2A）和多 Agent 框架（LangGraph / AutoGen / CrewAI）。

Q5（应用推广）：即便项目里只有一个 Agent，本集的心智模型能给你什么启发？

A：在 prompt 里也要让它扮演单一专家而不是全才——“专业的人做专业的事”在单 Agent 内部一样成立。如果你发现 prompt 里塞了 3 种以上不相干的能力，就该考虑拆 Agent 而不是继续堆 prompt。

§7 术语表

术语 一句话定义
多 Agent 协作 把复杂任务拆给多个专科 Agent 并行/串行执行，由主管 Agent 统筹。
主管 Agent（Orchestrator） 只负责切任务、派单、汇总，不直接干活的调度 Agent。
专科 Agent（Specialist） 只负责一类技能（地图 / 偏好 / 文档…）的执行 Agent。
任务切分 把”一句话需求”展开成可派单的原子步骤，是主管 Agent 的显式职责。
复杂任务处理公式 拆给专业的人 + 团队分工明确 = 复杂任务处理。
Agent 三能力反衬 感知/决策/执行齐全只是单 Agent 的下限，不能保证复杂任务可行。
生产力门槛 只能聊天≠生产力；能代替用户干活才算。本集把门槛从单 Agent 抬到多 Agent。
社会分工类比 “专业的人做专业的事”——本集多 Agent 设计的核心心智模型。
