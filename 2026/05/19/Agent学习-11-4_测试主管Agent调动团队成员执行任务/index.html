11-04 测试主管Agent调动团队成员执行任务

发表于2026-05-19|更新于2026-05-21|Agent学习第11章 MCP+A2A，助力旅游规划团队协作
|浏览量:

1. 一句话定位

把 11-3 那条”主管能找到远端成员”的连通线，再往里推一层——主管把 prompt 透传过去，让远端 Agent 进自己的 ReAct 循环，命中自己进程里的 @Tool，并在远端控制台留下证据日志。

2. 主体

2.1 三层调用链：两个 @Tool 分别长在哪

先把 11-1 的整体架构图（frame f001、f002）拎出来当锚：主管 Agent 节点通过 A2A 协议触达”路线制定 Agent 节点”，再由后者去调”百度地图 MCPServer”。本集把这张图里前两跳真正跑通，第三跳留个日志桩。

反直觉点（这是本集最容易混的地方）：远端 BaiduMapMCP.getBaiduMapMcp() 上 @Tool(description="百度地图Mcp Server") 的那段描述，主管 LLM 是看不见的。@Tool 的可见域只在自己进程里。主管之所以”调动”得了，是因为它先命中了自己进程里的 callRouteMakingAgent，然后由这个工具方法发起 A2A 调用，把 prompt 原样喂给远端。

2.2 远端的工具：BaiduMapMCP 桩 + 注册

  1. 类上没有 @Component——AgentScope 这一支风格里，工具实例不走 Spring 自动扫描，要在 builder 里手动 new 进去。这跟 4-5/4-6 那一支 Spring AI Alibaba @Tool + @Bean 的范式不一样，思维要切换一下。
  2. 方法体只是三行 log——讲师故意不接真 MCP。先用桩验证调用链通不通，真接入留给 11-5 / 11-6。这就是 11-2、11-3 用了一路的”桩日志驱动验证”思路在第三层的延续。
  3. @Tool 注解上的 description 是给远端 LLM 看的合同——本集 prompt 只有”调用百度地图Mcp”五个字，全靠这段描述匹配。

2.3 主管侧：把 agent.call() 换成 streamResponse

f022 抓到主管侧的关键改动（在 RemoteAgentTool.callRouteMakingAgent() 这个工具方法里）：

为什么必须换？ 11-3 那种 agent.call().block() 只验证”我能跟你说上话”。要让远端真去跑 ReAct 循环、真去命中工具，得把 prompt 喂进去并实时拿响应流。streamResponse 返回 Flux<Event>，.doOnNext 边出边打、.blockLast() 阻塞到结束——典型的 Reactor 流式消费三段式。

2.4 卡点：参数类型签名写窄了

f036 这一帧（也是讲师停下来 debug 的那一帧）抓到了红线：

第一眼会误判成”A2A 通信坏了”。其实纯粹是工具类签名的事：

  • 前面课程封装 AgentUtils.streamResponse 时，第一个参数写的是 @NotNull ReActAgent agent——因为当时手里只有 WeatAgent（继承 ReActAgent）。
  • 从 Nacos 拿回来的远端代理是 A2aAgent，不是 ReActAgent 的子类——这俩各走各的分支。
  • 但两者共享同一个父类 AgentBase（讲师当场点进去验证：WeatAgent → ReActAgent → AgentBase；A2aAgent → AgentBase）。

修复就一行：把 streamResponse 的第一个入参类型从 ReActAgent 上提到 AgentBase。本地 ReActAgent 子 Agent 和远程 A2aAgent 从此走同一条流式通道。

加工增量：消化稿没明说，但这一处其实是面向接口编程在 Agent 框架里的兑现——比起写两套 streamResponse 重载，把签名往父类抬一格就行。AgentBase 在这里扮演的是”本地/远程都满足的最小公约数”角色。后续如果 AgentScope 再加第三类 Agent（比如 P2P 直连版），只要也继承 AgentBase，这条工具方法照样通用。

2.5 联调与”胜利日志”

启动顺序：Nacos → RouteMakingAgentApplication → ManagerAgentApplication。两个 Agent 模块在 IDEA 多模块同时跑。

证据要在两个控制台都看到：

  • 主管端先打”工具方法：路线制定智能体…正在调用中”，再打”获取到的远程Agent描述：路线制定Agent”——这两条 11-3 就已经有了。
  • 路线制定 Agent 端打出”路线制定Agent调用了百度地图MCP Server”——这才是本集独有的胜利信号。

日志成对出现 = 跨进程调用链完整。

3. 没 get 的点

  • AgentUtils.streamResponse(agent, prompt) 把 prompt 透传给 A2aAgent 时，A2A 协议层具体怎么承运的？POST body 里包了一段任务对象？得回去翻 3-10 的 A2A 协议结构 + AgentScope 源码。
  • AgentBase 这个父类到底定义了什么契约？至少要有 getDescription() 和某种 run/stream 入口，但本集没展开看接口。
  • 远端 LLM 拿到”调用百度地图Mcp”这五个字之后，进自己的 ReAct 循环——它的 system prompt 是怎么拼的？是 description("路线制定Agent") 这段加上 AgentScope 内置模板？本集没明说。
  • ToolUtils.getToolkit(new BaiduMapMCP()) 这一行能否传多个工具实例？签名应该是 varargs，但本集只传一个，多实例场景留到 11-6 接真 MCP 时验证。

5. 知识地图

6. 自测题

Q1. 主管 LLM 能直接看到 BaiduMapMCP.getBaiduMapMcp() 上 @Tool(description="百度地图Mcp Server") 这段描述吗？为什么？

不能。@Tool 的可见域只在所在 Agent 的进程内。主管 LLM 只看见自己进程里的 callRouteMakingAgent，远端的 @Tool 是给远端 LLM 看的。主管之所以能”间接”触发远端工具，是先命中 callRouteMakingAgent，再由这个工具发起 A2A 调用、把 prompt 喂给远端，让远端 LLM 自己去匹配描述。

Q2. AgentUtils.streamResponse(agent, prompt) 报”cannot be applied to (A2aAgent, String)”。原因和最小修复是什么？

原因：工具方法第一个参数的类型写成了 ReActAgent，但 A2A 拿回来的远端代理是 A2aAgent，二者没有父子关系（只共享更上一层的 AgentBase）。最小修复：把参数类型从 ReActAgent 上提到 AgentBase，本地 ReActAgent 子类和远端 A2aAgent 就都能传。

Q3. 本集的 getBaiduMapMcp() 方法体里只有三行 log.info，没接真 MCP。为什么要这样做？

桩日志驱动验证。讲师要先验证”主管→远端→远端命中自己工具”这条调用链通不通，把真依赖（百度地图 MCP）隔离掉，分隔可疑域。等链路验证完，11-5 / 11-6 再来接真 MCP。

Q4. 路线制定 Agent 把 BaiduMapMCP 注册到 Toolkit 的代码是什么样？为什么不用 @Component 自动扫描？

ToolUtils toolUtils = new ToolUtils(); → Toolkit toolkit = toolUtils.getToolkit(new BaiduMapMCP()); → AgentUtils.getReActAgentBuilder().toolkit(toolkit).build()。不用 @Component 是因为 AgentScope 这一支不走 Spring 自动扫描，工具实例要在 builder 链里手动 new 进去——属于框架风格选择，跟 SAA 1.1 的 @Tool + @Bean 是两套范式。

Q5. 跑通本集需要在两个控制台同时看到哪些日志？只看主管端日志够吗？

主管端要看到”工具方法：路线制定智能体…正在调用中” + “获取到的远程Agent描述：路线制定Agent”；远端要看到”路线制定Agent调用了百度地图MCP Server”。只看主管端不够——那只能证明到 11-3 那一步（连通 + 描述拿到），证明不了远端 LLM 真的进了 ReAct 循环并命中自己的工具。本集独有的胜利信号就是远端控制台那行 log。
