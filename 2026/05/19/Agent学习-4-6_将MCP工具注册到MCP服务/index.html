4-6_将MCP工具注册到MCP服务

发表于2026-05-19|更新于2026-05-19|Agent学习第4章 SpringAi 1.1 实现 MCP+A2A
|浏览量:

1. 一句话定位

把”已写好的 @Tool 方法”打包成一张大模型能看到的工具清单，让 MCP 客户端能拉走。

2. 主体讲解

为什么光有 @Tool 还不够

上一集你给 WeatherTool 上的方法挂了 @Tool(description=...) 和 @ToolParam，你可能以为这就完事了 —— 注解都写了，大模型应该能看见。

不能。

@Tool 只解决了一件事：声明这个方法可以被工具调用机制识别。它没解决”大模型怎么知道当前这个 MCP 服务端里到底有哪几个方法”。这两件事是分开的。

把链路拆开你就懂了：大模型不直接连 MCP 服务端。中间隔着一个 MCP 客户端。客户端启动时会问服务端：”你有哪些工具？”服务端必须能拿出一张清单递过去。客户端拿到清单后再交给大模型。少了这张清单这一环，前面再多注解都白搭 —— 大模型那边一片空白。

所以本集要做的事就一件：在 MCP 服务端这一侧，生成那张清单。

清单的标准形状：ToolCallbackProvider

Spring AI 把”工具清单”这个概念抽成了一个接口，叫 ToolCallbackProvider。你的目标产物就是这个类型的对象。

记住”接口 = 契约”这个视角：清单长什么样不重要，符合 ToolCallbackProvider 这个契约就行。这给后面留了实现自由 —— 包括 Spring AI 自己提供的现成实现。

怎么造：Builder 模式

清单的实现类叫 MethodToolCallbackProvider（顾名思义，专门把”带 @Tool 注解的方法”打包成清单）。

这里有个小取舍：“为什么 Builder 模式而不是 new”这一节我不展开，它属于 Java 基础（解决多参数构造器可读性差 + 强制不可变），跟本集 MCP 主题无关。你只需要记住：见到这种 .builder().xxx().build() 链式调用，就是因为人家不让你 new。

怎么接入 Spring：方法是 Bean，类是 Configuration

光写完 toolList() 方法 Spring 不认。你得让容器知道这个方法的返回值要被托管。两层注解：

  • 方法上 @Bean：返回值交给容器。
  • 类上 @Configuration：让 @Bean 在这个类里生效（不加，@Bean 就被忽略）。
  • 参数 WeatherTool weatherTool 是容器自动注入进来的 —— 前提是 WeatherTool 类上有 @Component。

回头看两层模型

走完这一遍你会发现 @Tool / @ToolParam 和”工具清单”是两层不同的事：

层 解决的问题 载体
方法级声明 “这一个方法长什么样、做什么、要哪些参数” @Tool + @ToolParam
服务级清单 “这个服务端总共有哪些方法可调用” ToolCallbackProvider Bean

两层都做完，大模型才看得见你的工具。

3. 我一开始没 get 的点

  1. 如果你只写了 @Tool，会得到大模型完全看不到你的方法。 注解只是给工具机制”贴标签”，没有清单 Bean 把它们汇总，客户端拉不到任何东西。
  2. 如果你以为参数 WeatherTool weatherTool 要自己 new，会得到一个完全多余的实例（甚至 NPE）。 Spring 容器会按类型注入 —— 前提是 WeatherTool 类上有 @Component。这个 @Component 不是装饰，是命门。
  3. 如果你试 new MethodToolCallbackProvider(weatherTool)，会被编译器拦。 构造器私有，强制走 .builder().toolObjects(...).build()。
  4. 如果你给每个工具写一个 toolList 方法，会撞 Spring 的 Bean 冲突或者就是单纯多余。 一个方法 + varargs 就够了，所有工具塞同一张清单。

4. 跟其他集的连接

上承

3-4 给出过 MCP 三方架构的概念图，3-5 解释过”客户端不知道服务端有哪些工具，所以服务端得提供 list”。本集就是那个 list 的具体落地 —— Spring AI 版的实现方式。同章 4-1~4-5 应当已经搭好了 Spring AI MCP 工程脚手架并写完了 WeatherTool 类（开头明确提到”上节课定义了天气工具”），所以本集只补”注册”这最后一公里。

下启

清单只是服务端准备好了。客户端怎么发现这个服务、走什么传输（stdio / SSE / Streamable HTTP）、拿到清单后怎么实际触发调用、结果怎么回灌大模型 —— 本集一概没讲。下一集大概率是 MCP Server 启动配置或客户端对接。

横向

跟 3-7 / 3-8 的 Agent Skills 形成对比：Skills 走”文件 + 渐进式加载”，MCP 走”清单 + RPC”。都是”让大模型知道有哪些能力”，但分发方式和耦合粒度不同。3-6 的 HowToCook MCP 是消费一个现成的 MCP 服务，本集是自己造一个。

5. 知识地图

6. 自测题

Q1（概念回忆） 大模型最终能调用到你写的 @Tool 方法，整个链路上必须存在一个什么类型的 Bean？它扮演什么角色？
A1：必须存在一个 ToolCallbackProvider 类型的 Bean。它是”工具清单”的契约接口 —— MCP 客户端启动时把它拉走，再递给大模型，大模型才知道这个服务端有哪些工具。详见 §2 与 图 f014。

Q2（概念辨析） @Tool / @ToolParam 和 ToolCallbackProvider 都是”让大模型用上工具”的关键，它们的分工是什么？能不能只要其中一个？
A2：@Tool / @ToolParam 是方法级声明，描述单个方法长什么样、做什么、要什么参数；ToolCallbackProvider 是服务级清单，列出这个服务端总共有哪些方法。两者必须同时存在，缺任一层大模型都看不到工具。详见 §2 末尾的两层对比表。

Q3（反直觉陷阱） toolList(WeatherTool weatherTool) 的参数从哪儿来？为什么不能写成 toolList() { WeatherTool weatherTool = new WeatherTool(); ... }？
A3：参数靠 Spring 容器按类型自动注入，前提是 WeatherTool 类上有 @Component。手动 new 会绕过容器，绑不到那些依赖 Spring 生命周期的特性（如自动扫描、AOP、其他注入），而且和容器里的实例不是同一个对象。详见 §3 第 2 条。

Q4（跨集连接） 本集和 3-5 讲过的”MCP 客户端不直接调服务端，要先 list”是什么关系？
A4：3-5 给的是为什么要有 list 这一步的协议层动机；本集给的是 Spring AI 框架下怎么把这个 list 实际生产出来的代码层落地。3-5 是 why，本集是 how。详见 §4 上承。

Q5（应用 / 推广） 假设你新写了一个 DatabaseTool（也加了 @Component 和方法上的 @Tool），要把它和 WeatherTool 一起暴露出去。需要再写一个 toolList 方法吗？最小改动是什么？
A5：不需要再写方法。最小改动是把现有 toolList 的参数加上 DatabaseTool dbTool，然后 .toolObjects(weatherTool, dbTool) 多传一个。toolObjects 是 Object... varargs，天然支持任意数量。详见 §2 横向扩展段与 图 f076。

7. 关键词表

术语 一句话定义
工具清单（tool list） MCP 服务端启动时生成的、列出所有可调用工具的对象；客户端拉走后递交大模型
ToolCallbackProvider Spring AI 里”工具清单”的接口契约
MethodToolCallbackProvider 上述接口的实现类，把带 @Tool 的方法打包成清单
Builder 模式 Java 对象生成的第二种方式，链式 .builder().xxx().build()；本集出现是因为构造器私有
toolObjects(Object…) 变长参数 Builder 上的 varargs 方法，一次塞入任意多个工具实例
@Bean + @Configuration 把 toolList() 返回值交给容器；类必须 @Configuration，@Bean 才生效
@Component 自动注入 WeatherTool 上的 @Component 是 toolList(WeatherTool) 能拿到实例的前提

自检摘要

  • 取舍出现在 §2”怎么造：Builder 模式”段（主动放弃展开 Builder vs new 的 Java 基础对比，理由：与 MCP 主题无关）。
  • 加工增量在 §2 末尾的”两层模型对比表”和 §5 知识地图 —— understanding.md 只有零散概念清单，没有把”方法级声明 vs 服务级清单”这层抽象画成表，也没有把整条链路绘成图；这是本稿的新增结构化产物。
