4-2 导入MCP依赖

§1 一句话定位

把 MCP 的 Java 底层框架塞进 pom，并用第二个 BOM 把版本号也管起来。

§2 主体讲解

先认结论，再看坑

如果一年后你只想最短路径重做这一集，需要做的事只有两件：

  1. 在 <dependencyManagement> 里加 spring-ai-bom（与 spring-ai-alibaba-bom 并列），版本 1.0.0，type=pom、scope=import。
  2. 在 <dependencies> 里加 spring-ai-mcp（groupId 写 org.springframework.ai，不写 version，让 BOM 接管）。

剩下的”翻文档、查中央仓库、给豆包翻译英文介绍”那些动作，都是为了说服你为什么这么写的论证过程，不是必经路径。这里先点明，§2.2 之后展开。

为什么 alibaba-bom 不够、必须再来一个 spring-ai-bom

这是这一集最容易踩的逻辑陷阱。你的直觉大概是：上一集已经装了 spring-ai-alibaba-bom，它不就是版本管理的总管吗？再加一个 BOM 不重复了？

不重复。BOM 是按 groupId 来管的：

  • spring-ai-alibaba-bom 锁的是 com.alibaba.cloud.ai:* 那一条线下的 artifactId
  • 而 MCP 底层包 spring-ai-mcp 的 groupId 是 org.springframework.ai，根本不在 alibaba 那条线上

所以 alibaba-bom 管不到它。你要么手写 <version>1.0.0</version>，要么再引一个负责 spring 那条线的 BOM——也就是 spring-ai-bom。这两个 BOM 在 <dependencyManagement> 里平行放，互不串台。

groupId 错位陷阱：为什么不能照抄官方文档

按常识，要装”Spring AI Alibaba 体系下的 MCP”，那 groupId 应该跟 alibaba 走才对。错。MCP 是协议层的事情，底层框架由 Spring 官方提供，alibaba 那层只是上层封装。所以 MCP 底层包就在 org.springframework.ai 下。

更坑的是，Spring AI Alibaba 官方文档（1.0.0.2 版本页面）里给的代码片段是：

这一段过时了。如果你照抄，Maven 大概率拉不到包（或者拉到一个已经迁走的旧版）。正确做法是去 mvnrepository 搜 spring-ai-mcp，第一条结果”Spring AI MCP Client”——artifactId 一模一样，但 groupId 是 org.springframework.ai。

这里有一个反射动作值得养成：当文档与 Maven 中央仓库不一致时，无脑信中央仓库。中央仓库是包发布的真值源，文档是人写的，可能落后。

豆包翻译那一步（把 spring-ai-mcp 的英文 description 翻成中文）这里不展开——它只是辅助确认”这个包确实是 MCP 客户端 / 服务端的 Spring 抽象层”，能起到二次验证的作用，但不是关键依赖。取舍出现在 §2.3。

一个隐藏路径：怎么查 spring-ai 的最新版本

填 <spring-ai.version> 时你需要知道现在最新是多少。直觉：搜 spring-ai-core，看版本列表。

但你会发现 spring-ai-core 这个页面停在 1.0.0-M6（2025-02-14），看着像”最新就这个 milestone 了”。这是个误导。页面上方有个红框提示：

This artifact was moved to: org.springframework.ai:spring-ai-client-chat

跟着这个跳转过去，才能看到真正在维护的 1.0.0 GA 版本。这是 Maven 中央仓库上的常见模式——老包页面会留个”moved to”指针，要顺着跳一次才能拿到真值。这条经验以后查任何 spring 系列包都用得上。

加工增量：两层 BOM 的心智模型

把上面拼起来，可以总结成一张分层图（加工增量在 §5 知识地图，下面这段是 understanding 没明确写出来的整理）：

层 groupId 由谁维护 BOM 本集装的包
上层封装 com.alibaba.cloud.ai 阿里 spring-ai-alibaba-bom 上一集装的
底层框架 org.springframework.ai Spring 官方 spring-ai-bom spring-ai-mcp

把这张表记住，下次再遇到”装哪个包、用谁的 BOM”就不会绕。

§3 我一开始没 get 的点

  1. 如果你以为 alibaba-bom 能管所有 spring-ai-* 包的版本，会得到一个”为什么 mvn 报版本找不到 / 必须手写 version”的错状态——根因是 BOM 只管自家 groupId。
  2. 如果你照抄 SAA 官方文档的 org.springframework.experimental groupId，会得到一个拉不到包或拉到死分支的依赖错误。真值源是 mvnrepository，不是文档。
  3. 如果你用 spring-ai-core 页面来确认 spring-ai 最新版本，会以为最新就是 1.0.0-M6 milestone，实际上这个 artifact 已经 moved to spring-ai-client-chat，跳过去才看得到 1.0.0 GA。
  4. 如果你省掉 spring-ai-bom 直接在 spring-ai-mcp 上硬写 <version>1.0.0</version>，能跑，但以后引第二个、第三个 spring-ai-* 包时每个都要重复写版本号——这就是 BOM 想替你解决的痛点。

§4 跟其他集的连接

上承

承接 4-1：4-1 装的是上层 spring-ai-alibaba-bom，是阿里那条线的版本管理；本集装的是底层 spring-ai-mcp + spring-ai-bom，是 Spring 官方那条线的入口。这一集相当于把上一集教的 BOM 模式”再用一次”，但用在了不同的 groupId 上，正好暴露出”BOM 按 groupId 切分”的本质。概念上也呼应 3-4 / 3-5——MCP 是协议，底层框架由 Spring 出，alibaba 提供的是协议之上的应用层封装。

下启

收束句”通过这两节课我们就导入了 Spring AI 阿里巴巴的基础包以及 MCP 的基础包”是一个明显的过渡信号。两个基础包都齐了，下一集大概率开始用它们——写配置或写 Java 代码把项目接到 MCP server。从依赖准备进入到代码集成。

横向

跟 3-6 体验 JManus 配 MCP 做对比：3-6 是在 GUI 里配一个已有的 MCP server，相当于”用别人的 server”；本集是在 Java 项目里引入 MCP 的客户端/服务端框架，相当于”自己当 host / client”。两条路径解决的是 N×M → N+M 中不同的角色位。

§6 自测题

Q1 (概念回忆)：spring-ai-mcp 的 groupId 是什么？为什么不是 com.alibaba.cloud.ai？
A1：org.springframework.ai。因为 MCP 是协议，底层框架由 Spring 官方出，alibaba 那层只是上层封装。见 §2.3 / 图 f024。

Q2 (概念辨析)：spring-ai-alibaba-bom 和 spring-ai-bom 各自管什么？能互相替代吗？
A2：前者锁 com.alibaba.cloud.ai:* 的版本，后者锁 org.springframework.ai:* 的版本。不能互相替代——BOM 是按 groupId 切分作用域的，两个 BOM 必须并列存在。见 §2.2 / 图 f062。

Q3 (反直觉陷阱)：你在 mvnrepository 搜 spring-ai-core，看到页面停在 1.0.0-M6，能否据此断定 spring-ai 还停留在 milestone？
A3：不能。该 artifact 已 moved to spring-ai-client-chat，要跟着页面上的红框跳转才能看到 1.0.0 GA。这是 Maven 中央仓库的隐藏路径。见 §2.4 / 图 f067 / understanding.md。

Q4 (跨集连接)：本集和 4-1 都用了 BOM，但作用域不同。一句话说清两层 BOM 并存的合理性。
A4：4-1 装的 alibaba-bom 管阿里上层封装这条 groupId；本集装的 spring-ai-bom 管 Spring 官方底层这条 groupId；两条线 groupId 不同所以 BOM 必须各引一份，平行放在 <dependencyManagement> 里。见 §4 上承 / §5 知识地图。

Q5 (应用 / 推广)：假如某天你要引入一个新的 org.springframework.ai:spring-ai-openai 依赖，是否还需要新加 BOM？需要写 version 吗？
A5：不需要新加 BOM——它的 groupId 是 org.springframework.ai，已经被 spring-ai-bom 锁住。直接在 <dependencies> 里写 groupId + artifactId，不写 version，就能拿到 1.0.0。这就是 BOM 抽象付的”利息”。见 §2.5。

1. 一句话定位SubAgent 是主 Agent 在干活时，把某个”单个专业场景”（写 SQL、CRUD、登录接口）外包给一个跑在独立上下文里的小弟，唯一目的就是不让这点专业脏活污染主上下文。 2. 主体2.1 先把上一集的三层架构在脑子里挂好这集前 4 分钟全在复述上一集，把那张图想清楚再往下读会舒服很多： 总协调 Agent（总监级）：只做规划和需求切分，自己不下场。 Agent 主管（领域主管，前端 / 后端 / 测试 / 运维 / 安全 / 产品 等）：拿到本领域的任务后，继续切，再派给下面的执行者。 Agent 执行者（初级 / 实习生程序员）：真正动手，具有领域知识，能自己组合工具、调 MCP 和 Function Calling，不用反复问大模型”我该用啥工具”。 每一层内部都跑同一个循环：ReAct——思考、执行、再思考”结果对不对、和目标有没有出入”、有偏差就动态调整。讲师反复强调这一条，不是凑数，是后面 SubAgent 出场时的语境：SubAgent 内部也是这个循环，只是壳子不一样。 2....
