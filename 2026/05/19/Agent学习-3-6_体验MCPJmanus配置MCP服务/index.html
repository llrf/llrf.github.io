体验 MCP：在 JManus 里挂上第一个 MCP 服务

§1 一句话定位

你能在 5 分钟内，给 JManus 接上一个现成的 MCP 服务，让大模型开口讲菜谱。

§2 主体讲解

先看最末尾那张图，再回头看流程

📺 11:14–13:14 · 看尾段demo揭示数据真正来源

正常顺序是：打开 JManus → 配置 MCP → 发 prompt → 得到一份四人份晚餐菜单。但你如果按这个顺序看，会觉得”哇大模型好会做菜”——错觉。

直接跳到最后：那份菜单的数据来源是 GitHub 上 Anduin2017/HowToCook 仓库里的 markdown 菜谱文件。

⏱ 12:38

知道这一点之后，整集就清爽了：MCP 服务的本质，往往只是”把一份现有的数据/API 薄薄包一层”，让大模型可以通过统一协议调用它。HowToCook-MCP 这种”壳服务”，其实就是把 GitHub 仓库里的 markdown 包装成大模型能调的工具。先理解这一点，再去看配置流程，你会发现配置只是体力活。

为什么要有 MCP：N×M 痛点

⏱ 00:00–02:30 · 回顾FC问题引出MCP动机，纯讲

假设你有 N 个大模型（千问、DeepSeek、Claude……）和 M 个外部服务（支付宝、高德地图、GitHub……）。

没有 MCP 的世界：每个大模型都得自己写一遍”如何调用支付宝 API”、”如何调用高德 API”，N 个模型 × M 个服务 = N×M 份对接代码。换个模型就重写一次。

有了 MCP 的世界：每个服务只暴露一次 MCP 接口；每个大模型只需要会用 MCP 协议。对接成本从 N×M 降到 N+M——乘法变加法。

这是本集所有操作的”为什么”。如果你只记一句，记这个。

三层术语：Server / Service / Tools

⏱ 04:30–05:30 · 三层套娃概念辨析，纯讲

这一节用三五分钟时间反复在用”MCP 服务器”和”MCP 服务”两个词，听着像同义反复，其实是有层级的：

⏱ 04:59

口语里这三个词被混着用很正常，你只要心里有这张图就不会乱。大模型调的是 Tool，Tool 由 Service 提供，Service 跑在 Server 上。

这里我不深入讲 MCP 协议本身的报文格式，因为本集还没到那一层，理解到”三层套娃”就够用了。取舍出现在 §2。

核心操作链路（背下来）

📺 02:30–08:30 · 魔搭挑MCP+生成SSE URL现场操作

整个动手过程就三句：

  1. 去魔搭社区 MCP 广场（modelscope.cn/mcp）挑一个现成 MCP，点”连接”，生成一个 SSE URL。
  2. 在 JManus 工作台 → 设置 → MCP 里点新建，填名称 + 选 SSE + 粘 URL，保存。
  3. 回首页直接发 prompt，比如”今天吃什么，给我做一份四人晚餐菜单”。

⏱ 02:31

挑 MCP 的时候有个隐含技巧：别挑高德、支付宝那种需要 API Key 的，第一次跑通就挑零配置的，比如 HowToCook。等流程跑顺了再回头折腾鉴权。

⏱ 08:11

魔搭点”连接”时，有效期默认 24h——这是个会过期的临时凭证，不是永久配置。复制出来的 SSE URL 里通常带 token，别截图发到公开博客或群里。生产场景这条 URL 失效之后，JManus 那边的配置就废了，你得重新生成、重新粘——这点视频里没明说，是个雷。

JManus 新建 MCP 要填什么

📺 08:30–10:30 · JManus后台填表单接入MCP服务

页面上就三个字段：

  • 名称：随便起，自己看得懂就行（比如 HowToCook）。
  • 连接类型：三选一——STUDIO / SSE / STREAMING。
  • URL：粘魔搭那条。

⏱ 10:17

连接类型这里你可能会卡——STDIO、SSE、Streamable HTTP 到底差在哪？

这一集你不需要懂。规则极其简单：魔搭那边显示什么类型，你这边就选什么。本集魔搭显示 SSE，JManus 这边就选 SSE。

但有一个细节值得留个心：JManus 下拉里写的是 STUDIO，魔搭那边写的是 Stdio——大概率是 JManus 的拼写 typo，指的是同一个东西（标准输入输出，本地进程通信）。加工增量在 §2：理解上三种连接类型对应的部署形态——STDIO 是大模型和 MCP 跑在同一台机器、靠管道通信（典型场景：本地工具、Claude Desktop）；SSE 和 Streamable HTTP 都是远程通信，SSE 是单向服务器推送（旧方案、轻量但有连接超时问题），Streamable HTTP 是 MCP 协议较新的标准化远程方案（双向、更稳）。本集用 SSE 因为魔搭 Hosted 类型直接给的就是 SSE URL——这是为什么”照抄类型”这条规则能成立的底层原因。

验证它真的在工作

📺 10:30–13:14 · 发prompt看返回菜单+GitHub比对验证

保存完回首页，发 prompt，等几秒。

⏱ 11:14

返回的菜单如果是”番茄炒蛋 / 红烧排骨 / ……”这种具体到食材步骤的格式，基本就是 HowToCook-MCP 在背后干活；如果是泛泛的”建议吃清淡为主”，那就是没调到工具，模型自己在编。

怎么进一步验证不是错觉？回到那张 GitHub 截图——你能在仓库里找到 prompt 返回菜里的同名 markdown 文件。这是验证 MCP 链路是否真的接通最朴素的办法。

§3 我一开始没 get 的点

  1. “MCP 服务”和”MCP 服务器”听起来一样，其实是包含关系。如果你以为这俩是同义词在听，你会得到一个错的心智模型——分不清”调的是工具”、”工具属于服务”、”服务跑在服务器进程里”。三层一旦混乱，后面读官方 spec 会处处磕碰。

  2. 如果你以为大模型自己会做菜，你会得到一个错的”MCP 是什么”的印象。它不”会”做菜，它会”调用某个能拿到菜谱数据的工具”。MCP 服务多数情况下只是现有资源的薄包装——这个心态比记任何 API 都重要。

  3. 如果你以为连接类型必须懂原理才能选，你会卡在第一步。实际规则是”照抄上游”——魔搭显示 SSE 你就选 SSE。原理留给以后。

  4. 如果你以为 SSE URL 是永久配置，你过两天会发现 JManus 突然不灵了。它默认 24h 失效。生产用得换 Streamable HTTP 或自己部署 MCP Server。

§6 自测题

Q1（概念回忆）：用一句话说清 MCP 把对接成本从什么降到了什么，为什么？
A1：从 N×M 降到 N+M。M 个服务只需暴露一次 MCP 接口，N 个模型只需会用 MCP 协议，不再需要每个模型为每个服务单独写适配。详见 §2 “为什么要有 MCP”。

Q2（概念辨析）：MCP 服务器、MCP 服务、MCP 工具，三者是并列关系还是嵌套关系？
A2：嵌套。Server（进程/endpoint）⊃ Service（逻辑单元）⊃ Tools（大模型可调的最小单元）。大模型实际调的是 Tool。详见 §2 “三层术语” 和图 f020。

Q3（反直觉陷阱）：JManus 里 MCP 配好了，能发 prompt 拿到菜单。两天后突然不灵了，最可能的原因？
A3：魔搭生成的 SSE URL 默认 24h 失效。需要回魔搭重新生成 URL，粘回 JManus 配置。生产环境应换 Streamable HTTP 或自部署 MCP Server。详见 §3 第 4 条。

Q4（跨集连接）：MCP 和 Function Calling 是替代关系还是演进关系？为什么本集要放在 3-2/3-3 之后？
A4：演进关系。Function Calling 解决了”大模型能调外部”的问题，但每个模型每个服务都要单独适配；MCP 进一步把适配方式标准化（N×M → N+M）。3-2/3-3 没有 MCP 你也能让模型调工具，但成本不可扩展——本集是顺着这条复杂度曲线往下推一步。详见 §4 “上承”。

Q5（应用 / 推广）：你想让 JManus 帮你查实时天气，思路完全套用本集步骤吗？
A5：链路相同（魔搭挑→生成 URL→JManus 新建→粘 URL→发 prompt），但天气类 MCP 通常需要去和风/高德申请 API Key，配置那一步会多一个”填 Key”的字段；且如果是 Local 类型 MCP，要先在本机起进程而不是直接拿 URL。结论：链路通用，鉴权细节因服务而异。详见 §2 “核心操作链路”和 understanding.md “我以为得自己写 MCP 服务器”那条。
