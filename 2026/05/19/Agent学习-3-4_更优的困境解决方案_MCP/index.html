3-04 更优的困境解决方案：MCP

发表于2026-05-19|更新于2026-05-20|Agent学习第03章 MCP + Skills，Agent"工具+技能"的双轮驱动
|浏览量:

§1 一句话定位

把”各家自研的跑腿”换成”行业共享的外包”，工具一次开发、多模型通吃。

§2 主体讲解

2.1 先回到 Function Calling 留下的两个坑

3-3 给 LLM 配了个跑腿小弟 Function Calling（下文简称 FC）。它解决了 LLM 不会调 API、不会读本地文件、不会 CRUD 数据库的能力问题。但你顺着用一段时间会发现两件事很别扭：

第一件：一个跑腿照顾不过来无穷的需求。 A 用户问天气、B 用户问股票分时图、C 用户问交通状况——跑腿小弟得自己把每个 API 的调用函数都写一遍。视频里把这点叫作”忙不过来”，但你冷静想一下：忙不忙其实不是问题，写得完就行。真正的问题在下一条。

第二件，也是真正的痛点：N 家模型 × M 个工具的笛卡尔积爆炸。 OpenAI 有自己的 FC，DeepSeek、豆包、千问各有自己的 FC，互相不通用。你写一个”调高德地图”的工具，想给五家模型用，就得照着五套规范各写一遍。开发者扛不动这种重复劳动。

取舍：视频里把第一个坑（忙不过来）讲得比第二个坑还重，但落到工程现实，”忙不过来”靠多写几个函数就行，生态层面的不统一才是 MCP 真正要解决的事。所以下面我把权重压在第二点上。

2.2 MCP 的核心动机：先定标准，再共享外包

既然每家模型都得有跑腿，能不能大家共同定一个标准、然后调同一个跑腿？这个标准就是 MCP（Model Context Protocol）。

注意这里思路的拐点：MCP 解决问题的方式不是发明新能力——调 API、读文件、查库这些事 FC 时代就能做。MCP 改的是接口规范，让”工具”这一侧只按一套协议实现，所有遵守协议的模型都能直接用。这就是为什么我说 MCP 的价值是生态价值，不是能力价值。

2.3 三个角色：Host / Client / Server 各是谁

MCP 把”模型调工具”这件事拆成三个角色。先把三者认清，时序图才看得懂。

  • MCP Host：承载 LLM 的那一端。视频里直接说”Host 就是不同的语言大模型”，这是简化讲法。更严谨的说法是：Host 是装着 LLM 的应用（比如 Claude Desktop、Cursor 这类客户端软件），LLM 是 Host 内部的推理引擎。第一次学先按视频的简化版理解没问题，但你要知道这层简化在哪。
  • MCP Client：Host 内部的”中介前台”。它的职责很窄但很关键——握着一份工具列表，负责接 Host 的请求、向 Server 派单。一个 Host 可以有多个 Client，每个 Client 对接一个 Server。
  • MCP Server：真正干活的”业务后端”。调 API、读文件、查库的代码在这里。Server 启动时会声明”我能干哪些事”，这就是工具列表的来源。

容易踩坑的一点：你听到 Client / Server 会下意识以为是网络上的客户端/服务端（一个本机一个云端）。这里它们指的是角色，不是物理位置。三者完全可以全部跑在你本机上，Client 和 Server 之间用 stdio 通信也很常见。

2.4 工具列表：MCP 的命脉

工具列表（tools list）是这一集最该记住的数据结构。Server 启动时声明”我提供这些工具，每个工具的输入是啥、输出是啥”，写成一张清单。

它是 MCP 整条链路的信息源。Client 之所以知道”问天气的请求该派给哪个 Server”，靠的就是这张表。

2.5 完整时序：会话建立 + 循环

理解了角色和工具列表，时序图就只是把它们串起来。整个流程分成两个阶段。

阶段 A：会话建立（启动时只跑一次）

  1. Host 初始化 Client；
  2. Client 向 Server 请求工具列表；
  3. Server 返回工具列表，Client 把它缓存下来。

这一步走完，”会话建立”。这里有个容易误解的点：你可能以为每次用户提问 LLM 都要现去问 Server “你能干啥”，其实不是——工具列表是握手时一次性拉过来的，之后整段会话都用这份缓存。

阶段 B：循环（每次用户提问都跑一遍）

用户问”深圳现在多少度”。

  1. LLM 看一眼问题，判断需要外部数据 → 触发操作；
  2. Client 查本地缓存的工具列表，发现有”墨迹天气 API”工具 → 调 Server；
  3. Server 执行业务逻辑（真正去调墨迹天气的 HTTP 接口）→ 拿到实时温度；
  4. Server 把结果返回 Client，Client 再返回给 LLM；
  5. LLM 把结构化数据拼成自然语言答复用户。

关键是：业务逻辑全在 Server。Client 不写任何”怎么调天气 API”的代码，它只做派单和搬运。

2.6 回头看：FC 和 MCP 的差异到底在哪

把 FC 和 MCP 摆在一起对比，你会发现它们干的事情几乎一样——都是”让 LLM 能调外部工具”。差异只在两条：

维度 Function Calling MCP
谁写工具实现 每家模型厂商各写一遍 工具方按 MCP 协议写一次
跨模型复用 不通用 任何 MCP Host 都能接
业务逻辑位置 模型厂商的 FC 实现里 MCP Server 里
价值类型 能力扩展 生态标准化

加工增量：上面这张对照表 understanding.md 里没有，是我自己整理的。理由是，你只看视频很容易停留在”MCP 是 FC 的升级”这种模糊印象——但”升级”在哪一维度其实没说透。把”业务逻辑位置”和”价值类型”两行单独拎出来，你才能看清 MCP 的设计意图是把工具实现从模型生态里搬出来，让它独立演化。这也解释了为什么社区里 MCP Server 现在能像 npm 包一样被分享。

§3 我一开始没 get 的点 / 容易踩的坑

  1. 如果你以为 MCP 是 FC 的替代品（一种新能力），你会得到错的结论：”那我学了 FC 是不是白学了”。实际两者业务逻辑层完全一致，MCP 只是把接口协议化，FC 时代的所有调 API / 读文件 / 查库的代码模式都还能用。

  2. 如果你把 MCP Client 和 MCP Server 当成网络架构里的 C/S，你会去找”哪个跑在云端、哪个跑在本机”，找半天找不到。实际它们是角色分工——Client 是 Host 内的中介前台，Server 是工具方的业务后端，物理上可以都在本机。

  3. 如果你以为工具列表是每次提问时现拉的，你会算出离谱的延迟开销。实际它是会话建立阶段一次性同步的，循环阶段直接用本地缓存。这个设计是为了让运行时调用尽可能轻。

  4. 如果你把 MCP Host 直接等同于 LLM，在简单场景下不会出错，但接触 Claude Desktop、Cursor 这类产品时会困惑——LLM 怎么会”知道”我装了哪些 MCP？答案是：Host 才是那个真正知道的人，它管理 Client 实例，LLM 只是被 Host 调用的推理引擎。

§4 跟其他集的连接

上承

3-1 摆出 LLM 的两大缺陷（实时数据、私人数据”抓瞎”）。3-2、3-3 给出第一版解法 Function Calling——把 LLM 不擅长的”调外部”外包给跑腿小弟。本集是 3-3 的直接续集：FC 解决了能力问题，但留下”各家自研不互通”的生态问题，MCP 用统一协议补这一刀。

下启

本集只讲清了 MCP 的概念骨架（角色 / 工具列表 / 时序），没有动手部分。后续按序列推测应当会有”搭一个 MCP Server、接入到 Claude Desktop”这类实战集——届时今天的工具列表、Client/Server 分工、会话建立 + 循环这套抽象就会变成具体的代码和配置文件。

横向

MCP 与 Agent 概念有交集。Agent 的 ReAct 循环里 “Action” 那一步如果走 MCP，等于天然获得了跨模型的工具调用层——Agent 的工具调用因此不需要再绑定具体 LLM 厂商。

§6 自测题

Q1（概念回忆） MCP 协议中，”工具列表”是什么？由谁声明、由谁缓存、什么时候同步？
A1: 工具列表是 Server 声明自己能提供哪些工具（含输入输出契约）的清单。由 Server 声明，Client 缓存，会话建立阶段一次性同步，之后循环阶段直接用本地缓存。见 §2.4、§2.5。

Q2（概念辨析） MCP Client 和 MCP Server 跟传统网络架构的 C/S 是同一回事吗？
A2: 不是。这里的 Client/Server 是角色分工而非物理位置——Client 是 Host 内的中介前台、Server 是工具方的业务后端，两者可以都在本机用 stdio 通信。见 §2.3 与 §3 第 2 条。

Q3（反直觉陷阱） 用户每问一个问题，LLM 是不是都要重新去问 Server “你能干啥”？
A3: 不是。工具列表只在会话建立阶段拉一次并缓存在 Client，每次提问只走”循环阶段”——Client 直接查本地缓存派单。见 §3 第 3 条 / 图 f016。

Q4（跨集连接） 3-3 的 Function Calling 解决了什么？为什么还需要 MCP？
A4: FC 解决了 LLM 不会调 API / 读文件 / 查库这一能力问题，但每家模型自研 FC、互不通用，工具开发者得给 N 家模型各写一遍。MCP 用统一协议让工具一次开发多模型通吃，解决的是生态问题而非能力问题。见 §2.1、§2.6、§4 上承。

Q5（应用推广） 假设你要给公司内网做一个”查询员工考勤”的能力，让 ChatGPT、Claude、本地部署的 Qwen 都能用，你会用 FC 还是 MCP？为什么？
A5: 用 MCP。FC 路线意味着给每家模型各写一份 SDK 适配，三家就要写三遍且后续维护成本高。MCP 路线只需要写一个 MCP Server（封装考勤数据库的查询逻辑），三家模型分别在自己的 Host 里注册这个 Server 即可，工具一次开发多模型通吃。这正是 §2.6 对照表里”业务逻辑位置 = MCP Server / 价值类型 = 生态标准化”的直接应用。

§7 关键词表

关键词 一句话定义
MCP（Model Context Protocol） 让多家 LLM 共用同一个工具调用标准的协议
MCP Host 承载 LLM 的应用层（视频简化为”LLM 本身”）
MCP Client Host 内部的中介，维护工具列表、向 Server 派单
MCP Server 真正实现业务逻辑（调 API / 读文件 / 查库）的一方
工具列表（tools list） Server 声明能干啥的清单，Client 启动时拉取并缓存
会话建立阶段 初始化 Client → 请求工具列表 → 返回工具列表的三步握手
循环阶段 模型触发 → Client 调 Server → Server 返资源 → 返回模型的运行时循环
FC vs MCP 的核心差异 FC 各家自研不通用；MCP 是统一协议、一次开发多模型通吃

摘要：取舍出现在 §2.1（把”忙不过来”降权、把”生态不统一”升为真正痛点）。加工增量在 §2.6（FC vs MCP 四维对照表 + “业务逻辑位置 / 价值类型”两条 understanding 没有的辨析维度）。
