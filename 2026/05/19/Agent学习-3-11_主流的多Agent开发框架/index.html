主流的多Agent开发框架

摘要：这是一张”6 个多 Agent 框架的对比地图”，不是任何单个框架的实操课。读完你应该能在面试里五秒回答”AutoGen 和 CrewAI 差在哪、LangChain 为什么也算多 Agent 框架、Manus 凭什么是本课主角”。取舍出现在 §2.1（讲解顺序重排），加工增量在 §2.6 和 §3（横向对比表 + 反直觉判断）。

1. 一句话定位

把 6 个主流多 Agent 框架按”自动化程度 / 灵活度”摆成一张地图，钉住 JManus 的位置。

2. 主体讲解

2.1 先看全景，再看细节（这里做了一次取舍）

原视频是按 “演进背景 → AutoGen → CrewAI → LangChain → Manus → JoyAgent → muAgent” 顺序逐个介绍的。但你如果跟着这个顺序学，会发现每听到一个框架都没有锚点——因为根本没有对照对象。

所以这份笔记把顺序换成：先把对比表压进脑子 → Manus（本课主角）→ CrewAI（最强对照组）→ AutoGen（差一点的对照组）→ LangChain（造轮子底座）→ JoyAgent / muAgent（国内新秀）。理由：这集本质就是一张表，对比清楚了再看细节才有挂钩点；而且后面要学 JManus，Manus 思想必须最先抓牢。

2.2 演进主线：嘴 → 手 → 团队

复杂任务靠单个 Agent 走流水线，效率不行。类比公司：一个人单打独斗永远干不过分工的团队。所以 AI 发展线就是：

2.3 Manus 系：本课的主角（必懂）

Manus → OpenManus → JManus 是三层套娃：

  • Manus：原版，闭源产品。
  • OpenManus：Manus 的开源复刻（Python）。
  • JManus：在 OpenManus 之上做的 Java 版本——本课的主项目，”J” 就是 Java。

核心思想——这一段是这集最该背下的：用户说一句模糊需求（”帮我做个旅行计划”），框架自动把它切成多个步骤，再把每一步派给不同的子 Agent 执行。

2.4 CrewAI vs AutoGen：仿团队范式的两个版本

这俩放一起讲，因为它们是同一类——都试图模仿”公司团队怎么干活”。但 CrewAI 在这集被明确判定更”优胜”。

维度 AutoGen（微软） CrewAI
多 Agent 协调 ✓ ✓
人工干预 需要（卖点也是软肋） 不需要（更自动）
角色专业化 一般 强（每个 Agent 有专业身份）
任务分发 一般 强（主管 Agent 派活）
争议解决 弱 强（主管召集相关 Agent 讨论 + 投票）

⚠️ 反直觉点：微软光环不等于更强。”能人工干预” 在 2025 年的多 Agent 语境里反而是”还不够自动”的标签，是个减分项。

2.5 LangChain：乐高底座（不是开箱即用品）

LangChain（含 LangGraph）也能搭多 Agent，但它和上面那几位不是一个物种：

  • 优势：Python，模块化，自由度极高，可本地部署，能用代码自定义任何东西。
  • 代价：学习门槛高，参数要手动配（怎么部署、怎么调度都要自己写）。

可以把它理解成”乐高底座”——给你最大的自由，但你得自己拼。不像 Dify / n8n 那种拖拉拽工作流框架，开箱可用但自由度低（Dify / n8n 在本集被明确划到另一类，不算”开发框架”主流派——这条边界别忘）。

2.6 JoyAgent vs muAgent：国内新秀

这俩是 2025 年才出的新东西，特点都很清晰、单卖点：

框架 出品 技术栈 一句话卖点
JoyAgent 京东 Spring Boot 工具原子化 + 本地部署 + 复用历史任务经验
muAgent 蚂蚁集团 （未明说） 基于知识图谱，KG + LLM 联合增强决策

JoyAgent 的”复用历史任务经验”挺有意思——别的框架基本是无记忆地重新规划，它把过去的任务执行轨迹存下来给新任务参考，类似带 RAG 的多 Agent。muAgent 的方向更学术一点，把结构化知识（图谱）和非结构化推理（LLM）拼起来。

到这里你应该能在脑子里画出这张表：

框架 国别 最大卖点 自动化程度 你大概率会用到吗
AutoGen 美（微软） 多 Agent 协调 + 人工干预 中 工业界仍常用
CrewAI 美 仿团队 + 投票仲裁 高 想”开箱即用”选它
LangChain 美 模块化 + 极高自由度 看你写多少 想自己造轮子选它

muAgent 国（蚂蚁） KG + LLM 决策增强 高 需要强结构化知识

3. 我一开始没 get 的点（加工增量在这里）

  • 如果你以为 AutoGen 比 CrewAI 强（微软光环），你会得到错的结论：这集明确说 CrewAI 更”优胜”——因为”无需人工干预”+”主管派活+投票仲裁”。AutoGen 的”人工干预”在 2025 年的语境里是个负面信号，不是正面卖点。
  • 如果你以为 LangChain 是聊天机器人/RAG 框架，你会错过它作为多 Agent 框架的定位：它确实能搭多 Agent，只是要手写代码。它和 CrewAI/Manus 不是同种产品（底座 vs 成品）。
  • 如果你以为 Manus 卖点是”很强的单 Agent”，你会错过它真正的核心：Manus 卖的是 任务自动拆解+多 Agent 派活——一句模糊需求自动展开成多步骤多专员执行。这是 JManus 后面要复刻的本体。
  • 如果你以为 Dify / n8n 也算多 Agent 开发框架，你会把分类弄乱：拖拉拽工作流框架被明确划到另一类——自由度低、不属于”开发框架”主流派。这条边界不画清，后面学 JManus 时容易混淆。

5. 知识地图

6. 自测题

Q1（概念回忆）：Manus 系框架的”核心思想”用一句话怎么说？
A：用户给一句模糊需求，框架自动把它拆成多个步骤，再把每一步派给不同子 Agent 去执行。其官方标签是”规划-执行-验证 3 层分工协作”。

Q2（概念辨析）：AutoGen 和 CrewAI 都是仿团队范式，为什么这集判定 CrewAI 更优？
A：两条理由——① CrewAI 不需要人工干预（AutoGen 的”可人工干预”在这被视为减分项）；② CrewAI 仿团队模式更完整：主管 Agent 拆任务、派活、监管，争议时召集相关 Agent 讨论 + 投票仲裁。

Q3（反直觉）：LangChain 凭什么也被算作”多 Agent 开发框架”？它的代价是什么？
A：它通过 Python 代码 + 模块化，可以自定义搭出多 Agent 系统，所以算。但代价是学习门槛高、参数（部署等）要手动配——它是”乐高底座”，不是”开箱即用品”，和 CrewAI / Manus 不是同种产品。

Q4（跨集连接）：本集和 3-6（JManus 配置 MCP 服务）是什么关系？
A：MCP 解决”单个 Agent 怎么用工具”（手），多 Agent 框架解决”一群 Agent 怎么分工协作”（组织结构）。在 JManus 里，每个子 Agent 仍然通过 MCP 调外部工具，两层叠加。

Q5（应用推广）：如果让你做一个”接到模糊业务需求 → 自动拆步骤 → 分派给不同专员执行”的内部系统，你会优先看哪两个框架？为什么排除 Dify？
A：优先看 CrewAI（仿团队、开箱可用、有投票仲裁）和 Manus / JManus（核心思想就是任务自动拆解 + 派活，且是本课主角）。排除 Dify / n8n 的理由：它们是拖拉拽工作流框架，自由度太低，被明确划到了另一类，不属于”开发框架”主流派。

术语 一句话定义

AutoGen 微软出品；多 Agent 协调 + 允许人工干预（这里被视为减分项）
CrewAI 仿真团队范式；主管派活 + 角色专业化 + 投票解争议 + 无需人工干预
LangChain Python 多 Agent 底座；模块化、高自由度，代价是要手动写
