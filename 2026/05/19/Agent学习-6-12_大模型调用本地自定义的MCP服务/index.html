6-12 大模型调用本地自定义的MCP服务

发表于2026-05-19|更新于2026-05-21|Agent学习第06章 多 Agent + ReAct架构，SpringAi迈入Agent新时代
|浏览量:

1. 一句话定位

把”MCP Client 已经握上手 + 工具清单也拉过来了”这件事，从 6-11 收尾的位置，再往前推一步：让大模型真正知道有这些工具、并主动挑一个去用。

2. 主体

2.1 起点：你以为已经接通了，但其实没有

⏱ 02:20–02:55 · 推翻”握手成功 = 大模型有工具”的错觉

6-11 里你跑通了 Server（8081）和 Client（8080）之间的 SSE 握手。Server 日志写着 Registered tools: 2，Client 日志里也确认拿到了对端的实现信息——看起来一切都对。

⏱ 00:00

但本集要先打破这个错觉：MCP Client 拿到工具清单 ≠ 大模型拿到工具清单。中间还少一步”交接”。在你写下那一步之前，问大模型”你有什么工具”，它会按 LLM 默认行为东扯西扯，因为它根本不知道你这边连了 MCP。

为了能反复实验，先把 ChatController 里写死的 message 改成从 query 拿：

注意 value="message" 不能漏。你想分开”query key”和”Java 形参名”的时候——比如 query 里叫 message、Java 里也叫 message，但 Spring 不会自动靠名字猜——必须显式写 value。漏了直接 500（Tomcat 一大坨 stack trace 就在你眼前）。

2.3 第一次失败：答非所问

📺 06:55–08:40 · ApiFox 调接口 + 看大模型答非所问的返回

启动之后用 ApiFox 直接 GET http://127.0.0.1:8080/mcp/weather/，默认 message 就是”你有什么工具”。

返回的内容大致是一堆 WeatherAPI.com / AccuWeather 的注册建议、curl 示例、Python 代码片段——完全是 LLM 在凭空发挥，跟你的 WeatherTool 一点关系都没有。

⏱ 08:14

诊断很直白：你的客户端代码里没有任何一句把那张已经拿到的工具清单交给大模型。chatClient.prompt(...).call().content() 只是把用户问题原样送过去，没有附带任何工具描述。

2.5 命名陷阱：defaultTools vs defaultToolCallbacks

📺 11:39–12:10 · IDE 自动补全看 defaultTools vs defaultToolCallbacks 两个方法

IDE 自动补全里你会看到两个名字几乎一样的方法：

⏱ 11:39

  • defaultTools(...)：给本工程里自己写的 @Tool 用的。
  • defaultToolCallbacks(...)：吃 ToolCallbackProvider，是 MCP 拉来的清单走这条路。

而且 defaultToolCallbacks 自身还有两个重载：(ToolCallback...) 和 (ToolCallbackProvider...)。这一集走的是 Provider 那个。取舍出现在 §2.5：直接用 Provider 而不是把它拆成 ToolCallback[]——因为 Provider 是面向”一整张清单”的抽象，未来要加第二个 MCP Server 时，多注一个 Provider 就完事；如果走 ToolCallback[]，多一个 Server 就要写一遍展开/合并的胶水代码。

⏱ 12:06

不传参数时编译器分不清你想用哪个重载——这条报错本身也是给你看的提示：选哪个、传什么。

2.6 第二次验证：列出工具

📺 12:47–13:30 · ApiFox 重新调接口 + 看大模型列出两个工具

代码改完，启动 Client，再访问同一个接口（默认 message=”你有什么工具”）。这次返回：

我可以使用以下两个工具来帮助您获取天气信息：

  1. 获取指定城市的紫外线值
    函数名：spring_ai_mcp_client_imooc_weather_mcp_server_getUltraviolet
  2. 获取指定城市的温度
    函数名：spring_ai_mcp_client_imooc_weather_mcp_server_getTemperature

⏱ 12:55

工具清单确实进入了 LLM 上下文。注意那个超长的函数名前缀 spring_ai_mcp_client_imooc_weather_mcp_server_——这是 Spring AI Alibaba 自动加的命名空间，应该是为了避免多 Server 接入时同名工具冲突。

2.7 第三次验证：真正调用

📺 14:00–16:10 · 改 description + ApiFox 问”深圳温度”看抽参数 + 调用 + 包装

光列出工具还只是”知道有”，不是”会用”。要再验一次：大模型能不能从自然语言里抽参数、调用工具、把结果包装回自然语言？

先把 Server 端的 description 改得更精确一点（这是给 LLM 看的合同）：

⏱ 13:25

然后改 query：?message=深圳现在的温度是多少。

返回：深圳现在的温度是30度。

⏱ 15:06

三件事在这一次响应里同时发生：

  1. 大模型从”深圳现在的温度是多少”里挑出了 getTemperature（而不是 getUltraviolet）——靠的就是 description 里”温度”+”当前时间”。
  2. 把 深圳 抽出来填到 @ToolParam String cityName。
  3. 拿到工具返回的 "深圳温度值是30度"，包装成自然语言”深圳现在的温度是30度”。

这三步就是”大模型用工具”的两层能力：知道有什么 + 知道怎么用。

3. 没 get 的点

  • defaultToolCallbacks 有 (ToolCallback...) 和 (ToolCallbackProvider...) 两个重载——如果手里既有本工程的 @Tool 又有 MCP 拉来的清单，应该怎么组合？两次调用？还是合成一个数组？
  • 函数名前缀 spring_ai_mcp_client_imooc_weather_mcp_server_ 是怎么生成的？接入第二个 MCP Server、两边工具同名时会发生什么？前缀够不够撑住所有命名空间冲突？
  • 多工具选择是 LLM 自己干的还是 SAA 做了二次过滤？问”深圳紫外线高不高”会自动切到 getUltraviolet 吗？如果工具描述写得很相似，LLM 会同时调两个吗？
  • getTemperature 现在写死 30 度。真实场景下，这个方法体里去掉 30 度、改成请 WeatherAPI.com 的代码，对外部行为来说应该完全等价——所以”description 不变 / 实现可换”这件事到底是 MCP 的承诺还是只是表象？

4. 跟其他集连接

  • 上承 6-11：上一集把 Server↔Client 通信跑通了，但只到”日志互相打印”这一层。本集把”通信通”推进到”大模型真的用上工具”。
  • 上承 4-6（MethodToolCallbackProvider 注册工具）和 4-5（@Tool / @ToolParam 的 description）：本集是这两集的对称镜像——Server 端造的 Provider，Client 端拿来灌给 LLM；Server 端写的 description，Client 端这次被 LLM 拿去做工具选择。
  • 上承 4-1（Builder 模式）：chatClient.defaultToolCallbacks(...).build() 又是一次 Builder 套用。
  • 上承 3-4 / 3-5（MCP 三角色、跨厂商复用）：本集是 Host(LLM)/Client/Server 三方协作的代码落地，也是”Server description 改了 → Client 一行不改 → LLM 跟着变”的现场演示。
  • 横向 4-8：JManus 作为现成 Host 连同一个 Weather Server；本集是自己写的 Spring AI Client 连同一个 Server。Server 没动过——“一处实现处处复用”。
  • 下启：本集只演了一个 Server + 一个被命中的工具。下一集大概率讲多工具/多 Server 共存时 LLM 如何选；@McpTool（4-12）是后面更省事的写法。

6. 自测题

  1. MCP Client 日志里已经打印出”收到对端工具列表”了，为什么大模型还是答非所问？
  2. defaultTools(...) 和 defaultToolCallbacks(...) 都在 ChatClient.Builder 上，区别是什么？什么情况用哪个？
  3. ToolCallbackProvider 在 Server 端和 Client 端各扮演什么角色？这种对称使用揭示了 MCP 的什么设计意图？
  4. @Tool(description="...") 这段文字写得好坏会影响什么？请举一个本集出现过的具体例子。
  5. @RequestParam(value="message") 里的 value 漏了会发生什么？为什么 Spring 不能”靠形参名自动猜”？

7. 关键词表

术语 一句话
ToolCallbackProvider MCP 工具清单的对象本体；Server 端 @Bean 出来，Client 端构造注入直接拿到
defaultToolCallbacks ChatClient.Builder 上的方法，把工具清单真正塞进 LLM 上下文的那一步
客户端有 ≠ 大模型有 MCP Client 收到清单只是握手成功，要 Client 主动通过 ChatClient 注入才算 LLM “知道”
description 是给 LLM 看的合同 @Tool(description=...) 的文字直接决定大模型选不选这个工具、能不能听懂用户意图
大模型用工具的两步能力 (1) 知道有哪些工具；(2) 从自然语言抽参数 → 调用 → 包装结果回自然语言
@RequestParam value 不能省 显式写 value="message"，否则 Spring 不知道把 query key 映射到哪个形参，启动 500
MethodToolCallbackProvider ToolCallbackProvider 的标准实现，通过 .builder().toolObjects(...) 生成
Builder 模式 链式调用按需配置属性，本集第二次在 chatClient.defaultToolCallbacks(...).build() 上复用
