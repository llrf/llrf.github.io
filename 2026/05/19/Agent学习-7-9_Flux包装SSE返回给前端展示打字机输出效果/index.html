7-09 Flux包装SSE返回给前端展示打字机输出效果

发表于2026-05-19|更新于2026-05-21|Agent学习第07章 Graph 搭建旅游规划工作流，像拼积木一样轻松
|浏览量:

1. 一句话定位

你这一集要写”SpringBoot → 前端”那半段 SSE 接口——接收侧（AI → SpringBoot）上一集 7-8 已经讲完了，现在轮到 SpringBoot 自己当服务端往前端吐流，配方是 Flux.interval 当心跳源 + .map 把每次 tick 包装成 ServerSentEvent<String>，方法签名从 Flux<String> 升级成 Flux<ServerSentEvent<String>>。

2. 主体

整条链路你需要先把图刻进脑子里

⏱ 00:00–01:30 · 回顾上节，白板讲解整条链路

回看场景截图 f001 / f009 / f145（同一张白板图三次出现，最后一张才完整），它讲的就是这件事：

两端都跑 SSE 协议，中间靠 WebFlux 的 Flux 当容器。注意 Flux 是同一个 Flux，泛型不同——这是本集最容易绕的地方，§3 还会再骂一次。

你要满足的三个条件（讲师明说，照抄就行）

⏱ 04:45–07:35 · 罗列三条铁律，纯讲

锚定 f025 那条注释，三条铁律是：

  1. MIME 类型：produces = MediaType.TEXT_EVENT_STREAM_VALUE，常量值是 text/event-stream。前端收到这个 header 才知道”哦这是 SSE，我要走流式解析不要走一次性 JSON”。
  2. 消息格式：每条消息必须长成 三字段都可选，但末尾的 \n\n 是结束标志，少一个前端就会一直等下一帧。
  3. 持续发送：不是一次发完——是源源不断地推。

条件 ③ 怎么实现：Flux.interval

📺 09:18–10:00 · IDE 里看 Flux.interval 方法签名

Flux.interval(Duration.ofSeconds(1)) 每秒触发一次。看 f053 的方法签名补全：

⚠️ 加工增量：讲师没明说但你需要记住——Flux.interval 返回的是 Flux<Long>，里面装的是序号 0, 1, 2, ...。这个 Long 你用不上，它只是个心跳信号，告诉你”该发下一帧了”。所以下一步必然要 .map(seq -> ...) 把 Long 换成 SSE 消息。

推荐写法：ServerSentEvent.<String>builder()

builder 模式两步走：

  • 最后 .build() 才生成真正的 ServerSentEvent<String> 实例。

builder 自动帮你补 \n\n 结束符，你不用关心格式细节。

锚定 f143 那行报错前后对比：

⚠️ 加工增量：为什么必须改？因为 .map(seq -> ServerSentEvent.builder()....build()) 这个 lambda 返回的是 ServerSentEvent<String> 类型，整条流的泛型就被这个 lambda 钉死了。Flux 的泛型由 map 的返回类型决定，不是反过来。所以先想清楚最终要给前端发什么类型，倒推 map 的 lambda 返回类型，再倒推方法签名的 Flux 泛型——三者必须一致。

3. 没 get 的点

  • .event("message") 这个字符串前端怎么用？是 EventSource.addEventListener("message", ...) 还是默认的 onmessage 就收 message 类型？讲师没演示前端，待下一集补。
  • id 字段是 SSE 断线重连用的（HTTP header Last-Event-ID），讲师没展开。它和 chatId（对话 ID）大概率不是同一个东西。
  • Flux.interval 是固定每秒一个 Long，可现实里 AI 流不是匀速的——f045 那条注释提到”目标：用最少得线程去处理大量的请求工作”，但本集没演”AI 推一段我转发一段”的真异步源。这一步推测是下一集把 6-5 的 streamChat 返回的 Flux<String> 直接 .map 成 Flux<ServerSentEvent<String>> 就行了。
  • builder 没显式调 .id() 或留空字符串，协议层允不允许？SSE 规范上三字段都是可选的，但讲师没讲省略时的默认值。

4. 跟其他集连接

  • 上承：7-8 Flux就是装载SSE流式数据的容器 讲了 Flux 是什么、为什么 SpringBoot 用 WebFlux 接 SSE——本集是同一管道的下游（”后端 → 前端”那一半），把 Flux 容器从 Flux<String>（接 AI）升级到 Flux<ServerSentEvent<String>>（吐前端）。再往前 6-5 ChatClient流式响应获取数据 SSE 教了”AI → 后端”那一段（call → stream + Flux<String> + produces=text/event-stream），跟本集的 produces 一模一样，只是容器的泛型升了一级。SSE 协议本身的来历在 4-4 MCP的通信SSE实时传输，WebFlux 为什么天然契合 SSE 在 4-7 线程不会被卡住WebFlux框架。
  • 下启：下一集大概率写前端怎么接（new EventSource(url) + onmessage + 拼字符串成”打字机”），把 event / data / id 对应到 JS 回调里。再往后会把”AI → Flux<String> → Flux<ServerSentEvent<String>> → 前端”整条链串起来——6-5 的 streamChat 和本集的 sseToFrontPage 合并成真正可用的打字机接口。
  • 横向：和 6-5 是镜像关系——6-5 是消费 AI 的 SSE，本集是生产 SSE 给前端。两集合起来正是 4-3 MCP能连接万物的原因通信的分层设计 提到的”同节点跨节点”的具象：SpringBoot 在这条链路里既当 AI 的客户端又当前端的服务端。和 3-6 体验MCP 里讲的”MCP 用 SSE 当传输”是同一个协议，但本集是”自己写 SSE 接口”而不是”消费别人写好的 SSE”。

6. 自测题（5 卡）

  1. Q: @GetMapping 上 produces = MediaType.TEXT_EVENT_STREAM_VALUE 这个常量的字符串值是什么？为什么 SSE 接口必须挂它？
    A: 值是 "text/event-stream"。前端拿到这个响应头才能识别出”这是 SSE 流式响应”，从而走 EventSource 流式解析，而不是当成一次性的 JSON / HTML 收完才处理。

  2. Q: Flux.interval(Duration.ofSeconds(1)) 返回的 Flux 里装的是什么类型的数据？你为什么必须接一个 .map()？
    A: 装的是 Long，从 0 开始递增的序号（0, 1, 2, …）。它只是个”每秒一次”的心跳信号，你真正要发给前端的是 ServerSentEvent<String>，所以必须 .map(seq -> ...) 把 Long 转换成 SSE 消息对象，否则前端拿到一串数字没用。

  3. Q: 写下用 ServerSentEvent.<String>builder() 组装一条消息的完整链式调用，包含 event/data/id 三个字段和最后的 build。
    A:

    注意泛型 <String> 写在 builder 前面而不是 ServerSentEvent 后面，最后 .build() 不能漏（漏了拿到的是 builder 实例不是 SSE 对象）。

  4. Q: 如果你坚持用手拼字符串 .map(seq -> "{data:..,event:..,id:..}") 写 SSE，最容易漏掉哪两个东西？
    A: ① 末尾两个换行符 \n\n（在 Java 字符串里要写成 \\n\\n，少一个反斜杠或少一个 \n 前端就一直等下一帧）；② JSON 的花括号 / 冒号 / 引号格式很容易拼错（讲师原话”很容易出錯”）。这两个坑都是 ServerSentEvent.builder() 自动给你处理好的。

  5. Q: 方法签名从 Flux<String> 改成 Flux<ServerSentEvent<String>> 的根本原因是什么？泛型链是怎么从终点反推的？
    A: 因为 .map(seq -> ServerSentEvent.<String>builder()....build()) 这个 lambda 返回值类型是 ServerSentEvent<String>，根据 .map() 的签名（Function<? super T, ? extends V> → Flux<V>），整条流的下游泛型就被这个 lambda 钉死成 ServerSentEvent<String>，所以方法签名的返回类型必须同步升级。反推顺序：先想”我要给前端发什么对象” → 决定 map 的 lambda 返回什么 → 决定 Flux 的泛型 → 决定方法签名。
