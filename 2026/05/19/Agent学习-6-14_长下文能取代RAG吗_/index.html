6-14 长下文能取代RAG吗？

发表于2026-05-19|更新于2026-05-21|Agent学习第06章 多 Agent + ReAct架构，SpringAi迈入Agent新时代
|浏览量:

1. 一句话定位

这一集是一张”标题党”题面的真实答案：长上下文没取代 RAG，但它确实把 RAG 原来背着的几条护城河填平了，逼着 RAG 退守到”私人数据 + 多源异构”这两块阵地。

2. 主体

2.1 先复习 RAG 当年是来救命的

⏱ 00:00–00:35 · 回顾上一集 RAG 补的五个 LLM 缺陷

⏱ 00:00

整张 PPT 是一份”两年前的 RAG 庆功榜”：左边一条流水线（数据清洗 → 向量化 → 分块 → 入库 → 召回 → 重排 → 融合原始查询），右边五个红色气球——大模型自己解决不了的五件事：

  • 不是最新（时效性）
  • 不懂用户深层需求（模糊意图）
  • 胡说八道（幻觉）
  • 私人数据（喂不进去）
  • 上下文长度上限（窗口短）

RAG 当年的故事就一句话：用”外挂检索 + 融合查询”把这五个洞一次堵上。

2.2 但 RAG 自己也带病：链路长 + 分块机械化

⏱ 03:26–05:42 · 链路长误差放大 + 分块机械化碎片化

⏱ 01:09

PPT 左上多出来两个红字小标签——链路长、过于机械化。这两个是 RAG 自己的”原罪”，理解这一集的全部前提：

  • 链路长 = 文件 → 数据清洗 → 数据标注 → 分块 → 向量化 → 入库 → 查询 → 召回 → 重排 → 融合 → 喂给 LLM（见 §2.3 检索链十步图）。十步链条任何一节出错，误差会被链条放大——前面分块切错一刀，后面再怎么重排都救不回来。
  • 过于机械化 = 分块那一步几乎是”按字符数切”或”按段落切”，根本不懂语义。一篇文章承上启下的那段话会被一刀劈成两半，知识就碎片化了。

我之前把 RAG 当神器，忽略了这两块”原罪”。这一集的反转就建立在它们身上。

2.3 检索链十步：错误放大的现场

⏱ 01:48–03:26 · 流水线十步展开 + 误差逐级放大

⏱ 04:51

把 PPT 中央那条流水线展开数一下，刚好十步左右：

讲师在这张图上反复强调”链路长”三个字——不是嫌它步骤多，而是嫌每一步的误差会乘到下一步。十步全部 95% 准确，整条链端到端只剩 60%。这是 RAG 的工程现实。

2.4 长上下文的反攻：四发子弹

⏱ 05:43–07:23 · 长上下文逐项对账填平 RAG 护城河

⏱ 05:48

PPT 下方加了一行新框：基于注意力机制 / 长上下文 / 计算量倍增。讲师把这条新武器对准 RAG 的”五个救场”逐项打钩——

RAG 当年救的洞 长上下文今天还需要 RAG 吗
时效性 LLM 自己联网/工具调用，✓ 不需要
模糊意图（深层需求） 推理能力上来了，✓ 不需要
上下文长度上限 直接喂整本红楼梦，✓ 不需要
多轮对话记忆 记忆力超群，✓ 不需要
幻觉 LLM 自己仍解决不了 ✗
私人数据 喂进去成本太高 ✗

注意：第三列上”计算量倍增”那行——讲师说工程上已被解决（实际上是 sparse attention / flash attention 这类优化在硬扛 O(n²)，§3 会回头说）。

取舍出现在 §2.4：原本认为是”长上下文 vs RAG”二选一，这一集把它拆成”五件事逐项对账”。一旦逐项算账，结论就不可能是”谁吊打谁”，只能是”打成三比二”。

2.5 RAG 退守阵地：性能、个性化、多源异构

⏱ 08:18–10:38 · 私人数据 + 多源异构是 RAG 守住的两块

⏱ 06:47

PPT 左上又新出现一个红字：性能——RAG 还有第三个缺陷，就是十步链路本身慢。所以 LLM 长上下文在”日常通用问答”场景下，性能上也开始反超。

但右侧也长出新词：个性化数据 / 多源异构数据 / 持续进化。这就是 RAG 退守后的真正阵地——

  • 个性化私人数据：企业内部文档、私人笔记，喂给公网大模型既有合规风险也成本太高（要本地部署 + 大量显卡）。RAG 把这事解决在”检索层”，不用动模型权重。
  • 多源异构数据：音频、表格、PDF、网页、数据库……全部统一向量化成一个查询入口。这是长上下文做不到的——你没法把一段音频”塞进 context window”。

2.6 长上下文这一面：记忆力 + 多轮对话

⏱ 07:23–08:10 · 记忆力超群的比喻 + 多轮对话不再依赖 RAG

⏱ 07:23

⏱ 07:27

PPT 右下角又长出两个新词：记忆力超群 / 多轮对话。讲师用了一个比喻——“长上下文 = 一个记忆力超群的人”，所以多轮对话再也不用 RAG 帮它”记住前文”了。

这里有个隐性陷阱：长上下文的”记忆”是每次推理都把整段上下文重新跑一遍，不是真的”记住了”。生产里成本可能比 RAG 还贵——但讲师这一集没展开，留给 §3。

2.7 终局图：哪些被填平，哪些没填平

⏱ 10:38–11:06 · 总结哪些被填平、哪些 RAG 守住

⏱ 07:47

⏱ 08:00

最后两张是讲师拼出来的完整因果图。我自己把它压成一张四象限表更好记：

LLM 长上下文已能解决 LLM 短期攻不下
RAG 原本胜任 时效性、模糊意图、上下文长度、多轮记忆 私人数据、多源异构（RAG 守住）
RAG 原本缺陷 （链路长 + 分块机械 + 性能）→ 长上下文绕过 幻觉、私人数据落地成本（都不强）

加工增量在 §2.7：消化稿里讲师按”先复习 → 列原罪 → 反攻 → 退守 → 结论”线性推进，我把它换成四象限——抓住右下两栏就够了：RAG 守的是右上，两边都没解决的是右下。

2.8 学习方法论彩蛋

⏱ 11:06–11:33 · “学持久趋势，避剧烈变动”的选材逻辑

讲师顺手丢了一句重要的话：“我故意不把 RAG 作为项目重点演示。” 理由是 RAG 还在”中间发展态”，学了明天可能就过时。这其实是他全课的选材逻辑——学有持久趋势的，避开还在剧烈变动的。

这也解释了为什么整门课的主线压在 MCP + A2A + Agent Skills 上：这几个抽象更稳定。RAG 等 GraphRAG / Self-RAG / Agentic RAG 这一波尘埃落定再补。

3. 没 get 的点

  • 长上下文真的”解决”了窗口长度吗？ 讲师说”计算量倍增”已经解决——但注意力的 O(n²) 复杂度不会因为模型变强就消失，只是 sparse attention / flash attention / KV-cache 在工程上硬扛。这个”解决”更像是”成本变得勉强可接受”而不是”复杂度被消掉了”。
  • “幻觉短期无解” 是录课时的判断，2025 年下半年 reasoning model + 自验证 + RAG-as-tool 这一路其实在压幻觉了。讲师没更新。
  • RAG 持续进化的具体形态：GraphRAG / Self-RAG / Agentic RAG 都属于”用 Agent 把 RAG 链路某几步动态化”的尝试，讲师没展开。
  • 转录里反复出现的 “REC / WEC / WAC” 都是 RAG 的同音误识，”照馗 / 非重” = “重排（rerank）”，记一下不被绕进去。

4. 跟其他集连接

上承

  • 3-1 大模型困境数据获取与整合上的”抓瞎”：3-1 给 LLM 列了”时效性 + 私人数据”两大原罪，这一集是这条原罪两年后的更新版——时效性已经被 LLM 自己解决，私人数据仍是死结。
  • 3-4 更优的困境解决方案：MCP / 3-5 对比 Function Calling，MCP 的不同：MCP 走”工具/API → 结构化结果”，RAG 走”非结构化文本 → 向量”。这一集的”多源异构 = RAG 护城河”等于明确两条路不互替。

下启

  • 这一集是第 6 章的态度宣言。下一集大概率回到 Agent 工程实战主线（5-x 旅行规划多 Agent / 4-1x SAA 1.1 + A2A + MCP）。主线推进继续靠 MCP + A2A，不靠 RAG。

横向

  • 3-7 具有专业知识的 Agent Skills + 3-8 工具调用最强组合：Agent Skills + MCP：Skills 的”按需加载”和长上下文是两种应对上下文爆炸的策略——长上下文是”硬塞”，Skills 是”按需取”。这一集的”喂整本红楼梦”是前者，生产里后者更经济。
  • 3-9 搞定复杂活儿，得靠多个 Agent 协作：多 Agent 横向切任务，RAG 纵向检索数据，两条正交不冲突。
  • 3-6 体验 MCP：MCP 用”工具列表”统一异构能力，RAG 用”向量化”统一异构数据——同一个”统一异构”模式落在不同层。
