4-10_SpringAi_11_整合MCP

发表于2026-05-19|更新于2026-05-19|Agent学习第4章 SpringAi 1.1 实现 MCP+A2A
|浏览量:

1. 一句话定位

SAA 1.1 把 MCP SDK 焊进 agent-framework，配 yml 一行切传输协议。

2. 主体讲解

心智模型先立住：MCP 在 SAA 里是分两层的

你看到”MCP 依赖”四个字，先停一下，问自己：是底层 SDK，还是服务端 starter？这是两个层级，1.0 和 1.1 在两层的变化完全不同。

  • 底层 SDK（协议实现，io.modelcontextprotocol.sdk:mcp）：1.0 时代你得手动导 spring-ai-mcp，它再传递依赖到 mcp SDK 0.10；1.1 时代直接被 spring-ai-alibaba-agent-framework 传递依赖进来，版本是 0.14。这一层你不再需要写一行依赖。
  • 服务端 starter（spring-ai-starter-mcp-server-webflux 或 -webmvc）：你要做 MCP Server，还是得显式导入这个 starter。1.0 怎么写，1.1 还是怎么写——这一层没变。

为什么要立这个模型？因为如果你只听一句”1.1 不用导 MCP 依赖了”，就会以为 pom 里干干净净就能跑 server，那是错的。SDK 层省了，starter 层省不了。

1.0 vs 1.1：两层各自的变化

把上面那张图固定住，对比就很清楚：

服务端 starter spring-ai-starter-mcp-server-webflux 同上，不变

依赖树打开能直接看到：

注意 io.modelcontextprotocol.sdk:mcp:0.14.0 这一行——它是被 spring-ai-alibaba-agent-framework:1.1.0.0-RC2 带进来的，你的 pom 里压根没写它。

双版本变量并存（容易踩的坑）

服务端 starter 属于 org.springframework.ai，所以你还是要导 spring-ai-bom 管它的版本。于是 properties 里会同时出现两个版本号：

注意写法差异：SAA 是四段 + RC2 后缀，SpringAI 是三段。两个 BOM 同时进 dependencyManagement，谁也别想省。

四种传输方式（这一集真正的新东西）

mcp SDK 从 0.10 升 0.14 不是版本号好看，是协议层扩了两种新传输：

  1. STDIO——进程间通信。Server 和 Client 在同一台电脑才能用。
  2. SSE——单向流式，服务端单点推消息给客户端。1.0 时代唯一的网络传输。默认值，yml 里什么都不写就是它。
  3. Streamable HTTP——SSE 的升级版，仍然是单向流。新增。
  4. Stateless——无状态流式，给微服务/分布式场景用。新增。

后三种都是流式，所以都能跑在 WebFlux 或 WebMVC 上，starter 依赖不动。切换靠 yml，不靠 pom——这一点是这集最反直觉的（加工增量在 §2 末尾）。

用 yml 切传输：一个开关搞定

值就三个：sse / streamable / stateless。STDIO 是另一条线，靠 spring.ai.mcp.server.stdio=true。

取舍：WebFlux 还是 WebMVC？（取舍出现在 §2）

三种流式协议在 WebFlux 和 WebMVC 上都能跑。这集的取舍是性能优先选 WebFlux——文档里也明确推荐。WebMVC 的好处是同步模型简单、和老 Spring MVC 项目无缝；WebFlux 在长连接和高并发场景上更适合 SSE/Streamable 这类长连接流。课程的选择是：先跑通，性能不留隐患，统一上 WebFlux。

加工增量：依赖不动，传输切换全在配置（加工增量在 §2）

讲师顺序是”看依赖 → 发现 0.14 → 翻文档枚举 4 种传输 → 写 yml”。我把它重排成 “两层模型 → 两层各自变化 → 传输扩展 → yml 开关”，因为这样能立刻回答两个问题：(1) 为什么 1.1 还要导 BOM？答：starter 层没省。(2) 为什么换协议不换依赖？答：协议在 SDK 层，starter 只是搭运行时框架，开关在 yml。这两个问题在原视频里是散落的，重排后是因果链。

3. 我一开始没 get 的点

  • “1.1 不用导 MCP”是半句话。完整版是”不用导 MCP 底层 SDK，但服务端 starter 该导还得导”。两层别混。
  • SAA 版本 ≠ SpringAI 版本。是两条并行版本线，1.1.0.0-RC2 和 1.1.0，pom 里两个变量两个 BOM 并存，不是写错。
  • Streamable HTTP 不是全新协议，它是 SSE 的升级版，同样单向。名字里有 HTTP 容易让你以为是双向，不是。
  • 切传输不用换依赖。我以为 streamable 要换 starter，结果就是 yml 里 protocol: streamable 一行。SSE 默认值连写都不用写。

4. 跟其他集的连接

上承

  • 4-1：BOM 三件套（type=pom + scope=import + dependencyManagement）这集继续用，只是变量从一个变两个。
  • 4-2：1.0 时代手动导 spring-ai-mcp 的那一段——本集正是它的”消失”现场。
  • 4-3 / 4-4：MCP 协议层 / 传输层的分层 + SSE 的单向流模型，是理解”为啥 Streamable 算 SSE 升级版”的前提。
  • 4-5 / 4-6：@Tool + ToolCallbackProvider 注册工具——本集做完依赖切换后，下集就能继续往这些工具上接 1.1 的运行时。

下启

  • 下一集会在 1.1 环境里真的跑起来 MCP server，并测 Streamable HTTP 传输是否生效。
  • 客户端那边的 1.1 整合（mcp client starter）也是悬而未决。

横向

  • 3-6 JManus MCP 配置三要素是 STDIO / SSE / Streamable HTTP；本集在 Java 侧把这三种凑齐，并补上了第四种 Stateless。终于把”前端配置看到的协议名”和”后端 starter 里的 protocol 值”对齐了。

7. 关键词表

术语 说明
SAA 1.1 内置 MCP SDK mcp SDK 已被 agent-framework 传递依赖，无需再手动导 spring-ai-mcp
两层 MCP 依赖 底层 SDK（协议实现）vs 服务端 starter（webflux/webmvc），变化范围不同
双版本变量 spring-ai-alibaba.version=1.1.0.0-RC2 与 spring-ai.version=1.1.0 并存，两个 BOM 同进 dependencyManagement
MCP SDK 0.10 → 0.14 1.0 → 1.1 的底层升级根因，带来新增的 Streamable HTTP 和 Stateless
四种 MCP 传输方式 STDIO（进程内）/ SSE（单向流，默认）/ Streamable HTTP（SSE 升级版）/ Stateless（无状态）
spring.ai.mcp.server.protocol yml 配置开关，值为 sse / streamable / stateless，留空默认 SSE
Streamable HTTP（SSE 升级版） 单向流式协议，是 SSE 的演进版本，名字有 HTTP 但不是双向
Stateless（无状态传输） 流式但不维持 session，适合微服务和分布式场景
