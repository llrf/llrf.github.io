3-5 对比 Function Calling 与 MCP 的不同

1. 一句话定位

看完你能用一张对位表把 FC 和 MCP 说清楚，并解释为什么后者注定要替代前者。

2. 主体讲解

先把对位表立起来

你只要记住一句话：LLM 自己从来不亲自调外部 API，永远派一个”小弟”出门。FC 和 MCP 的所有差异，都是这个”小弟”长什么样、住在哪里、谁来管。

Function Calling MCP
小弟住哪 模型内部的一个调用模块 模型外部的两个节点（客户端 + 服务端）
工具描述怎么来 开发人员手动投喂给模型 客户端主动向服务端拉取工具列表
工具谁写 每家大模型公司自己写一套 任何第三方写一次，所有 LLM 都能用

这张表就是这一集的全部。下面三段把它拆开。

不同点一：小弟的位置（在内还是在外）

你看这张图里”小弟”这两个字贴在 Function Calling 上——它是大模型自带的一个内置模块。LLM 判断”用户问的是深圳今天天气，我没有实时数据”，于是它在内部把任务交给 Function Calling 这个模块：「你拿着深圳这个参数，去调墨迹天气 API」。整个过程的边界都在模型这一坨里。

切到 MCP，小弟跑到外面去了，而且拆成了两个节点：MCP 客户端 + MCP 服务端。客户端是嵌在”MCP Host”（也就是承载大模型的那一侧，比如 Claude Desktop 这种壳子）里的一个模块；服务端则是另一个独立的进程，专门管着一堆工具。

这里我刻意不展开 MCP Host 到底是 SDK 还是独立进程的实现细节，因为这集只讲架构对比，进入实现层会跑题（取舍标记 §2）。

不同点二：工具列表怎么进入大模型的视野

这一点是位置带来的直接后果，你顺着想就能推出来。

FC 的小弟在模型里，模型怎么知道有哪些工具可调？答案是开发人员写一段 schema 手动塞进去——这一步在概念图里被标为”手动投喂”。你想加一个新工具，得改代码、重新部署。

MCP 的小弟在模型外，模型自己看不见服务端里有什么工具。于是协议规定了一套握手流程：客户端先初始化 → 请求工具列表 → 服务端返回工具列表 → 会话建立。

四步走完，LLM 才透过客户端”看见”服务端有哪些工具。注意这里的关键差别不是”自动 vs 手动”——而是工具的来源被解耦了：FC 时代工具描述跟模型代码捆死，MCP 时代工具描述变成一个可以远程拉取的”清单”。

不同点三：工具谁来写（这才是杀手锏）

前两点是技术差异，第三点是生态差异——也是 MCP 真正要取代 FC 的根本原因。

在 FC 方案里，工具函数必须由大模型自家公司的开发人员写。OpenAI 想让 GPT 能查天气，OpenAI 的工程师就得自己写一个调墨迹天气 API 的函数；阿里通义千问想要同样的能力，阿里的工程师再写一遍。字节豆包要？再写一遍。

你立刻能看到问题：同一个墨迹天气 API，被 N 家厂商各写了 N 份适配代码。这就是所谓的”标准不统一”。

MCP 把这件事改了：调墨迹天气的工具函数只需要任何一个第三方开发者写一次，做成一个 MCP 服务端发布出去。然后 GPT、Claude、通义、豆包——任何遵守 MCP 协议的 LLM 都能直接接上来用。

你把它跟 USB 类比一下就懂了：FC 时代每个品牌的电脑都得自己设计自家的鼠标接口；MCP 时代统一了 USB 接口，鼠标厂商做一款，所有电脑都能插。

3. 我一开始没 get 的点

  • 如果你把 MCP 客户端理解成”用户界面/Claude Desktop”，你会得到错的部署模型。 MCP 客户端是 Host 进程里的一个 SDK 模块，不是用户能看见的 UI。Host 才是”装着大模型的那个壳”。Claude Desktop 这种产品 = Host + 内嵌的 MCP 客户端。
  • 如果你把 FC 和 MCP 当成同一层抽象在比较，你会得到错的结论。 FC 是模型内置的函数调用能力，MCP 是外部架构协议。它们功能上替代彼此，但抽象层不一样——这也是为什么 MCP 在底层可能还是借助 FC 把工具描述喂给模型（这点视频没讲，但合理怀疑）。
  • 如果你认为”自动 vs 手动”是 MCP 和 FC 的关键差别，你会错过真正的杀手锏。 自动拉取只是手段，工具函数能跨厂商复用才是 MCP 存在的意义。
  • 如果你把”小弟”听成贬义只是个段子，你会丢掉这一系列课的主线隐喻。 从 3-3 到 3-5，”LLM 永远不亲自动手，永远找小弟”是贯穿三集的中枢比喻，记住它就抓住了主干。

4. 跟其他集的连接

上承

3-1 给出了大模型的两大缺陷（实时数据 / 私人数据，俗称”抓瞎”）；3-2、3-3 给出了第一种解法——Function Calling，把它解释成”大模型的跑腿小弟”；3-4 给出了第二种解法——MCP 上下文协议。本集是这两种解法的对比收官，把 3-1 的问题、3-3 的 FC 解法、3-4 的 MCP 解法收成一张对位表。

下启

本集明确指向”为什么 MCP 会代替 FC”——答案锁定在”工具函数跨厂商复用”上。下一集（3-6）大概率会进入 MCP 的实操层：写一个 MCP 服务端，或者在 Claude Desktop 里配置一个 MCP 服务接入。

横向

“小弟”是 3-3 到 3-5 的核心隐喻。还有一条隐线值得标记：从 3-1 “LLM 知识冻结” → 3-3 “找内部小弟跑腿” → 3-5 “把小弟搬出去做成行业协议”，整个 Chapter 3 是一条从问题到协议化解法的演进。

5. 知识地图

6. 自测题

Q1（概念回忆）：用一句话说出 LLM 调外部 API 时为什么必须有”小弟”。
A1：因为 LLM 自身只能做语义分析和生成，不能执行 HTTP/文件等真实操作，必须把”决定要调什么”和”实际去调”分开，后者交给一个代办模块（小弟）。见 §2 不同点一 / 图 f006

Q2（概念辨析）：MCP 客户端 vs MCP Host，二者关系是什么？
A2：MCP Host 是承载大模型的整体壳（如 Claude Desktop），MCP 客户端是 Host 进程内的一个 SDK 模块，负责与 MCP 服务端通信。Host 装着客户端，不是同一个东西。见 §3 第一条

Q3（反直觉陷阱）：FC 和 MCP 是同一层抽象吗？
A3：不是。FC 是大模型内置的函数调用能力，MCP 是外部架构协议+三节点（Host/客户端/服务端）。它们功能上互相替代，但抽象层不一样。见 §3 第二条

Q4（跨集连接）：本集如何收束 3-1 提出的问题？
A4：3-1 指出 LLM 有”实时数据缺位”和”私人数据缺位”两大抓瞎；3-3 给出第一种解法 FC，3-4 给出第二种解法 MCP；本集把两种解法做对位比较，并解释为什么 MCP 会胜出（工具跨厂商复用）。见 §4 上承

Q5（应用/推广）：假设未来出现一个新协议叫 “Universal Plugin Protocol (UPP)”，号称要替代 MCP。你会用本集的什么标准去评估它？
A5：用三层因果链评估——(1) 小弟位置是否进一步解耦（比如完全无状态的服务）？(2) 工具列表分发方式是否更标准/更安全？(3) 生态上能否吸引第三方写一次让所有 LLM 用？前两点是手段，第三点才是它能不能赢的关键。见 §2 因果链 / understanding.md 关键概念清单

7. 关键词表

术语 一句话解释
小弟（中间人） LLM 永远不亲自调外部 API，必须通过代办模块——FC 的小弟在模型内，MCP 的小弟在模型外
MCP Host 承载大模型的运行容器（如 Claude Desktop），不是大模型本身
MCP 客户端 / 服务端 客户端是 Host 里的 SDK 模块；服务端是独立进程持有工具，二者通过四步握手建立连接
工具列表（tool list） MCP 服务端持有的工具清单，由客户端主动拉取并暴露给 LLM
手动投喂 FC 方案下开发人员把工具描述塞给大模型的方式，不可跨厂商复用
标准不统一问题 FC 时代同一个 API 被各家大模型各写一份适配，MCP 的根本动机就是终结这件事
跨厂商复用 MCP 杀手锏——一个第三方工具能被所有遵守协议的 LLM 共用
因果链：位置→分发方式→生态 三个不同点不是平行的，而是层层推出来的，记住链条就不用背三条
